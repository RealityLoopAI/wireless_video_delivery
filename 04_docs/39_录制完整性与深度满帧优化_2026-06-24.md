# 录制完整性与深度满帧优化

日期：2026-06-24

## 目标

本轮优化以录制完整稳定优先：允许 30 秒以上缓存/延迟，但尽量不丢帧。预览链路可以继续低优先级和可丢帧，主 RGB/Depth 录制数据必须优先保完整、时间戳准确、封装正常收尾。

## 主要改动

### 发送端

- 增加 `recording_buffer` 配置项，主 RGB、Depth、Depth 压缩队列可按录制场景放大，不再只有“最新帧覆盖”的低延迟策略。
- RGB 非关键帧在 `recording_buffer.enabled=true` 时不再因为队列已有包就拒绝，避免录制时 H.264 中间帧被主动丢弃。
- Depth 取消 `depth_emit_due()` 软件节流。相机 profile 已控制采集 fps，原软件节流会因调度抖动把稍早到达的有效 depth 帧跳过，造成 66/99ms gap。
- 相机启动改为异步懒启动：一路相机缺失或 SDK open 卡住时，不阻塞其他在线相机开始发送。
- 相机重连最大退避默认提高到 30 秒，并支持 `GEMINI_SENDER_CAMERA_RECONNECT_MAX_DELAY_SECONDS` 覆盖，减少缺失相机时的无效重试压力。
- CMake 和启动脚本支持按 `ORBBEC_SDK_ROOT` 或实际链接库选择 Orbbec SDK，避免 Gemini305 设备被错误链接到 v1 SDK。

### 接收端

- 录制写盘改为每相机独立 record worker 和有界队列，主接收线程不再直接做 depth 解压、CSV/视频写盘。
- 移除录制路径中 `try_lock(segment_mutex)` 导致的静默丢包；录制停止时等待队列清空再关闭 segment。
- 压缩 depth 只在录制 worker 中解压，预览只有被请求时才解压，减少接收线程 CPU 抢占。
- `/api/status` 增加 `record_queue_*`、`record_enqueued_packets`、`record_dequeued_packets`、`record_backpressure_waits`、`record_write_errors` 等诊断字段。
- `receiver_ubuntu-01.json` 增加 `record_queue_max_mb=512`。

## OrangePi Gemini305 SDK 结论

`orangepi5pro-d12a4719` 上 Linux USB/v4l2 能看到 Gemini305，但 v1.10.27 C++ SDK 枚举为 0：

```text
devices=0
error: no Orbbec device found
```

同一设备使用 SDK v2 后可正常枚举：

```text
devices=1
selected sn=CV2R46P00091 name=Orbbec Gemini 305 fw=1.0.70 conn=USB3.2
```

因此该设备必须用 SDK v2 构建：

```bash
cmake -S . -B 12_build_sender_v2 \
  -DGWV3_BUILD_SENDER=ON \
  -DGWV3_BUILD_RECEIVER=OFF \
  -DORBBEC_SDK_ROOT=/home/orangepi/Desktop/wireless_video_delivery/11_third_party/orbbec/linux_arm64/OrbbecSDK_v2.8.6
cmake --build 12_build_sender_v2 --target gemini_sender -j2
```

验证链接库：

```text
libOrbbecSDK.so.2 => .../OrbbecSDK_v2.8.6/lib/libOrbbecSDK.so.2
```

## 验证结果

### 第一次录制验证

录制目录：

```text
/home/fz/Desktop/nas/orangepi5pro-d12a4719_cam01/2026-06-24/190421
/home/fz/Desktop/nas/rk3588-ubuntu_cam01/2026-06-24/190421
```

接收端录制队列表现：

```text
orangepi5pro-d12a4719_cam01 enq=2096 deq=2096 peak_q=12 err=0 backpressure=0
rk3588-ubuntu_cam01        enq=2069 deq=2069 peak_q=12 err=0 backpressure=0
```

MP4/MKV 封装可被 `ffprobe` 正常读取，说明 moov atom 和 segment 收尾正常。但 CSV 显示 depth 仍少发：

```text
OrangePi RGB 1065 / 35.44s = 30.02fps
OrangePi Depth 1031 / 35.41s = 29.09fps
RK3588 RGB 1067 / 35.41s = 30.10fps
RK3588 Depth 1001 / 35.39s = 28.26fps
```

根因定位为发送端 depth 软件节流，不是接收端写盘队列。

### 去掉 depth 软件节流后验证

录制目录：

```text
/home/fz/Desktop/nas/orangepi5pro-d12a4719_cam01/2026-06-24/191024
/home/fz/Desktop/nas/rk3588-ubuntu_cam01/2026-06-24/191024
```

录制期间队列无积压：

```text
q=0, backpressure=0, write_errors=0
```

最终帧数：

```text
OrangePi RGB   1080 / 35.94s = 30.02fps
OrangePi Depth 1080 / 35.94s = 30.02fps
RK3588 RGB     1082 / 35.94s = 30.08fps
RK3588 Depth   1083 / 35.99s = 30.07fps
```

CSV 时间戳检查：

```text
frame_system_timestamp_us backward=0
OrangePi depth max_gap_ms=33.62
RK3588 depth max_gap_ms=46.03
```

结论：去掉 depth 软件节流后，当前两路在线发送端 RGB/Depth 均可按约 30fps 完整落盘，且封装可正常 seek。

## 剩余瓶颈

- 本机 `1280x800@30` 大深度压缩仍约 18-23ms/帧，当前能满帧，但余量不大。
- 主媒体链路仍混合 TCP/UDP 方案，后续若多路同时恢复，仍建议做每路独立通道或 SRT/RTP 分流。
- Web 预览仍可能竞争编码/网络资源，应保持低优先级、按需生成、可丢帧。
- 真正零拷贝还未完全实现；当前已减少接收端主线程大块处理，但 RGB 编码、H.264 包装和接收端视频写盘仍有内存搬运。
- 无硬件同步线时，多设备画面内容级同步仍受曝光时刻、传感器时钟和 USB/SDK 调度影响，软件时间戳只能做到“尽早标记和一致落盘”。
