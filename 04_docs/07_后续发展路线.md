# 后续发展路线

更新时间：2026-07-07

本文档区分当前已经实现的能力、已知限制和后续规划。规划不是当前承诺，只有代码、配置和验证都落地后才能改写成当前实现。

## 1. 当前已经具备的基础

当前系统已经形成完整闭环：

1. Linux 发送端采集 Orbbec RGB/Depth。
2. RGB H.264 编码后发送。
3. Depth 以 `uint16` 母版传输，支持原始帧、zlib 无损和量化/分块压缩。
4. TCP 媒体通道、UDP 状态通道和 UDP CLOCK_SYNC 通道。
5. Linux 接收端接收、预览派生、录制控制和 NAS 落盘。
6. Web Monitor 状态查看和录制控制。
7. `frames.csv` 记录时间戳、`global_timestamp_us`、帧号、RGB 视频帧索引和诊断字段。
8. 发送端预检、watchdog、Wi-Fi guard 和运行状态脚本。
9. 接收端 systemd 用户服务、日志轮转和 CLI。

## 2. 当前最重要的限制

1. 多发送端高码率运行时，TCP 回压仍是主要风险。
2. Depth 高分辨率会同时增加 USB、CPU、压缩、网络和接收端写盘压力。
3. 当前同步依赖 chrony、CLOCK_SYNC 和离线处理，不是硬件级曝光同步。
4. Web 预览是监控用途，不能作为正式数据依据。
5. 不同设备、不同 SDK、不同相机型号的兼容性需要逐台验证。
6. 历史现场状态和当前主线能力不能混为一谈。

## 3. 近期路线

近期目标是让当前链路更稳定、更容易判断状态。

### 3.1 文档和配置继续收敛

目标：

1. 主文档保持少而清楚。
2. 历史问题继续压缩成排障结论。
3. 配置模板区分默认交付、单路压力测试、双路测试。
4. 设备身份字段保持稳定。

验收：

1. README 不再堆历史细节。
2. 新人按文档能理解系统并跑通基本链路。
3. 旧文档不会被误读成当前实现。

### 3.2 运行状态观测增强

目标：

1. 更直观看 RGB/Depth 帧率、码率、延迟和 send failure。
2. 更直观看网络质量和剩余带宽趋势。
3. 更直观看发送端 CPU、内存、温度和 USB 压力。
4. Web 页面区分“在线”“有状态但无媒体”“录制中”“预览可用”。

验收：

1. 出现无画面时能快速定位是身份、网络、采集、编码、接收还是预览问题。
2. 多发送端运行时能看到总码率和各路占比。

### 3.3 录制后自动检查

目标：

1. 停止录制后自动检查文件齐全。
2. 自动统计 RGB/Depth 实际帧率。
3. 自动检查 `frames.csv` 与 `rgb.mp4` 帧数映射。
4. 自动提示异常段。

验收：

1. 每段录制有清楚的健康状态。
2. 下游处理前能先过滤坏段。

## 4. 中期路线

中期目标是提高多发送端承压能力。

### 4.1 预览链路和录制链路分离

当前预览已经有独立思路，但仍需要进一步明确资源边界。

方向：

1. 录制链路优先保证完整和时间戳可靠。
2. 预览链路允许降帧、降码率、跳帧。
3. 预览异常不能拖垮正式录制。

### 4.2 RGB 和 Depth 通道隔离

方向：

1. 评估 RGB 与 Depth 分连接发送。
2. 避免 Depth 大包阻塞 RGB。
3. 避免 RGB 回压影响 Depth。
4. 为不同流设置不同队列和丢弃策略。

### 4.3 接收端多实例或分片

方向：

1. 多实例分担不同发送端或不同相机。
2. Web Monitor 汇总多个接收实例状态。
3. 录制目录仍保持统一身份和统一格式。

## 5. 传输协议候选

当前实现是 TCP 媒体 + UDP 状态。后续可以评估：

| 方案 | 可能收益 | 风险 |
| --- | --- | --- |
| 保持 TCP 并优化队列 | 改动小，兼容当前实现 | 回压问题仍需控制 |
| RGB/Depth 多 TCP 连接 | 隔离不同流 | 连接管理复杂度增加 |
| SRT | 抗抖动和拥塞控制更强 | 集成和调参成本增加 |
| RTP/UDP | 低延迟，适合视频 | 丢包恢复和 Depth 完整性需要额外设计 |
| WebRTC | 浏览器预览友好 | 不适合作为正式录制母版的简单替代 |

任何传输路线落地前，都必须先定义：

1. 丢包时正式数据怎么处理。
2. 时间戳怎么保留。
3. Depth 母版是否仍无损。
4. 下游文件格式是否变化。
5. 多发送端高负载如何验收。

## 6. 同步路线

当前同步能力：

1. 保留设备时间戳。
2. 保留发送端系统时间戳。
3. 保留接收端诊断时间。
4. CLOCK_SYNC 维护 sender 到 receiver 的 offset/delay/drift。
5. `frames.csv` 写入 `global_timestamp_us`，供离线多发送端对齐。

后续方向：

1. 更严格的 chrony 配置和同步状态检查。
2. 录制前自动阻止明显未同步的发送端。
3. 下游 strict / realtime 配对工具。
4. PTP 评估。
5. 硬件同步评估。
6. 内容级标定补偿工具和漂移复核报告。

硬件同步和 PTP 不属于当前已实现能力。

## 7. 数据交付路线

当前正式交付以录制 segment 为单位：

```text
rgb.mp4
depth.mkv
frames.csv
meta.json
calibration.json
```

后续方向：

1. 每段录制生成健康报告。
2. 明确 Orbbec 兼容导出的最小必需字段。
3. 提供稳定的离线读取示例。
4. 必要时支持逐帧 Depth PNG 导出，但不作为默认。
5. 明确长期存储和清理策略。

## 8. 测试路线

当前需要补强：

1. 单发送端单相机冒烟测试。
2. 双发送端并发测试。
3. 多发送端压力测试。
4. 录制文件完整性测试。
5. `frames.csv` 与视频帧映射测试。
6. Web/REST 接口测试。
7. 配置合法性测试。
8. 断网、NAS 不可写、相机拔插、服务重启等异常测试。

测试结果应进入主文档的结论或归档的历史报告，避免散落在聊天记录和临时日志里。

## 9. 版本路线

建议后续按下面方式管理版本：

1. 主分支保持能构建、能读懂、文档不自相矛盾。
2. 设备适配分支只放设备专项改动。
3. 大规模实验使用实验分支，不直接改默认交付配置。
4. 重要架构取舍可以用简短 ADR 记录。
5. 每次合入影响数据格式、接口或配置的改动，都同步更新主文档。

## 10. 不建议短期做的事

1. 在没有测试前直接切换传输协议。
2. 把历史现场配置写成默认配置。
3. 为了预览效果牺牲正式录制链路。
4. 把 Depth 伪彩当作正式数据。
5. 把硬件同步、PTP 或 7x24 稳定性写成当前承诺。
6. 在文档里保存密码或私有凭据。
