## 52d2 无线隔离证据

为避免仅凭媒体帧率猜测原因，在没有用户录制时暂停该机 sender，测试纯 TCP，并自动恢复服务。

| 测试 | 结果 | 可以说明什么 |
| --- | --- | --- |
| 相机关闭，向 receiver 定速目标 10 Mbps、短时发送 3.75 MB | 实收约 9.336 Mbps | 只能证明这几秒达到该值，不是最大或持续吞吐 |
| 相机关闭，向 receiver 发送 37.5 MB，目标 30 Mbps | 实收 62.102 秒，4.831 Mbps | 没有相机采集/编码参与时，链路仍可明显低于正式媒体所需吞吐 |
| 相机关闭，向同 AP 的 e8cc 发送 12.5 MB，目标 20 Mbps | 对端全部收到，38.141 秒，2.622 Mbps；发送脚本等待回执超时 | 慢不只存在于 NAS 或 receiver 路径；此项是双无线跳，不可直接当作到 receiver 的容量 |

52d2 的 RGB 配置本身为 6 Mbps，另有 Depth 和预览；4.831 Mbps 的样本无法持续承载它们。
当时相机 USB 为 5000M，温度约 51 C，采集接近 30 FPS，编码提交约 0.1 ms，
receiver 录制队列和 NAS 上传队列未积压。这些是当时状态，不证明过去每个断流的原因完全一致。

试过三个现有 AP、关闭 Wi-Fi 省电、临时禁止 rtw88 深度省电、重绑定 Wi-Fi 驱动、
仅对 `0bda:c820` Wi-Fi USB 设备执行一次 `USBDEVFS_RESET`；均未取得持续恢复。
15:42 复位后约十秒低延迟，随后再次积压。没有复位相机 USB 或替换内核无线驱动。
将原因定为天线损坏、供电故障或特定驱动 bug 都还缺实物对照证据。

最终保留原 TP-LINK_5G_215E 网络，5 GHz、Wi-Fi 省电关闭；备用 666666 优先级低于当前网络。
已删除本次创建的未自动连接的 88888888 测试配置；`disable_lps_deep` 恢复原 N，
USB 复位曾使 qdisc 变成 `noqueue`，第二次实录处于该状态；清理时已恢复原 `pfifo limit 128`。
此前在 pfifo 下的纯 TCP 测试也未达持续所需吞吐，不能将全部失败归因于这次 qdisc 重置。
恢复后又观察一分钟，52d2 仍有约 30 秒积压，ab748372 在该窗口也曾积压约 32 秒后补发恢复。
没有留下自动复位或自动切网任务；最终网络配置仍需要后续现场对照和长期复验。
下一步最小物理对照是把 52d2 临时移到 AP 旁避开遮挡；再比较同位置正常设备、天线与供电。
没有持续吞吐证据前，不应靠扩大队列或周期性重启宣布根治。

## 严格验收工具

原 `run_deployment_acceptance.py` 主要检查交付与容器可读，不会因 `partial` 自动失败，
且文件校验抛异常后 JSON 可能残留 `ok=true`。新增严格选项并保证异常报告 `ok=false`。
报告新增每段的质量状态、`quality_passed` 和原因；旧调用默认仍是交付冒烟测试，语义不暗改。

```bash
python3 05_tools/run_deployment_acceptance.py \
  --admin http://127.0.0.1:18080 \
  --config /etc/gwv3/receiver.json \
  --record-seconds 180 \
  --require-complete-recording \
  --output /tmp/recording-acceptance.json
```

严格模式要求 `ready=true`、`recording_complete=true`、`recording_quality_status=complete`。
partial 或旧元数据无法证明完整时返回失败，不执行成功后的测试文件清理。
新增测试覆盖 partial 保留证据、失败 JSON 和 complete 正常清理；本机实际通过。
这仍需配合 CSV 连续性、无效 clock 行和全视频解码检查，不能只相信质量标签。
现有 quality 的覆盖率门槛包含 98% 等规则；严格模式没有把这些规则改成绝对零丢帧，
仍须核对每帧索引和时间差，尤其不能据此承诺内容级同步。
