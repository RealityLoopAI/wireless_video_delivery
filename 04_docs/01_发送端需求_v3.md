# 发送端需求文档 v3

## 1. 文档定位

本文档面向 3.0 发送端开发人员，定义 Linux ARM 发送端需要实现的功能、边界、配置、数据输出和验收要求。

发送端运行在树莓派 5、香橙派等 Linux ARM 设备上，负责从 Orbbec Gemini 深度相机采集 RGB 与 Depth 数据，完成 RGB 编码、Depth 无损处理、状态上报、本地预览，并把数据发送到 Linux 接收端。

本文档不定义接收端录制、Web 页面、NAS 写入和 REST API 细节。这些内容由接收端需求文档负责。

## 2. 发送端职责

发送端必须负责：

1. 通过 Orbbec C/C++ SDK 采集 Gemini 相机 RGB 与 Depth。
2. 读取或派生发送端 `sender_id`，并读取每个相机的 `camera_id`。
3. 采集每路相机的 RGB 和 `depth_raw`。
4. 对 RGB 进行编码，优先使用硬件编码。
5. 对 Depth 进行无损或原始帧处理。
6. 按中间传输数据格式向接收端发送注册、心跳、状态、RGB 帧、Depth 帧和事件。
7. 提供发送端本地 RGB + 伪彩 Depth 预览。
8. 提供一键启动、停止和状态查看脚本。
9. 记录发送端本机运行日志。

发送端不负责：

1. 写 NAS。
2. 录制文件切片。
3. 生成 `rgb.mp4`、`depth.mkv`、`meta.json`、`frames.csv`。
4. 提供 Web 监控页。
5. 提供 REST 录制控制接口。
6. 接收端录制开始/停止逻辑。
7. 接收端设备 ID 分配。

## 3. 运行平台

正式发送端平台：

1. 树莓派 5。
2. 香橙派。
3. Linux ARM / ARM64 系统。

开发前置条件：

1. 必须获取并验证 Orbbec C/C++ SDK 的 Linux ARM64/aarch64 包。
2. 当前已有 Linux x64 SDK 包只能作为 API 参考，不能直接代表发送端可部署。
3. 需要确认各发送端设备上的硬件编码能力。

## 4. 相机与 SDK 要求

### 4.1 相机范围

当前正式相机范围为 Orbbec Gemini 系列深度相机。

### 4.2 SDK 使用原则

发送端采集层必须基于 Orbbec C/C++ SDK。

SDK 调用必须封装在相机适配层中，不允许散落在业务逻辑中。

适配层至少应抽象：

1. 设备枚举。
2. 设备打开和关闭。
3. RGB/Depth profile 查询。
4. RGB/Depth 流启动。
5. `FrameSet` 获取。
6. RGB 帧读取。
7. Depth 帧读取。
8. 时间戳和帧号读取。
9. `depth_scale` 读取。
10. 相机标定参数读取。
11. D2C 对齐能力查询。

### 4.3 已确认可参考的 SDK 能力

根据 OrbbecSDK C/C++ v1.10.27 Linux ARM64 包，以下能力可作为 3.0 设计参考：

1. `ob::Context` 查询设备。
2. `ob::Pipeline` 打开 RGBD 流。
3. `FrameSet` 获取 `colorFrame()` 和 `depthFrame()`。
4. 帧对象获取 `index()`。
5. 帧对象获取 `timeStamp()`、`timeStampUs()`、`systemTimeStamp()`。
6. 帧对象获取 `width()`、`height()`、`format()`。
7. 帧对象获取 `data()`、`dataSize()`。
8. `DepthFrame::getValueScale()` 获取深度换算比例。
9. `Pipeline::getCameraParam()` 获取相机参数。
10. `ALIGN_D2C_HW_MODE` 和 `ALIGN_D2C_SW_MODE` 支持硬件/软件 D2C 对齐。
11. SDK 示例包含多设备采集和同步对齐参考代码。

## 5. 发送端身份与配置

### 5.1 身份规则

1. `sender_id` 由发送端配置或按机器唯一信息自动派生。
2. `camera_id` 由发送端配置。
3. 发送端启动时必须校验 ID 非空。
4. `sender_id` 和 `camera_id` 必须只使用 ASCII 字母、数字、下划线 `_`、短横线 `-`。
5. `sender_id` 最大 64 字节。
6. `camera_id` 最大 64 字节。
7. 协议主 ID 不允许中文、空格或特殊符号。

### 5.2 配置文件

发送端使用 JSON 配置文件。

配置至少包括：

1. `sender_id`
2. 每个相机的 `camera_id`
3. 相机绑定信息，例如 SDK 设备序列号、UID 或设备索引
4. RGB 目标 profile
5. Depth 目标 profile
6. RGB 编码策略
7. Depth 传输策略
8. 接收端 IP
9. 接收端媒体端口
10. 接收端状态消息端口或通道配置
11. 本地预览开关
12. 本地预览帧率或降级策略

接收端 IP、端口、相机 ID、编码参数都由发送端配置决定。接收端不远程下发这些配置。

## 6. 采集需求

### 6.1 RGB 采集

1. RGB 目标上限为 1080p@30fps。
2. 实际 profile 以设备可稳定输出的最高规格为准。
3. RGB 帧必须保留原始帧号和时间戳。
4. RGB 帧必须携带宽、高、像素格式、编码格式等必要信息。

### 6.2 Depth 采集

1. Depth 采集 `depth_raw`。
2. 原始数据类型为 `uint16`。
3. Depth 目标规格待现场实测确认。
4. Depth 必须保留原始帧号和时间戳。
5. 必须读取并上报 `depth_scale`。
6. 必须保存或上报空间对齐所需标定信息。

### 6.3 RGB/Depth 配对

1. RGB 与 Depth 独立采集、独立发送。
2. RGB 和 Depth 各自有 `frame_id` 和 `timestamp_us`。
3. 如果发送端能明确提供配对关系，可填写相同 `pair_id`。
4. 如果不能明确配对，`pair_id` 可为空。
5. 不强制 RGB/Depth 必须一一对应。

## 7. RGB 编码需求

1. RGB 在发送端优先硬件编码。
2. 推荐首选 H.264。
3. H.265/HEVC 作为可选方案。
4. 硬件编码不可用时允许软件编码 fallback。
5. 编码器必须抽象封装，避免绑死单一板卡。
6. 发送端输出给接收端的 RGB payload 应为编码后的 H.264/H.265 数据。
7. 接收端应能直接封装 RGB payload 到 `rgb.mp4`，无需重编码。

## 8. Depth 处理需求

1. Depth payload 是一整帧 `depth_raw`。
2. 原始数据类型为 `uint16`。
3. 只允许无压缩或无损压缩。
4. 支持的候选压缩方式包括 `none`、`lz4`、`zstd`。
5. 禁止默认有损压缩。
6. 具体压缩方案由现场 Wi-Fi 带宽、CPU 负载和 Depth 规格实测后定。
7. 发送端必须在帧头中标明压缩方式、宽、高、原始数据类型和 payload 大小。

## 9. 发送数据要求

发送端必须按《03_中间传输数据格式_v3.md》发送数据。

发送端需要发送：

1. `sender_hello`
2. `camera_announce`
3. `heartbeat`
4. `camera_offline`
5. `event`
6. RGB 媒体帧
7. Depth 媒体帧

发送端不接收接收端的录制控制命令。

录制开始/停止只控制接收端写盘，不控制发送端采集和发送。

## 10. 状态心跳

发送端必须周期性上报心跳。

心跳至少包含：

1. `sender_id`
2. 程序版本
3. 主机名
4. 运行时间
5. 相机数量
6. 每路相机在线状态
7. RGB 当前 profile
8. Depth 当前 profile
9. RGB 编码方式
10. Depth 压缩方式
11. 帧率统计
12. 丢帧统计
13. 重连状态
14. 硬件编码是否启用

## 11. 本地预览

1. 发送端必须提供本地预览。
2. 默认开启。
3. 一个发送端一个监控墙窗口。
4. 显示该发送端所有相机。
5. 每个相机显示 RGB + 伪彩 Depth。
6. 伪彩 Depth 从 `depth_raw` 派生，仅用于预览。
7. 预览不能影响采集和发送主链路。
8. 资源紧张时应允许关闭或降级预览。

## 12. 异常处理

发送端必须处理并上报：

1. Orbbec SDK 初始化失败。
2. 相机未找到。
3. 相机掉线。
4. RGB 流缺失。
5. Depth 流缺失。
6. 编码器初始化失败。
7. 硬件编码失败并 fallback 到软件编码。
8. 网络发送失败。
9. 接收端不可达。
10. 帧队列积压或丢帧。

异常必须写本机日志，并通过 `event` 消息上报给接收端。

## 13. 一键启动

发送端需要提供：

1. 一键启动脚本。
2. 一键停止脚本。
3. 一键状态脚本。
4. Ubuntu 图形环境下可双击的 `.desktop` 入口。
5. 终端可执行的 `.sh` 入口。

一键启动前必须检查：

1. Orbbec SDK 动态库是否存在。
2. Orbbec SDK 运行配置是否存在。
3. 相机是否可访问。
4. 配置文件是否存在且字段合法。
5. 接收端 IP 和端口是否配置。
6. 媒体依赖是否可用。

失败时必须输出中文错误提示。

## 14. 日志

1. 发送端运行日志写发送端本机。
2. 日志需要滚动。
3. 日志不得无限增长写满系统盘。
4. 关键错误必须同时通过事件消息上报接收端。

## 15. 首版验收

发送端首版验收包括：

1. 能启动 C++ 发送端程序。
2. 能读取 JSON 配置。
3. 能识别至少 1 台 Gemini 相机。
4. 能采集 RGB。
5. 能采集 `depth_raw`。
6. 能获取帧号、时间戳和 `depth_scale`。
7. 能发送 `sender_hello`。
8. 能发送 `camera_announce`。
9. 能发送心跳。
10. 能发送 RGB 编码帧。
11. 能发送 Depth 无损帧。
12. 能显示本地 RGB + 伪彩 Depth 预览。
13. 能在相机掉线时上报事件。
14. 能通过一键脚本启动、停止和查看状态。
