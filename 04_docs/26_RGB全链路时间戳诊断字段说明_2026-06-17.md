# RGB全链路时间戳诊断字段说明

日期：2026-06-17

## 背景

下游当前使用 `frame_system_timestamp_us` 做多路 RGB 帧对齐。这个字段必须代表发送端在拿到 SDK 帧时读取到的主机时间戳，不能混入编码、排队、网络或接收端落盘时间。

本次改动保持 `frame_system_timestamp_us` 语义不变：

- Orbbec RGB 帧从 `frameset->colorFrame()` 取出后，立即读取 `color->systemTimeStampUs()`。
- 如果 SDK 系统时间戳不可用，才回退到发送端当前系统时间。
- 编码前不再重新构造一份新的 RGB timing，而是沿用采集后立即创建的 `RgbEncodeTiming`。

## 发送端采集到发送链路

新增协议 v2 诊断字段，用于定位时间偏差来自哪个环节：

| 字段 | 含义 |
| --- | --- |
| `sender_capture_host_timestamp_us` | 发送端从 SDK 拿到 frameset 后立刻记录的主机时间 |
| `sender_timing_bound_timestamp_us` | RGB timing 对象创建并绑定帧 ID / SDK 时间戳的时间 |
| `sender_encode_start_timestamp_us` | RGB 帧提交给 H.264 编码器前的时间 |
| `sender_encode_done_timestamp_us` | 编码器返回 encoded access unit 后的时间 |
| `sender_packet_queued_timestamp_us` | 构造媒体包并准备进入发送队列前的时间 |

这些字段只用于诊断，不替代下游同步使用的 `frame_system_timestamp_us`。

## 接收端 CSV 新增列

`frames.csv` 和 `rgb_recorded_frames.csv` 新增以下列：

| 字段 | 诊断目标 |
| --- | --- |
| `receiver_minus_frame_system_us` | 接收端落盘时间与发送端帧系统时间的差值 |
| `sender_capture_to_timing_bound_us` | 采集后到 timing 绑定的延迟 |
| `sender_timing_bound_to_encode_start_us` | timing 绑定后到编码开始的排队/处理延迟 |
| `sender_encode_duration_us` | RGB 编码耗时 |
| `sender_encode_done_to_packet_queued_us` | 编码完成到发送队列前的耗时 |
| `sender_packet_queued_to_receiver_us` | 发送队列前到接收端落盘的端到端传输/接收延迟 |

判断方法：

- 如果 `frame_system_timestamp_us` 本身单调正常，但 `sender_packet_queued_to_receiver_us` 抖动大，优先查网络、接收端 TCP 队列和落盘压力。
- 如果 `sender_timing_bound_to_encode_start_us` 变大，说明发送端采集后处理或编码前排队赶不上。
- 如果 `sender_encode_duration_us` 变大，说明编码器或输入格式转换成为瓶颈。
- 如果 `sender_capture_to_timing_bound_us` 异常变大，说明采集线程在拿到帧后没有及时绑定时间信息。

## 兼容性

接收端支持旧协议 v1 和新协议 v2：

- 旧发送端仍可发送 v1 包，新增诊断列会留空。
- 新发送端发送 v2 包，接收端会写出完整诊断字段。

因此可以先升级接收端，再逐台升级发送端。
