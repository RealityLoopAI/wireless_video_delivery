# RGB 编码输出时间戳与下游视频索引同步整改说明

日期：2026-06-10

## 1. 现象

现场出现了一个容易误判的问题：

1. 发送端本机 OpenCV 合成预览看起来同步。
2. 接收端保存后，下游按时间戳对齐 `rgb.mp4`，画面仍然不一致。
3. 只看 `frames.csv` 中的 `frame_system_timestamp_us`，差值可能已经很小，但渲染出来的画面仍像错帧。

这说明问题不只在“选哪一列时间戳”，还在“视频画面和 CSV 行时间戳是否一一对应”。

## 2. 根因

### 2.1 本机预览不经过 H.264 编码链路

发送端本机 OpenCV 预览使用的是采集线程里的 RGB 帧，按采集到的 `system_timestamp_us` 做合成显示。

这条链路是：

```text
Orbbec RGB frame -> 本机 decode/resize -> OpenCV preview
```

下游看到的是接收端保存的：

```text
Orbbec RGB frame -> GStreamer H.264 encoder -> TCP -> receiver -> ffmpeg -> rgb.mp4 -> OpenCV/cv2 read
```

所以本机预览同步，只能证明采集线程里两路 RGB 帧的时间接近，不能证明 H.264 输出包、接收端 MP4、下游视频帧索引也同步。

### 2.2 旧发送端会把“当前采集帧时间戳”套到“编码器当前输出画面”上

旧代码中，发送端给 GStreamer 输入 buffer 设置了 PTS：

```text
input buffer PTS = rgb_system_timestamp_us
```

但编码器输出 H.264 sample 时，旧代码没有读回输出 sample 的 PTS，而是直接把当前采集帧的：

```text
frame_id
timestamp_us
system_timestamp_us
```

写入当前吐出的 H.264 payload 协议头。

如果编码器内部有排队、缓冲、B 帧、硬件管线延迟或启动阶段滞后，就会变成：

```text
H.264 payload 画面 = 第 N-k 帧
协议头时间戳 = 第 N 帧
```

这正是“时间戳看起来对，但画面内容不同步”的根因之一。

### 2.3 接收端 MP4 不保存发送端逐帧时间戳

接收端 `rgb.mp4` 是由 ffmpeg 从 H.264 bytestream copy 出来的，MP4 内部 PTS 是 ffmpeg 按输入帧率生成或整理后的容器时间，不是发送端 `frame_system_timestamp_us`。

因此下游不能用 MP4 自己的 PTS 做跨相机同步。同步必须以 `frames.csv` 中当前 RGB 行自己的 `frame_system_timestamp_us` 为准。

### 2.4 CSV 第 N 个 RGB 行不一定永远等于 MP4 第 N 帧

`new_sync` 脚本中有这种逻辑：

```python
FrameRecord(
    video_index=len(rows),
    ...
)
```

这等价于假设：

```text
第 N 个 RGB CSV 行 == rgb.mp4 第 N 帧
```

这个假设在以下情况下会出错：

1. 录制刚开始时，接收端收到的 H.264 还没到第一个可解码 IDR/SPS/PPS。
2. ffmpeg 解码或封装丢掉了前面不可解码的 H.264 包。
3. 旧发送端编码输出画面和协议头时间戳错配。
4. 某段 MP4 可读帧数少于 CSV RGB 行数。

`sync_multi_segments.py` 已经有 `--verify-readable-frames` 和 `--align-decodeable-frames`，但默认时间列仍是旧的 `packet_system_timestamp_us`，而且 `sync_videos.py` 没有同等的可解码帧对齐能力。

## 3. 已在 RK3588 发送端完成的修复

本机 RK3588 发送端已经改为：

1. GStreamer 编码器输出 `EncodedH264Frame`。
2. 每个输出 H.264 sample 带回真实输出 PTS。
3. 发送端保留最近 RGB 输入帧的：

```text
frame_id
device_timestamp_us
system_timestamp_us
width
height
```

4. H.264 输出后，按输出 PTS 找回对应原始 RGB 帧信息，再写入媒体包协议头。

涉及文件：

```text
01_sender_linux/include/gwv3_sender/gst_h264_encoder.hpp
01_sender_linux/src/gst_h264_encoder.cpp
01_sender_linux/src/main.cpp
```

修复后，协议头中的：

```text
frame_id
timestamp_us
system_timestamp_us
```

描述的是“当前 H.264 payload 实际画面对应的原始 RGB 帧”，不是“编码器调用时的当前采集帧”。

## 4. 现场验证结果

修复前，接收端短录 `tscheck` 中 RK3588 两路 RGB 最近邻：

```text
rk3588-ubuntu_cam01 vs rk3588-ubuntu_cam02
p50 = 12.349 ms
max = 19.750 ms
```

修复后，接收端短录 `ptsmatch` 中 RK3588 两路 RGB 最近邻：

```text
rk3588-ubuntu_cam01 vs rk3588-ubuntu_cam02
p50 = 4.276 ms
p90 = 4.554 ms
max = 13.435 ms
```

这说明编码输出 PTS 回填修复后，RK3588 双路保存数据里的 RGB 画面时间关系明显改善。

注意：`raspberrypi-01` 发送端尚未同步此修复，因此如果下游继续把 `raspberrypi-01_cam01` 和 RK3588 两路一起比较，仍可能看到旧逻辑造成的画面/时间戳错配。

### 5.2 接收端：新增显式视频帧索引映射

```text

```

```text

```

原因是 `frames.csv` 是媒体包级日志，录制开头可能包含 H.264 尚未出现 SPS/PPS/IDR 的不可解码包；同时编码器/封装链路也可能出现重复包或被 ffmpeg 丢弃的包。下游把 `frames.csv` 第 N 个 RGB 行当作 `rgb.mp4` 第 N 帧，会造成“时间戳看起来对，但画面错帧”。

接收端已新增：

```text

```

该文件只记录实际写入 `rgb.mp4` 输入码流的 RGB VCL 视频帧，字段包括：

```text

frame_id
timestamp_us
frame_system_timestamp_us
packet_system_timestamp_us
rgb_exposure_us
rgb_gain
rgb_auto_exposure
rgb_actual_fps
```

下游按 `rgb.mp4` 顺序解码第 `video_frame_index` 帧，再用同一行的 `frame_system_timestamp_us` 做跨相机最近邻匹配。`frames.csv` 继续保留为包级诊断文件，不再作为视频帧号来源。

## 6. 下游脚本具体修改要求

### 6.1 时间列优先级

把候选时间列改成：

```python
TIME_COLUMNS = (
    "frame_system_timestamp_us",
    "packet_system_timestamp_us",
    "local_time_us",
    "timestamp_us",
)
DEFAULT_TIME_COLUMN = "frame_system_timestamp_us"
```

`sync_videos.py` 中同理：

```python
TIME_CANDIDATES = (
    "frame_system_timestamp_us",
    "packet_system_timestamp_us",
    "local_time_us",
    "timestamp_us",
)
```

生产同步不要使用 `auto` 自动选择时间列。`auto` 可能因为某次数据统计更小而选中 `local_time_us` 或旧字段，但语义上跨设备/跨相机应固定使用：

```text
frame_system_timestamp_us
```

只有旧数据没有 `frame_system_timestamp_us` 时，才退回：

```text
packet_system_timestamp_us
```

禁止使用：

```text
timestamp_us
local_time_us
```

做跨相机画面对齐。

### 6.2 FrameRecord 增加 frame_system_timestamp_us

`FrameRecord` 中增加：

```python
frame_system_timestamp_us: int | None
```

读取 CSV 时增加：

```python
frame_system_timestamp_us=parse_int(row.get("frame_system_timestamp_us"))
```

输出 `sync_matches.csv` 时保留：

```text
<camera>_frame_system_timestamp_us
<camera>_packet_system_timestamp_us
<camera>_timestamp_us
<camera>_local_time_us
<camera>_frame_id
<camera>_video_index
<camera>_csv_row_number
```

这样现场能回查“时间匹配正确但画面不对”到底是时间列问题、视频索引问题，还是发送端编码时间戳问题。

### 6.3 使用 rgb_recorded_frames.csv 作为 MP4 帧号来源

新数据优先读取每个 segment 下的：

```text
rgb_recorded_frames.csv
```

构造 `FrameRecord` 时：

```python
video_index = int(row["video_frame_index"])
timestamp_us = int(row["frame_system_timestamp_us"])
frame_id = int(row["frame_id"])
```

不要再用 `video_index=len(rows)` 从 `frames.csv` RGB 行顺序推断 MP4 帧号。

旧数据没有 `rgb_recorded_frames.csv` 时，`video_index=len(rows)` 只能作为兼容路径。渲染前必须做以下保护：

1. 开启可读帧校验：

```text
--verify-readable-frames
```

2. 对齐可解码帧：

```text
--align-decodeable-frames
```

3. 如果使用 `sync_videos.py`，也需要从 `sync_multi_segments.py` 移植这两个能力。

4. 对每个输入 segment 输出检查：

```text
rgb_csv_rows
rgb_mp4_reported_frames
rgb_mp4_sequential_readable_frames
video_index_offset
```

如果：

```text
rgb_csv_rows != rgb_mp4_sequential_readable_frames
```

必须明确记录差值，不要直接渲染后声称“时间戳不对”。

### 6.4 推荐下游命令

多 segment 或现场真实数据优先用：

```powershell
python E:\Sync_video\new_sync\sync_multi_segments.py `
  --inputs <cam01_segment_or_root> <cam02_segment_or_root> `
  --output E:\Sync_video\new_sync\outputs\multi_sync `
  --time-column frame_system_timestamp_us `
  --max-delta-ms 15 `
  --verify-readable-frames `
  --align-decodeable-frames
```

先只出匹配表，不渲染：

```powershell
python E:\Sync_video\new_sync\sync_multi_segments.py `
  --inputs <cam01_segment_or_root> <cam02_segment_or_root> `
  --output E:\Sync_video\new_sync\outputs\multi_sync `
  --time-column frame_system_timestamp_us `
  --max-delta-ms 15 `
  --verify-readable-frames `
  --align-decodeable-frames `
  --no-render
```

先检查 `sync_matches.csv` 的：

```text
delta_ms
<camera>_frame_system_timestamp_us
<camera>_video_index
<camera>_csv_row_number
render_status
```

确认匹配正确后再渲染。

## 8. 验收方法

### 8.1 先短录

在接收端执行：

```bash
curl --noproxy '*' -X POST \
  'http://127.0.0.1:18080/api/record/start-all?file_prefix=syncverify_'
sleep 8
curl --noproxy '*' -X POST \
  'http://127.0.0.1:18080/api/record/stop-all'
```

### 8.2 检查 CSV

每路 `frames.csv`：

```text
有 frame_system_timestamp_us
RGB 行 frame_system_timestamp_us 非 0
packet_system_timestamp_us == frame_system_timestamp_us
```

### 8.3 最近邻统计

使用 `frame_system_timestamp_us` 统计 RGB 最近邻：

```text
p50 <= 5 ms       较好
p90 <= 15 ms      可接受
max <= 33 ms      不跨整帧
```

### 8.4 渲染验收

下游渲染时同时叠加：

```text
camera_key
frame_id
video_index
csv_row_number
frame_system_timestamp_us
delta_ms
```

如果 `delta_ms` 很小但运动画面仍明显错位，按顺序排查：

1. 该发送端是否已经同步本次 H.264 输出 PTS 修复。
2. `video_index` 是否因 MP4 开头不可解码帧而偏移。
3. 下游是否仍使用 `packet_system_timestamp_us` / `local_time_us` / `timestamp_us`。
4. 是否存在无硬件同步导致的真实曝光时刻差。

## 9. 判断边界

本次修复能解决：

```text
H.264 payload 画面与协议头 frame_system_timestamp_us 错配
```

不能解决：

```text
两台独立 USB 相机没有硬件同步导致的真实曝光时刻差
```

如果所有发送端都已修复、下游也按 `frame_system_timestamp_us` 和正确视频索引渲染，但高速运动仍有稳定残差，那就是硬件同步能力边界。软件最多再做每路 `timestamp_offset_us` 固定补偿，不能替代外触发/硬同步。
