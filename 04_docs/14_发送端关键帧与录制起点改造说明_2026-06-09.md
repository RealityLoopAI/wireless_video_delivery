# 发送端关键帧与录制起点改造说明 2026-06-09

## 1. 背景

接收端当前保存 RGB 录像的方式是接收 H.264 Annex B 码流，并封装为 `rgb.mp4`。H.264 的 P/B 帧依赖前面的参考帧，不能从任意位置独立解码。

现场已经确认：

- 接收端实时收到的 RGB 帧率可以稳定接近 30fps。
- 如果录制开始时收到的是 H.264 中间帧，接收端直接封装会导致 `rgb.mp4` 开头损坏。
- 接收端现在已经做了防护：只从 SPS/PPS/IDR 之后开始写入 MP4。
- 这个防护会丢弃录制开始后、下一次关键帧到来前的 P 帧。
- 在短录制场景下，这会让 `rgb.mp4` 的可解码帧数少于 `frames.csv` 中记录的真实到达帧数，看起来像录像帧率下降。

因此，要同时满足“不损坏”和“录制开始不丢开头帧”，必须由发送端保证录制起点附近立刻产生可独立解码的关键帧。

## 2. 当前接收端行为

接收端已经落地以下兜底：

```text
1. RGB MP4 只从 SPS + PPS + IDR 起点开始封装。
2. 如果 rgb.mp4 关闭后不可探测，则用同段 rgb_debug.h264 重新封装修复。
3. retime 只允许 0.8..1.25 范围内的小幅修正，避免异常低帧率段被强行拉伸。
```

这些逻辑可以避免坏 MP4，但不能凭空恢复关键帧前的 P 帧。关键帧前的 P 帧缺少参考关系，本身不能作为 MP4 开头。

## 3. 发送端必须修改的目标

发送端需要满足下面目标：

```text
录制开始后，接收端在 1 帧到 2 帧内收到 SPS + PPS + IDR。
切片开始后，接收端在 1 帧到 2 帧内收到 SPS + PPS + IDR。
重连后，第一组 RGB 数据必须包含 SPS + PPS + IDR。
```

推荐目标：

```text
30fps 下，录制开始到首个 IDR 的延迟 <= 66ms。
最低要求，录制开始到首个 IDR 的延迟 <= 200ms。
```

## 4. 推荐实现方案

### 4.1 固定 GOP 缩短

发送端编码器应固定较短 GOP：

```text
fps = 30
gop/keyint = 30
idr_period = 30
```

含义：

```text
每 1 秒至少一个 IDR。
```

这个改动可以降低最坏等待时间，但只能把最坏开头丢帧控制在 1 秒内。它还不能保证点击录制后第一帧就是关键帧。

### 4.2 支持强制 IDR

发送端应在以下时机主动请求编码器产生 IDR：

```text
1. 发送端启动并建立 media TCP 后。
2. 收到接收端录制开始通知后。
3. 发送端内部检测到重连后。
4. 每个录制切片边界前后。
```

如果当前编码器是 V4L2 M2M / 硬编码，应优先使用编码器支持的 force keyframe / request IDR 控制接口。

如果当前编码器封装层不支持运行中强制 IDR，至少要做到：

```text
1. 缩短 GOP 到 30。
2. 每个 IDR 前重复输出 SPS/PPS。
3. 重连后重建编码器或刷新编码器，使第一帧为 IDR。
```

### 4.3 每个 IDR 前重复 SPS/PPS

发送端必须保证每个 IDR 前带完整参数集：

```text
SPS
PPS
IDR
```

接收端不能只依赖连接建立时的一次 SPS/PPS，因为录制可能从任意时刻开始，接收端也可能切片或重连。

发送端输出 H.264 Annex B 时，推荐每个关键帧 access unit 形态如下：

```text
00 00 00 01 SPS
00 00 00 01 PPS
00 00 00 01 IDR
```

允许存在 AUD / SEI，但 SPS/PPS/IDR 必须在同一个关键帧组附近可见。

## 5. 接收端录制控制与发送端触发方式

当前已有 REST 控制入口在接收端 Web 服务侧：

```text
POST /api/record/start-all
POST /api/record/stop-all
POST /api/record/start?sender_id=...&camera_id=...
POST /api/record/stop?sender_id=...&camera_id=...
```

发送端如果暂时不能接收独立控制通道，可以先采用固定 GOP + 每 IDR 重复 SPS/PPS。

更完整的方案是增加一条接收端到发送端的轻量控制通道：

```text
receiver -> sender: request_keyframe
fields: sender_id, camera_id, request_us, reason
reason: recording_start | segment_rotate | reconnect | manual
```

收到 `request_keyframe` 后，发送端应在下一个 RGB access unit 触发 IDR，并附带 SPS/PPS。

## 6. 协议字段要求

发送端当前媒体包已有 `flags` 字段。发送端需要准确设置关键帧标记：

```text
flags & key_frame != 0 表示该 RGB payload 含 IDR 或关键帧 access unit。
```

要求：

```text
1. 含 IDR 的 RGB 包必须设置 key_frame。
2. 不含 IDR 的普通 P 帧不得设置 key_frame。
3. 如果 SPS/PPS 与 IDR 分包发送，IDR 包仍必须设置 key_frame。
4. 接收端仍会扫描 H.264 NAL 类型做兜底，flags 不能作为唯一依据。
```

## 7. 验收方法

### 7.1 短录制测试

在接收端连续执行 10 次 10 秒短录制：

```bash
curl -X POST 'http://127.0.0.1:18080/api/record/start-all?file_prefix=idrcheck_'
sleep 10
curl -X POST 'http://127.0.0.1:18080/api/record/stop-all'
```

每一路检查：

```bash
ffprobe -v error -select_streams v:0 \
  -show_entries format=duration:stream=avg_frame_rate,r_frame_rate,nb_frames \
  -of default=noprint_wrappers=1 rgb.mp4

ffmpeg -v error -i rgb.mp4 -f null -
```

通过标准：

```text
ffmpeg 解码返回码为 0。
ffmpeg 日志没有 non-existing PPS / decode_slice_header / no frame。
rgb.mp4 可被 ffprobe 正常探测。
10 秒录制的 rgb.mp4 可解码帧数应接近 300。
```

### 7.2 frames.csv 对比

对比 `frames.csv` 中 RGB 到达帧数与 `rgb.mp4` 中可解码帧数：

```text
frames.csv RGB frames - rgb.mp4 nb_frames <= 2
```

如果差值达到几十帧，说明录制开始后接收端仍在等待关键帧，发送端没有及时输出 IDR。

### 7.3 切片测试

长时间录制跨过至少 2 个切片边界。

通过标准：

```text
每个切片的 rgb.mp4 都能 ffprobe。
每个切片开头都能立即解码。
每个切片 frames.csv 与 rgb.mp4 可解码帧数差值 <= 2。
ffmpeg.log 不出现 moov atom not found。
```

## 8. 当前责任边界

接收端已负责：

```text
1. 不从不可解码 P 帧开头封装 MP4。
2. MP4 探测失败时尝试从 rgb_debug.h264 重新封装。
3. 保留 frames.csv，记录真实收到的每个 RGB/Depth 包。
```

发送端需要负责：

```text
1. 按固定 GOP 周期产生 IDR。
2. 支持录制开始时快速产生 IDR。
3. 每个 IDR 前重复 SPS/PPS。
4. 正确设置 key_frame flag。
```

只有发送端完成这些改动后，接收端才能同时保证：

```text
MP4 不损坏
短录制开头不丢帧
MP4 帧数与 frames.csv 接近一致
播放器看到的平均帧率接近 30fps
```
