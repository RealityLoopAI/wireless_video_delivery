# 本地暂存与 NAS 可靠发布

日期：2026-07-21

## 1. 当前数据路径

正式录制不再直接把实时媒体写入 CIFS NAS。当前路径是：

```text
sender media
  -> receiver 可靠录制队列
  -> receiver 本地 recording_staging
  -> 快速关闭无 global_sidx 的 fragmented RGB MP4、Depth MKV、CSV 和元数据
  -> recording_staged.json
  -> 独立 gwv3-recording-uploader.service
  -> 校验关闭状态并复制原始 capture 包到 NAS 隐藏队列
  -> 文件 fsync、清单校验、recording_capture_ready.json
  -> 按 rgb_output_mode 直接保留 fMP4，或兼容性重封装普通 MP4
  -> recording_nas_finalized.json
  -> 持久化发布日志并移动最终目录
  -> 最后原子发布 recording_ready.json
```

这样 NAS 抖动和 SMB page cache 不再阻塞 receiver 媒体接收线程。2026-07-29 起，生产配置使用 `rgb_output_mode=fragmented_mp4`，下游直接接收完整 fMP4，取消 RGB 全文件重封装；`conventional_mp4` 保留为旧播放器兼容回退。

## 2. 文件可见性规则

录制中的目录只在本地暂存区。receiver 收尾成功后发布 `recording_staged.json`，上传器处理完成后才在 NAS 最终目录发布 `recording_ready.json`。

receiver 和 uploader 的快速校验要求源 fragmented MP4 同时具备 `moov+moof+mfra`，不执行源文件 duration 全扫描。fMP4 生产模式通过结构校验后直接发布；普通 MP4 兼容模式才执行独立 uploader 的 `-c:v copy` 全文件重封装和输出时长校验。

文件可能带录制前缀，例如：

```text
test_Short_0048_recording_staged.json
test_Short_0048_recording_ready.json
```

上传器支持任意合法前缀。下游应读取 `meta.json` 的 `recording_ready_file`，不能写死无前缀文件名。

NAS 上没有 ready 标记的目录不得进入数据集。隐藏 capture queue 只使用 `recording_capture_ready.json` 和 `recording_nas_finalized.json`，不会出现正式 ready。最终目录清理完成后才原子生成 `recording_ready.json`，因此下游不会把复制中、校验中或重封装中的数据当作完成数据。ready 还会写入 `rgb_container_format` 和 `rgb_fragmented`，下游无需根据文件扩展名猜测容器类型。

完成状态分两级：

1. `local_pending_segments=0`：本地 closed 分片已由 NAS capture 安全接管，receiver 本地空间可回收。
2. 总 `pending_segments=0`：目标 RGB 容器、最终目录和正式 ready 均已完成，可以交付下游。

## 3. 故障行为

### NAS 临时不可用

receiver 继续写本地暂存。上传器保留已完成分片并周期重试，不删除唯一副本。NAS 恢复后自动追平。

### 上传器中途重启

每段使用内核 `flock`。进程退出后锁自动释放，不会因遗留锁停滞一小时。capture 复制中断时保留本地唯一副本并重试；容器校验或兼容重封装失败时保留 NAS 上的原始 fMP4；若进程恰好在最终目录移动后退出，capture queue 根目录的发布日志会在重启后补齐内部标记清理和正式 ready。

### sender 离线

媒体超过 `recording_staging.idle_finalize_ms` 未到达时，receiver 独立定时器结束旧分片；sender 重连后创建新分片，不等待旧连接再发包。

### receiver 正常停止

服务先停止接收录制请求、排空每路队列并关闭本地分片。systemd 不使用强制 SIGKILL 打断媒体收尾。上传器是独立服务，可在 receiver 重启后继续处理 backlog。

主机突然断电仍可能留下没有 staged/ready 标记的当前活动分片；断电保护和活动分片离线抢救不等同于正常收尾，正式无人值守场景仍建议使用 UPS。

## 4. 配置

```json
{
  "nas_root": "/home/fz/Desktop/nas",
  "recording_staging": {
    "enabled": true,
    "root": "/home/fz/recording_staging",
    "defer_player_compatible_finalize": true,
    "rgb_output_mode": "fragmented_mp4",
    "idle_finalize_ms": 5000,
    "upload_interval_ms": 2000,
    "upload_bandwidth_limit_mbps": 240,
    "full_copy_workers": 3,
    "active_recording_full_copy_workers": 1,
    "incremental_mirror_workers": 6,
    "incremental_mirror_max_copy_mb_per_file": 4,
    "incremental_mirror_fsync_interval_ms": 30000,
    "nas_capture_queue_directory": ".gwv3_capture_queue",
    "pause_during_receiver_finalize": true,
    "quiet_before_segment_finalize_ms": 10000,
    "pause_record_queue_bytes": 8388608,
    "pause_record_queue_oldest_age_ms": 500,
    "delete_after_upload": true
  },
  "min_free_disk_mb": 10240
}
```

`min_free_disk_mb` 在启用 staging 时约束本地暂存文件系统。低于保留水位后拒绝继续录制，避免写满系统盘。

`upload_bandwidth_limit_mbps` 是增量镜像、历史补拷和最终发布共享的总 NAS 写入预算，不是单 worker 预算。录制中无高复用镜像的整段补拷最多使用 `active_recording_full_copy_workers`；录制停止后恢复到 `full_copy_workers`。这样实时录制优先使用本地盘顺序写入能力，空闲期再并行清理历史积压。

`incremental_mirror_workers` 在六路现场配置为 6，每路活跃切片都能同时向前镜像；所有 worker 仍共享 240 Mbit/s 总预算，不会按 worker 数倍增带宽。`incremental_mirror_max_copy_mb_per_file` 限制每路每轮处理的单文件字节数，现场配置为 4 MiB，使每个 chunk 快速完成并更新镜像状态。如果在一轮 16 MiB 或更大拷贝中途停录，已写但尚未返回的进度无法进入持久状态，会在最终 capture 重新校验/补拷。4 MiB 粒度将该停录损失上限降到单 chunk。

增量镜像是可重建的预取缓存，本地 staging 始终是权威副本。镜像周期 `fsync` 间隔为 30 秒，用于减少 uploader 崩溃后的重拷量；正常停录交接时不再对预取句柄额外 `fsync`，因为随后的最终 capture 会校验所有复用 chunk，并对完整文件执行一次统一持久化屏障。

## 6. 当前容量基线

2026-07-21 五路现场输入约 `80.85 Mbit/s`，当时上传上限为 `120 Mbit/s`。2026-07-27 生产配置将本地到 NAS capture 上限调整为 `240 Mbit/s`，并以 receiver 队列字节数、最老包等待时间和切片边界主动让路。接收端本地盘当时约有 53 GiB 可用，并保留 10 GiB 水位，按当前码率只能覆盖约一小时级 NAS 故障，不是无限队列。

2026-08-10 复测确认 NAS 本身不是当前瓶颈；历史切片多路整文件并发补拷时，receiver 本地盘读等待显著升高，因此并发数越高不代表有效吞吐越高。调度器现在会在录制期间将低优先级整段补拷限制为 1，并保留当前切片的增量镜像；空闲时才使用 3 路补拷。

若增加相机、分辨率或码率，必须重新计算：

```text
可缓冲秒数 = 可用于 staging 的字节数 * 8 / 总入站 bit/s
```

## 7. 验收

自动测试覆盖：

1. NAS 不可用后本地数据保留。
2. 上传进程在复制中被终止后立即续传。
3. 带文件前缀的 staged/ready 标记。
4. fMP4 直发必须保留 `moov+moof+mfra`，且能读取、定位和解码；普通 MP4 回退必须有 `moov` 且无 `moof`。
5. ready 最后原子发布。
6. sender 离线后的定时收尾与重连新分片。
7. 外部 FFmpeg 子进程不持有已删除录制文件描述符。
8. marker 中的文件名必须是安全的单层文件名，拒绝绝对路径和 `../` 越界。
9. 限速复制期间持续更新阶段、字节数、百分比和耗时。
10. 实时 fragmented MP4 正常关闭时必须有 `mfra`，但不依赖全文件回填 `global_sidx`。
11. 缺失 `mfra` 的截断 fragmented MP4 不得发布 ready。
12. receiver 快速收尾不对无 `global_sidx` 的源 fragmented MP4 执行 duration 全扫描。
13. 容器校验或 NAS 重封装失败时原始 fMP4 capture 仍然保留。
14. capture queue 中任何阶段都不会暴露正式 `recording_ready.json`。
15. 最终目录移动后进程中断，可由发布日志自动恢复并最后生成 ready。
16. fMP4 直发模式不得启动 FFmpeg 整文件重封装，ready 必须声明实际容器类型。
17. 多个增量镜像/补拷 worker 的汇总写入不得突破共享带宽预算。
18. 录制活跃时低镜像复用率全量补拷不得超过 `active_recording_full_copy_workers`，空闲时应恢复并行清仓。
