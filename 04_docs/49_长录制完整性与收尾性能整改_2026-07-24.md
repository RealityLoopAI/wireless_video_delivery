# 长录制完整性与收尾性能整改

日期：2026-07-24

## 1. 输入报告复核

本次复核输入为：

```text
/home/linaro/下载/complete_report_excluding_1hour (1).html
```

报告覆盖 10 轮录制。逐文件复核结论：

1. 55 个 RGB 文件和 65 个 Depth 文件均通过严格解码，没有发现媒体文件损坏。
2. 10 轮录制均存在停止/收尾时长偏差，短录制约为 53.9 至 77.9 秒，中长录制约为 209.9 至 212.6 秒。
3. 15 分钟和 30 分钟轮次共出现 10 个仅含 2 至 3 帧、时长 0.056 至 0.108 秒的 Depth 尾段。
4. 按报告明细重算，共有 10 个相机/轮次的 RGB 或 Depth 时长偏差超过正负 2 秒，不是摘要中的 8 个；最大 RGB 偏差为正 14.405 秒，最大 Depth 偏差为负 7.632 秒。
5. 报告中的暗帧样本表现为遮挡或场景阴影，没有坏块、解码错误或文件损坏证据。

因此本次修复重点不是画质算法，而是切片边界、停止收尾、I/O 竞争、状态可观测性和过期状态判定。

## 2. 根因

### 2.1 实时 fragmented MP4 的全局索引

旧配置在实时 RGB MP4 上使用：

```text
+frag_keyframe+empty_moov+default_base_moof+global_sidx
```

`global_sidx` 会在关闭时扫描并改写整个文件。多路长录制同时结束时，这个操作与 uploader 的普通 MP4 重封装和 NAS 复制竞争磁盘。现场曾观察到约 94% 磁盘利用率、43% 至 68% I/O wait、约 9 秒录制队列等待以及最高约 3.68 秒媒体处理延迟。

实时录制阶段本来只需要快速产生可恢复的 fragmented MP4；播放器兼容的普通 MP4 已由独立 uploader 生成，因此实时文件不需要 `global_sidx`。

### 2.2 自动切片没有严格落在可解码 RGB 边界

旧逻辑按任意媒体包触发轮转：

1. 可能由 Depth 包先创建新段。
2. 新段可能从 H.264 P 帧开始。
3. 接收端随后等待下一帧 IDR，形成最长约 964 ms 的 RGB 边界缺口。

### 2.3 离线收尾后的 Depth 首包产生微小尾段

sender 暂时离线后，接收端会按 idle timeout 关闭旧段。重连或残留包到达时，如果 Depth 比可解码 RGB 关键帧先到，旧逻辑会立即创建只包含少量 Depth 帧的新段。这就是报告中 2 至 3 帧微小尾段的主要来源。

### 2.4 CLOCK_SYNC 报告和探针存活混为一体

receiver 只按 sender report 的更新时间判断模型是否过期。状态上报暂时拥塞时，即使双向 clock probe 仍持续成功，模型也可能被误判失效。

### 2.5 上传器和错误状态可观测性不足

旧 uploader 只暴露当前段名，看不到处于重封装、复制还是校验阶段，也没有字节进度。长文件处理时容易被误判为卡死。

同时，普通连接/事件日志可能写入 `last_error`，健康心跳也不能可靠清理瞬态错误；日志轮转使用重命名，长期持有文件描述符的服务仍继续写旧 inode，导致日志表面轮转、实际文件继续增长。

### 2.6 配置与实际协议不一致

receiver 配置曾声明 media UDP 已启用，但当前主媒体链路实际仍为 TCP。该字段会误导运行状态判断。

## 3. 已实施修复

### 3.1 快速关闭实时 MP4

实时 RGB MP4 改为：

```text
+frag_keyframe+empty_moov+default_base_moof
```

receiver 的 staging 校验要求 fragmented MP4 带文件头 `moov`、正常关闭产生的尾部 `mfra`，并可由 `ffprobe` 读取；不再要求会触发全文件回填的 `sidx`。uploader 仍在本地使用 `-c:v copy` 生成最终普通 MP4，并在校验后原子发布 NAS。

### 3.2 关键帧边界轮转

达到切片时长后：

1. receiver 将该路标记为待轮转。
2. 每秒向 sender 请求一次 `force_rgb_keyframe`。
3. 只有收到同时包含 SPS、PPS 和 IDR 的 RGB payload 时才切换 writer。
4. 触发轮转的关键帧写入新段，确保新 RGB 文件从可解码边界开始。
5. 在关键帧到达前，Depth 继续写入旧段，避免先创建 Depth-only 新段。

新增状态字段：

```text
segment_rotation_keyframe_requested_us
segment_rotation_keyframe_requests
```

### 3.3 新段 RGB 起始门控

没有活动 writer 时，如果该相机声明会发送 RGB：

1. 压缩 Depth 仍先执行输入长度和解压校验，异常包不会绕过安全检查。
2. 在首个可解码 RGB 关键帧到达前，丢弃没有 RGB 配对依据的 Depth。
3. 丢弃不能独立解码的 RGB 起始 P 帧。
4. 首个 SPS/PPS/IDR 到达后创建完整 RGBD 段。

新增计数：

```text
segment_prestart_depth_drops
segment_prestart_rgb_drops
```

明确声明 `rgb_profile.enabled=false` 的 Depth-only sender 不受该门控影响。

### 3.4 CLOCK_SYNC 存活判定

每个 sender 的模型新增：

```text
clock_report_stale
clock_last_probe_receiver_us
clock_probe_count
```

模型只在 sender report 和双向 probe 都超过超时时间时失效。probe 回复成功日志按 sender 限制为最多每 30 秒一条，避免高频日志反压。

### 3.5 uploader 进度和中断安全

uploader 新增阶段和进度状态：

```text
active_phase
active_bytes_done
active_bytes_total
active_progress_percent
active_elapsed_ms
```

重封装、限速复制和校验期间均周期刷新状态。外部进程通过轮询运行，收到停止或超时后会正常终止，不遗留无主 ffmpeg。

### 3.6 错误、日志和配置修正

1. 连接成功、重连成功和暖机成功不再污染 `last_error`。
2. sender 健康心跳可清理瞬态错误；媒体已经持续到达时，receiver 会忽略 sender 尚未清除的历史 `media TCP` 连接错误，但不会覆盖需要人工关注的 `recording_*` 错误。
3. receiver 和 sender 日志轮转改为 copy-truncate，保持服务当前 inode 有效。
4. receiver 轮转同时覆盖 `recording_uploader.log`。
5. 日志目录支持 `GWV3_LOG_DIR`，便于隔离测试。
6. receiver 默认配置将 `media_udp_enabled` 修正为 `false`。

## 5. 仍然存在的边界

1. MP4 是固定帧率容器，其播放器 duration 不等于严格的采集时间跨度。数据集时间轴必须使用最终 `frames.csv` 的 `global_timestamp_us` 和 `rgb_video_frame_index`。
2. 停止录制后 receiver 可很快接受下一次录制，但 NAS ready 是异步完成的。交付前仍需等待 uploader backlog 归零。
3. 没有硬件触发或同步线时，CLOCK_SYNC 只能统一设备软件时间轴，不能保证不同相机同时曝光。
4. RGB 新段建立前丢弃的 Depth 本身没有同段 RGB 配对依据；计数已暴露，便于验收，不应把这些帧强行写入 RGBD 数据集。
5. 报告中的遮挡和场景暗部不是本次录制链路修复范围；应通过现场照明、相机位置和曝光基线处理。

## 6. 生产部署与验收

本次开发和测试期间，生产 receiver 正在录制，因此没有热替换生产二进制，也没有重启生产服务。部署应安排在当前录制和 uploader backlog 完成后执行。

部署后至少连续验证一次 30 分钟以上多路录制：

1. 所有新 RGB 段均能从首帧解码，边界无秒级缺口。
2. 不再生成 2 至 3 帧的 Depth-only ready 尾段。
3. `record_queue_peak_wait_ms` 和 `record_prequeue_peak_delay_ms` 不出现全路同步跃增。
4. 停止后 receiver 可立即接受下一次录制。
5. uploader 的 `active_phase` 和进度持续变化，最终 `pending_segments=0`。
6. NAS 每个交付目录最后存在对应 `recording_ready.json`。
7. 下游只读取 ready 数据，并用最终 CSV 的统一时间轴字段对齐。
