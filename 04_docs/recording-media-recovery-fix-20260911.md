# 录制断流提前收尾修复报告

## 修复范围

针对 2026-09-10 `172605` 批次暴露的“短暂断流触发接收端提前结束片段”问题。
本次只修改接收端，不改变发送端采集、编码、相机参数、TCP 协议、原始时间戳或 CSV 字段。
不修改历史录像，不插重复帧、黑帧或伪造缺失数据。

## 原因和证据

接收端原来把设备媒体暂时没有到达和录制应当结束混在一起：`idle_finalize_ms=5000`，
连续约 5 秒没有媒体就立即关闭片段，恢复后重新建立片段。

本机 9 月 10 日 17:28:15 被触发收尾，同一秒媒体恢复，RGB 接收间隔约 5.204 秒，
随后建立 `172605_001`。e8 在 17:28:36 触发同一路径，后来收到的 RGB/Depth 已延迟约 45/47 秒。
因此恢复目录并非 NAS 上传失败造成，而是接收端按短超时主动收尾。

这不是这批全部缺帧的唯一原因。发送端已经丢弃、相机没有交付或根本没有送到接收端的数据，
不能靠延长等待自动恢复。`ready=true` 仅表示文件交付完成，不能代替内容完整性检查。
17:30:16 的 stop-all 请求是独立的停止操作，其客户端身份仍未确认。

## 修改后的行为

| 场景 | 新行为 |
| --- | --- |
| 录制中超过 5 秒没有正式媒体 | 标记 `record_media_stalled=true`，保留当前片段及会话，继续接受数据 |
| 120 秒内媒体恢复 | 写入实际收到的帧，不因这次暂停单独拆出恢复片段 |
| 连续 120 秒仍没有正式媒体 | 有界收尾；保留已有会话恢复机制，后续来帧允许续录 |
| 人员主动点击停止 | 使用原有尾帧排空期限，不额外等待恢复宽限期 |
| 磁盘容量故障 | 原有容量保护优先，不等待恢复期限 |
| 只收到心跳、预览或照片 | 不当作正式 RGB/Depth 恢复，不刷新录制媒体活动计时 |
| 系统时间被校准 | 恢复期限使用 `steady_clock`，不因墙钟跳变提前收尾 |

收到的迟到帧仍遵守原录制窗口和切片规则。跨正常切片边界时仍可能正常旋转文件；
“不断片”指不因这次短暂媒体暂停额外分割，不是取消 15 分钟切片。

## 配置与观测

```json
{
  "recording_staging": {
    "idle_finalize_ms": 5000,
    "media_recovery_grace_ms": 120000
  }
}
```

- 新字段缺省值为 120000ms，旧配置不添加字段也启用修复。
- 设为 0 可恢复旧的 idle 收尾策略，供兼容回退使用，不推荐现场使用。
- 非零时必须大于等于 `idle_finalize_ms`，最大 900000ms；错误配置拒绝启动。
- 状态 API 增加配置值和每相机 `record_media_stalled`；原有 `live` 仍表示在线状况，不伪装在线。
- 日志在进入等待和恢复时各记录一次，避免每轮维护循环刷屏。

120 秒是接收端愿意等待的期限，不代表发送端有 120 秒无损缓存。
发送端仍受帧数和字节上限约束，持续拥塞可能丢帧；时钟模型超期仍标记无效，不延长时钟可信期掩盖问题。
