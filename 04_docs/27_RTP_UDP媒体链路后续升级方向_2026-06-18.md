# RTP/UDP 媒体链路后续升级方向

日期：2026-06-18

## 背景

当前 v3 工程并不是 RTP/UDP 媒体传输：

- 状态心跳：UDP `50011`，发送 JSON 状态。
- 媒体数据：TCP `50010`，发送自定义媒体 packet，包含 RGB H.264 和 Depth raw/zlib。
- Web 预览：HTTP `8080`，由接收端从媒体 TCP 中解码生成 JPEG/BMP 预览。

代码层面 `01_sender_linux/src/config.cpp` 只允许 `status_protocol=udp` 和 `media_protocol=tcp`，接收端也以 `SOCK_STREAM` 监听媒体端口。因此当前所有 `Send-Q`、TCP 背压、队头阻塞分析都是针对现有实现成立的。

## 当前问题

树莓派 Gemini305 现场配置为 RGB `1280x800@30 MJPG -> H.264`、Depth `1280x800@30 Y16 -> zlib`。在 Wi-Fi 抖动或实际吞吐不足时，Depth 压缩包可接近 `0.8-0.9MB/帧`，RGB 和 Depth 又共用同一条 TCP 连接，会出现：

- Depth 大包填满 TCP 发送队列。
- TCP 队头阻塞导致 RGB 小包也发不出去。
- 接收端收不到连续 H.264 IDR/P 帧，Web RGB 预览卡住或变成无图。
- 若守护逻辑把 depth 背压误判成整路故障，会触发发送端反复重启。

当前已做的短期修复方向是：在 TCP 背压下把 Depth 当作 bulk 数据优先丢弃，保留 RGB 发送空间；同时避免在 RGB 仍能发送时因为 Depth 丢包触发整路重启。这只能缓解问题，不能从协议层消除 TCP 队头阻塞。

## 后续升级目标

后续应把实时媒体从“单 TCP 自定义包流”升级为“按用途拆分的低延迟链路”：

1. RGB 实时预览或主实时流走 RTP/UDP。
2. Depth 与 RGB 拆分通道，避免 Depth 大包阻塞 RGB。
3. 状态/控制继续保留 UDP/HTTP，减少改动面。
4. NAS 录制格式和下游 `frames.csv` 时间戳字段保持兼容。

## 建议技术路线

第一阶段：增加 RTP/UDP RGB 预览通道。（2026-06-18 已完成第一版，详见 `04_docs/28_RTP_UDP_RGB预览拆通道实现说明_2026-06-18.md`。）

- 发送端新增低码率 RGB H.264 RTP/UDP 输出，优先服务 Web 预览。
- 接收端用独立 RTP jitter buffer 解码预览，不再依赖媒体 TCP 中的 RGB 主码流生成网页画面。
- TCP 主媒体链路先保留，用于现有录制和兼容。

第二阶段：拆分 RGB 与 Depth 传输通道。

- RGB 实时流：RTP/UDP，允许丢包但保持低延迟。
- Depth 数据：独立 TCP 或独立 UDP/FEC 通道，按下游是否必须完整帧决定。
- 两个通道都携带同一套 `frame_system_timestamp_us`、设备时间戳和 frame id，接收端按时间戳合并落盘。

第三阶段：完善丢包恢复与监控。

- RGB RTP 使用关键帧请求/周期 IDR，接收端丢包后等待下一个 IDR 恢复。
- 接收端状态页区分 capture fps、send fps、receive fps、decode fps、drop fps。
- 增加每路实际网络吞吐、RTP 丢包率、jitter、late frame、queue depth。

## 取舍

RTP/UDP 的优势：

- 不会因为单个 depth 大包阻塞后面的 RGB 帧。
- 更适合实时预览和低延迟监看。
- 网络抖动时表现为局部丢帧，而不是整条 TCP 流积压。

RTP/UDP 的代价：

- 需要处理丢包、乱序、jitter buffer、关键帧恢复。
- 不能天然保证每帧都到达，正式录制如需完整帧仍需可靠通道或接收端质量标记。
- 需要新增调试指标，否则问题会从 “TCP Send-Q 堵塞” 变成 “RTP 丢包/乱序/迟到”。

## 验收指标

- 在同等 Wi-Fi 环境下，Depth 背压不应导致 RGB Web 预览长期无图。
- RGB Web 预览保持接近 30fps，允许画质降低但不应长时间冻结。
- 接收端记录每路 RTP 丢包率和恢复次数。
- 录制落盘字段保持兼容，下游仍可用 `frame_system_timestamp_us` 对齐。
- 断网、重连、单路相机拔插时，其他路预览不被连带阻塞。

## 当前现场建议

在 RTP/UDP 改造完成前，满规格 `1280x800@30` Depth 仍可能压垮 Wi-Fi。现场优先级建议为：

1. 需要稳定网页 RGB：降低 RGB 实时码率，Depth 背压时优先丢弃。
2. 需要完整 RGBD 录制：优先换有线或把树莓派放到更稳定的 AP/CPE 链路。
3. 需要同时稳定 RGB 预览和高分辨率 Depth：不要继续依赖单 TCP 媒体流，应进入 RTP/UDP 拆通道升级。
