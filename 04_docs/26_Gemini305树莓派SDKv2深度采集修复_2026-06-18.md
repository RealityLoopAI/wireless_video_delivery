# Gemini305 树莓派 SDK v2 深度采集修复记录

日期：2026-06-18

## 背景

树莓派发送端更换为 Orbbec Gemini305 后，用户要求保持高档位运行：

```text
RGB:   1280x800@30 MJPG
Depth: 1280x800@30 Y16/Z16
```

现场现象是工程通过 V4L2/UVC 直接读取 Depth 时，Depth 帧率只能到约 2fps，明显低于官方规格。用户明确要求不要降低深度档位，需要找出真实原因并修复。

## 根因

本工程此前为了绕过 SDK v1 无法枚举 Gemini305 的问题，给树莓派新增了 `capture_backend=v4l2`。该方案能读取 RGB，但对 Gemini305 的 Depth 不正确：

1. Gemini305 官方推荐使用 Orbbec SDK v2，SDK v1 对 Gemini305 不适配。
2. 直接从 Linux V4L2 节点读取 Gemini305 Depth，绕过了 Orbbec SDK v2 的设备初始化、profile 选择和深度数据链路。
3. 现场用官方 SDK v2 probe 验证，同一台相机同一条 USB3.2 链路可以同时跑 RGB `1280x800@30 MJPG` 和 Depth `1280x800@30 Y16`，稳定约 28-30fps。
4. 因此低帧率不是树莓派 USB3.0、线缆、接收端或网络导致，而是发送端 Depth 采集后端用错了。

官方参考：

- Orbbec SDK v2: https://github.com/orbbec/OrbbecSDK_v2
- Gemini 305 产品页: https://www.orbbec.com/products/tof-camera/gemini-305/

## 修复内容

### 1. Gemini305 改回 Orbbec SDK 后端

配置文件：

```text
06_configs/sender_raspberrypi-01_gemini305_v4l2.json
```

关键配置改为：

```json
"capture_backend": "orbbec_sdk",
"rgb_profile": {
  "width": 1280,
  "height": 800,
  "fps": 30,
  "format": "mjpg"
},
"depth_profile": {
  "width": 1280,
  "height": 800,
  "fps": 30,
  "format": "y16"
}
```

同时删除旧的人工 `uid=gemini305-CV2R46P00091`。SDK v2 实际枚举到的 UID 是 USB 拓扑值，例如 `3-1-2`，不是固定相机身份；该配置现在只用稳定的 `serial_number=CV2R46P00091` 选设备。

### 2. 支持 SDK v1/v2 自动选择

`01_sender_linux/CMakeLists.txt` 支持以下两类 SDK 目录：

```text
11_third_party/orbbec/linux_arm64/OrbbecSDK_v2.8.6
11_third_party/orbbec/linux_arm64/OrbbecSDK_C_C++_v1.10.27_.../OrbbecSDK_v1.10.27/SDK
```

如果现场安装了 SDK v2，CMake 和启动脚本优先使用 SDK v2；否则仍回落到 SDK v1，避免影响其他 Gemini Pro/RK 发送端。

新增脚本：

```text
05_tools/orbbec_sdk_env.sh
```

用途是统一解析 `ORBBEC_SDK_ROOT`、SDK 动态库目录和 SDK 配置 XML。

### 3. 兼容 SDK v1/v2 属性名差异

SDK v1 和 SDK v2 的 RGB 最大增益属性编号相同，但枚举名不同：

```text
SDK v1: OB_PROP_COLOR_MAXIMAL_GAIN_INT
SDK v2: OB_PROP_COLOR_AE_MAX_GAIN_INT
```

源码通过 `GWV3_ORBBEC_SDK_V2` 编译定义选择正确枚举名。

### 4. 深度 zlib 压缩从采集线程拆出

原来 SDK 采集线程内同步执行高分辨率深度 zlib 压缩。`1280x800` 深度帧约 2MB，zlib 即使用最快压缩也会占用约 30ms/帧，在树莓派上会拖慢采集循环。

本次新增 `LatestDepthCompressionQueue`：

- 采集线程拿到 SDK Depth 帧后立即记录帧号、设备时间戳、系统时间戳和 profile 元数据。
- 如果 `depth_transport.compression=zlib`，只复制当前最新深度帧到压缩队列。
- 压缩线程异步完成 zlib 后再发布到媒体发送队列。
- 队列只保留每路最新帧，旧帧会被覆盖，避免高延迟堆积。

该改动保证 SDK 采集输入可以保持 30fps；当树莓派 CPU 或网络处理不过来时，发送端丢旧深度帧，而不是阻塞相机采集。

### 5. watchdog 单实例锁

现场曾出现 systemd 服务和手动启动脚本同时拉起 sender，导致两个 watchdog/发送端争抢相机节点。

`05_tools/sender_watchdog.sh` 新增：

```text
12_build/sender.lock
```

第二个 watchdog 无法获得锁时直接退出，避免重复占用相机。

### 6. RGB 曝光配置

迁移 SDK v2 后，Gemini305 当前默认使用自动曝光。为了尽量保持 30fps，仍保留 `auto_exposure_priority=0`：

```text
auto_exposure=true
auto_exposure_priority=0
power_line_frequency=3
```

如果自动曝光导致帧率或亮度不符合现场要求，再切回手动曝光并重新标定 `exposure/gain` 数值。

```json
"color_controls": {
  "auto_exposure": true,
  "auto_exposure_priority": 0,
  "power_line_frequency": 3
}
```

## 现场部署步骤

树莓派需要把 Orbbec SDK v2 解压到仓库忽略路径：

```text
/home/berry/Desktop/wireless_video_delivery/11_third_party/orbbec/linux_arm64/OrbbecSDK_v2.8.6
```

构建命令：

```bash
cd /home/berry/Desktop/wireless_video_delivery
cmake -S . -B 12_build \
  -DGWV3_BUILD_RECEIVER=OFF \
  -DGWV3_BUILD_SENDER=ON \
  -DORBBEC_SDK_ROOT=/home/berry/Desktop/wireless_video_delivery/11_third_party/orbbec/linux_arm64/OrbbecSDK_v2.8.6
cmake --build 12_build --target gemini_sender -j2
```

启动命令：

```bash
sudo systemctl restart gemini-sender.service
```

## 剩余风险

1. 树莓派在 `1280x800@30` 深度 zlib 下已经接近压缩极限，`depth_sent_fps` 会在 20 多到 30fps 间波动。采集输入是 30fps，波动来自 zlib 压缩和网络发送，不是相机采集掉帧。
2. 如果必须严格落盘 30fps 高分辨率深度，需要考虑后续协议升级：例如增加 LZ4/Zstd-fast 深度压缩、允许接收端解压新格式，或改为有线网络/更强发送端 CPU。
3. 不建议再把 Gemini305 切回 V4L2 Depth。V4L2 只能作为故障排查时的临时 RGB/节点枚举工具，不作为正式采集后端。
