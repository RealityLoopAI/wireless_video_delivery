# 少量 RGB 缺帧定位记录（2026-09-10）

## 1. 目标与结论边界

本轮接受少量真实缺帧，但需要知道缺在哪个环节，判断是否值得修复。
没有通过重复帧、修改时间戳、降低档位或放宽 JPEG 校验隐藏缺帧。
本轮首先修补诊断盲区，不把新增日志说成已经修好所有缺帧。

当前已把问题分为两类：

- **采集输入被 JPEG 完整性检查拒绝**：52d2 在 09-09 18:22:34 的 frame 26043 有明确日志。
  09-10 10:22:09 的 frame 6633、10:25:14 的 frame 12182 再次出现同类拒绝。
  历史文件没有保存对应原始载荷，尚不能区分 USB 数据缺失、SDK/固件处理或有效 JPEG 后有异常尾部。
- **送入编码后没有匹配输出**：新诊断在 09-10 10:27:45 捕捉到 52d2 frame 1402 已提交，
  匹配到的下一个输出是 frame 1403。范围已缩小到 JPEG 解析/解码、编码及其内部队列。
  此事件发生在短录制开始前，不冒充录制期间的缺帧。

09-09 的另两个具体历史缺口（52d2 frame 1397、fe0f7222 frame 18125）
仍不能用今天的相似事件直接定案。需要相应帧的阶段证据，历史日志没有这些字段。

**补充实录证据**：09-10 10:32:35，fe0f7222 frame 6513 已提交编码，随后匹配到 frame 6514。
本次 NAS CSV 恰好缺少 6513，前后为 6512/6514，视频索引为 4947/4948，
`global_timestamp_us` 间隔 63876us。同一秒 `rgb_source_missing=0`、
`rgb_encode_unmatched_inputs=1`、JPEG/时间匹配/发送错误计数均为 0。
这次已将实录缺口对应到发送端编码管线，不是接收端封装或 NAS 搬运丢掉已编码帧。

## 2. 已核查的代码

### 2.1 现有编码路径确实可能主动丢帧

`01_sender_linux/src/gst_h264_encoder.cpp` 的单路管线包含：

```text
queue max-size-buffers=2 leaky=downstream
appsink ... max-buffers=8 drop=true
```

双编码管线还包含会丢旧帧的 appsrc 和分支队列。
当消费者暂时跟不上时，丢帧可以不伴随编码错误。
本轮确认其存在，没有直接放大所有队列或改成阻塞，以免把压力转移到 SDK 采集线程。
新日志仍不能分辨同一编码管线里的哪一个内部队列丢了某帧。

### 2.2 旧日志为什么没找到

`resolve_rgb_encode_timing()` 根据输出 PTS 找到待匹配帧后，会移除它之前的待匹配项。
此前这些被移除的项没有独立统计；历史列表超过 64 项后的移除也没有计数。
因此“没有 timing mismatch 日志”不能证明所有编码输入都有输出。
本轮保留原匹配和移除行为，只增加可审查计数与帧号范围。

### 2.3 SDK 帧号的含义

核对官方 OrbbecSDK v2.8.6 源码，tag 对应提交为
`63994096ce6a0c07a235500802ce5379490404b7`。
`ObLibuvcDevicePort::onFrameCallback()` 使用自己的 `loopFrameIndex` 给回调帧编号，
并在回调中读取主机系统时间。因此连续的软件帧号不保证传感器每个曝光周期都被交付。

来源：[官方 SDK 回调实现](https://github.com/orbbec/OrbbecSDK_v2/blob/v2.8.6/src/platform/usb/uvc/ObLibuvcDevicePort.cpp)。
这条结论针对该 SDK/后端，不能直接套用所有相机或 SDK v1 的编号实现。

### 2.4 官方 SDK 的 JPEG 校验有盲区

同版本 `utils::checkJpgImageData()` 首先检查 SOI，随后最多检查末尾 10 个字节。
如果这 10 个字节都是零，函数没有继续查找真正的 EOI，仍可能返回成功。
实测正常相机载荷的零填充远不止 10 字节，因此“SDK 没报 JPEG 校验失败”不是完整性的证明。

来源：[官方 SDK 校验实现](https://github.com/orbbec/OrbbecSDK_v2/blob/v2.8.6/src/shared/utils/Utils.cpp)。
本项目会去掉整个连续零填充区，再检查真正的首尾标记，未放宽此规则。
新增测试覆盖“有 SOI、无 EOI、大量尾部零填充”的拒绝行为。
这解释了异常数据可能通过 SDK 首层检查，但没有证明历史每个拒绝帧的具体损坏形式。

## 3. 新增诊断与保护

代码提交：`f9f5411dee7e`；sender source hash：`1d8f7d0e0ec20cb3`。

每秒 `perf` 新增：

| 字段 | 含义 |
| --- | --- |
| `rgb_source_missing` | 程序采集入口看到的帧号缺口数量，不等同于全部传感器漏采 |
| `rgb_source_duplicates` | 采集入口重复帧号 |
| `rgb_source_resets` | 采集入口帧号回退，重启/重连需单独解释 |
| `rgb_encode_unmatched_inputs` | 找到更新输出 PTS 时，移除的未匹配旧输入数量 |
| `rgb_timing_history_evictions` | 编码时间信息列表达到上限后移除的项数 |

异常日志给出前后帧号或未匹配帧号范围，按相机限频，累计计数不受日志限频影响。
JPEG 拒绝日志补充 `soi`、`trimmed_size`、`first_eoi_end`、`last_eoi_end`。
EOI 字节模式存在不证明 JPEG 可完整解码，所以这些字段只用于定位，不用于放行。
正常输入不增加整帧拷贝，也不增加正式录制文件字段。

## 4. 纯采集取证工具

扩展 `orbbec_fps_probe`，新增：

- `--audit-directory NEW_DIR`：记录原始帧号、设备时间、SDK 系统时间、主机取帧时间和 JPEG 首尾信息。
- `--audit-max-files N`：仅限量保存被现有首尾规则拒绝的原始载荷，默认 8，最大 32。
- `--context-config XML`：只在此工具进程使用指定 SDK 配置，便于后续受控后端对照。

取证目录要求新建并设为仅属主可访问，单个保存载荷不超过 8MiB；审计时长最多 3600 秒。
工具会直接打开相机，**不能与正式 sender 同时占用同一相机，也不能在正式录制中运行**。
它会同步写少量 CSV 和限量异常文件，是隔离实验，不是生产采集路径。

```sh
orbbec_fps_probe --index 0 --streams both --aggregate any --seconds 300 \
  --color-width 1280 --color-height 800 --depth-width 320 --depth-height 200 \
  --depth-format y16 --auto-exposure 0 --exposure 220 --gain 40 \
  --audit-directory /tmp/NEW_AUDIT_DIR --audit-max-files 8
```

请按实际相机填写参数。这条命令是本次 52d2 实验参数，不是新的出厂曝光配置。
不要拿工具的 `any` 聚合模式、静态曝光和无编码负载，冒充完整生产链路的等价压力测试。

## 7. 接下来如何判断是否修复

1. 如果 `rgb_source_missing` 增加：结合 SDK 队列溢出、CPU 调度、USB 内核日志和设备时间跨度排查。
   重启预热期间的缺口单独计，不混入正式录制统计。
2. 如果 `rgb_encode_unmatched_inputs` 增加且采集入口连续：对具体编码管线的 queue、解析器、解码器和编码器加阶段观测，
   然后测试调整有限缓冲或隔离预览负载的收益，不能直接归罪于网络。
3. 如果 JPEG 拒绝重复：保存原始异常载荷，区分真实截断和合法图像后的额外数据。
   不允许补 EOI 或跳过解码检查伪造完整图像。
4. V4L2 是候选对照，不是已经验证的修复；本轮没有将其切入生产。
   [官方后端性能说明](https://orbbec.github.io/OrbbecSDK_v2/docs/tutorial/performance_tuning.html)
   也要求检查内核、元数据/时间戳兼容性和重新插拔条件。

原则：解决有证据的软件缺陷；对仍未定位的低概率缺帧保留证据和质量标记，
不能用短测通过替代长时间、不同场景的验证。
