## 6. 配置

### 6.1 发送端身份

当前 RK3588 配置使用固定发送端 ID：

```json
"sender_id": "rk3588-ubuntu"
```

手动值必须只包含 ASCII 字母、数字、下划线 `_`、短横线 `-`，长度 1-64。

多发送端现场规则：

1. 接收端使用 `<sender_id>_<camera_id>` 作为唯一相机 key，预览、录制控制、状态统计和默认存储目录都依赖这个 key。
2. `sender_id` 必须对应一台物理发送端；复制配置到另一台机器时必须先改成该机器自己的固定 ID，或使用 `auto` 派生唯一 ID。
3. `camera_id` 必须对应该发送端上的稳定相机槽位；不要为了适配仓库默认配置、本机 IP 或临时调试把已交付 key 改名。
4. 改动 `sender_id` / `camera_id` 前，先查接收端 `/api/status` 是否已有同名 live key，并查看 `sender_preflight.sh` 是否提示 ID conflict。

实际启动使用的 ID 以预检或状态命令输出为准：

```bash
./05_tools/sender_preflight.sh
./05_tools/status_sender.sh
```

### 6.2 接收端地址

修改接收端 IP：

```json
"receiver": {
  "ip": "192.168.66.196",
  "media_port": 50010,
  "status_port": 50011
}
```

### 6.3 RGB 与 Depth

修改 RGB 规格和码率：

```json
"rgb_profile": {
  "width": 1920,
  "height": 1080,
  "fps": 30,
  "format": "mjpg"
},
"rgb_encoding": {
  "codec": "h264",
  "mode": "hardware",
  "gstreamer_encoder": "mpph264enc",
  "bitrate_bps": 12000000
}
```

修改 Depth 压缩：

```json
"depth_transport": {
  "compression": "rvl",
  "quantization_step_mm": 2
}
```

支持值：

```text
none
zlib
rvl
qdelta
lz4
plz4
pzlib
q8lz4
q8zlib
pq8zlib
```

使用 `zlib` 时，接收端必须先解压 Depth payload，再按 `uint16 little-endian` 解析。
`rvl` 是面向 Depth 图的轻量差分/游程/变长编码，接收端解码后同样按 `uint16 little-endian` 解析，适合树莓派 Gemini305 高分辨率 Depth 的实时发送实验。
`plz4` 和 `pzlib` 会先按 `quantization_step_mm` 量化 `uint16` Depth，再分块并行压缩；它们保留 `uint16` 全量程，适合 4mm 这类较小量化步长。
`q8lz4`、`q8zlib` 和 `pq8zlib` 会先把 `uint16` Depth 量化为 8-bit index 再压缩，接收端解码后仍输出 `uint16 little-endian` Depth 帧；它们会降低深度数值精度，但不改变落盘格式。`pq8zlib` 是分块并行 zlib 版本，用更多 CPU 换更低单帧压缩延迟。
`quantization_step_mm` 默认值为 `0`，表示不量化；设置为 `2` 时，发送端会在压缩前把非零 Depth 值按 2mm 步长规整，输出仍是 `uint16 little-endian` Depth 帧。
2026-06-22 现场实测中，`rvl + 2mm` 尚未稳定通过树莓派 Wi-Fi 链路验证，默认录制配置仍使用 `zlib`。
2026-06-23 Orange Pi Gemini305 `1280x800@30` 精度优先配置改为 `plz4 + 4mm`，实测 Depth 多数秒约 `29-31fps`、码率约 `137-190Mbps`，无发送失败；该配置比 `pq8zlib + 128mm` 精度高很多，但网络压力也明显更高。

### 6.4 多相机绑定

双路相机必须为每一路配置唯一 `camera_id`，并使用 `serial_number` 绑定物理相机；现场双路还应同时写入稳定 USB 端口 UID。发送端会拒绝重复 `camera_id`、重复序列号，以及旧配置里的 `depth_camera_id`。RGB 和 Depth 对外默认使用同一个 `camera_id`，避免接收端或本地预览出现 RGB/Depth 对反。

Orbbec SDK 在部分设备上可能只从 depth 侧枚举到 UID，发送端会通过 sysfs 查找配对的 RGB USB2 序列号。`uid` 可以写稳定端口前缀，例如 `10-1.2` 或 `8-1.4.2`；运行时 SDK 返回 `10-1.2-7`、`8-1.4.2-6` 这类带设备号的 UID 时，发送端会归一到同一个 sysfs 设备后再匹配。现场应优先使用 `serial_number + uid` 双重约束：UID 锁定物理 USB 口，序列号防止插错相机。

```json
{
  "camera_id": "cam01",
  "serial_number": "AY2M54302ZH",
  "uid": "10-1.2"
}
```

发送端同时支持两种配对拓扑：USB3 Depth 与 USB2 RGB 分别出现在相邻 bus 上，以及相机降级为 USB2-only 时 Depth/RGB 出现在同一 bus 的相邻端口上。只要 RGB 侧 sysfs 暴露稳定序列号，重新插拔后会按 `serial_number` 重新匹配。

如果两路 RGB 各自正确，但 Depth 物理视角互相交叉，在双路配置根节点启用：

```json
{
  "swap_depth_between_cameras": true
}
```

该开关要求正好配置两路相机。启用后发送端只交换 Depth 的媒体包 `camera_id` 和本地 Depth 预览归属，RGB 不交换；当任一路离线时，Depth 临时回落到本路，双路恢复在线后再重新交换。启动日志会打印 `depth stream remap enabled`，预检和状态脚本会打印 `depth_remap: swap_depth_between_cameras=true`。`time_sync camera_id=...` 中的 `camera_id` 表示采集源，启用 remap 后日志会追加 `depth_output_camera_id=...` 表示该 Depth 实际发往的接收端相机 key。现场判断是否修正时，应抓取接收端每路 RGB/Depth 预览并并排对照；网页主预览如果还选着旧 sender key，会看起来像没有修正。

如果配置中的某一路相机未插入，发送端会保留其他相机继续运行，并定期上报该路 `camera_offline` / 重连失败原因。

### 6.5 运行中热插拔

发送端运行中每 2 秒扫描一次 Orbbec 设备列表。当前交付预期为默认一路 RGBD；热插拔保留为扩展能力。发现配置文件之外的新设备时，会自动按序分配新的 `camera_id` 并启动发送，例如当前默认配置已有 `cam02`，新插入一路会分配为 `cam03`，再插入一路会分配为 `cam04`。

热插拔路使用当前满规格模板：

```text
RGB: 1920x1080@30 MJPG -> H.264/mpph264enc 12Mbps
Depth: 320x200@30 y12 -> zlib
Color controls: auto_exposure=false, exposure=312, gain=80
Preview: 默认使用每路 OpenCV RGB/Depth 预览窗口。需要调试双 RGB 时间戳对齐预览时，将配置中的 `preview.aligned_rgb` 改为 `true`；对齐窗口会按 `system_timestamp_us` 对齐显示，阈值 15ms，超过阈值丢弃较旧预览帧。
```

现场 `SV1301S_U3 / AY2MC31010W` 经 `orbbec_depth_probe` 枚举确认最低 Depth profile 为 `320x200@5 y11/y12`，最高 Depth profile 为 `1280x800@30 y11/y12`。当前默认 Depth 已按交付预期切到 `320x200@30 y12`；单路最高 Depth 测试可使用 `06_configs/sender_rk3588-01_cam02_depth_max.json`。最高档会显著提高 USB、zlib、网络和接收端压力，不作为默认交付配置。

`y11` / `y12` 是 Orbbec Depth stream 的设备输出格式档位。发送端经 SDK 获取后，对外仍统一发送 `uint16 depth frame`；接收端不需要按 `y11` / `y12` 分开解析。默认使用 `y12`，因为它比 `y11` 多 1 bit 深度量化信息。

Depth 运行时，发送端会按 `depth_profile.fps` 对 Depth 压缩和媒体发送限流；排查运行状态时，以 `depth_sent_fps` 和 `depth_mbps` 判断接收端实际收到的 Depth 数据量，`depth_input_fps` 只表示 SDK 输入到发送端的实际帧率。

2026-06-05 单路最高 Depth 档有效采样结论：`RGB 1920x1080@30 + Depth 1280x800@30 y12 -> zlib` 在链路正常时可跑到 RGB/Depth 约 30fps，网络总码率约 74.5Mbps，其中 Depth 约 62.5Mbps；Depth USB 输入约 492Mbps，Depth zlib 平均约 15.8ms/帧，send failure 为 0。该结论只适用于单路最高档测试，不能直接外推为双路最高 Depth 稳定能力。

热插拔限制和故障处理：

1. 最多同时发送 4 路相机；超过 4 路的新设备会被忽略，并通过日志和 status `hotplug_camera_ignored` event 上报。
2. 4 路是发送端逻辑上限；实际稳定路数取决于当前无线链路和接收端吞吐。链路拥塞时发送端按媒体 TCP 背压保护丢弃尚未写入 socket 的完整媒体包，并在 `perf` 日志中记录 `rgb_send_failures` / `depth_send_failures`，不会伪造满帧率。
3. 热插拔分配只在当前进程内生效，不写回主配置文件，也不写 runtime state。
4. 动态分配的编号不复用。动态路离线后保留该 `camera_id` 的离线状态；后续再插入设备会继续分配下一个编号。
5. 新设备启动失败后按设备 key 冷却 30 秒再重试，并通过 `hotplug_camera_start_failed` event 上报；已有路不受影响。
6. 配置内的 `cam01` / `cam02` 仍按 `serial_number` / `uid` 绑定并独立重连。

1. 当前交付预期改为默认一路 RGBD，目标是降低 Wi-Fi 上行、USB、中断、CPU 压缩和远程操作通道之间的资源竞争。

6. 单路最高 Depth 档约 74.5Mbps，明显高于默认单路 `320x200@30 y12`；若 Wi-Fi tx bitrate 掉到约 120Mbps 以下、ping 出现丢包/尖峰，或 Send-Q 快速堆积，不应继续按最高 Depth 档交付，应保持默认档或降低 RGB 码率。

## 7. 一键运行

所有启动入口都会先执行发送端预检，并在终端里显示：

```text
配置文件、sender_id、camera_id、接收端 IP/端口、媒体/状态协议、RGB profile、RGB 编码器和码率、
Depth profile、Depth 压缩方式、预览开关、日志目录、到接收端的路由、Wi-Fi 链路信息、配置校验结果
```

预检失败会输出中文错误，不会继续启动。`start_sender.sh` 和 `start_sender_preview.sh` 会启动 `05_tools/sender_watchdog.sh` 守护进程；守护进程负责拉起 `gemini_sender` 子进程，并在子进程退出后默认 3 秒自动重启。`12_build/sender.pid` 是守护进程 PID，`12_build/sender_child.pid` 是当前发送端子进程 PID。

当前设备的一键启动脚本默认启用 Wi-Fi guard：默认只要求 `wlan0` 的当前频率不低于 5000MHz，避免自动落到 2.4G 网络后媒体 TCP 被背压卡住；如果现场需要固定某个 SSID，再通过环境变量显式指定。相关环境变量：

```bash
GEMINI_SENDER_DEFAULT_WIFI_CONNECTION=现场5G网络名
GEMINI_SENDER_WIFI_CONNECTION=现场5G网络名
GEMINI_SENDER_WIFI_REQUIRED_SSID=现场5G网络名
GEMINI_SENDER_WIFI_MIN_FREQ_MHZ=5000
GEMINI_SENDER_WIFI_IFACE=wlan0
```

守护进程运行中也会周期检查 Wi-Fi 策略；如果发现链路不符合要求，会重新连接指定 Wi-Fi，并杀掉发送端子进程，让下一轮启动重建媒体 TCP 连接。发送端自身也会检测“RGB/Depth 采集正常但媒体持续发送失败”的状态，默认连续 5 个性能采样周期后主动退出，由 watchdog 自动重启。

### 7.1 桌面时间与熄屏设置

当前 Orange Pi GNOME 桌面熄屏时间设置为 3600 秒，桌面时钟显示到秒。这两项是当前用户的桌面 `gsettings`，不属于发送端进程参数：

```bash
gsettings get org.gnome.desktop.session idle-delay
gsettings get org.gnome.desktop.interface clock-show-seconds
```

如需重新应用当前现场值：

```bash
./05_tools/set_desktop_screen_timeout.sh 3600
gsettings set org.gnome.desktop.interface clock-show-seconds true
```

熄屏脚本会设置：

```text
org.gnome.desktop.session idle-delay = 3600
org.gnome.desktop.screensaver lock-delay = 0
```

当前现场还要求 Web Monitor 页面上的可读时间统一按北京时间 UTC+8 显示到秒：

```text
系统时间: YYYY-MM-DD HH:mm:ss
Last media / Last status: YYYY-MM-DD HH:mm:ss (+/- 相对秒数)
```

该要求只影响页面展示。发送端协议、接收端 API 和落盘字段中的 `*_timestamp_us` / `last_*_us` 仍保留 Unix epoch microseconds 原始值，用于 RGB/Depth 和多发送端跨流时间线对齐。

多路或最高 Depth 档运行前，启动脚本会尝试执行 `05_tools/prepare_rk3588_usb.sh`，并在预检中打印当前 `usbfs_memory_mb`、`net.core.wmem_max`。如果没有 root 权限，这些参数不会被写入，预检会继续启动但会给出 warning；此时可能出现 Orbbec SDK `无法分配内存`、某一路 Depth 长期为 0fps，或 TCP 背压丢包。现场建议先执行：

```bash
echo 256 | sudo tee /sys/module/usbcore/parameters/usbfs_memory_mb
echo 8388608 | sudo tee /proc/sys/net/core/wmem_max
echo 1048576 | sudo tee /proc/sys/net/core/wmem_default
```

采集自恢复策略：

```text
单路 RGB 或 Depth 超过默认 8 秒无帧，但相机工作线程仍在返回 frameset：只重启该 camera_id 的 Orbbec pipeline。
相机工作线程卡死，连续性能采样中 waitForFrames 没有返回：发送端子进程退出，由 watchdog 整体拉起。
同一 camera_id 的采集停滞重连默认有 30 秒冷却，避免系统 USB 缓冲不足时反复冲击 Orbbec SDK。
可用 GEMINI_SENDER_CAPTURE_STALL_SECONDS、GEMINI_SENDER_CAPTURE_STALL_RESTART_SAMPLES、GEMINI_SENDER_CAPTURE_STALL_RECONNECT_COOLDOWN_SECONDS 覆盖默认阈值。
```

停止脚本会先停 watchdog 和当前子进程，再清理残留 `gemini_sender`；普通 `kill` 超时后会升级到 `kill -9`，避免旧进程继续占用 UVC 设备导致下一次启动报 `uvc_open already opened`。

媒体 TCP 发送采用非阻塞背压保护。配置项 `transport.send_timeout_ms` 控制一个媒体包在 TCP 背压下允许占用发送路径的最长时间，默认 80 ms；`transport.send_buffer_bytes` 是发送端请求的 socket 发送缓冲大小，RK3588 现场配置为 4 MiB，实际值仍受系统 `net.core.wmem_max` 限制。当 socket 已有积压且新包无法完整进入发送队列时，发送端会在写入前丢弃该完整包并保留 TCP 连接；如果连续背压丢包，则主动关闭 media socket 并重连，避免采集还在跑但接收端帧数长期不增长。

## 9. 常见问题

接收端只收到 H.264 头，没有有效画面：

```text
确认发送端源码包含 videoconvert 后强制 NV12 的修复。
确认运行的是最新构建出的 gemini_sender。
```

接收端无法解析 Depth：

```text
确认接收端已支持 codec_or_compression=zlib。
未升级接收端时改用 sender_orangepi5pro-01.json。
```

从有线切到无线后连接异常：

```text
先执行 ./05_tools/stop_sender.sh
再执行 ./05_tools/start_sender.sh
```

原因是已有 TCP 连接会保留旧本地 IP，需要重启 sender 重新建连。

本地没有预览窗口：

```text
使用 ./05_tools/start_sender_preview.sh。
确认 DISPLAY 正确。
无桌面环境时使用 ./05_tools/start_sender.sh。
```

Depth 伪彩预览闪烁：

```text
SV1301S_U3 官方有效深度范围为 0.25m-2.5m。
发送端本地预览和接收端网页 Depth 预览都应使用固定 250mm-2500mm 伪彩范围。
不要使用每帧 min/max 自动拉伸，否则单个远点或噪点变化会导致整张伪彩图颜色跳变。
```

Wi-Fi 多路卡顿：

```text
当前交付预期为一路 RGBD，默认 `320x200@30 y12`，RGB 保持 `1920x1080@30 H.264 12Mbps`。
最高 Depth 单路实测约 74.5Mbps，会明显挤占 Wi-Fi 上行和远程操作通道。
多设备或多路不是当前默认目标；若未来重新启用，应优先把接收端 NAS 和发送端改成有线，或使用多个有线回程 Wi-Fi 6/6E AP 分流。
不要把远程控制、Git/网页预览和多路 RGBD 大流量全部挤在同一个不稳定 Wi-Fi 上。
```

媒体发送突然掉到 0：

```text
现象: 本地相机仍在采集，日志有 rgb_input_fps/depth_input_fps，但 rgb_sent_packets_s/depth_sent_fps 变成 0。
优先检查: ss -tinpe 'dst 192.168.66.196:50010' 的 Send-Q、sender_stdout.log 的 media send failed。
原因之一: 系统 net.core.wmem_max 太小，socket 实际发送缓冲被限制，连续媒体帧积压后触发背压。
原因之二: 发送端 Wi-Fi 漂到错误 SSID 或 2.4GHz 频段，媒体 TCP 实际吞吐不足。
现场修复值: net.core.wmem_max=8388608，net.core.wmem_default=1048576，transport.send_buffer_bytes=4194304。
持久化示例: /etc/sysctl.d/99-gemini-video-transport.conf。
当前启动脚本默认只保 5GHz；如果需要强制切回某个 SSID，再显式设置 GEMINI_SENDER_DEFAULT_WIFI_CONNECTION 或 GEMINI_SENDER_WIFI_* 环境变量。
```

USB 相机导致键鼠卡顿：

```text
RK3588 上双 Orbbec + 无线 HID 接收器可能共用 USB 控制器或经过同一 hub。
05_tools/prepare_rk3588_usb.sh 会将 OTG 切到 host、增大 usbfs_memory_mb，并关闭 Orbbec、UGREEN HID 和 USB hub 的 autosuspend。
udev 规则模板位于 05_tools/99-orbbec-noautosuspend.rules、05_tools/99-ugreen-hid-noautosuspend.rules、05_tools/99-usb-hubs-noautosuspend.rules。
2026-05-28 RK3588 现场实测：单台 Orbbec 在 USB2-only 链路上可以同时跑当前 profile，即 RGB MJPG 1920x1080@30 + Depth 640x400@30。发送端日志显示 RGB 输入约 55-62Mbps，Depth 输入约 118-128Mbps，合计约 175-190Mbps。2026-06-01 之后配置显式使用 SDK 支持的 `y12` profile；SDK 仍向发送端提供 uint16 depth frame。
该结论只适用于当前 profile 和单相机。USB2 理论 480Mbps，实际稳定可用带宽通常低很多；MJPG 帧大小会随画面和曝光变化，UVC 还可能有带宽预留。不要把两台相机或键鼠接收器堆在同一条 USB2 root bus / hub 上作为长期方案。
若仍卡顿，应把两路相机分到独立 USB3 控制器/独立 root bus 或独立供电 hub，键鼠接另一条 USB2 总线或蓝牙，避免和相机共享高带宽链路。
```
