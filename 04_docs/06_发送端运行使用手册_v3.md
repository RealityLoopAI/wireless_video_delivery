# 发送端运行使用手册 v3

## 1. 适用范围

本文档说明 RK3588 / Orange Pi 5 Pro 发送端工程的构建、配置、启动、验证和常见问题。GitHub 仓库以源码形态交付，不包含当前机器的运行日志、PID 文件和压缩归档包。

发送端主体目录：

```text
01_sender_linux/     发送端 C++ 源码
03_common_core/      媒体包协议公共定义
04_docs/             文档
05_tools/            一键启动、停止、状态脚本
06_configs/          发送端配置
11_third_party/      Orbbec SDK 放置说明
```

## 6. 配置

### 6.1 发送端身份

当前 RK3588 配置使用固定发送端 ID：

```json
"sender_id": "rk3588-ubuntu"
```

手动值必须只包含 ASCII 字母、数字、下划线 `_`、短横线 `-`，长度 1-64。

实际启动使用的 ID 以预检或状态命令输出为准：

```bash
./05_tools/sender_preflight.sh
./05_tools/status_sender.sh
```

### 6.2 接收端地址

修改接收端 IP：

```json
"receiver": {
  "ip": "192.168.66.196",
  "media_port": 50010,
  "status_port": 50011
}
```

### 6.3 RGB 与 Depth

修改 RGB 规格和码率：

```json
"rgb_profile": {
  "width": 1920,
  "height": 1080,
  "fps": 30,
  "format": "mjpg"
},
"rgb_encoding": {
  "codec": "h264",
  "mode": "hardware",
  "gstreamer_encoder": "mpph264enc",
  "bitrate_bps": 12000000
}
```

修改 Depth 压缩：

```json
"depth_transport": {
  "compression": "zlib"
}
```

支持值：

```text
none
zlib
```

使用 `zlib` 时，接收端必须先解压 Depth payload，再按 `uint16 little-endian` 解析。

### 6.4 多相机绑定

双路相机必须为每一路配置唯一 `camera_id` 和 `serial_number` 或 `uid`。发送端会拒绝重复 `camera_id`、重复序列号，以及旧配置里的 `depth_camera_id`。RGB 和 Depth 永远使用同一个 `camera_id`，避免接收端或本地预览出现 RGB/Depth 对反。

Orbbec SDK 在部分设备上可能只从 depth 侧枚举到 UID，发送端会通过 sysfs 查找配对的 RGB USB2 序列号。现场应优先用相机机身序列号绑定，不建议把 `uid` 写死到运行配置里，因为部分 USB 拓扑下 uid 会包含设备号，重新插拔后可能从类似 `7-1.4.2-9` 变成 `7-1.4.2-12`：

```json
{
  "camera_id": "cam01",
  "serial_number": "AY2M54302ZH"
}
```

发送端同时支持两种配对拓扑：USB3 Depth 与 USB2 RGB 分别出现在相邻 bus 上，以及相机降级为 USB2-only 时 Depth/RGB 出现在同一 bus 的相邻端口上。只要 RGB 侧 sysfs 暴露稳定序列号，重新插拔后会按 `serial_number` 重新匹配。

如果配置中的某一路相机未插入，发送端会保留其他相机继续运行，并定期上报该路 `camera_offline` / 重连失败原因。

## 7. 一键运行

所有启动入口都会先执行发送端预检，并在终端里显示：

```text
配置文件、sender_id、camera_id、接收端 IP/端口、媒体/状态协议、RGB profile、RGB 编码器和码率、
Depth profile、Depth 压缩方式、预览开关、日志目录、到接收端的路由、Wi-Fi 链路信息、配置校验结果
```

预检失败会输出中文错误，不会继续启动。`start_sender.sh` 和 `start_sender_preview.sh` 会启动 `05_tools/sender_watchdog.sh` 守护进程；守护进程负责拉起 `gemini_sender` 子进程，并在子进程退出后默认 3 秒自动重启。`12_build/sender.pid` 是守护进程 PID，`12_build/sender_child.pid` 是当前发送端子进程 PID。

当前设备的一键启动脚本默认启用 Wi-Fi guard：启动前会优先切到 `土著拯救器-5G`，并要求 `wlan0` 的当前频率不低于 5000MHz，避免自动落到 2.4G 网络后媒体 TCP 被背压卡住。相关环境变量可覆盖：

```bash
GEMINI_SENDER_WIFI_CONNECTION=土著拯救器-5G
GEMINI_SENDER_WIFI_REQUIRED_SSID=土著拯救器-5G
GEMINI_SENDER_WIFI_MIN_FREQ_MHZ=5000
GEMINI_SENDER_WIFI_IFACE=wlan0
```

守护进程运行中也会周期检查 Wi-Fi 策略；如果发现链路不符合要求，会重新连接指定 Wi-Fi，并杀掉发送端子进程，让下一轮启动重建媒体 TCP 连接。发送端自身也会检测“RGB/Depth 采集正常但媒体持续发送失败”的状态，默认连续 5 个性能采样周期后主动退出，由 watchdog 自动重启。

后台启动，不打开本地预览：

```bash
./05_tools/start_sender.sh
```

带本地 RGB + Depth 预览启动：

```bash
./05_tools/start_sender_preview.sh
```

指定其他配置启动：

```bash
./05_tools/start_sender.sh 06_configs/sender_orangepi5pro-01.json
```

查看状态：

```bash
./05_tools/status_sender.sh
```

只做启动前检查、不启动：

```bash
./05_tools/sender_preflight.sh
```

停止：

```bash
./05_tools/stop_sender.sh
```

日志：

```text
08_reports/sender_logs/sender.log
08_reports/sender_logs/sender_stdout.log
```

媒体 TCP 发送采用非阻塞背压保护。配置项 `transport.send_timeout_ms` 控制一个媒体包在 TCP 背压下允许占用发送路径的最长时间，默认 80 ms；`transport.send_buffer_bytes` 是发送端请求的 socket 发送缓冲大小，RK3588 现场配置为 4 MiB，实际值仍受系统 `net.core.wmem_max` 限制。当 socket 已有积压且新包无法完整进入发送队列时，发送端会在写入前丢弃该完整包并保留 TCP 连接；如果连续背压丢包，则主动关闭 media socket 并重连，避免采集还在跑但接收端帧数长期不增长。

## 8. 验证

配置校验：

```bash
./12_build/bin/gemini_sender --config 06_configs/sender_rk3588-01_two_cameras.json --validate-config
```

本机采集验证，不发送、不预览：

```bash
./12_build/bin/gemini_sender --config 06_configs/sender_rk3588-01_one_camera.json --run-seconds 5 --no-preview --no-send
```

确认实际走无线还是有线：

```bash
ip route get 192.168.66.196
ss -tinpe 'dst 192.168.66.196:50010'
iw dev wlan0 link
```

正常无线发送示例：

```text
192.168.66.196 dev wlan0 src 192.168.66.85
ESTAB 0 0 192.168.66.85:xxxxx 192.168.66.196:50010
```

确认相机实际 profile：

```bash
tail -n 80 08_reports/sender_logs/sender_stdout.log
```

应能看到类似：

```text
camera started camera_id=cam01 color=1920x1080@30 format=mjpg depth=640x400@30 format=unknown
```

接收端帧数差分验证：

```bash
curl -s http://192.168.66.196:8080/api/status
```

重点看对应相机的 RGB / Depth 包计数是否持续增长、`media_age_ms` 是否保持在秒级以内，以及发送端日志中的 `rgb_send_failures` / `depth_send_failures` 是否为 0。发送端性能日志里的 `rgb_usb_mbps` / `depth_usb_mbps` 表示相机输入帧本身的数据量，可用于判断 USB 链路压力；`rgb_mbps` / `depth_mbps` 是压缩后发送到接收端的网络码率。

## 9. 常见问题

接收端只收到 H.264 头，没有有效画面：

```text
确认发送端源码包含 videoconvert 后强制 NV12 的修复。
确认运行的是最新构建出的 gemini_sender。
```

接收端无法解析 Depth：

```text
确认接收端已支持 codec_or_compression=zlib。
未升级接收端时改用 sender_orangepi5pro-01.json。
```

从有线切到无线后连接异常：

```text
先执行 ./05_tools/stop_sender.sh
再执行 ./05_tools/start_sender.sh
```

原因是已有 TCP 连接会保留旧本地 IP，需要重启 sender 重新建连。

本地没有预览窗口：

```text
使用 ./05_tools/start_sender_preview.sh。
确认 DISPLAY 正确。
无桌面环境时使用 ./05_tools/start_sender.sh。
```

Depth 伪彩预览闪烁：

```text
SV1301S_U3 官方有效深度范围为 0.25m-2.5m。
发送端本地预览和接收端网页 Depth 预览都应使用固定 250mm-2500mm 伪彩范围。
不要使用每帧 min/max 自动拉伸，否则单个远点或噪点变化会导致整张伪彩图颜色跳变。
```

Wi-Fi 多路卡顿：

```text
单路 1080p RGBD 当前实测约 15-20Mbps。
6 路建议按 150-210Mbps 工程预算规划，并给 Wi-Fi 留 300-500Mbps 稳定可用吞吐。
接收端 NAS 建议有线接路由器/交换机。
多路建议使用 2 个 Wi-Fi 6/6E AP，每个 AP 承载 3 路。
```

媒体发送突然掉到 0：

```text
现象: 本地相机仍在采集，日志有 rgb_input_fps/depth_input_fps，但 rgb_sent_packets_s/depth_sent_fps 变成 0。
优先检查: ss -tinpe 'dst 192.168.66.196:50010' 的 Send-Q、sender_stdout.log 的 media send failed。
原因之一: 系统 net.core.wmem_max 太小，socket 实际发送缓冲被限制，连续媒体帧积压后触发背压。
原因之二: 发送端 Wi-Fi 漂到错误 SSID 或 2.4GHz 频段，媒体 TCP 实际吞吐不足。
现场修复值: net.core.wmem_max=8388608，net.core.wmem_default=1048576，transport.send_buffer_bytes=4194304。
持久化示例: /etc/sysctl.d/99-gemini-video-transport.conf。
当前启动脚本会自动切回 土著拯救器-5G 并重启子进程；如果需要放宽策略，显式覆盖 GEMINI_SENDER_WIFI_* 环境变量。
```

USB 相机导致键鼠卡顿：

```text
RK3588 上双 Orbbec + 无线 HID 接收器可能共用 USB 控制器或经过同一 hub。
05_tools/prepare_rk3588_usb.sh 会将 OTG 切到 host、增大 usbfs_memory_mb，并关闭 Orbbec、UGREEN HID 和 USB hub 的 autosuspend。
udev 规则模板位于 05_tools/99-orbbec-noautosuspend.rules、05_tools/99-ugreen-hid-noautosuspend.rules、05_tools/99-usb-hubs-noautosuspend.rules。
2026-05-28 RK3588 现场实测：单台 Orbbec 在 USB2-only 链路上可以同时跑当前 profile，即 RGB MJPG 1920x1080@30 + Depth 640x400@30。发送端日志显示 RGB 输入约 55-62Mbps，Depth 输入约 118-128Mbps，合计约 175-190Mbps。
该结论只适用于当前 profile 和单相机。USB2 理论 480Mbps，实际稳定可用带宽通常低很多；MJPG 帧大小会随画面和曝光变化，UVC 还可能有带宽预留。不要把两台相机或键鼠接收器堆在同一条 USB2 root bus / hub 上作为长期方案。
若仍卡顿，应把两路相机分到独立 USB3 控制器/独立 root bus 或独立供电 hub，键鼠接另一条 USB2 总线或蓝牙，避免和相机共享高带宽链路。
```
