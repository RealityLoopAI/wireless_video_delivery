# 接收端需求文档 v3

## 1. 文档定位

本文档面向 3.0 接收端开发人员，定义 Linux x86_64 接收端需要实现的功能、边界、配置、Web 监控、录制控制、NAS 写入和验收要求。

接收端运行在 Ubuntu 24.04 x86_64 PC/服务器上，负责接收发送端数据，提供实时网页预览，通过 REST API 控制录制，并把 RGB 与 Depth 数据写入通过 NFS 挂载的 NAS。

本文档不定义发送端采集实现细节，不定义 Orbbec SDK 调用细节，不定义发送端硬件编码实现。发送端细节由《01_发送端需求_v3.md》负责。

## 2. 接收端职责

接收端必须负责：

1. 接收所有在线发送端上报的注册、心跳、状态和事件。
2. 接收 RGB 编码帧。
3. 接收 Depth 无损帧。
4. 管理发送端和摄像头在线状态。
5. 检测 `sender_id/camera_id` 冲突。
6. 提供网页实时预览。
7. 提供 REST 录制控制接口。
8. 提供轻量 CLI 控制工具。
9. 支持全局和单路开始/停止录制。
10. 按切片写入 NAS。
11. 生成 `rgb.mp4`。
12. 生成 `depth.mkv` 或等价无损 Depth 文件。
13. 生成 `meta.json`。
14. 生成 `frames.csv`。
15. 记录本机运行日志。
16. 提供一键启动、停止和状态查看脚本。

接收端不负责：

1. 采集相机。
2. 修改发送端采集参数。
3. 修改发送端 `sender_id` 或 `camera_id`。
4. 控制发送端采集启停。
5. 给算法提供实时取流 SDK。
6. 历史回放和文件下载。

## 3. 运行平台

接收端平台要求：

1. Linux x86_64 PC/服务器。
2. Ubuntu 24.04。
3. NAS 通过 NFS 挂载到接收端。
4. Web/API 默认端口为 8080，可配置。

## 4. 接收与录制关系

1. 接收端服务启动后持续接收所有在线摄像头数据。
2. 未开始录制时也保持实时预览。
3. `recording=false` 时不写 NAS。
4. 开始录制后才按切片写 `rgb/depth/meta/frames`。
5. 停止录制只停止接收端写盘，不停止发送端采集或发送。
6. 停止录制后网页实时预览仍然可用。

## 5. 设备管理

### 5.1 设备 ID

1. 接收端从发送端消息中读取 `sender_id` 和 `camera_id`。
2. 接收端不自动分配正式 ID。
3. 接收端必须校验 ID 是否为空。
4. 接收端必须校验 ID 是否重复。
5. 默认 `camera_key` 为 `sender_id_camera_id`。

### 5.2 ID 冲突处理

当两个设备上报相同 `sender_id/camera_id` 时：

1. 网页和日志必须报警。
2. 后接入的冲突设备不进入录制。
3. 不写入已有设备目录。
4. 原已接入设备不受影响。
5. 修改发送端 ID 后可重新接入。

### 5.3 在线状态

接收端必须根据注册、心跳、媒体帧和事件维护：

1. 发送端在线/离线状态。
2. 摄像头在线/离线状态。
3. RGB 流状态。
4. Depth 流状态。
5. 录制状态。
6. 预览状态。
7. 错误状态。

## 6. 数据接收

接收端必须按《03_中间传输数据格式_v3.md》解析数据。

接收端需要处理：

1. `sender_hello`
2. `camera_announce`
3. `heartbeat`
4. `camera_offline`
5. `event`
6. RGB 媒体帧
7. Depth 媒体帧

接收端不通过该中间传输格式向发送端下发控制命令。

## 7. RGB 处理

1. 接收端收到的 RGB payload 是发送端编码后的 H.264/H.265 数据。
2. 接收端录制时优先不重编码。
3. 接收端应直接将 RGB 编码流封装为 `rgb.mp4`。
4. 接收端只为网页预览解码 RGB。
5. RGB 编码格式从帧头或相机公告中读取。

## 8. Depth 处理

1. 接收端收到的 Depth payload 是一整帧 `depth_raw` 的无压缩或无损压缩数据。
2. 接收端必须按帧头中的压缩方式还原 Depth。
3. Depth 原始类型为 `uint16`。
4. 接收端必须无损保存 16bit Depth 母版。
5. 推荐首选 `depth.mkv + FFV1`。
6. 如果实测发现性能、兼容性或后处理不合适，允许替换为等价无损格式。
7. 无论格式如何变化，必须保留 `depth_scale`、帧时间戳、帧号和与 RGB 的配对索引。

## 9. RGB 与 Depth 配对

1. 接收端不要求跨摄像头严格同步。
2. 接收端不要求跨发送端严格同步。
3. 每路 RGB 和 Depth 独立接收。
4. 如果帧头存在 `pair_id`，接收端应优先使用 `pair_id` 记录配对关系。
5. 如果 `pair_id` 为空，接收端按最近时间戳生成配对关系。
6. 配对结果写入 `frames.csv`。
7. 必须记录 `pair_delta_ms`。
8. 超过阈值时标记为未配对或弱配对，不得假装对齐。

## 10. 录制控制

### 10.1 控制来源

录制控制来源包括：

1. 网页监控页。
2. HTTP REST API。
3. CLI 控制工具。

三者必须复用同一套接收端录制控制逻辑。

### 10.2 全局开始录制

全局开始录制语义：

1. 所有当前在线摄像头立即开始录制。
2. 录制期间后上线的摄像头自动加入录制。
3. 离线摄像头不阻塞全局开始。
4. 所有在线摄像头默认参与全局录制。
5. 不做“参与全局录制”勾选配置。
6. 不想录某一路时，可使用单路停止。

### 10.3 全局停止录制

全局停止录制语义：

1. 结束所有录制状态。
2. 不等待断线设备恢复。
3. 已收到的数据正常封装。
4. 异常和不完整状态写入 `meta.json`、`frames.csv` 和日志。

### 10.4 单路录制控制

1. 支持单独开始某一路录制。
2. 支持单独停止某一路录制。
3. 单路录制目标由 `sender_id/camera_id` 指定。
4. 单路操作不影响其他路。

## 11. 数据缺失策略

1. 允许开始录制。
2. 如果某路只有 RGB 没有 Depth，先录 RGB，并标记 `Depth missing`。
3. 如果某路只有 Depth 没有 RGB，也记录对应状态。
4. 缺失、恢复、断流都写入 `meta.json`、`frames.csv` 和日志。
5. 全局录制不因单路某个流缺失而失败。

## 12. 文件与目录

### 12.1 切片目录规则

NAS 录制目录规则为：

```text
<NAS_ROOT>/<camera_key>/<YYYY-MM-DD>/<HHMMSS>/
```

示例：

```text
<NAS_ROOT>/
  sender01_cam01/
    2026-05-09/
      143000/
        rgb.mp4
        depth.mkv
        meta.json
        frames.csv
```

### 12.2 切片文件

每个切片目录内基础文件为：

```text
rgb.mp4
depth.mkv
meta.json
frames.csv
```

如果 Depth 最终采用等价无损格式替换 `depth.mkv`，文件名和格式必须在 `meta.json` 中明确记录。

### 12.3 切片策略

1. 必须支持按时间切片。
2. 默认切片时长作为配置项。
3. 具体默认切片时长待定。
4. 切片边界要保证 RGB、Depth、metadata 可对应。
5. 异常断电后，最多只影响当前切片，已完成切片应可读。

## 13. meta.json

`meta.json` 记录切片级信息。

至少包括：

1. `sender_id`
2. `camera_id`
3. `camera_key`
4. 设备名称、序列号、UID、固件版本、连接类型等可获得信息
5. RGB profile
6. Depth profile
7. RGB 编码方式
8. Depth 保存格式
9. 标定参数
10. `depth_scale`
11. 切片开始时间
12. 切片结束时间
13. 录制状态
14. 异常事件摘要
15. 文件名和文件大小

## 14. frames.csv

`frames.csv` 记录逐帧索引。

至少包括：

1. RGB 帧号
2. RGB 时间戳
3. Depth 帧号
4. Depth 时间戳
5. `pair_id`
6. `pair_delta_ms`
7. RGB 文件内时间位置
8. Depth 文件内时间位置
9. RGB 丢帧标记
10. Depth 丢帧标记
11. 断流/恢复事件标记
12. 配对状态

## 15. NAS 与存储异常

### 15.1 NAS 基线

1. NAS 型号为绿联 DXP4800 Pro。
2. NAS 通过 NFS 挂载到接收端。
3. NAS 挂载路径实施阶段配置。
4. 录制根目录必须可配置。
5. 读写速度暂不作为当前瓶颈。

### 15.2 开始录制前检查

开始录制前必须检查：

1. NAS 路径是否存在。
2. NAS 路径是否可写。
3. 剩余空间是否高于阈值。
4. 当前切片目录是否可创建。

### 15.3 录制中异常

当出现 NFS 断开、目录不可写、空间不足或写入失败时：

1. 立即停止受影响路录制。
2. 网页标红报警。
3. 日志记录错误。
4. 不默认切到本地系统盘。
5. 本地应急缓存不作为首版默认功能。

### 15.4 空间策略

1. 不自动删除旧数据。
2. 录制中低于阈值时网页和日志报警。
3. 空间不足导致写入失败时停止受影响录制。
4. 数据保留策略由人工或 NAS 侧管理。

## 16. Web 监控页

### 16.1 使用范围

1. Web 监控页只在局域网内使用。
2. 3.0 不做复杂用户体系和权限管理。
3. 可预留简单访问口令或 token，但不作为复杂权限系统实现。

### 16.2 页面能力

Web 监控页首版必须提供：

1. 实时 RGB 预览。
2. 实时伪彩 Depth 预览。
3. 在线/离线状态。
4. 录制状态。
5. 全局开始/停止录制。
6. 单路开始/停止录制。
7. 当前写入路径。
8. 当前切片状态。
9. NAS 异常提示。
10. ID 冲突提示。
11. 发送端和摄像头状态。

首版不做：

1. 历史回放。
2. 文件下载。
3. 录像检索。

### 16.3 预览策略

1. 总览页同时显示全部在线路的 RGB + 伪彩 Depth 预览。
2. 单路详情页或放大视图显示选中摄像头的更高码率、更大画面 RGB + 伪彩 Depth 预览。
3. 预览码率、分辨率和帧率应可配置。
4. 预览不能影响录制主链路。
5. 资源紧张时，预览允许自动降帧、降分辨率、降码率或暂停部分路。
6. 降级状态需要在网页和日志中提示。

### 16.4 预览技术路线

1. 优先评估 WebRTC。
2. WebRTC 适合浏览器实时预览。
3. 具体实现可根据 C++ 集成成本和现场效果调整。
4. 可选备选方案包括 MJPEG、WebSocket JPEG、HLS。
5. HLS 只适合低实时性场景。
6. 需求层面不锁死唯一预览实现。

## 17. HTTP REST API

### 17.1 接口定位

HTTP REST API 是 3.0 保留给其他工程师调用的唯一正式控制接口。

该接口只覆盖：

1. 录制控制。
2. 必要状态查询。

该接口不提供：

1. 视频取流。
2. Python SDK 数据读取。
3. 算法实时取数。
4. 发送端采集参数修改。

### 17.2 推荐接口范围

接口命名可在实现阶段调整，但能力范围应包括：

```text
POST /api/recordings/start
POST /api/recordings/stop
POST /api/cameras/{sender_id}/{camera_id}/recording/start
POST /api/cameras/{sender_id}/{camera_id}/recording/stop
GET  /api/recordings/status
GET  /api/cameras
GET  /api/health
```

### 17.3 默认端口

1. Web 监控页默认端口为 8080。
2. HTTP REST API 默认复用该服务端口。
3. 端口必须可配置。
4. 一键启动前检查端口占用。

## 18. CLI 控制工具

需要提供轻量 CLI 控制工具。

示例能力：

```bash
recctl start --all
recctl stop --all
recctl start --camera <sender_id>/<camera_id>
recctl stop --camera <sender_id>/<camera_id>
recctl status
```

CLI 只封装 HTTP REST API，不另起一套控制逻辑。

## 19. 配置

接收端使用 JSON 配置文件。

配置至少包括：

1. 监听 IP 和端口。
2. Web/API 端口。
3. NAS 录制根目录。
4. 切片时长。
5. 低空间报警阈值。
6. 预览分辨率、帧率、码率。
7. 日志目录。
8. 传输协议选择。
9. 录制格式选择。

## 20. 一键启动

接收端需要提供：

1. 一键启动脚本。
2. 一键停止脚本。
3. 一键状态脚本。
4. Ubuntu 图形环境下可双击的 `.desktop` 入口。
5. 终端可执行的 `.sh` 入口。

一键启动前必须检查：

1. 媒体依赖是否可用。
2. 配置文件是否存在且字段合法。
3. NAS 路径是否挂载。
4. NAS 路径是否可写。
5. NAS 剩余空间是否足够。
6. 监听端口是否被占用。
7. Web 端口是否被占用。

失败时必须输出中文错误提示。

## 21. 日志

1. 接收端运行日志写接收端本机 `logs/` 目录。
2. 日志需要滚动。
3. 日志不得无限增长写满系统盘。
4. 每个切片相关录制事件和异常摘要写入 NAS 对应切片的 `meta.json`。

## 22. 首版验收

接收端首版验收包括：

1. 能启动 C++ 接收端程序。
2. 能读取 JSON 配置。
3. 能接收 `sender_hello`。
4. 能接收 `camera_announce`。
5. 能接收心跳。
6. 能接收 RGB 编码帧。
7. 能接收 Depth 无损帧。
8. 能显示 Web RGB + 伪彩 Depth 预览。
9. 能全局开始/停止录制。
10. 能单路开始/停止录制。
11. 能按目录规则写入 NAS。
12. 能生成 `rgb.mp4`。
13. 能生成 `depth.mkv` 或等价无损 Depth 文件。
14. 能生成 `meta.json`。
15. 能生成 `frames.csv`。
16. 能在 NAS 异常时报错并停止受影响录制。
17. 能检测 ID 冲突并阻止混写。
18. 能通过一键脚本启动、停止和查看状态。
