## 本次底层故障证据

NAS 192.168.1.89 内核日志：

```text
17:54:59 QEMU worker blocked for more than 120 seconds
17:55:25 nvme nvme2: Device not ready; aborting reset, CSTS=0x1
17:55:25 nvme nvme2: Disabling device after reset failure: -19
17:55:25 I/O error, dev nvme2n1
17:55:25 EXT4-fs (dm-0): Remounting filesystem read-only
```

`lsblk` 显示 nvme2n1 大小 0B。接收端 QEMU 的 qcow2 磁盘位于 NAS `/volume1/@kvm/`。接收端随后在 17:55:40 出现 vda 写错误、EXT4 journal aborted、emergency_ro；后续连 `/usr/bin/curl` 也返回 Input/output error。

故障链有明确证据：NAS NVMe 设备不可用、数据卷只读，影响同卷的接收端虚拟磁盘。剩余容量显示接收端约 222GiB、NAS 约 2.1TiB，不能将这次事故简单称为空间不足。设备失联的物理原因（供电、温度、控制器、连接或介质）尚未确定。故障发生于回归期间，不能据此宣称测试导致硬件故障，也不能反推所有历史缺帧均由它引起。

## 当前措施与恢复顺序

停止新增测试和部署写入，不执行强制 rw 挂载、不在线 fsck、不重建阵列、不删除数据。完整回归已经退出；生产状态 API 因磁盘 I/O 错误无法可靠查询。

现场先在 NAS 管理界面确认存储池和 SSD 状态，保留日志；保护重要数据后按 NAS 支持的流程恢复设备与存储卷。设备恢复可见并不等于文件系统及已写文件完整。离线文件系统检查必须在相关虚拟机和卷停止使用后执行，由现场确认维护窗口。

恢复后先验证 NAS 卷、接收端虚拟磁盘和 staging 文件，再重新编译校验产物、运行全回归和短录制，最后部署。后续应将接收端 staging 与 NAS 数据卷故障域分离，否则所谓本地缓存仍会与 NAS 同时失效。
