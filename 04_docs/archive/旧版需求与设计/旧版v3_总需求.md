# wireless_video_delivery 需求文档

## 1. 文档定位

本文档定义 `wireless_video_delivery` 的重构升级目标、产品边界、架构方向、数据格式、运行方式和首版验收标准。

本项目不再沿用 2.0 的“Windows 接收端 + Python SDK 调库输出”定位，而是重构为一个全 Linux 环境下的高性能多路 RGBD 采集、传输、预览和 NAS 录制系统。

本文档只记录当前已经确认的需求。未确认或依赖现场实测的数据，统一标记为“待实测确认”，不得在实现中被默认当作固定承诺。

## 2. 核心变化

相比 2.0，本项目的核心变化如下：

1. 全部核心代码使用 C++ 重构，目标是提升性能和降低运行时开销。
2. 接收端从 Windows 改为 Linux x86_64，当前基线为 Ubuntu 24.04。
3. 正式数据输出从 Python SDK 实时取流改为 NAS 上的录制文件。
4. 不再保留 Python SDK、算法实时取流接口或后续算法工程师调库接口。
5. 接收端只保留录制控制接口，供网页监控页和其他工程师调用。
6. 接收端需要提供网页监控页，用于实时预览、状态查看和录制控制。
7. RGB 与 Depth 均需要采集和录制，Depth 以原始无损数据为正式母版。
8. NAS 通过接收端挂载目录写入；现场可使用 NFS、CIFS/SMB 或等价网络文件系统，具体以接收端配置和实际挂载状态为准。

### 2.1 从旧版保留的长期语义

1. 稳定身份仍是核心模型：每台发送端必须有稳定 `sender_id`，每个物理相机必须有稳定 `camera_id`。
2. 接收端和下游都以 `<sender_id>_<camera_id>` 定位逻辑摄像头；业务别名只能用于显示和存储命名，不能替代原始 ID。
3. 系统应同时支持全局摄像头视图和发送端树形视图；当前落点是 Web/REST 状态和录制目录，而不是旧 2.0 的 Python SDK。
4. RGB 与 Depth 必须保留各自独立的帧号和时间戳；任何 pair 级结果都不能覆盖或隐藏原始单流时间戳。
5. strict / realtime 配对思想保留为下游数据语义：严格配对按阈值判断是否成对，实时优先允许取最近帧但必须暴露 `pair_delta_ms` 和完整性。当前接收端负责记录足够字段，具体算法在离线处理或下游工具中实现。
6. UI 只消费统一状态和预览派生结果，不定义底层数据语义。

旧 1.0/2.0 文档中的 Windows 接收端、Python SDK 调库输出、RTP/UDP 交付链路和本地 Windows 路径不属于当前事实，只作为历史参考。

## 3. 一句话目标

`wireless_video_delivery` 是一个全 Linux、C++ 实现的多路 Gemini RGBD 无线采集与录制系统，用于从多个 Linux ARM 发送端采集 RGB 与 Depth 数据，经 Wi-Fi 传输到 Linux x86_64 接收端，并由接收端实时预览和写入 NAS 录制文件。

## 4. 正式范围

### 4.1 平台范围

正式平台范围如下：

1. 发送端：Linux ARM 设备，当前包括树莓派 5 和香橙派。
2. 接收端：Linux x86_64 PC/服务器。
3. 接收端系统基线：Ubuntu 24.04。
4. NAS：绿联 DXP4800 Pro，通过接收端挂载目录写入，挂载协议以现场配置为准。
5. 相机：Orbbec Gemini 系列深度相机。

本项目不再考虑 Windows 接收端，也不要求跨平台兼容。

### 4.2 软件范围

正式软件范围如下：

1. C++ 发送端程序。
2. C++ 接收端程序。
3. 接收端网页监控页。
4. HTTP REST 录制控制接口。
5. 轻量 CLI 录制控制工具。
6. 一键启动、停止、状态脚本。
7. Ubuntu 图形环境下可双击的一键启动入口。
8. JSON 配置文件。

### 4.3 数据范围

正式录制数据包括：

1. RGB 视频。
2. 原始 Depth 数据 `depth_raw`。
3. 时间戳、帧号、配对关系和异常事件。
4. 相机标定参数。
5. `depth_scale` 等深度换算信息。

可选数据包括：

1. `depth_aligned_to_rgb`，作为可选产物，不作为首版母版必录项。
2. 伪彩 Depth，仅用于网页预览或离线导出，不作为正式录制母版。

## 5. 明确非目标

首版明确不做以下内容：

1. Python SDK。
2. 算法实时取流接口。
3. Windows 接收端。
4. Web 端历史回放。
5. Web 端文件下载。
6. 录像检索系统。
7. 用户权限体系。
8. 自动删除 NAS 旧数据。
9. 接收端远程修改发送端采集参数。
10. 硬件同步、PTP 或严格跨摄像头时间同步。
11. 长时间 7x24 稳定性承诺。
12. 独立离线录制校验工具，首版暂不要求。

## 6. 总体系统形态

系统由发送端、接收端、NAS 和网页监控页组成。

```text
Gemini RGBD 相机
    -> Linux ARM 发送端 C++ 程序
        -> Orbbec C++ SDK 采集
        -> RGB 硬件编码优先
        -> Depth 无损传输优先
        -> Wi-Fi 网络传输
    -> Linux x86_64 接收端 C++ 程序
        -> 接收媒体流与状态
        -> 实时预览派生
        -> 录制控制
        -> 写入 NAS 挂载目录
    -> NAS 录制文件
    -> Web 监控页 / REST API / CLI
```

## 7. 规模目标

规模目标分为设计原则和首版验收规模。

### 7.1 设计原则

1. 代码层不写死发送端数量。
2. 代码层不写死摄像头数量。
3. 来一台发送端可以接入一台。
4. 发现一台摄像头可以发送一台。
5. 发送端和接收端应以动态注册和状态管理方式处理设备上下线。

### 7.2 当前实际规模

当前实际预期如下：

1. 单发送端通常接入 1 至 2 台 Gemini 相机。
2. 当前总摄像头数量约 6 台。
3. 首版核心验收按 6 路 RGB+Depth 同时录制数分钟验证功能。

首版不承诺长时间满负载稳定运行。长时间稳定性作为后续阶段目标。

## 8. 发送端需求

### 8.1 发送端职责

发送端负责：

1. 通过 Orbbec C/C++ SDK 采集 Gemini RGB 与 Depth。
2. 本地生成或读取 `sender_id` 和 `camera_id`。
3. 对 RGB 进行编码。
4. 对 Depth 进行无损或原始帧传输。
5. 向接收端发送媒体数据。
6. 向接收端上报状态心跳。
7. 提供本地 RGB + 伪彩 Depth 预览。

发送端不负责：

1. 写 NAS。
2. 录制文件切片。
3. 接收端录制控制。
4. Web 监控页。

### 8.2 发送端身份

1. `sender_id` 由发送端配置或按机器唯一信息自动派生。
2. `camera_id` 由发送端配置。
3. 接收端不自动分配正式 ID。
4. 接收端只负责校验 ID 是否为空、是否重复。
5. 文件目录默认使用 `sender_id_camera_id` 作为 `camera_key`。

### 8.3 采集规格

1. RGB 目标上限为 1080p@30fps。
2. Depth 目标规格待实测确认。
3. RGB 与 Depth 均应优先使用设备可稳定输出的最高规格。
4. 正式验收规格以现场实测稳定档位为准。

### 8.4 Orbbec C++ SDK 使用要求

发送端采集层应基于 Orbbec C/C++ SDK。

当前可参考的 SDK 包为：

```text
OrbbecSDK_C_C++_v1.10.27_linux_arm64_release
```

该包已经确认提供以下能力：

1. `ob::Context` 查询设备。
2. `ob::Pipeline` 打开 RGBD 流。
3. `FrameSet` 获取 `colorFrame()` 和 `depthFrame()`。
4. 帧对象获取 `index()`、`timeStamp()`、`timeStampUs()`、`systemTimeStamp()`。
5. 帧对象获取 `width()`、`height()`、`format()`、`data()`、`dataSize()`。
6. `DepthFrame::getValueScale()` 获取深度换算比例。
7. `Pipeline::getCameraParam()` 获取相机参数。
8. `ALIGN_D2C_HW_MODE` 和 `ALIGN_D2C_SW_MODE` 支持硬件/软件 D2C 对齐。
9. 示例包含多设备采集、同步对齐、录制回放等参考代码。

注意：

1. 当前参考包是 Linux x64 包。
2. 发送端是树莓派 5 / 香橙派，因此正式开发前必须获取并验证 Orbbec C/C++ SDK 的 Linux ARM64/aarch64 包。
3. Orbbec SDK 调用必须封装在相机适配层中，不允许散落在业务逻辑中。

### 8.5 RGB 编码

1. RGB 在发送端优先使用硬件编码。
2. 推荐编码格式为 H.264，H.265/HEVC 作为可选方案。
3. 硬件编码不可用时允许软件编码 fallback。
4. 发送端应抽象编码适配层，避免绑死单一板卡或单一编码器。

### 8.6 Depth 传输

1. Depth 从 Orbbec SDK 获取 `uint16 depth_raw`。
2. Depth 优先无损传输，保证测量数据可信。
3. 可评估 raw frame、LZ4/Zstd 帧级无损压缩或其他等价无损方案。
4. 具体 Depth 传输压缩方案待现场 Wi-Fi 带宽、CPU 负载、Depth 分辨率/帧率实测后定。
5. 若后续启用有损或近似压缩，必须明确误差边界，且不得默认替代无损母版。

### 8.7 发送端本地预览

1. 发送端需要本地预览。
2. 本地预览默认开启。
3. 一个发送端一个监控墙窗口。
4. 显示该发送端所有相机。
5. 每个相机显示 RGB + 伪彩 Depth。
6. 伪彩 Depth 从 `depth_raw` 派生，仅用于预览。
7. 预览不能影响采集和发送主链路，资源紧张时应可配置关闭或降级。

## 9. 接收端需求

### 9.1 接收端职责

接收端负责：

1. 接收所有在线发送端的 RGB 与 Depth 数据。
2. 管理发送端和摄像头在线状态。
3. 检测 `sender_id/camera_id` 冲突。
4. 提供网页实时预览。
5. 提供全局和单路录制控制。
6. 将录制数据写入 NAS。
7. 生成录制切片目录和元数据文件。
8. 提供 HTTP REST API 和 CLI 控制。

接收端不负责：

1. 修改发送端相机 ID。
2. 修改发送端采集分辨率、帧率、码率。
3. 修改发送端目标 IP 或端口。
4. 控制发送端采集启停。

### 9.2 接收与录制关系

1. 接收端服务启动后持续接收所有在线摄像头数据。
2. 未开始录制时也保持实时预览。
3. `recording=false` 时不写 NAS。
4. 开始录制后才按切片写入 `rgb/depth/meta/frames`。
5. 停止录制只停止接收端写盘，不停止发送端采集或发送。
6. 停止录制后网页实时预览仍然可用。

### 9.3 ID 冲突策略

当两个设备上报相同 `sender_id/camera_id` 时：

1. 网页和日志必须报警。
2. 后接入的冲突设备不进入录制。
3. 不写入已有设备目录，避免数据混淆。
4. 原已接入设备不受影响。
5. 修改发送端 ID 后可重新接入。

## 10. 传输需求

### 10.1 网络环境

发送端到接收端主链路为 Wi-Fi。

### 10.2 传输策略

当前传输策略采用平衡模式：

1. 默认尽量保持实时。
2. 为录制完整性允许有限缓冲。
3. 允许后续配置重传和缓冲参数。
4. 不追求无限等待或完全无丢帧。

### 10.3 协议选型

传输协议不在需求阶段写死，需实验选型。

候选方向：

1. RGB 传输优先实测 SRT 与现有 UDP/RTP 路线。
2. Depth 传输优先无损可靠，具体方案现场/实验后定。
3. WebRTC 主要作为网页预览候选，不反向决定录制主链路。
4. QUIC 可作为长期技术储备，首版不直接承诺自研 QUIC 主线。

实现要求：

1. 必须有传输抽象层。
2. 不允许 C++ 重构后再次绑死单一传输实现。
3. 验收前需要形成传输方案评估结论。

### 10.4 断网缓存与补传

1. 架构上预留发送端本地缓存与恢复后补传能力。
2. 首版默认关闭，不作为主路径启用。
3. 现场根据 Wi-Fi 稳定性、存储空间和录制完整性要求再决定是否开启。
4. 即使不开启，也必须在元数据中记录断流、丢帧、重连等事件。

### 10.5 状态与控制通道

1. 发送端主动连接接收端。
2. 发送端定期心跳上报状态。
3. 心跳内容至少包括 `sender_id`、`camera_id`、RGB/Depth profile、编码方式、帧率、丢帧/重连状态、硬件编码是否启用。
4. 接收端不下发采集参数。
5. 接收端可以返回录制状态确认、错误信息或必要控制响应。
6. 媒体数据通道和状态控制通道应解耦。

## 11. 录制需求

### 11.1 录制执行位置

录制由 Linux 接收端执行。发送端只采集和发送，不直接写 NAS。

### 11.2 录制数据

每路摄像头正式录制内容包括：

1. RGB 视频。
2. `depth_raw` 无损 16bit 深度母版。
3. 切片级元数据。
4. 逐帧索引。
5. 标定参数。
6. `depth_scale`。

### 11.3 RGB 文件格式

1. RGB 默认录制为 `rgb.mp4`。
2. 默认编码为 H.264。
3. H.265/HEVC 作为可选方案，用于降低 NAS 存储压力。
4. 接收端录制时优先不重编码，直接封装发送端编码流。
5. 接收端只为网页预览解码，不为了录制重新编码。

### 11.4 Depth 文件格式

1. 正式要求是无损保存 `16bit depth_raw` 母版。
2. 推荐首选 `depth.mkv + FFV1`。
3. 如果实测发现性能、兼容性或后处理不合适，允许替换为等价无损格式。
4. 无论格式如何变化，必须保留 `depth_scale`、帧时间戳、帧号和与 RGB 的配对索引。

### 11.5 元数据文件

每个切片目录内基础文件为：

```text
rgb.mp4
depth.mkv
meta.json
frames.csv
calibration.json
```

`meta.json` 用于记录切片级信息：

1. `sender_id`
2. `camera_id`
3. `camera_key`
4. 设备名称、序列号、UID、固件版本、连接类型等可获得信息
5. RGB profile
6. Depth profile
7. RGB 编码方式
8. Depth 保存格式
9. `calibration_file`
10. 标定参数摘要或原始 announce 备份
11. `depth_scale`
12. 切片开始时间
13. 切片结束时间
14. 录制状态
15. 异常事件摘要

`frames.csv` 用于记录逐帧索引：

1. RGB 帧号
2. RGB 时间戳
3. Depth 帧号
4. Depth 时间戳
5. `pair_delta_ms`
6. RGB 文件内时间位置
7. Depth 文件内时间位置
8. 丢帧标记
9. 断流/恢复事件标记
10. 配对状态

不要求把全部逐帧信息塞进一个巨大 JSON。

### 11.6 切片策略

1. 录制必须支持按时间切片。
2. 默认切片时长作为配置项。
3. 具体默认切片时长待定。
4. 切片边界要保证 RGB、Depth、metadata 可对应。
5. 异常断电后，最多只影响当前切片，已完成切片应可读。

### 11.7 目录组织

NAS 录制目录规则为：

```text
<NAS_ROOT>/<camera_key>/<YYYY-MM-DD>/<HHMMSS>/
```

示例：

```text
<NAS_ROOT>/
  sender01_cam01/
    2026-05-09/
      143000/
        rgb.mp4
        depth.mkv
        meta.json
        frames.csv
        calibration.json

      143500/
        rgb.mp4
        depth.mkv
        meta.json
        frames.csv
        calibration.json

  sender01_cam02/
    2026-05-09/
      143000/
        rgb.mp4
        depth.mkv
        meta.json
        frames.csv
        calibration.json
```

规则说明：

1. `camera_key` 优先使用 `sender_id_camera_id`。
2. 后续可配置显示别名，但不改变原始 ID。
3. `YYYY-MM-DD` 是录制日期。
4. `HHMMSS` 是切片开始时间。
5. 同一秒冲突时追加 `_02`、`_03`。
6. 不强制生成全局 `index.json`。
7. 后续如果网页回放或检索需要，可通过扫描目录和读取每个 `meta.json` 构建索引缓存。

### 11.8 全局开始录制

全局开始录制语义如下：

1. 点击全局开始时，所有当前在线摄像头立即开始录制。
2. 录制期间后上线的摄像头自动加入录制。
3. 离线摄像头不阻塞全局开始。
4. 所有在线摄像头默认参与全局录制。
5. 不做“参与全局录制”勾选配置。
6. 不想录某一路时，可使用单路停止。

### 11.9 全局停止录制

全局停止录制语义如下：

1. 全局停止会结束所有录制状态。
2. 不等待断线设备恢复。
3. 已收到的数据正常封装。
4. 异常和不完整状态写入 `meta.json`、`frames.csv` 和日志。

### 11.10 单路录制控制

1. 支持单独开始某一路录制。
2. 支持单独停止某一路录制。
3. 单路录制目标由 `sender_id/camera_id` 指定。
4. 单路操作不影响其他路。

### 11.11 数据缺失策略

1. 允许开始录制。
2. 如果某路只有 RGB 没有 Depth，先录 RGB，并标记 `Depth missing`。
3. 如果某路只有 Depth 没有 RGB，也记录对应状态。
4. 缺失、恢复、断流都写入 `meta.json`、`frames.csv` 和日志。
5. 全局录制不因单路某个流缺失而失败。

### 11.12 音频

当前不包含音频录制。

## 12. RGB 与 Depth 配对需求

### 12.1 跨摄像头同步

1. 不要求所有摄像头严格时间对齐。
2. 不要求所有发送端严格时间对齐。
3. 系统定位是采集与存储，不做多相机同步算法平台。
4. 可建议发送端和接收端使用 NTP 保持系统时间基本一致，但不作为严格硬指标。
5. 不做硬件同步/PTP 作为正式要求。

### 12.2 单路 RGB/Depth 对齐

每一路内部必须满足：

1. RGB 和 Depth 各自保留原始帧号与时间戳。
2. 每个 RGB 帧可以在 `frames.csv` 中找到最近的 Depth 帧或配对状态。
3. 记录 `pair_delta_ms`。
4. 超过阈值时标记为未配对或弱配对，不得假装对齐。
5. 网页预览可使用最近帧做近似配对。

### 12.3 空间对齐

1. 必须保存空间对齐所需标定信息。
2. 标定信息至少包括 RGB 内参、Depth 内参、外参、畸变参数和 `depth_scale`。
3. `depth_aligned_to_rgb` 作为可选产物。
4. 首版正式母版仍以 `depth_raw` 为准。
5. 接收端每个 segment 必须写入 `calibration.json`，展开保存 `camera_announce` 中的设备信息、RGB/Depth profile、标定和离线对齐产物约定。
6. 后续算法人员可基于 `depth_raw + calibration.json` 离线生成对齐深度。

## 13. NAS 与存储异常需求

### 13.1 NAS 基线

1. NAS 型号为绿联 DXP4800 Pro。
2. NAS 通过 NFS、CIFS/SMB 或等价网络文件系统挂载到接收端。
3. NAS 挂载路径和挂载协议由现场配置决定。
4. 录制根目录必须可配置。
5. 读写速度暂不作为当前瓶颈。

### 13.2 开始录制前检查

开始录制前必须检查：

1. NAS 路径是否存在。
2. NAS 路径是否可写。
3. 剩余空间是否高于阈值。
4. 当前切片目录是否可创建。

### 13.3 录制中异常

当出现 NAS 挂载断开、目录不可写、空间不足或写入失败时：

1. 立即停止受影响路录制。
2. 网页标红报警。
3. 日志记录错误。
4. 不默认切到本地系统盘。
5. 本地应急缓存不作为首版默认功能。

### 13.4 空间保留策略

1. 不自动删除旧数据。
2. 录制中低于阈值时网页和日志报警。
3. 空间不足导致写入失败时停止受影响录制。
4. 数据保留策略由人工或 NAS 侧管理。

## 14. 网页监控页需求

### 14.1 使用范围

1. 网页监控页只在局域网内使用。
2. 首版不做复杂用户体系和权限管理。
3. 可预留简单访问口令或 token，但不作为复杂权限系统实现。

### 14.2 页面能力

网页监控页首版必须提供：

1. 实时 RGB 预览。
2. 实时伪彩 Depth 预览。
3. 在线/离线状态。
4. 录制状态。
5. 全局开始/停止录制。
6. 单路开始/停止录制。
7. 当前写入路径。
8. 当前切片状态。
9. NAS 异常提示。
10. ID 冲突提示。
11. 发送端和摄像头状态。

首版不做：

1. 历史回放。
2. 文件下载。
3. 录像检索。

### 14.3 预览策略

1. 总览页同时显示全部在线路的 RGB + 伪彩 Depth 预览。
2. 单路详情页或放大视图显示选中摄像头的更高码率、更大画面 RGB + 伪彩 Depth 预览。
3. 预览码率、分辨率和帧率应可配置。
4. 预览不能影响录制主链路。
5. 资源紧张时，预览允许自动降帧、降分辨率、降码率或暂停部分路。
6. 降级状态需要在网页和日志中提示。

### 14.4 预览技术路线

1. 优先评估 WebRTC。
2. WebRTC 适合浏览器实时预览。
3. 具体实现可根据 C++ 集成成本和现场效果调整。
4. 可选备选方案包括 MJPEG、WebSocket JPEG、HLS。
5. HLS 只适合低实时性场景。
6. 需求层面不锁死唯一预览实现。

### 14.5 默认端口

1. Web 监控页默认端口为 8080。
2. HTTP REST API 默认复用该服务端口。
3. 端口必须可配置。
4. 一键启动前检查端口占用。

## 15. HTTP REST 录制控制接口

### 15.1 接口定位

HTTP REST API 是项目保留给其他工程师调用的唯一正式控制接口。

该接口只覆盖：

1. 录制控制。
2. 必要状态查询。

该接口不提供：

1. 视频取流。
2. Python SDK 数据读取。
3. 算法实时取数。
4. 发送端采集参数修改。

### 15.2 推荐接口范围

接口命名可在实现阶段调整，但能力范围应包括：

```text
POST /api/recordings/start
POST /api/recordings/stop
POST /api/cameras/{sender_id}/{camera_id}/recording/start
POST /api/cameras/{sender_id}/{camera_id}/recording/stop
GET  /api/recordings/status
GET  /api/cameras
GET  /api/health
```

### 15.3 CLI 控制工具

需要提供轻量 CLI 控制工具。

示例能力：

```bash
recctl start --all
recctl stop --all
recctl start --camera <sender_id>/<camera_id>
recctl stop --camera <sender_id>/<camera_id>
recctl status
```

CLI 只封装 HTTP REST API，不另起一套控制逻辑。

## 16. 日志需求

1. 录制母版数据写 NAS。
2. 接收端运行日志写接收端本机 `logs/` 目录。
3. 发送端运行日志写发送端本机。
4. 每个切片相关录制事件和异常摘要写入 NAS 对应切片的 `meta.json`。
5. 日志需要滚动，避免长期运行写满系统盘。

## 17. 配置需求

### 17.1 配置文件格式

1. 项目继续使用 JSON 配置文件。
2. 发送端和接收端分别维护配置。

### 17.2 发送端配置

发送端配置至少包括：

1. `sender_id`
2. 每个相机的 `camera_id`
3. 相机绑定信息
4. RGB 目标 profile
5. Depth 目标 profile
6. RGB 编码策略
7. Depth 传输策略
8. 接收端 IP
9. 接收端媒体端口
10. 接收端状态通道端口
11. 发送端本地预览开关

### 17.3 接收端配置

接收端配置至少包括：

1. 监听 IP 和端口。
2. Web/API 端口。
3. NAS 录制根目录。
4. 切片时长。
5. 低空间报警阈值。
6. 预览分辨率、帧率、码率。
7. 日志目录。
8. 传输协议选择。
9. 录制格式选择。

### 17.4 接收端不下发配置

以下配置由发送端决定，接收端不远程修改：

1. 接收端 IP。
2. 媒体端口。
3. 发送端 ID。
4. 相机 ID。
5. 相机采集规格。
6. RGB 编码参数。
7. Depth 传输参数。

## 18. 运行与部署需求

### 18.1 首版运行方式

1. 发送端和接收端首版采用命令行程序 + 脚本启动。
2. 不强制 systemd 服务化。
3. 可预留后续服务化，但不作为首版正式要求。

### 18.2 一键启动

发送端和接收端都需要一键启动：

1. 发送端：一键启动采集与发送。
2. 发送端：一键停止。
3. 发送端：一键状态。
4. 接收端：一键启动接收服务和网页监控。
5. 接收端：一键停止。
6. 接收端：一键状态。

Ubuntu 图形环境下需要提供 `.desktop` 双击入口，同时保留 `.sh` 终端入口。

### 18.3 一键启动环境检查

一键启动必须包含环境检查。

发送端检查至少包括：

1. Orbbec SDK 动态库是否存在。
2. Orbbec SDK 运行配置是否存在。
3. 相机是否可访问。
4. 发送端配置文件是否存在且字段合法。
5. 接收端 IP 和端口是否配置。
6. 媒体依赖是否可用。

接收端检查至少包括：

1. 媒体依赖是否可用。
2. 配置文件是否存在且字段合法。
3. NAS 路径是否挂载。
4. NAS 路径是否可写。
5. NAS 剩余空间是否足够。
6. 监听端口是否被占用。
7. Web 端口是否被占用。

失败时必须输出中文错误提示，不得静默失败。

## 19. 工程组织与第三方库

### 19.1 工程组织

项目使用独立工程目录：

```text
wireless_video_delivery/
```

保留 v2 作为参考实现和回退基线。

推荐目录结构：

```text
sender/
receiver/
common/
web/
tools/
configs/
docs/
```

项目使用 CMake 管理 C++ 构建。

### 19.2 第三方库原则

C++ 代码允许并鼓励使用成熟第三方库：

1. 编解码和封装优先使用 FFmpeg / GStreamer 等成熟方案。
2. 图像处理和伪彩预览可使用 OpenCV。
3. HTTP REST 和网页服务使用成熟 C++ Web 框架。
4. JSON 配置使用成熟 JSON 库。
5. 日志使用成熟日志库。

原则：

1. 不手写 H.264/H.265 编码器。
2. 不手写 MP4/MKV 封装器。
3. 不手写 HTTP server。
4. 除非实测证明必须自研，否则优先复用成熟库。

## 20. 首版验收标准

首版以功能跑通为主，不以长时间稳定性为主。

### 20.1 核心功能验收

首版核心验收包括：

1. 6 路摄像头同时在线。
2. 6 路 RGB+Depth 同时接入接收端。
3. 接收端网页显示实时 RGB + 伪彩 Depth 预览。
4. 全局开始录制可用。
5. 全局停止录制可用。
6. 单路开始录制可用。
7. 单路停止录制可用。
8. 每路生成切片目录。
9. 每个切片目录包含 `rgb.mp4`、`depth.mkv` 或等价无损深度文件、`meta.json`、`frames.csv`、`calibration.json`。
10. NAS 路径异常时能报警并停止受影响录制。
11. ID 冲突能报警并阻止混写。
12. 发送端本地预览可显示 RGB + 伪彩 Depth。

### 20.2 录制时长

首版只要求 6 路 RGB+Depth 同时录制数分钟，验证全链路可用。

不在首版需求中承诺：

1. 1 小时连续录制。
2. 4 小时连续录制。
3. 24 小时连续录制。
4. 7x24 稳定运行。

长时间稳定性作为后续阶段目标。

## 21. 待实测确认项

以下内容必须实测后再定：

1. Orbbec C/C++ SDK ARM64 包在树莓派 5 / 香橙派上的可用性。
2. RGB 硬件编码路径，分别针对树莓派 5 和香橙派确认。
3. RGB 最终使用 H.264 还是 H.265。
4. RGB 传输协议，SRT 与 UDP/RTP 对比。
5. Depth 传输协议和无损压缩方案。
6. Depth 实际稳定分辨率和帧率。
7. Depth 文件格式，首选 MKV+FFV1，但允许等价无损格式替换。
8. 网页预览技术路线，优先评估 WebRTC。
9. 切片默认时长。
10. Wi-Fi 现场带宽、丢包率和抖动情况。
11. 是否启用发送端本地缓存和恢复后补传。

## 22. 结论

项目的核心不是继续扩展 2.0 的 Python SDK 平台能力，而是转向 C++ 高性能采集、传输、预览和 NAS 录制。

首版应优先跑通以下闭环：

1. Linux ARM 发送端采集 RGB+Depth。
2. Wi-Fi 传输到 Linux x86_64 接收端。
3. 接收端网页实时预览。
4. 接收端通过 REST/API 控制录制。
5. 接收端写入 NAS 切片文件。
6. RGB、Depth、元数据和逐帧索引可对应。

未实测确认的协议、编码、切片时长和 Depth 格式不得提前写死，应通过现场验证后进入实现细化文档。
