# 多发送端技术路线对比 2026-06-09

## 1. 先说当前实现

当前工程不是全链路 `UDP/RTP`。

当前落地实现是：

```text
状态上报: UDP 50011
媒体数据: TCP 50010
管理接口: HTTP 8080
```

代码和配置约束都已经写死在当前版本里：

```text
01_sender_linux/src/config.cpp
01_sender_linux/src/transport.cpp
02_receiver_linux/src/main.cpp
```

其中发送端当前只接受：

```text
transport.status_protocol = udp
transport.media_protocol = tcp
```

如果配置成别的协议，当前 sender 会直接报错退出，而不是自动切到 RTP/SRT。

因此，文档中出现的 `UDP/RTP`、`SRT`，在当前仓库里应理解为：

```text
候选技术路线
不是当前已交付实现
```

## 2. 当前多发送端瓶颈在哪

在多发送端长期同时在线的前提下，当前实现的主要问题不是“线程数不够”，而是：

```text
1. 多 sender 共享同一个 Wi-Fi 空口
2. RGB 和 Depth 复用同一条媒体 TCP 通道
3. 预览、录制、状态统计在接收端仍存在较强耦合
4. TCP 在弱网或接收端变慢时会出现队头阻塞和背压
```

所以，真正能带来较大提升的路线，不是继续在现有单媒体 TCP 主链上小修小补，而是分通道、分职责，必要时替换传输协议。

## 3. 候选路线对比

### 3.1 路线 A：保持现有 TCP，只优化接收端内部结构

内容：

```text
收包 / 预览 / 录制解耦
per-camera 有界队列
预览按需和分级
主数据优先，预览降级
```

优点：

```text
对当前工程侵入较小
可以渐进落地
不会立刻影响现有 sender/receiver 对接协议
```

缺点：

```text
无法消除 TCP 自身的队头阻塞
RGB 和 Depth 仍可能互相拖累
提升通常是中等，不是数量级变化
```

适用判断：

```text
适合短期稳态优化
适合不想立刻动协议栈的阶段
```

### 3.2 路线 B：RGB 和 Depth 分通道

内容：

```text
RGB 独立媒体通道
Depth 独立媒体通道
必要时不同端口 / 不同 socket / 不同处理队列
```

优点：

```text
RGB 与 Depth 不再共享同一条拥塞路径
更容易分别做优先级、限流、诊断
比完全换协议更容易渐进实施
```

缺点：

```text
协议头、连接管理、接收端状态管理都要扩展
Web 侧和录制侧也要适配双通道到同一 camera key
```

适用判断：

```text
这是当前工程里投入产出比很高的一条路线
如果只能选一个中期方向，优先考虑这条
```

### 3.3 路线 C：预览链路和录制链路分离

内容：

```text
实时收流 / 录制走主链路
网页预览走派生链路或低码率链路
避免 Web 预览直接压主数据路径
```

优点：

```text
“有人看页面就拖慢录制”的问题会明显缓解
适合多 sender 长期在线场景
接收端职责更清晰
```

缺点：

```text
要增加派生流或预览转码逻辑
部署和排障链路会比现在更长
```

适用判断：

```text
如果接收端长期承担网页预览和录制双重职责，这条很值得做
```

### 3.4 路线 D：sender 侧双流

内容：

```text
一路高质量主流用于录制
一路低码率预览流用于网页或实时查看
```

优点：

```text
主数据和预览彻底解耦
接收端不必从高质量主流里再派生所有预览
多 sender 并发时更稳
```

缺点：

```text
sender 侧编码、协议和调度复杂度上升
接收端要管理一主一辅两类流
```

适用判断：

```text
如果以后长期走“在线预览 + 后续录制导出”双目标，这条路线很强
```

### 3.5 路线 E：TCP 替换为 SRT

内容：

```text
保留相对可靠的实时传输语义
用 SRT 替换当前媒体 TCP
```

优点：

```text
比 TCP 更适合抖动链路
抗弱网能力和实时性通常更平衡
比自研 UDP/RTP 可靠性处理成本低
```

缺点：

```text
需要替换 sender/receiver 传输层
需要重新定义连接、重连、统计和排障方法
引入新依赖和新运行参数
```

适用判断：

```text
如果明确要升级传输层，SRT 是很现实的中期路线
```

### 3.6 路线 F：TCP 替换为 UDP/RTP

内容：

```text
媒体改成 UDP 承载
在 RTP 或自定义序号头上处理乱序、丢包、重组
```

优点：

```text
低延迟
避免 TCP 队头阻塞
多 sender 并发时通常更容易维持“持续出画”
```

缺点：

```text
工程复杂度最高之一
应用层要自己补完可靠性、排序、关键帧策略、统计指标
接收端录制一致性要求更高时实现更复杂
```

适用判断：

```text
如果目标是强实时预览优先，且能接受较大协议重构，可以走这条
```

### 3.7 路线 G：接收端分片，多实例接入

内容：

```text
不是一个 receiver 进程吃所有 sender
按 sender 分组启动多个 receiver 实例
不同实例监听不同 media/status/admin 端口
上层 Web 再聚合状态
```

优点：

```text
不同 sender 组之间隔离更强
单进程热点降低
不必第一步就大改现有媒体协议
```

缺点：

```text
不能解决 Wi-Fi 空口竞争
部署、日志和运维复杂度上升
```

适用判断：

```text
如果 sender 数量持续增加，这是一条很务实的扩展路线
```

## 4. 综合排序

按“提升幅度 / 落地难度 / 对现有工程侵入性”综合考虑，建议顺序：

```text
第一梯队:
1. RGB / Depth 分通道
2. 预览链路 / 录制链路分离
3. 接收端内部解耦与有界队列

第二梯队:
4. 接收端分片，多实例接入
5. sender 双流

第三梯队:
6. TCP -> SRT
7. TCP -> UDP/RTP
```

这个排序的理由是：

```text
先把“谁和谁互相拖累”拆开
再考虑“底层协议要不要整个替换”
```

如果一上来就切 `UDP/RTP`，理论提升可能很大，但改造面太大；反而更容易把当前能跑的系统拉回重构期。

## 5. 针对当前工程的建议结论

如果以后仍然默认：

```text
多 sender 同时在线
接收端同时承担录制和网页预览
网络设备短期不大改
```

那么最值得优先推进的不是直接改成 `UDP/RTP`，而是：

```text
1. 先承认当前实现是“状态 UDP + 媒体 TCP”
2. 先把 RGB / Depth 拆通道
3. 再把预览链路和录制链路拆开
4. 然后再评估是否升级到 SRT 或 UDP/RTP
```

一句话概括：

```text
当前工程最大的提升空间，不在“把现有 TCP 再抠一点”，
而在“把统一大通道拆成多个职责明确的小通道”。
```
