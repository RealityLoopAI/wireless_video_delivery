# RGB MP4 封装收尾失败修复说明

更新时间：2026-06-16

## 1. 现场现象

下游反馈部分 RGB MP4 无法打开，典型报错为：

```text
moov atom not found
Invalid data found when processing input
```

本次问题集中在：

- `raspberrypi-01_cam01`
- `rk3588-ubuntu_cam01`

同批次其他 RGB MP4 基本正常，5 路 depth MKV 均可读取。因此问题不是整路相机完全未录制，也不是 depth 链路失败，而是部分 RGB MP4 容器收尾失败。

## 2. 直接证据

坏段目录内存在较大的 `rgb.mp4`。旧版本中，`rgb_recorded_frames.csv` 和 `meta.json` 也显示接收端写入了约 30fps 的 RGB 帧；新版本已将 RGB 视频帧索引合并进 `frames.csv`。

对应 `ffmpeg.log` 中可见：

```text
rgb initial validation failed
rgb repair skipped: raw h264 missing
```

或：

```text
moov atom not found
rgb retime failed
rgb repair skipped: raw h264 missing
```

这说明接收端已经检测到 MP4 不可读，但当时 `write_debug_h264=false`，没有可用于重封装的原始 H264 旁路，所以自动修复无法执行。

## 3. 为什么会缺 `moov`

`rgb.mp4` 不是接收端手写容器，而是由 ffmpeg 从发送端 H.264 码流直接 copy 封装：

```text
ffmpeg -fflags +genpts -r <fps> -f h264 -i pipe:0 -c:v copy -movflags +faststart rgb.mp4
```

MP4 的 `moov` 索引通常在封装结束时写入。启用 `+faststart` 后，ffmpeg 还会在结束阶段整理索引位置，便于播放器快速打开。

因此以下情况都可能留下“文件很大但缺 `moov`”的 MP4：

- 停止录制时 ffmpeg 管道未完整关闭。
- 接收端进程或服务在 ffmpeg 收尾阶段被重启、退出或杀掉。
- NAS/磁盘写入在收尾阶段失败或变慢。
- retime/后处理在原 MP4 尚未可靠校验前被打断。

Depth 使用 Matroska/FFV1，容器对收尾失败更不敏感，所以同一路 depth 正常不代表 RGB MP4 一定已完成封装。

## 4. 修复策略

2026-06-15 修复后，接收端 RGB 录制流程调整为：

1. 录制期间始终同步写一份 `rgb_debug.h264` 恢复旁路。
2. 这份 H264 只从可解码起点开始写，和送入 MP4 封装器的码流起点保持一致。
3. 停止录制时先关闭 ffmpeg 管道，再做 MP4 最终校验、retime 和必要修复。
4. retime/repair 不再使用 detached 后台线程，而是纳入 segment finalizing 生命周期；只有处理完成后才认为该 segment 结束。
5. 如果 `rgb.mp4` 缺 `moov` 或 ffprobe 不可读，接收端会用同段 `rgb_debug.h264` 自动重新封装。
6. `write_debug_h264=false` 时，最终校验成功后自动删除 `rgb_debug.h264`；如果修复失败则保留，方便人工排查。
7. `write_debug_h264=true` 时，即使校验成功也保留 `rgb_debug.h264`，用于调试或二次转换。

## 4.1 2026-06-16 NAS/CIFS 再次加固

现场再次发现 `raspberrypi-01_cam01` 的 RGB MP4 打不开，同批次另外三路 RGB MP4 正常，树莓派 depth MKV 正常。坏段的 `meta.json` 显示 `closed=true`，`ffmpeg.log` 里曾记录：

```text
rgb final validation ok
rgb recovery h264 removed after final validation
```

但之后重新 `ffprobe` 同一个 MP4 时仍出现缺 `moov`。接收端 NAS 挂载为 CIFS：

```text
//192.168.66.149/video_database on /home/fz/Desktop/nas type cifs (...,soft,retrans=1,closetimeo=1,...)
```

这说明仅靠“普通 MP4 收尾后校验一次”在网络盘场景下仍不够稳。2026-06-16 起，RGB 录制、H264 修复重封装和 retime 后输出统一改成 fragmented MP4：

```text
ffmpeg -fflags +genpts -r <fps> -f h264 -i pipe:0 -c:v copy \
  -movflags +frag_keyframe+empty_moov+default_base_moof -flush_packets 1 rgb.mp4
```

该方式会在文件开头写入 `moov`，媒体数据按 fragment 持续落盘，降低停止录制、NAS close、接收端重启或网络盘短暂抖动时整段 MP4 因缺最终 `moov` 而完全打不开的概率。H264 恢复旁路仍保留，作为第二层兜底。

## 5. 下游影响

正常成功录制的目录仍以 `rgb.mp4`、`depth.mkv`、`frames.csv`、`meta.json` 为主。

下游同步和抽帧仍应使用：

```text
rgb.mp4 + frames.csv
```

不要用 MP4 内部 PTS 做跨相机时间同步。跨相机同步应在 `frames.csv` 中筛选 `stream_type=rgb && rgb_recorded=1`，用 `rgb_video_frame_index` 对应 `rgb.mp4` 第 N 帧，再读取同一行的 `frame_system_timestamp_us`。

`rgb_debug.h264` 只在以下情况会留在目录中：

- `write_debug_h264=true`
- `rgb.mp4` 最终校验或修复失败

如果看到 `rgb_debug.h264` 被保留，而 `write_debug_h264=false`，应优先检查同目录 `ffmpeg.log`。
