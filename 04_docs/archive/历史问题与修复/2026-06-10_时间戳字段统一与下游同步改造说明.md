# 时间戳字段统一与下游同步改造说明

日期：2026-06-10

本文用于其他设备同步修改发送端、接收端和后处理工具，避免下游继续把相机设备时间戳当成跨相机同步时间。

## 1. 结论

跨相机、跨发送端 RGB 对齐必须优先使用接收端 `frames.csv` 中当前行自己的：

```text
frame_system_timestamp_us
```

不要用以下字段做主同步：

```text
timestamp_us
local_time_us
rgb_timestamp_us
depth_timestamp_us
pair_delta_ms
```

原因：

1. `timestamp_us` 是 Orbbec SDK 的设备/帧时间戳，即 `frame->timeStampUs()`，不同相机不保证同一绝对时间基准。
2. `local_time_us` 是接收端收到包并写 CSV 的时间，会受网络抖动、TCP 排队、写盘和接收端负载影响。
3. `rgb_*` / `depth_*` 是兼容旧字段，表示“最近一帧 RGB/Depth”，不是当前 CSV 行自己的严格同步记录。
4. `pair_delta_ms` 只用于快速诊断，不是下游严格配对依据。

如果旧数据或旧工具暂时没有 `frame_system_timestamp_us`，RGB 行可以退一步使用 `packet_system_timestamp_us`。但新工具、新设备、新录制验收都应以 `frame_system_timestamp_us` 为主。

## 2. 字段契约

### 2.1 发送端媒体包

媒体包固定头中两个时间戳字段含义固定如下：

```text
timestamp_us        = Orbbec 设备/SDK 时间戳，来自 frame->timeStampUs()
system_timestamp_us = 发送端系统时间戳，优先来自 frame->systemTimeStampUs()，缺失时使用采集线程 host_now_us
```

`flags` 必须设置：

```text
bit 3 = has_system_timestamp
```

### 2.2 接收端 frames.csv

`frames.csv` 是媒体包索引，不是一行一组同步帧。严格读取当前行自己的字段：

```text
stream_type
frame_id
timestamp_us
frame_system_timestamp_us
codec_or_compression
```

跨相机 RGB 对齐过滤条件：

```text
stream_type == "rgb"
time_key = frame_system_timestamp_us
```

RGBD 或诊断场景才额外查看：

```text
rgb_system_timestamp_us
depth_system_timestamp_us
pair_delta_ms
```

## 3. 发送端需要检查或修改的位置

文件：

```text
01_sender_linux/src/main.cpp
01_sender_linux/src/gst_h264_encoder.cpp
```

### 3.1 统一系统时间戳来源

`01_sender_linux/src/main.cpp` 中应保留以下逻辑：

```cpp
uint64_t frame_system_timestamp_us_or(const std::shared_ptr<FrameT> &frame, uint64_t fallback_us) {
    const uint64_t timestamp = frame->systemTimeStampUs();
    return timestamp == 0 ? fallback_us : timestamp;
}
```

RGB 路径应分别写入设备时间和系统时间：

```cpp
const uint64_t rgb_device_timestamp_us = color->timeStampUs();
const uint64_t rgb_system_timestamp_us = frame_system_timestamp_us_or(color, frame_host_now_us);

meta.timestamp_us = rgb_device_timestamp_us;
meta.system_timestamp_us = rgb_system_timestamp_us;
meta.flags = has_system_timestamp | ...;
```

Depth 路径同理：

```cpp
const uint64_t depth_device_timestamp_us = depth->timeStampUs();
const uint64_t depth_system_timestamp_us = frame_system_timestamp_us_or(depth, frame_host_now_us);

meta.timestamp_us = depth_device_timestamp_us;
meta.system_timestamp_us = depth_system_timestamp_us;
meta.flags = has_system_timestamp;
```

不要把 `timestamp_us` 和 `system_timestamp_us` 写成同一个值。

### 3.2 H.264 编码时间轴

`01_sender_linux/src/gst_h264_encoder.cpp` 中，`encode_*` 的 `timestamp_us` 参数应传 RGB 的 `system_timestamp_us`，用于 GStreamer PTS：

```cpp
GST_BUFFER_PTS(buffer) = static_cast<GstClockTime>(timestamp_us) * GST_USECOND;
```

不要改成 Orbbec 设备时间戳，否则跨相机录制视频时间轴会重新变得不可比。

## 4. 接收端需要检查或修改的位置

文件：

```text
02_receiver_linux/src/main.cpp
```

### 4.1 读取协议头

固定头 offset 必须保持：

```text
28  uint64 timestamp_us
36  uint64 system_timestamp_us
```

读包后字段应分别进入：

```cpp
packet.timestamp_us = read_le64(header + 28);
packet.system_timestamp_us = read_le64(header + 36);
```

### 4.2 CSV 表头

`frames.csv` 必须包含：

```text
local_time_us,stream_type,rgb_frame_id,rgb_timestamp_us,depth_frame_id,depth_timestamp_us,pair_id,pair_delta_ms,width,height,payload_size,packet_system_timestamp_us,rgb_system_timestamp_us,depth_system_timestamp_us,frame_id,timestamp_us,frame_system_timestamp_us,codec_or_compression
```

### 4.3 当前行自己的字段

写 CSV 时，最后四个字段必须来自当前媒体包：

```cpp
packet.frame_id
packet.timestamp_us
packet.system_timestamp_us
packet.codec_or_compression
```

也就是：

```text
frame_id                  = 当前行对应流自己的帧号
timestamp_us              = 当前行对应流自己的设备/SDK 时间戳
frame_system_timestamp_us = 当前行对应流自己的发送端系统时间戳
```

不要在 RGB 行把 `depth_system_timestamp_us` 当当前帧时间，也不要在 Depth 行把 `rgb_system_timestamp_us` 当当前帧时间。

## 5. 后处理工具需要检查或修改的位置

仓库内工具：

```text
05_tools/analyze_rgb_timestamp_sync.py
```

读取 RGB 行时优先级应为：

```text
frame_system_timestamp_us
packet_system_timestamp_us
rgb_system_timestamp_us
timestamp_us
```

外部下游脚本也应按同样顺序，生产模式显式指定：

```text
--time-column frame_system_timestamp_us
```

## 6. 设备时间同步要求

每台发送端启动采集前执行：

```bash
cd wireless_video_delivery
./05_tools/setup_sender_chrony_client.sh 192.168.66.196
./05_tools/wait_chrony_sync.sh 0.010
```

检查：

```bash
chronyc tracking
chronyc sources -v
date '+%F %T.%6N %z %Z'
```

验收要求：

```text
Leap status: Normal
当前 source 指向 192.168.66.196
offset 优先小于 10ms
```

## 7. 录制后验收

接收端录一段样本后运行：

```bash
./05_tools/analyze_rgb_timestamp_sync.py \
  /path/to/rk3588-ubuntu_cam01/2026-06-10/xxxxxx \
  /path/to/rk3588-ubuntu_cam02/2026-06-10/xxxxxx \
  --target-ms 10 \
  --max-ms 33.333
```

判断：

```text
优先目标：P95 或绝大多数匹配 < 10ms
最低要求：最近邻匹配误差 < 33.333ms
```

如果 `timestamp_us` 两路相差很大，这是正常现象，说明它是设备本地时间戳，不代表 `frame_system_timestamp_us` 错。

## 8. 常见误用症状

| 症状 | 常见原因 | 正确处理 |
|---|---|---|
| 两路 `timestamp_us` 差几秒、几小时或几天 | 用了相机设备时间戳 | 改用 `frame_system_timestamp_us` |
| 按 `local_time_us` 偶发大跳变 | 网络或接收端落盘抖动 | `local_time_us` 只作诊断 |
| RGB 行里的 `depth_*` 看起来不对 | `depth_*` 是最近 Depth 参考，不是当前 RGB 帧 | 当前行读取 `frame_*` 字段 |
| 时间戳匹配了但快速运动仍有相位差 | 无硬件同步，曝光时刻不完全一致 | 软件最近邻只能降低误差，严格同步需要硬件触发 |

## 9. 给其他设备的最小同步清单

1. 拉取最新仓库。
2. 确认发送端 `timestamp_us` 和 `system_timestamp_us` 没有写反或写成同一个值。
3. 确认接收端 `frames.csv` 有 `frame_system_timestamp_us`，且当前行写的是 `packet.system_timestamp_us`。
4. 下游同步工具新增并优先使用 `frame_system_timestamp_us`。
5. 每台发送端都同步到 `192.168.66.196` 的 chrony。
6. 用 `05_tools/analyze_rgb_timestamp_sync.py` 对一段新录制样本验收。
