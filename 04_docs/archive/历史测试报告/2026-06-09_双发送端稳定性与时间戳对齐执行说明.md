# 2026-06-09 双发送端稳定性与时间戳对齐执行说明

## 1. 目的

本文档用于归档 2026-06-09 现场检查结论，说明：

- 多发送端同时运行时接收不稳定的主要原因。
- 当前缩减为两台发送端后的接收状态。
- 双发送端时间戳对齐的执行方法和验收标准。

## 2. 现场结论

### 2.1 多发送端不稳定的主因

本次检查确认，问题主因不在接收端服务是否存活，而在部分发送端链路质量和发送端自身稳定性：

- 接收端 `gemini_receiver` 和 Web 监控服务均可持续运行。
- 多发送端同时运行时，不同发送端的网络质量差异很大。
- 部分发送端会周期性主动断开 media TCP 连接，或在高延迟链路下频繁重连。
- 多路同时运行时，网页预览解码和轮询压力会进一步放大卡顿观感。

结论：

- 不是“接收端不支持多发送端”。
- 而是“多发送端并发 + 部分发送端链路/发送状态较差”导致整体体验变差。

### 2.2 缩减到两台发送端后的状态

将现场发送端数量缩减后，接收端状态明显恢复：

- `active_media_clients=2`
- 在线发送端：
  - `raspberrypi-01_cam01`
  - `rk3588-ubuntu_cam01`
  - `rk3588-ubuntu_cam02`

6 秒采样结果：

```text
raspberrypi-01_cam01: RGB 30.17 fps, Depth 29.17 fps
rk3588-ubuntu_cam01: RGB 30.0 fps, Depth 30.0 fps
rk3588-ubuntu_cam02: RGB 30.0 fps, Depth 30.0 fps
```

当时接收端看到的媒体 TCP RTT 约为：

```text
192.168.66.210: 约 2.02 ms
192.168.66.85 : 约 1.95 ms
```

并且无明显 `Send-Q` 堵塞。说明在两台发送端场景下，接收端当前可以稳定接近 30fps 接收。

## 3. 接收端侧已落地的相关措施

### 3.1 统一时间源

接收端已作为局域网 `chrony` 时间源运行：

```text
receiver ip: 192.168.66.196
timezone: Asia/Shanghai
NTP listen: UDP 123
```

接收端当前要求发送端统一向该地址对时，不再各自走公网 NTP。

### 3.2 网页预览轮询优化

网页预览已将固定硬轮询改为分路自调度，避免主画面 RGB、Depth 和缩略图在同一节奏上同时抢占浏览器与 Web 服务连接。

当前节奏：

```text
状态刷新: 1000ms
主 RGB: 90ms
主 Depth: 180ms
缩略图 RGB: 350ms
缩略图 Depth: 650ms
页面隐藏: 1000ms
```

该改动的作用是降低网页预览链路的排队和积压，不改变录像保存质量。

## 4. 双发送端时间戳对齐执行方法

### 4.1 接收端角色

接收端负责：

- 作为统一 `chrony` 时间源。
- 保存每路相机目录下的 `frames.csv`。
- 在录制后基于 `frame_system_timestamp_us` 做跨发送端最近帧配对分析。

### 4.2 发送端执行步骤

每台发送端都应执行：

```bash
./05_tools/setup_sender_chrony_client.sh 192.168.66.196
./05_tools/wait_chrony_sync.sh 0.010
```

启动前检查：

```bash
chronyc tracking
chronyc sources -v
date '+%F %T.%6N %z %Z'
```

重点要求：

- `Leap status: Normal`
- 时间源指向 `192.168.66.196`
- 当前 offset 优先控制在 `10ms` 内

### 4.3 录制后验收

录制一段样本后，在接收端执行：

```bash
./05_tools/analyze_rgb_timestamp_sync.py \
  /path/to/segment_a \
  /path/to/segment_b \
  --target-ms 10 \
  --max-ms 33.333
```

判定标准：

- 优先目标：最近帧匹配误差 `< 10ms`
- 最低要求：最近帧匹配误差 `< 33.3ms`

说明：

- 跨发送端对齐以 `frame_system_timestamp_us` 为主。
- `local_time_us` 只用于接收端诊断，不作为跨设备对齐依据。
- 如果后续要做严格同步曝光或高速运动测量，软件对时仍不等于硬件同步。

## 5. 对现场配置的建议

当前建议如下：

- 默认交付以两台发送端稳定运行作为第一目标。
- 双发送端稳定后，再逐步增加发送端数量，不要一次恢复全部历史设备。
- 新增发送端前先确认其 `chrony` 已收敛、网络 RTT 稳定、媒体连接不会周期性重连。
- 当前接收端侧最有价值的发送端改动方向仍是：
  - 降低默认 Depth 档位
  - 默认单路发送
  - 修复 sender identity
  - 修复 backpressure
