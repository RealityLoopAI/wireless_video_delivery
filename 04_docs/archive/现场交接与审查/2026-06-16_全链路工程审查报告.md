## 1. 总体判断

当前系统已经具备可用的多发送端 RGBD 无线采集、接收、网页预览和 NAS 落盘能力。2026-06-16 15:40 左右的现场状态下，4 路在线 RGB 基本接近 30fps，Depth 也基本接近 30fps；最新 15:42 短录制的 4 路 RGB MP4 均可被 `ffprobe` 打开，`frames.csv` 中 `rgb_recorded=1` 的行数与实际视频帧数一致。

但这个工程还没有达到“根因级稳定交付”的状态。主要风险不在单点代码是否能跑，而在以下几个系统性问题：

1. 多设备代码和配置版本不一致，现场运行依赖多处未提交配置和远端设备上的本地改动。
2. 时间戳已经在采集拿帧处生成和传输，但 MP4 内部时间轴仍由 ffmpeg 根据帧率重建，不能作为跨相机帧同步的唯一依据。
3. 网页预览当前以多路 JPEG 轮询方式实现，4 路在线时会给接收端 CPU 和多个 ffmpeg 预览 decoder 带来明显压力。
4. 接收端 NAS 落盘仍强依赖 CIFS 网络文件系统的收尾行为；虽然已改为 fragmented MP4 并有 H264 recovery/repair，但异常断电、软挂载、服务退出时仍要按最终校验状态判断文件是否可用。
5. RK3588 本机 USB 拓扑仍存在 RGB UVC、外接 Hub、键鼠共享 USB2 链路的硬件风险。

## 3. 源码主链路理解

### 3.1 发送端

核心入口：

- `01_sender_linux/src/main.cpp`
- `01_sender_linux/src/transport.cpp`
- `01_sender_linux/src/gst_h264_encoder.cpp`
- `03_common_core/include/gwv3_common/protocol.hpp`

架构：

1. 每路相机对应一个 `camera_worker_loop` 采集线程。
2. RGB/Depth/Web RGB preview 分别生成媒体包。
3. 媒体包进入 `LatestMediaQueue`，每路每种流一个槽位，只保留最新包。
4. 单独 `media_sender_loop` 串行通过 TCP 发给接收端。

这个设计的优点是不会无限积压，网络或接收端背压时系统更偏实时；代价是会覆盖旧帧，所以它不是“完整无丢帧录制传输”模型。

关键代码位置：

- `LatestMediaQueue`：`01_sender_linux/src/main.cpp`
- 每路相机线程：`camera_worker_loop`
- 媒体发送线程：`media_sender_loop`
- TCP 背压丢包与重连：`01_sender_linux/src/transport.cpp`

### 3.2 接收端

核心入口：

- `02_receiver_linux/src/main.cpp`
- `09_web_monitor/server.py`
- `09_web_monitor/static/index.html`

接收端做的事情：

1. UDP 50011 收状态。
2. TCP 50010 收媒体包。
3. C++ 管理接口 127.0.0.1:18080 提供状态、录制、预览接口。
4. FastAPI Web 8080 代理管理接口并展示网页。
5. RGB H264 写入 `rgb.mp4`，Depth 写入 `depth.mkv`，并写 `frames.csv` / `meta.json`。

接收端录制现在会把临时的 RGB 录制帧索引合并进 `frames.csv`：

- `rgb_recorded=1`：该 RGB packet 对应实际写入视频的帧。
- `rgb_video_frame_index`：对应 MP4 解码帧序号。
- `frame_system_timestamp_us`：下游跨相机按系统时间对齐时应该使用的时间戳。

## 4. 时间戳与帧同步审查

### 4.1 当前时间戳路径

发送端在拿到帧后立即读取时间戳：

- RGB 设备时间：`ColorFrame::timeStampUs()`
- RGB 系统时间：`ColorFrame::systemTimeStampUs()`，没有则回退到发送端当前系统时间
- Depth 同理

媒体包中：

- `timestamp_us` 当前写设备时间戳
- `system_timestamp_us` 当前写发送端系统时间戳
- `has_system_timestamp` flag 标明系统时间有效

GStreamer 编码时，发送端把 RGB `system_timestamp_us` 写入 buffer PTS，用于尽量保留帧时间信息。

### 4.2 当前能保证什么

能保证：

1. 同一路相机内，RGB/Depth 的系统时间戳和设备时间戳可追踪。
2. 接收端 `frames.csv` 可追踪每个收到的 packet。
3. `frames.csv` 可标出哪些 RGB packet 实际进入了 MP4 视频帧。
4. 多发送端系统时间目前已由 NTP/chrony 对齐到接收端，偏移在几十微秒到约 0.3ms 量级。

不能保证：

1. 没有硬件同步线时，不同相机不会同时曝光。
2. 系统时间戳对齐不等价于传感器曝光瞬间对齐。
3. MP4 内部 PTS 不等价于采集系统时间戳。
4. 用 MP4 自己的时间轴做多机位同步会有天然误差。

### 4.3 关键风险：MP4 内部时间轴不是精确同步依据

最新 15:42 录制的 4 路 `ffmpeg.log` 都有类似警告：

```text
Timestamps are unset in a packet for stream 0. This is deprecated and will stop working in the future.
```

说明接收端写入 ffmpeg 管道的是裸 H264 byte stream，ffmpeg 并没有拿到逐帧真实 PTS，只能根据 `-r` 估算时间轴。当前接收端会在收尾阶段根据录制时长做 retime，但这解决的是视频文件播放时长，不等于给每帧写入真实采集时间。

因此下游同步必须使用：

```text
frames.csv
stream_type == "rgb"
rgb_recorded == "1"
frame_system_timestamp_us
rgb_video_frame_index
```

而不能只使用 MP4 的内部时间轴。

## 6. 网页预览审查

当前网页前端配置：

```text
STATUS_REFRESH_MS = 1000
MAIN_RGB_REFRESH_MS = 33
THUMB_RGB_REFRESH_MS = 33
MAIN_DEPTH_REFRESH_MS = 180
THUMB_DEPTH_REFRESH_MS = 650
```

问题：

1. 主 RGB 每 33ms 拉一次。
2. 所有缩略 RGB 也每 33ms 拉一次。
3. 每路 RGB 预览在接收端可能对应一个 ffmpeg `image2pipe` decoder。
4. 4 路在线时，Web 页面会对接收端制造额外 CPU 和 HTTP 压力。

接收端现场状态：

- `gemini_receiver` 约 90% CPU
- `gwv3-web-monitor` 约 8% CPU
- 多个 ffmpeg image2pipe 预览 decoder 常驻

结论：

网页卡顿的主要风险不只是网络，而是“多路 JPEG 轮询 + 多 decoder + 30fps 缩略图”的整体架构压力。

建议：

1. 主画面保 30fps，缩略图降到 5-10fps。
2. 或只对当前主画面解码，缩略图用最近缓存帧。
3. 中长期改为 H264 streaming、MSE/WebCodecs/WebRTC，而不是 JPEG 轮询。

## 11. 建议整改路线

### 第一步：固化当前可用版本

目标：

1. 每台设备运行的 commit 可追踪。
2. 每台设备运行的 config 可追踪。
3. 启动路径统一。
4. 回滚路径明确。

建议做法：

1. 建立 `deploy/` 或 `06_configs/site/`，按设备保存正式配置。
2. 所有设备配置进入 git，不再靠 `.bak` 和桌面散落 JSON。
3. 接收端、树莓派、两台 OrangePi 都对齐到同一远端 commit 或明确的设备分支。
4. 文档中维护一张“设备 IP / hostname / sender_id / camera_id / config / commit”的表。

### 第二步：修正下游同步接口

标准下游用法：

```text
读取 frames.csv
过滤 stream_type == "rgb"
过滤 rgb_recorded == "1"
使用 rgb_video_frame_index 对应 MP4 解码帧
使用 frame_system_timestamp_us 做跨相机时间对齐
```

禁止：

```text
用所有 stream_type=rgb 行当视频帧
用 meta.json 的 rgb_frames 当视频帧索引
只按 MP4 PTS 做多相机精确同步
```

### 第三步：预览链路降压

短期：

1. 主画面 RGB 30fps。
2. 缩略 RGB 5-10fps。
3. Depth 缩略保低频。
4. 页面不可见时停止预览请求。

中期：

1. Web 改 H264 stream 或 WebRTC。
2. 接收端不为每个缩略图单独跑高频 ffmpeg JPEG 解码。
3. 主预览和录制链路资源隔离。

### 第四步：录制封装与异常恢复

继续保留：

1. fragmented MP4。
2. `rgb_debug.h264` recovery。
3. final validation。
4. `frames.csv` 合并后的 `rgb_recorded` 字段。

需要增强：

1. stop-all 返回时暴露每路 finalizing 状态。
2. 前端显示“正在收尾/已校验/失败”。
3. NAS 写入失败或 repair 失败时要在 API 中显式暴露。
