## 2. 已融合的信息

从接收端文档确认并保留：

1. RGB 录制使用 fragmented MP4，降低 NAS/CIFS 收尾阶段缺 `moov` 的风险。
2. RGB 视频帧索引合并进 `frames.csv`，下游通过 `stream_type=rgb && rgb_recorded=1` 和 `rgb_video_frame_index` 对齐 `rgb.mp4`。
3. `frame_system_timestamp_us` 是多路 RGB 对齐的优先时间字段。

从旧 1.0/2.0 文档保留为长期原则：

1. 稳定 `sender_id` 和 `camera_id`。
2. 每个物理相机对应一个逻辑摄像头。
3. 同时支持全局摄像头视图和发送端树形视图。
4. RGB 与 Depth 保留独立帧号和独立时间戳。
5. strict / realtime 配对语义作为下游处理策略保留。
6. UI 只消费统一状态，不定义底层数据语义。

从树莓派现场文档保留为运行原则：

1. 发送端 Wi-Fi guard 默认不写死现场 SSID，只校验 5GHz 或显式配置的最低频率。
2. systemd active 不代表采集子进程一定已启动，需检查 watchdog 是否卡在 Wi-Fi guard 或预检阶段。
3. Gemini305 / V4L2 适配资料只作为设备侧参考；当前分支没有对应配置和完整主线代码时，不能写成当前默认能力。

## 4. 后续整理原则

1. README 只保留项目介绍、当前入口和不可违反的边界。
2. 运行手册只放当前分支可执行入口和排障步骤。
3. 历史问题保留根因、修复结论和验证方法，不重复长日志。
4. 设备侧专项资料必须标注适用设备、分支和是否已经合入当前主线。
5. 当代码行为变化时，优先更新 `04_docs/00_文档索引_v3.md`、对应运行手册和对应专题归档，避免同一事实在 README、索引和专题文档中反复复制。
