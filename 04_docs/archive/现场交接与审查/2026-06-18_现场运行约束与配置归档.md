# 现场运行约束与配置归档

更新时间：2026-06-18

本文档归档原 README 中不适合放在仓库首页的现场运行细节、配置边界和历史注意事项。README 只保留项目介绍和入口说明；具体设备运行参数、历史测试结论和现场约束以本文及对应专题文档为准。

## 1. 配置归属

仓库中的默认配置可以随交付目标调整，但设备身份和相机绑定不能随意改。

需要谨慎处理的字段：

1. `sender_id`
2. `camera_id`
3. 接收端地址和端口
4. 相机序列号绑定
5. RGB/Depth profile
6. 码率、压缩方式和预览策略
7. 热插拔策略

接收端以 `<sender_id>_<camera_id>` 作为唯一相机 key。这个 key 会影响 Web 主预览、录制控制、落盘目录和下游同步。多发送端设备同时接入时，任何新设备、新配置或临时调试都必须先检查是否会复用已有 key。

## 2. 当前交付目标

当前现场交付预期优先收敛为一路 RGBD 稳定发送。多路能力仍保留，但属于手动指定配置下的扩展或实验场景，不作为默认运行目标。

这样做的原因是多路链路会同时增加：

1. 发送端 USB 压力。
2. RGB 编码和 Depth 压缩压力。
3. Wi-Fi 上行压力。
4. 接收端解包和落盘压力。
5. 远程控制通道被抢占的风险。

历史容量测试显示，本机算力不是唯一瓶颈。网络链路、接收端吞吐和 TCP 回压会更早暴露问题。因此多路验证必须结合接收端状态、发送端 perf、TCP 队列、Wi-Fi 链路和 Web 预览一起判断。

## 3. 多发送端唯一 key 约束

固定 `sender_id` 必须和物理设备一一对应。不要为了本机 IP、当前网段或临时调试随意改名。

风险示例：

1. 两台发送端复用同一个 `<sender_id>_<camera_id>`。
2. 旧 Web 主预览仍选中历史 key，新发送端改名后看起来像“没有预览”。
3. 录制控制指向旧 key，实际 live key 已变化。
4. 存储目录或 CSV 被不同物理设备混写。

排查顺序：

1. 查看接收端 `/api/status` 中 live key 是否存在。
2. 检查目标 key 的 `rgb_packets` 和 `depth_packets` 是否增长。
3. 确认 Web 主预览目标是否指向当前 live key。
4. 运行发送端预检并处理 ID conflict 提示。

## 4. Orange Pi 5 Pro 现场约束

Orange Pi 5 Pro 现场单路配置需要保留历史相机 key。身份和设备绑定字段不能为了适配本机 IP 临时改掉。

当前相关配置入口：

```text
06_configs/sender_orangepi5pro-01_depth_zlib.json
```

现场排查时，优先确认接收端状态里目标 key 的包计数是否增长，再切换 Web 主预览目标。不要只根据浏览器当前主预览是否有画面判断发送端是否在发送。

## 5. RK3588 配置约束

RK3588 单路默认配置入口：

```text
06_configs/sender_rk3588-01_one_camera.json
```

RK3588 双路现场配置入口：

```text
06_configs/sender_rk3588-01_two_cameras.json
```

双路配置需要同时核对：

1. 发送端本地预览标签。
2. 接收端 `/api/status` 中对应 key 的包计数。
3. 接收端 RGB/Depth 预览画面。
4. RGB 和 Depth 是否按同一 `camera_id` 对应。

只有现场确认两路 Depth 物理视角与 RGB 交叉时，才使用 swapped 测试配置做反向验证。默认配置不应因为单次画面观察就改为交换 Depth。

## 6. Depth profile 约束

现场 `SV1301S_U3 / AY2MC31010W` 枚举确认的 Depth profile 范围包括：

1. 低档：`320x200@5 y11/y12`
2. 高档：`1280x800@30 y11/y12`

当前默认交付优先使用低分辨率高帧率 Depth 档，以降低 USB、zlib、网络和接收端压力。最高 Depth 档配置只用于容量和画质验证，不作为默认交付配置。

最高 Depth 单路测试配置：

```text
06_configs/sender_rk3588-01_cam02_depth_max.json
```

判断 Depth 实际输出时，应看发送端状态中的 `depth_sent_fps` 和 `depth_mbps`。`depth_input_fps` 只表示 SDK 输入到发送端的实际帧率，不等同于成功发送帧率。

## 7. 网络和回压约束

媒体 TCP 发送使用非阻塞背压保护。短暂拥塞时优先丢弃尚未写入 socket 的完整媒体包并保留连接；连续背压丢包后会主动关闭 media socket 并重连，避免发送计数长期卡住。

如果采集正常但媒体连续发不出去，发送端会主动退出并交给 watchdog 重启。

排查网络链路时需要同时看：

1. 发送端 perf 中 RGB/Depth fps 和 Mbps。
2. TCP Send-Q。
3. Wi-Fi 频段、速率、重传和信号。
4. 接收端 `/api/status` 的包计数和 last media 时间。
5. 接收端 CPU、磁盘和 NAS 写入压力。

## 8. 时间显示和时间戳约束

桌面和 Web Monitor 的可读时间统一按北京时间 UTC+8 显示到秒。

协议、API、CSV 和落盘中的 `*_timestamp_us` / `last_*_us` 保持 Unix epoch microseconds 原始值，用于 RGB/Depth 和多发送端时间线对齐。

跨设备同步不以北京时间显示为准，应统一使用局域网时间源，并以接收端 `frames.csv` 中的 `frame_system_timestamp_us` 作为配对入口。

## 9. 本地预览约束

本地预览用于确认发送端采集和编码入口是否正常，不等同于接收端已经成功接收、录制或下游同步正常。

如果本地预览正常但网页没有画面，应优先检查：

1. 接收端是否看到当前 live key。
2. Web 主预览目标是否指向当前 live key。
3. RGB/Depth 包计数是否增长。
4. 媒体连接是否有背压、断连或重连。
5. 浏览器页面是否仍缓存旧目标。

## 10. Wi-Fi Guard 约束

发送端 Wi-Fi guard 的默认策略应只校验链路处于 5GHz 或满足显式配置的最低频率，不应在仓库默认脚本中写死现场 SSID。

换 AP、换路由器、CPE/AP 拆分或重命名 Wi-Fi 后，优先让 NetworkManager 自动连接现场网络，发送端只校验频段。只有某次测试明确要求固定到某个 AP 时，才通过 systemd drop-in 或临时环境变量设置 `GEMINI_SENDER_DEFAULT_WIFI_CONNECTION` / `GEMINI_SENDER_WIFI_CONNECTION`。

如果服务显示 active 但接收端没有画面，应同时检查 watchdog 是否卡在 Wi-Fi guard 启动前阶段，而不是只看 systemd active 状态。

## 11. 跨设备资料处理原则

各设备上的历史文档可以作为参考，但不能直接当作当前分支事实：

1. 树莓派 Gemini305 / V4L2 文档说明了 SDK v1 可能无法枚举 Gemini305、V4L2 可作为设备侧适配方向；只有对应代码和配置合入当前分支后，才能写成当前主线能力。
2. 旧 1.0/2.0 文档中的稳定身份、逻辑摄像头、全局/树形视图、strict/realtime 配对语义继续保留为长期设计原则。
3. 旧 Windows 接收端、Python SDK 调库、RTP/UDP 交付链路和本地 Windows 路径不属于当前 v3 事实，不应在 README 或运行手册中作为当前入口出现。

## 12. 不应进入 GitHub 的内容

以下内容不应提交到 GitHub：

1. 现场密码。
2. 私有网络凭据。
3. NAS 录制数据。
4. 本地临时备份配置。
5. 只适用于当前机器的一次性调试文件。
6. Orbbec SDK 实体文件，除非已经确认分发许可。

需要交接的现场信息，应尽量写成非敏感坐标、路径、运行入口和排查方法，避免记录密码和私有凭据。
