# 历史文档说明

更新时间：2026-06-18

本目录保存旧文档、现场记录、问题归档和历史测试报告。它们用于追溯背景，不代表当前实现。

## 1. 阅读前先看

历史归档有三个使用规则：

1. 先读 `04_docs/` 顶层主文档，再看归档。
2. 归档里的命令、IP、路径、配置和结论可能已经过时。
3. 如果归档和主文档冲突，以当前代码、配置模板和主文档为准。
4. 归档原文里的旧链接可能仍指向旧文件名，这是历史材料的一部分，不作为当前入口维护。

密码和私有凭据不应写入仓库文档。如果历史资料里需要现场凭据，应通过本地安全方式管理，不进入 Git。

## 3. 已经提炼进主文档的结论

下面这些历史结论已经融合进当前主文档：

1. 稳定 `sender_id` / `camera_id` 是多发送端系统的核心约束。
2. `<sender_id>_<camera_id>` 是接收端、Web、存储和下游同步的唯一相机 key。
3. RGB 与 Depth 必须保留各自独立帧号和时间戳。
4. 多路 RGB 对齐不能依赖 MP4 第 N 帧等于 CSV 第 N 行，必须使用 `frames.csv` 的 `rgb_video_frame_index`。
5. `frame_system_timestamp_us` 是多发送端离线对齐的优先字段。
6. Web 预览不是正式数据源。
7. Depth 伪彩只用于预览，正式母版是 `uint16` Depth。
8. Wi-Fi guard 默认不应写死现场 SSID。
9. systemd active 不代表采集子进程一定已经正常发送媒体。
10. 旧 Windows 接收端、Python SDK 实时输出、RTP/UDP 5600 不是当前主线事实。

## 4. 什么时候需要看归档

适合看归档的情况：

1. 需要追溯某个历史问题的证据和修复过程。
2. 需要理解为什么当前技术路线没有采用旧方案。
3. 需要查看某台设备曾经出现过什么现场问题。
4. 需要把旧资料里的结论继续提炼到主文档。

不适合看归档的情况：

1. 想知道当前怎么启动。
2. 想知道当前接口怎么调用。
3. 想知道当前数据格式是什么。
4. 想复制当前默认配置。

这些都应该看 `04_docs/` 顶层主文档。

## 5. 归档维护规则

1. 新的历史问题归档文件名建议使用 `YYYY-MM-DD_问题标题.md`。
2. 新的旧版说明不要放回 `04_docs/` 顶层。
3. 如果归档里有仍然有用的结论，应提炼到主文档，而不是让读者翻历史长文。
4. 归档文档可以保留细节，但不应成为日常阅读入口。
