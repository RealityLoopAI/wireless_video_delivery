# 接收端多路 RGB 主码流 RTP 转发

日期：2026-08-27

## 目标

在不改变 sender 到 receiver 的 RGBD 主链路、录制和 NAS 落盘流程的前提下，把 receiver 已收到的每路 RGB H.264 主码流同时转发到下游主机 `192.168.66.226`。

## 实现

- receiver 从本机管理接口读取各相机的 Annex-B H.264 主码流。
- 不解码、不缩放、不重新编码，仅封装为 RFC 6184 H.264 RTP/UDP。
- 每路相机使用独立 UDP 端口，某一路离线不会阻塞其他路。
- 离线路由按退避间隔自动重连，相机恢复后无需重启 relay。
- relay 是独立用户服务；停止或故障不影响 RGBD 接收、录制和 NAS 落盘。

服务：`gwv3-rgb-rtp-relay.service`

配置：`06_configs/rgb_rtp_relay_loop.json`

实现：`05_tools/rgb_rtp_relay.py`

所有端口使用动态载荷类型 `96`、RTP 时钟 `90000 Hz`。配置中的离线相机会保留端口并自动等待上线。

## 下游接收

每路建立一个 SDP 文件，按需替换端口：

```sdp
v=0
o=- 0 0 IN IP4 127.0.0.1
s=GWV3 RGB
c=IN IP4 0.0.0.0
t=0 0
m=video 5600 RTP/AVP 96
a=rtpmap:96 H264/90000
a=recvonly
```

Windows 防火墙需要允许所需 UDP 端口。FFmpeg/ffplay 示例：

```powershell
ffplay -fflags nobuffer -flags low_delay -probesize 32 -analyzeduration 0 -protocol_whitelist file,udp,rtp -i cam5600.sdp
```

## 运维

```bash
systemctl --user status gwv3-rgb-rtp-relay.service
systemctl --user restart gwv3-rgb-rtp-relay.service
systemctl --user stop gwv3-rgb-rtp-relay.service
tail -f ~/Desktop/wireless_video_delivery/08_reports/receiver_logs/rgb_rtp_relay.log
```

## 验证与限制

- receiver 回环基准：`30.03 FPS`，连续 RTP 序号缺口 `0`。
- 6 路在线时 relay 约占 `9%` 单核、`48 MB` RSS，不增加编码负担。
- receiver 到 `.226` 当前从 `ens3` 出口转发；relay 运行时复测 30 个 ICMP 包为 `0%` 丢包、平均 `4.92 ms`、峰值 `20.90 ms`。此前高频 ICMP 测试曾出现秒级排队，但仅凭该结果不能判断 `.226` 最后一跳是有线还是 Wi-Fi。若下游画面卡顿，应分别检查 `.226` 的实际接入网卡、Windows 防火墙、接收程序消费速度和局域网排队。
- RTP/UDP 以实时低延迟为目标，不保证网络拥塞时重传。录制数据仍使用原 RGBD 主链路，relay 丢包不会污染 NAS 文件。
