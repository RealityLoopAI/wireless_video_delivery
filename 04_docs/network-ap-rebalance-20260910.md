## 迁移前证据

52d2 采集仍约 30fps，但 RGB 发送降到约 12fps，一次状态读取显示画面晚到约 30.68 秒。
e8 也有明显排队及历史累计丢帧。其余四台当时基本正常。
Receiver 录制写入队列为空，写入错误无对应增长。

| 测量 | 52d2 迁移前 | e8 迁移前 | 同 AP 的 ab |
| --- | ---: | ---: | ---: |
| RSSI | 约 -49dBm | 约 -45dBm | 约 -48dBm |
| 到 AP ping 平均值 | 103.8ms | 50.7ms | 9.0ms |
| 到 Receiver ping 平均值 | 157.2ms | 136.4ms | 9.1ms |

每组 ping 只有 5 个包，52d2 到 AP 该组丢 1 个包。不能将 1/5 当成全天丢包率。
这说明问题不只是弱信号，也不能断言整台 TP-LINK 所有客户端都达到同样瓶颈。
无线驱动对重试计数的支持不同，空的 station dump 或始终为零的重试字段不能证明没有重传。

## 修改与恢复保护

52d2 沿用已有 `666666` profile：`3d20d7cf-b978-4392-bd02-255c604cac0f`。
原 profile 已指定 5GHz、BSSID 且关闭省电；这些不是本轮新发现的优化。
本次将其自动连接优先级从 30 提高到 **60**，高于原 TP-LINK 的 50。
原 TP-LINK profile `039896f5-089e-47a9-9882-d21abfe7112e` 保留，可作为备用。
没有设置静态 IP，没有删除其他已保存网络，也没有向仓库写入 Wi-Fi 密码。

迁移前设置 180 秒临时回退 timer，通过独立 systemd oneshot 执行连接切换，
以新 IP 和已有 SSH host key 验证设备身份。稳定恢复后已取消 timer，
确认 `ActiveState=inactive`、`SubState=dead`，不会稍后又自动切回。

IP 切换初期旧 TCP 源地址仍在重传，应用需要重建媒体连接，出现了几十秒恢复过程。
`52-after.json` 对应这个过渡阶段，不能拿其中低接口发送量当作新 AP 的稳定吞吐。
`52-settled.json` 才是恢复后测量，两个新媒体连接的 Send-Q 均为 0。
没有主动重启 sender 服务；检查服务 `NRestarts=0`，启动时间仍为 11:08:17。
网络切换期间计数增长不能记成正式录制中的缺帧，因为切换发生在录制收尾结束后。

手动回到旧 AP 也会断网，应只在确认录制空闲后使用：

```sh
sudo nmcli connection modify uuid 3d20d7cf-b978-4392-bd02-255c604cac0f connection.autoconnect-priority 30
sudo nmcli connection up uuid 039896f5-089e-47a9-9882-d21abfe7112e ifname wlan0
```

## 仍然存在的无线布局问题

`iw dev wlan0 info` 确认，88888888 与 666666 虽主信道分别为 40、44，
但都为 80MHz、中心频率 5210MHz，实际上覆盖同一段频谱。
所以三个 AP **不是三份独立无线带宽**，平均分配数量不能消除这个问题。

下一步可在停录维护窗口，通过路由器后台确认并测试：

- 88888888 用 40MHz 的 36+40 频段；
- 666666 用 40MHz 的 44+48 频段；
- TP-LINK 保持高频段 149 起的当前频段。

需要核对实际 HT40 方向与中心频率，不能只改主信道号码。
这是待验证选项，可能降低单客户端峰值 PHY 速率，但可减少低频段两台 AP 的频谱重叠。
