# RGB编码输出滞后与RGBD配对标记修复

日期：2026-07-01

## 背景

下游反馈使用 `global_timestamp_us` 对齐多发送端画面后，部分录制内容仍然无法帧同步。现场排查确认：

- `clock_sync` 模型本身稳定，在线发送端 offset 多数在微秒到 1ms 级。
- 异常录制中 `global_timestamp_us` 单调递增，没有出现时间戳倒退。
- `orangepi5pro-d12a4719_cam01` 在 2026-06-30 的异常段中，RGB 主编码输出延迟约 1.96s。
- receiver 的 `frames.csv` 会按“最近 RGB + 最近 Depth”写同一行，因此当 RGB 输出滞后时，同一行 RGB/Depth 会被污染成错误配对。

这类问题不是系统时钟漂移，也不是单纯曝光差异。曝光不一致会影响亮度、运动模糊和内容级观感，但不能解释 2 秒级错位。

## 修复内容

### 发送端

文件：`01_sender_linux/src/main.cpp`

新增 RGB 编码输出滞后保护：

- 阈值：`500000us`。
- 如果主 RGB H.264 输出帧的 `encode_done_timestamp_us - system_timestamp_us` 超过阈值：
  - 丢弃当前滞后输出。
  - 重建 RGB 主编码器。
  - 重建 Web RGB preview 编码器。
  - 清空 RGB timing 队列。
  - 临时压制 Web RGB preview 10 秒。
  - perf 日志新增 `rgb_encoder_lag_resets`。

触发日志示例：

```text
rgb encoder output lag reset camera_id=cam01 frame_id=... lag_us=... threshold_us=500000 ...
```

目标是避免旧画面继续被发送到 receiver，防止旧 RGB 内容污染后续录制。

### 接收端

文件：`02_receiver_linux/src/main.cpp`

`frames.csv` 新增列：

```text
rgb_depth_pair_valid
```

规则：

- 最近 RGB 与最近 Depth 都存在。
- 优先使用 `system_timestamp_us` 计算 pair delta。
- RGB/Depth 时间差 `<=100ms` 时写 `1`，否则写 `0`。

旧字段不删除，`pair_delta_ms` 仍保留。新增列只用于明确提示同一行 RGBD 是否可直接作为近似配对使用。

## 下游使用建议

多发送端 RGB 对齐：

- 使用 `stream_type=rgb`。
- 使用 `rgb_recorded=1`。
- 使用 `rgb_video_frame_index` 定位 MP4 中的帧。
- 使用 `global_timestamp_us` 做跨设备时间轴对齐。

RGBD 同行数据：

- 不要只因为 RGB 和 Depth 在 `frames.csv` 同一行就认为硬同步。
- 必须检查 `rgb_depth_pair_valid=1`。
- 更严格的离线 RGBD 配对，应分别取 RGB 行和 Depth 行，再按 `global_timestamp_us` 或 `frame_system_timestamp_us` 做最近邻匹配，并设置下游可接受阈值。

## 后续建议

1. receiver 可进一步把 RGB 行和 Depth 行拆成独立 dataset 索引，避免“最近帧同行”被误用为严格 RGBD 对。
2. Web RGB preview 与主录制链路应继续隔离，预览允许丢帧，主录制优先完整。
3. 没有硬件同步线时，`clock_sync + global_timestamp_us` 只能提供软件时间轴；内容级同步仍可能存在半帧级误差，需要标定补偿或硬件触发。
