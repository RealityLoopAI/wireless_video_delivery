发送端依赖 Orbbec ARM64 SDK，SDK 实体不进入 GitHub 仓库。多发送端现场以 `<sender_id>_<camera_id>` 作为接收端唯一 key，任何改动都必须避免与其他发送端冲突。当前 RK3588 单路默认配置为 `06_configs/sender_rk3588-01_one_camera.json`，接收端地址 `192.168.66.196`，当前预期稳定运行一路 RGBD，默认相机为 `cam02 / AY2MC31010W`。配置中的 `sender_id` 已改为 `auto`；在当前机器上会派生为 `orangepi5pro-c973b736`。默认 RGB 保持 `1920x1080@30 MJPG -> H.264 12Mbps`，默认 Depth 使用 `320x200@30 y12 -> zlib`，当前颜色控制为 `auto_exposure=false, exposure=333, gain=80`。运行中仍保留配置外 Orbbec 设备热插拔能力，可自动分配 `cam03` / `cam04`，但多路不作为默认交付目标。Wi-Fi guard 当前默认只要求 `wlan0` 保持在 `>=5000MHz` 的 5GHz 网络，不再默认写死单一 SSID；如现场需要固定某个 Wi-Fi，可通过 `GEMINI_SENDER_DEFAULT_WIFI_CONNECTION` 或 `GEMINI_SENDER_WIFI_*` 环境变量显式指定。2026-06-05 现场枚举确认 `SV1301S_U3 / AY2MC31010W` 最低 Depth profile 为 `320x200@5 y11/y12`，最高 Depth profile 为 `1280x800@30 y11/y12`，单路最高 Depth 测试配置为 `06_configs/sender_rk3588-01_cam02_depth_max.json`。2026-06-05 单路最高 Depth 档断开前有效采样为 RGB/Depth 约 30fps、总网络约 74.5Mbps、send failure 为 0。2026-05-29 历史多路容量测试中，3 路可运行但会出现 media TCP 背压丢包；详见 `04_docs/06_发送端运行使用手册_v3.md`。

2026-06-05 时间显示约定：Web Monitor 可读时间统一按北京时间 UTC+8 显示到秒，桌面 GNOME 时钟也显示到秒；协议、API 和落盘中的微秒级 Unix 时间戳保持原始值，用于 RGB/Depth 和多发送端时间线对齐。

2026-06-08 多发送端时间戳同步方案：跨设备对齐不以北京时间显示为准，应统一使用局域网 chrony 时间源，并以接收端 `frames.csv` 中的 `frame_system_timestamp_us` 作为配对入口；详见 `04_docs/11_多发送端时间戳同步与对齐方案_v3.md`。

2026-06-09 树莓派发送端现场问题与处理：涵盖 Wi-Fi 守护误判、接收端多客户端背压、USB 线缆与 `usbfs_memory_mb` 对高档位 Depth 的影响，以及当前树莓派建议稳定配置；详见 `04_docs/12_树莓派发送端现场问题与处理记录_2026-06-09.md`。

2026-06-11 RGB 传输回压坏帧处理：正式录制默认关闭大体量 debug/raw 落盘；发送端在 RGB 传输失败后等待下一帧 IDR，再恢复发送非关键帧，避免 H.264 参考帧链断裂扩散；详见 `04_docs/17_RGB传输回压坏帧排查与整改说明_2026-06-11.md`。

2026-06-15 Gemini 305 树莓派适配：Gemini 305 在当前 Orbbec SDK v1 路径下不可枚举，本次新增 V4L2/UVC 采集后端并使用 `06_configs/sender_raspberrypi-01_gemini305_v4l2.json`，当前现场档位为 RGB `1280x800@30 MJPG`、Depth `320x200@30 Z16`；详见 `04_docs/18_Gemini305树莓派V4L2适配说明_2026-06-15.md`。

2026-06-18 Gemini305 SDK v2 深度采集修复：Gemini305 正式路径改为 Orbbec SDK v2，树莓派配置保持 RGB `1280x800@30 MJPG`、Depth `1280x800@30 Y16`；V4L2 Depth 低帧率问题确认为后端错误，不再作为正式采集方式。发送端新增 SDK v1/v2 自动选择、深度异步 zlib 压缩队列、watchdog 单实例锁，Gemini305 默认 RGB 曝光改回自动曝光并设置 `auto_exposure_priority=0`；详见 `04_docs/26_Gemini305树莓派SDKv2深度采集修复_2026-06-18.md`。

2026-06-18 RTP/UDP 媒体链路后续升级方向：当前工程是 UDP `50011` 发状态、TCP `50010` 发 RGB/Depth 媒体包，不是 RTP/UDP 媒体传输。树莓派 Gemini305 高分辨率 Depth 在 Wi-Fi 抖动下会通过 TCP 队头阻塞拖慢 RGB，后续建议新增 RGB RTP/UDP 预览通道并拆分 Depth 通道；详见 `04_docs/27_RTP_UDP媒体链路后续升级方向_2026-06-18.md`。

2026-06-22 树莓派 Depth 2mm 近无损量化：为降低 Gemini305 `1280x800@30` Depth 压缩和 TCP 发送压力，发送端新增 `depth_transport.compression=rvl` 与 `depth_transport.quantization_step_mm=2`，接收端解码后仍按 `uint16 gray16le` 落盘；详见 `04_docs/29_树莓派Depth_2mm近无损量化说明_2026-06-22.md`。

2026-06-22 Gemini305 Depth LZ4 2mm 传输优化：在 Orange Pi Gemini305 `1280x800@30` Depth 场景下，`rvl` 和 `zlib` 码率更低但达不到 30fps，当前部署 `depth_transport.compression=lz4`、`quantization_step_mm=2`，接收端短窗口可达 RGB/Depth 约 30fps，Depth 约 210-249Mbps，但 Wi-Fi/TCP 余量较小；详见 `04_docs/30_Gemini305_Depth_LZ4_2mm传输优化记录_2026-06-22.md`。

2026-06-22 Gemini305 Depth UDP 分片与 PLZ4 实验：新增 `media_udp` 实验开关，支持 RGB/Depth 主媒体按流走 UDP，并新增 `plz4` 分块 LZ4 Depth 压缩；实测全 UDP 可以跑通但 Depth 存在明显分片丢失导致的有效帧率下降，不能直接替代可靠媒体链路；详见 `04_docs/31_Gemini305_Depth_UDP分片与PLZ4实验记录_2026-06-22.md`。

2026-06-22 Gemini305 Depth TCP LZ4 32mm 降码率：主媒体链路已切回 TCP，Orange Pi Gemini305 当前部署 `depth_transport.compression=lz4`、`quantization_step_mm=32`；实测 RGB/Depth 约 30fps，Depth 约 125-143Mbps，TCP Send-Q 约 0.3-0.6MB，未再触发 Depth 回压丢包；详见 `04_docs/32_Gemini305_Depth_TCP_LZ4_32mm降码率记录_2026-06-22.md`。
