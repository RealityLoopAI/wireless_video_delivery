# Gemini305 USB 停流与 SDK 部署修复

日期：2026-07-14

## 1. 问题现象

`orangepi5pro-d12a4719` 连接 Gemini 305 时，Web 端表现为 RGB 画面偶发卡死。发送端和内核日志证明，故障不只发生在 RGB 预览：RGB 和 Depth 会同时停流。

典型顺序：

```text
SDK:    setXu failed
kernel: usb_submit_urb returned -19
kernel: reset SuperSpeed USB device
SDK:    Device response with bad magic
sender: RGB/Depth 0fps -> camera pipeline reconnect
```

2026-07-14 的一段异常运行中共观察到约 40 次 USB reset、2365 次 `bad magic` 和 4426 次 `setXu failed`。期间还出现两次真实 USB disconnect/re-enumeration。

## 2. 根因和放大因素

### SDK 部署错配

systemd 和目录名都声明 `OrbbecSDK_v2.8.6`，但该目录中的库实际是指向 pyorbbecsdk 的 `libOrbbecSDK.so.2.7.6` 软链接。

必须同时检查：

```bash
ldd 12_build/bin/gemini_sender | grep Orbbec
readlink -f 11_third_party/orbbec/linux_arm64/OrbbecSDK_v2.8.6/lib/libOrbbecSDK.so.2
```

修复后真实库为：

```text
libOrbbecSDK.so.2.8.6
```

Gemini 305 固件已是 1.0.70，符合 SDK 2.8.6 推荐版本，本次没有刷写固件。

### 运行中频繁读取 XU 属性

`log_perf()` 原本每秒通过 SDK 同步读取自动曝光、曝光、增益和曝光优先级。这些读取走 UVC XU 控制通道，并在故障时首先报 `setXu failed`。

修复后：

1. 性能日志只使用每帧 metadata 中的曝光、增益和帧率。
2. 相机属性只在启动应用配置时读写和回读。
3. 移除了运行中的每秒 XU 轮询和对采集状态锁的占用。

### 重连可能在坏 SDK context 内循环

原机制在 pipeline 打开成功时立即清零重连次数。如果 pipeline 打开后数秒内再次停流，永远无法达到进程级重启阈值。

新机制：

1. 每个相机保留近期停流时间点。
2. 默认 300 秒窗口内达到 3 次停流，sender 子进程以 75 退出。
3. 外层 `sender_watchdog.sh` 重启子进程，重建 Orbbec Context、Device 和 Pipeline。
4. pipeline 成功打开后立即重新启用停流检测，不再受上一次 30 秒冷却限制。

可调环境变量：

```text
GEMINI_SENDER_CAMERA_FLAP_RESTART_EVENTS=3
GEMINI_SENDER_CAMERA_FLAP_WINDOW_SECONDS=300
```

把 events 设为 0 可关闭该进程级升级恢复。

## 3. SDK API 兼容

SDK 2.7.x 及 v1 头文件使用 `OB_PROP_COLOR_MAXIMAL_GAIN_INT`，SDK 2.8.6 使用 `OB_PROP_COLOR_AE_MAX_GAIN_INT`。CMake 现在在配置阶段检测可用符号，同一套源码可以使用新旧 SDK 编译。

## 4. 验证

1. 使用原 SDK 头文件编译通过。
2. 使用官方 ARM64 SDK 2.8.6 头文件和库编译通过。
3. 仓库 `ctest` 3 项全部通过。
4. `.133` 实机能用 SDK 2.8.6 枚举 Gemini 305，固件 1.0.70，连接为 USB3.2。
5. RGB `1280x800@30 MJPG` 和 Depth `320x200@30 Y16` 均恢复约 30 FPS。
6. 接收端 RGB 低码率预览和 Depth 预览请求均能返回 200。
7. sender 启动日志和 heartbeat 均已确认上报 `orbbec_sdk_version=2.8.6`、`orbbec_sdk_version_number=20806`。

## 5. 剩余风险

Gemini 305 USB 描述符申报 896mA，接近 USB 3.0 单口 900mA 上限。当天未观察到欠压、过流或过热日志，但如果后续仍出现内核级 `USB disconnect`，应继续排查 USB 线缆、接口和 5V 供电。
