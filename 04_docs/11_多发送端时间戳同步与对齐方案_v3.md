# 多发送端时间戳同步与对齐方案 v3

更新时间：2026-06-08

## 1. 已确认需求

当前工程基于多台发送端设备采集 Orbbec 相机数据，并统一发送到接收端。现场遇到的问题是：多发送端之间的帧时间戳无法稳定对齐，即使设备桌面时间都显示为北京时间，接收端按时间戳配对时仍然存在偏差。

本次方案按以下现场条件设计：

1. 设备形态：多台 Ubuntu 发送端电脑，每台发送端连接自己的相机，一个 Ubuntu 接收端统一接收。
2. 网络条件：Wi-Fi，不使用有线 PTP，不具备发送端之间的硬件同步线。
3. 对齐对象：先只对齐 RGB，Depth 暂不纳入本阶段验收。
4. 接收端 IP：`192.168.66.196`，当前固定。
5. 精度目标：现有条件下越小越好；RGB 30fps 一帧约 33.3ms，最低验收为小于一帧间隔，优先争取小于 10ms。
6. 执行方式：允许在接收端和发送端安装并启用 `chrony`，允许增加工程脚本供其他设备执行。

本方案目标：

1. 所有发送端只同步到同一个局域网时间源，避免各设备本机时钟漂移导致 RGB 帧时间戳不可比。
2. 接收端按发送端采集 RGB 帧时写入的 `frame_system_timestamp_us` 做跨发送端帧配对。
3. 输出可量化的 RGB 对齐误差，例如 `delta_us` / `delta_ms`，便于判断某组帧是否可用。
4. 保留 RGB、发送端、相机 ID 等身份字段，避免不同设备之间的数据混淆。
5. 方案可以被其他 Ubuntu 发送端复用执行，不依赖单台设备的临时配置。

本方案不解决的问题：

1. 不做 RGB-D 空间对齐。深度图投影到 RGB 图需要内参、外参和 D2C 对齐流程。
2. 不处理 Depth 时间对齐；本阶段只看 RGB。
3. 不保证多个相机同一时刻曝光。严格曝光同步需要硬件同步线、主从触发或外部触发。
4. 不使用接收端收到包的时间作为主对齐依据，因为网络抖动会污染接收时间。

## 2. 偏差原因

北京时间只是显示方式，不是同步机制。两台设备都显示 `Asia/Shanghai` 或 `UTC+8`，只能说明它们用相同的时区显示时间，不代表底层 Unix epoch 微秒时间一致。

当前现场仍有偏差，常见原因如下：

1. 各发送端没有同步到同一个时间源。
2. `systemd-timesyncd` 只能说明系统已同步过，不能保证实时 offset 足够小。
3. Wi-Fi 网络抖动会影响 NTP 校时精度。
4. 旧版本曾把 `timestamp_us` 和 `system_timestamp_us` 写成同一类时间戳；排查时应确认当前 segment 是否已经分开记录设备时间和系统时间。
5. Orbbec 的帧时间戳表示 SDK/驱动拿到帧附近的时间，不一定是曝光开始时间。
6. 30fps RGB 的帧间隔约 33.3ms，最近帧匹配本身会存在半帧以内误差。

## 3. 当前工程现状

协议中已经有时间戳字段：

```text
timestamp_us
system_timestamp_us
```

接收端落盘的 `frames.csv` 已包含：

```text
local_time_us
packet_system_timestamp_us
rgb_system_timestamp_us
depth_system_timestamp_us
frame_id
timestamp_us
frame_system_timestamp_us
```

跨发送端对齐时，优先使用：

```text
frame_system_timestamp_us
```

不要优先使用：

```text
local_time_us
```

原因是 `local_time_us` 是接收端收到媒体包的时间，会受到网络排队、TCP 背压、编码耗时和接收端写盘压力影响。

## 4. 推荐总体方案

推荐使用“统一局域网时间源 + 发送端系统时间戳 + 接收端最近帧匹配”的软件同步方案。

默认角色：

```text
接收端 Ubuntu: 192.168.66.196，作为局域网 chrony 时间源
各 Ubuntu 发送端: 作为 chrony 客户端，只同步到 192.168.66.196
```

数据流：

```text
发送端采集 RGB 帧
发送端写入 RGB frame_system_timestamp_us
发送端通过媒体 TCP 发给接收端
接收端落盘 frames.csv
下游按 sender_id + camera_id + stream_type=rgb + frame_system_timestamp_us 做配对
```

## 5. 可执行脚本

本仓库提供以下脚本：

```text
05_tools/setup_receiver_chrony_server.sh
05_tools/setup_sender_chrony_client.sh
05_tools/wait_chrony_sync.sh
05_tools/analyze_rgb_timestamp_sync.py
```

### 5.1 接收端作为时间源

在接收端 `192.168.66.196` 执行：

```bash
cd wireless_video_delivery
./05_tools/setup_receiver_chrony_server.sh 192.168.66.0/24
```

脚本会完成：

```text
安装 chrony
关闭 systemd-timesyncd
备份 /etc/chrony/chrony.conf
允许 192.168.66.0/24 网段同步本机
启用 local stratum 10 作为局域网兜底时间源
重启 chrony 并打印 chronyc sources / tracking
```

说明：

1. 如果接收端可以访问公网，优先使用公网 NTP 源。
2. 如果现场局域网完全离线，`local stratum 10` 允许接收端作为本地时间源，但必须先确认接收端系统时间正确。
3. 所有发送端必须指向同一个接收端时间源，不要各自同步不同公网 NTP。

### 5.2 发送端同步到接收端

在每台 Ubuntu 发送端执行：

```bash
cd wireless_video_delivery
./05_tools/setup_sender_chrony_client.sh 192.168.66.196
```

脚本会完成：

```text
安装 chrony
关闭 systemd-timesyncd
备份 /etc/chrony/chrony.conf
禁用原有 pool/server/peer 时间源
只配置 server 192.168.66.196 iburst prefer minpoll 3 maxpoll 4
执行 chronyc makestep
执行 wait_chrony_sync.sh，默认等待 offset 收敛到 10ms 内
```

手动检查：

```bash
chronyc sources -v
chronyc tracking
```

验收重点：

```text
Reference ID 指向 192.168.66.196 或接收端时间源
Leap status: Normal
System time offset 尽量小于 10ms，理想小于 5ms
```

### 5.3 发送端启动前等待同步

发送端开始采集前执行：

```bash
./05_tools/wait_chrony_sync.sh 0.010
```

含义：

```text
0.010 = 10ms
```

如果 Wi-Fi 条件较好，可以收紧到 5ms：

```bash
./05_tools/wait_chrony_sync.sh 0.005
```

如果现场网络抖动较大，10ms 长时间等不到，可以先用 20ms 启动，但最终 RGB 最近帧匹配仍应低于 33.3ms：

```bash
./05_tools/wait_chrony_sync.sh 0.020
```

## 6. 发送端启动前置要求

发送端服务启动前应等待时间同步完成。建议在发送端 watchdog 或 systemd service 前增加以下检查：

```bash
./05_tools/wait_chrony_sync.sh "${GEMINI_CHRONY_MAX_CORRECTION_S:-0.010}" || exit 20
```

如果 `chrony` 未同步完成，发送端应拒绝开始采集，避免产生不可对齐的数据。

每台 Ubuntu 发送端都应使用同一套策略，但配置文件中的身份字段必须保持各自唯一：

```text
sender_id
camera_id
```

## 7. 工程字段建议

当前发送端把两个时间戳字段分开使用：

```text
timestamp_us        = Orbbec 设备/帧时间戳 frame->timeStampUs()
system_timestamp_us = 发送端系统时间戳 frame->systemTimeStampUs()，如果为空则用采集时 host_now_us
```

这样可以同时满足两类需求：

1. 跨发送端对齐：使用 `system_timestamp_us` / `frame_system_timestamp_us`。
2. 排查相机内部时钟或 SDK 行为：查看 `timestamp_us`。

下游仍应以 `frame_system_timestamp_us` 为主，不应直接使用设备时间戳跨发送端或跨相机比较。

## 8. RGB 配对规则

以一路参考流为基准，例如：

```text
sender_id=sender-a
camera_id=cam01
stream_type=rgb
```

对每一帧参考帧时间：

```text
t_ref = frame_system_timestamp_us
```

在其他发送端对应流中寻找：

```text
min(abs(t_other - t_ref))
```

输出配对结果：

```json
{
  "group_timestamp_us": 1780905238685211,
  "reference": {
    "sender_id": "sender-a",
    "camera_id": "cam01",
    "stream_type": "rgb",
    "frame_id": 54360,
    "frame_system_timestamp_us": 1780905238685211
  },
  "matches": [
    {
      "sender_id": "sender-b",
      "camera_id": "cam02",
      "stream_type": "rgb",
      "frame_id": 53102,
      "frame_system_timestamp_us": 1780905238690080,
      "delta_us": 4869
    }
  ]
}
```

建议阈值：

```text
RGB 30fps 优先目标: delta <= 10000us
RGB 30fps 最低验收: delta <= 33333us
```

超过阈值时不要硬配，应该标记为：

```text
unsynced
missing_match
delta_exceeded
```

## 9. RGB 对齐验收流程

每台发送端启动前检查：

```bash
date '+%F %T.%6N %z %Z'
chronyc tracking
chronyc sources -v
```

接收端运行后检查 `frames.csv`：

```bash
head -1 frames.csv
tail -n 20 frames.csv
```

确认存在：

```text
frame_system_timestamp_us
```

推荐直接使用脚本分析接收端落盘目录：

```bash
./05_tools/analyze_rgb_timestamp_sync.py \
  /path/to/sender-a/cam01/segment \
  /path/to/sender-b/cam01/segment \
  --target-ms 10 \
  --max-ms 33.333
```

第一个目录作为参考流，后续目录作为待匹配流。路径可以是 segment 目录，也可以直接是 `frames.csv`。

验收标准：

1. 所有发送端 `chronyc tracking` 显示 `Leap status: Normal`。
2. 所有发送端同步源一致，优先为 `192.168.66.196`。
3. 每台发送端 `System time offset` 尽量小于 10ms，理想小于 5ms。
4. RGB 30fps 多发送端最近帧匹配误差优先小于 10ms。
5. RGB 30fps 多发送端最近帧匹配误差最低应小于 33.3ms。
6. 日志和落盘数据中可以追溯 `sender_id`、`camera_id`、`frame_id`、`frame_system_timestamp_us`。

## 10. 升级路线

如果软件同步后仍无法满足业务需求，按以下顺序升级：

1. 将 `systemd-timesyncd` 全部切换为 `chrony`，并统一接收端时间源。
2. 在发送端启动脚本中强制执行 `wait_chrony_sync.sh`。
3. 优化 Wi-Fi 链路，降低 NTP 和媒体传输抖动。
4. 有条件时用有线网络替代 Wi-Fi。
5. 如果交换机和网卡支持，使用 PTP / linuxptp。
6. 如果需要严格同步曝光，使用 Orbbec 硬件同步、主从模式或外部触发。

硬件同步适用于高速运动、三维重建、严格测量等场景。普通多路预览、录制和后处理配对，优先使用本方案的软件时间戳对齐。

## 11. 后续可选改造

以下内容不阻塞本方案执行，但会继续提升可观测性和精度：

1. 接收端自动生成跨发送端 RGB 配对结果文件。
2. 发送端状态包上报 `chronyc tracking` 摘要和当前 offset。
3. 发送端 watchdog 在采集前内置 `wait_chrony_sync.sh` 检查。
4. 进一步改造发送端协议，把设备时间戳和系统时间戳彻底拆开记录。
