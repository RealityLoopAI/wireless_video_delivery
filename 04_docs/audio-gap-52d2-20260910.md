# Audio Gap Investigation

日期：2026-09-10，北京时间。设备：`lubancat-52d2ef0c`，发送端 `192.168.1.156`，
接收端 `192.168.1.196:50030/UDP`。本次只读排查，没有修改配置或重启服务。

## 结论

不是预期 DTX 静音停发。运行中的 `gst-launch-1.0` 使用 Opus CBR、32kbps、
20ms/包、48kHz，未设置 dtx；设备现场 `gst-inspect-1.0 opusenc` 确认 dtx 默认 false。
语音进程为 `--no-audio-stream-pause-during-playback`、`capture-playback-mode keep`，
播放时不停流。识别端 low_rms/VAD 过滤只控制识别，不控制独立 Opus 推流分支。
对应 NAS 元数据 `playback_events=[]`。

四段 `late_packets=0`、`duplicate_packets=0`。RTP timestamp 的前后差也与这些序号缺口吻合。
这不是只有 global 时间换算导致的空洞，更符合 RTP 编号之后到接收入口之间的包缺失。
仍不能凭接收端端点记录断言缺包已经成功从无线网卡发射，或确定丢在某一个 AP。

接收端空槽会写入 `OPUS_SILENCE_20_MS` 以维持音频时长，并记录 silence_packets/outage_intervals。
所以 `silence_packets` 在这里表示缺包后补的静音，不是发送端检测到现场安静。
录音即使可播放、时长完整，也不意味着原始声音完整；无法从缺失包判断当时有无实际人声。
完整性要求收到比例至少 99%，且最长缺口不超过 1s；这几段 partial 判定有依据，不应改成 complete。

## 定位进展

15:19:41 发送端 CLOCK_SYNC 探测超时；15:19:42 同时出现 RGB/Depth TCP 背压。
15:19:43 RGB 发送降至约 1fps，15:19:44 RGB 与 Depth 都暂时为 0，
但视频采集仍约 30fps。该时间重叠支持传输路径短时受阻，不支持仅把故障归因于音频静音。

当前接收端 UDP `RcvbufErrors=0`，50030 socket drops=0；发送端本地 UDP drops=0。
未发现当前内核 UDP 收包缓冲溢出的计数证据，不代表所有网卡层和历史链路都无丢包。
发送端 Python UDP 转发器对 `sendto` 异常仅 continue，没有逐目的地失败计数或重传，
因此现有日志不足以完成历史丢包点的最终归因。

## 不干扰录制的现场验证

对发送端 loopback、wlan0 出口和 receiver ens3 入口做 35/40 秒被动抓包，
只保存 RTP 包头文本，不保存音频内容；timeout 返回 124 表示预定时间结束。
排除两端启停边界后的共同窗口 32.861 秒：

- 本机生成 1642 包；1642 包均在 wlan0 出口出现。
- 这 1642 包全部在接收端入口出现。
- 两端 tcpdump 均报告内核抓包丢弃 0。

本次短测未复现缺口，只能说明测试窗口恢复正常，不能推翻历史文件的缺包证据。

## 建议处理顺序

1. 增加本机 RTP 收到、各目的地 sendto 成功/失败、序号缺口、入口 socket drop 的计数，
   用有界包头环形记录在故障触发时保留证据，区分本机转发和网络问题。
2. 保留实时 UDP 监听；对 NAS 正式音频增加独立的可靠传输/缓存补传，避免正式母版依赖裸 UDP。
   小幅加大缓冲只能吸收部分抖动，不能找回已经丢失的 UDP 包。
3. 缺口补齐成功前继续标 partial，区分原始静音与缺包补静音；不能靠放宽质量阈值解决。

这些是建议，尚未实现。本次未改变现有音视频采集、录制和传输。
