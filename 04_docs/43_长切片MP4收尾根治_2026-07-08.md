# 长切片 MP4 收尾根治

日期：2026-07-08

## 现象

15 分钟切片或更长切片结束后，个别 RGB MP4 在下游设备上打不开，目录里会残留：

```text
*_rgb.retime_replace_tmp.mp4
*_rgb_debug.h264
```

部分目录的 `meta.json` 也可能停留在 `closed=false` 或缺少完整结束信息。

## 根因

接收端在 `SegmentWriter::close()` 中关闭 ffmpeg 后，又同步执行一次 RGB MP4 retime/faststart 重封装。15 分钟 1080p30 文件通常是 GB 级，重封装需要读写大文件并做临时文件替换。

这个过程有两个风险：

1. 录制 worker 会被大文件重封装阻塞，下一段切片启动和停止都被拖慢。
2. 如果此时脚本、systemd 或人工重启把 receiver 杀掉，容易留下半成品 `retime_replace_tmp.mp4`，造成封装状态不一致。

现场日志确认过 receiver 曾被 systemd 以 `SIGKILL` 结束，时间点正好处于 retime/faststart 后处理阶段。

## 修复

接收端实时录制路径不再做大文件重封装：

1. `finalize_completed_media()` 只做快速可读性校验。
2. RGB MP4 校验成功后删除 `rgb_debug.h264`。
3. RGB MP4 校验失败时保留 `rgb_debug.h264`，用于离线修复。
4. 不再生成 `*.retime_replace_tmp.mp4`。
5. 原始 RGB MP4 保持录制器输出的 fragmented MP4 格式，优先保证录制完整性和进程可停止。
6. 清理旧 `retime/repair` 死代码，源码中不再保留会生成 `*.retime_replace_tmp.mp4` 的实时后处理入口。
7. MP4 `moov` 校验只扫描文件前 8MB。当前 fragmented MP4 的 `moov` 应在文件开头，坏文件不会再触发 GB 级全文件扫描。

停止脚本和自启动安装脚本也同步加了保护：

1. 停 receiver 前先请求 `/api/record/stop-all`。
2. 轮询 `/api/status`，等待所有相机 `segment_active=false`、`segment_finalizing=false`、录制队列为空。
3. receiver systemd service 使用 `KillMode=mixed`、`TimeoutStopSec=180s` 和 `SendSIGKILL=no`。停止时只先通知 receiver 主进程，由它关闭 pipe 让录制 ffmpeg 正常写尾；不能使用 `KillMode=control-group` 同时中断 ffmpeg。

## 验证

在接收端临时把 `segment_seconds` 改为 10 秒，三路 `orangepi5pro-d12a4719` 1080p30 RGB 录制约 25 秒，产生 9 个测试切片：

```text
cam01: 9.95s / 10.15s / 4.94s
cam02: 9.95s / 10.17s / 4.94s
cam03: 9.97s / 10.12s / 4.93s
```

验证结果：

1. 9 个 `codex_segment_fixrgb.mp4` 均可被 `ffprobe` 读取 duration。
2. 每段 `codex_segment_fixmeta.json` 均为 `closed=true`。
3. 未生成 `*.retime_replace_tmp.mp4`。
4. 成功校验后 `codex_segment_fixrgb_debug.h264` 被删除。
5. 测试后配置已恢复为 `segment_seconds=900`。

## 使用注意

当前优先目标是录制完整、切片可靠、不会因后处理阻塞导致长切片损坏。若后续需要给普通播放器或分发场景生成更标准的 faststart MP4，应做离线批处理，不要放在 receiver 实时录制收尾路径中。

## 2026-07-14 播放器拖动兼容性补充

现场发现正常结束、`ffprobe` 可读且带 `mfra` 的 fragmented MP4，在部分 Windows 或网页播放器中仍可能无法拖动进度条。原因是旧封装只有尾部 `mfra`，没有部分播放器依赖的文件头全局 `sidx`。

修复后录制参数增加 `global_sidx`：

```text
+frag_keyframe+empty_moov+default_base_moof+global_sidx
```

该方案继续保留 fragmented MP4 的抗中断特性，不执行 GB 级 faststart 重封装。正常结束时只补充全局 fragment 索引，不改变 RGB 编码数据。最终校验同时解析 MP4 顶层 box：普通 MP4 必须有 `moov`；fragmented MP4 必须同时有 `moov`、`sidx` 和 `mfra`。缺少完成索引时保留 `rgb_debug.h264` 并进入自动恢复，不能再仅因 `ffprobe` 能读取 duration 就发布 `recording_ready.json`。

## 2026-07-14 播放器实机复测修正

实机复测确认：`global_sidx + mfra` 能让 ffmpeg 和 VLC 定位，但部分 Windows 播放器仍不能拖动 fragmented MP4。最终方案调整为两阶段发布：

1. 录制期间继续写 fragmented MP4，并同步保留 H.264 恢复旁路。
2. 正常停止后从 fragmented MP4 单次 `-c:v copy` 无损重封装到同目录 `rgb_seekable.tmp.mp4`。
3. 临时文件必须通过 duration 和顶层 box 校验，且最终结构必须有 `moov`、不能有 `moof`。
4. 校验成功后才原子替换正式 `rgb.mp4`；失败或进程中断时原文件保持不动，恢复旁路也不会删除。
5. 不使用 `+faststart`，避免为移动 `moov` 再做一次 GB 级文件搬运。普通 MP4 即使 `moov` 位于文件尾，完整关闭后仍支持本地和 SMB 播放器拖动。
