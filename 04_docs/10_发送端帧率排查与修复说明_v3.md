# 发送端帧率排查与修复说明 v3

## 1. 问题现象

2026-05-26 现场检查时，发送端 `orangepi5pro-b439137c / cam02` 能正常连接接收端，但接收端统计显示实际到达帧率不足 30fps：

```text
RGB:   约 17.4 fps，约 7 Mbps
Depth: 约 17.4 fps，约 8 Mbps
```

同时发送端日志中持续出现：

```text
Pipeline source frameset queue fulled, drop the oldest frame
```

该日志说明发送端主循环消费 Orbbec frameset 的速度低于相机输出速度，SDK 队列满后开始丢旧帧。

## 2. 排查结论

网络不是主要瓶颈：

```text
Wi-Fi: 5G，协商 433 Mbps
Ping 接收端: 0% packet loss，平均约 2ms
TCP 发送队列: 基本为空
```

本机关闭本地预览后帧率仍只有约 18fps，因此预览窗口不是主因。

根因在发送端 H.264 编码取输出逻辑。每帧送入 GStreamer 后，代码使用：

```cpp
gst_app_sink_try_pull_sample(..., 20 * GST_MSECOND)
```

循环读取编码输出。最后一次读取通常会等到 20ms 超时才退出，导致每帧额外引入固定等待，主循环无法稳定消费 30fps frameset。

## 3. 修复方式

将编码输出 drain 改成非阻塞读取：

```cpp
gst_app_sink_try_pull_sample(..., 0)
```

这样每次只取当前已经编码完成的 sample，不再为“没有更多 sample”额外等待 20ms。GStreamer pipeline 仍然保留 appsink 缓冲和 drop 策略，后续帧到来时会继续取出已经完成的编码输出。

修复文件：

```text
01_sender_linux/src/gst_h264_encoder.cpp
```

## 4. 验证结果

修复后重新编译并重启发送端，接收端 10 秒采样结果：

无本地预览：

```text
RGB:   约 30.08 fps，约 12.02 Mbps
Depth: 约 30.18 fps，约 14.27 Mbps
```

带本地预览：

```text
RGB:   约 29.28 fps，约 11.69 Mbps
Depth: 约 29.48 fps，约 13.93 Mbps
```

修复后发送端恢复接近 30fps。Orbbec 队列满日志从持续高频刷屏下降为零星出现。

## 5. 后续注意

如果再次出现接收端帧率明显低于 30fps，应按以下顺序检查：

1. 接收端 `/api/status` 中对应相机的 `rgb_packets` / `depth_packets` 10 秒差分。
2. 发送端 `sender_stdout.log` 是否持续出现 frameset queue full。
3. `ss -tin` 中 TCP 发送队列是否长期堆积。
4. Wi-Fi 信号、ping 丢包和发送端 CPU 温度。
5. 是否重新引入阻塞式等待、同步磁盘写入或高成本预览处理。

## 6. 2026-05-28 RK3588 媒体 TCP 背压掉线

### 6.1 现象

RK3588 发送端单路相机运行时，本地采集仍然正常，日志中仍有 `rgb_input_fps` / `depth_input_fps`，但接收端帧计数不再增长，发送端统计变成：

```text
rgb_sent_packets_s=0
depth_sent_fps=0
rgb_send_failures>0
depth_send_failures>0
```

此时 ping 接收端正常，接收端 TCP 端口也可连接，说明不是相机采集掉线，也不是接收端 IP 错误。

### 6.2 原因

发送端 media TCP socket 遇到发送背压。现场系统默认：

```text
net.core.wmem_max = 212992
net.core.wmem_default = 212992
```

虽然配置请求 1 MiB 发送缓冲，但实际受 `wmem_max` 限制，只能得到约 213 KiB。1080p H.264 和 Depth 包连续积压时，几个媒体包就可能填满发送队列。旧逻辑会持续丢包计数，但不会因为连续背压主动重连，所以表现为采集还在跑、媒体发送长期为 0。

### 6.3 修复

代码修复：

```text
01_sender_linux/src/transport.cpp
01_sender_linux/include/gwv3_sender/transport.hpp
01_sender_linux/src/main.cpp
```

修复点：

```text
连续 TCP 背压丢包后主动关闭 media socket 并重连。
发送失败时打印 media send failed，日志包含 camera_id、stream 和具体错误。
发送端配置 send_buffer_bytes 提升到 4194304。
```

系统参数：

```bash
sudo sysctl -w net.core.wmem_max=8388608 net.core.wmem_default=1048576
```

持久化：

```text
/etc/sysctl.d/99-gemini-video-transport.conf
```

内容：

```text
net.core.wmem_max = 8388608
net.core.wmem_default = 1048576
```

### 6.4 验证

修复后单路 `cam01` 20 秒接收端差分：

```text
RGB:   +400 packets，约 20 fps
Depth: +602 frames，约 30 fps
TCP:   ESTABLISHED，Send-Q=0
```

发送端近期日志无 `media send failed`，`rgb_send_failures=0`，`depth_send_failures=0`。双路发送时仍需关注总带宽、接收端解码压力和 Wi-Fi 链路，但同类“背压后一直不恢复”的问题应由发送端自动重连恢复，并在日志中留下明确原因。
