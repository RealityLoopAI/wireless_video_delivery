# 全天音频归档与 NAS 发布

## 1. 功能边界

音频归档独立于视频录制任务，接收端开机后默认全天运行。点击视频“开始/停止录制”不会改变音频归档状态。

发送端只做一次 Opus 编码，同一个 RTP 包同时发送到：

1. `192.168.66.32`：下游实时监听。
2. `192.168.66.196`：接收端全天归档。

音频归档暂停时，实时 RTP、本机关键词唤醒、语音回复和拍照流程继续运行。

## 3. 分片和文件结构

每路按接收端墙钟的 `HH:00/15/30/45` 边界生成 15 分钟 Ogg/Opus 文件：

```text
audio/<sender_id>/YYYY-MM-DD/HHMMSS/
  audio.opus
  audio_timing.csv
  audio_meta.json
  audio_ready.json
```

只有 `audio_ready.json` 存在时，该目录才算发布完成。下游扫描 NAS 时应忽略没有 ready 标记的目录。

`audio.opus` 是标准 Ogg/Opus 文件，VLC、FFmpeg、ffplay、mpv 和常见音频库可以直接读取，不需要项目专用播放器。

## 4. 时间轴和缺包处理

发送端门控线程在拿到已编码 RTP 包时记录 RTP sequence/timestamp、SSRC、sender 系统时间、sender 单调时钟和 stream instance ID。

接收端用现有 CLOCK_SYNC 的 `receiver_clock - sender_clock` offset，把 RTP 时间映射到视频共用的 `global_timestamp_us`。音频和视频因此可以在同一个全局时间轴上做离线匹配。

`audio_timing.csv` 每秒一行，包含：

- `global_timestamp_us` 和该秒的全局时间窗口；
- 期望、实收、静音补包数量；
- 首末 RTP sequence/timestamp；
- 首末 sender 系统时间和 receiver 接收时间；
- clock sync valid、offset、delay、drift；
- 迟到包和重复包数量。

接收端使用 250 ms 抖动缓冲。某个 20 ms RTP 包超时后写入标准 Opus 静音包，保持文件时间轴连续，不会把后续音频向前压缩。无 CLOCK_SYNC 模型时继续归档，但 `clock_sync_valid=0`，时间临时退化为接收端到达时间。

注意：sender 音频时间来自编码出口时间减去一个 20 ms 帧长，仍包含 ALSA/GStreamer 固定管线延迟。需要音频与画面内容级精确对齐时，应通过拍板声/闪光做一次固定偏移标定；CLOCK_SYNC 解决的是设备时钟差，不等于声画硬同步。

## 5. 可靠发布

接收端流程分为三层：

1. 切片线程直接把 Opus 包封装为 Ogg，不解码、不转码、不运行每路 FFmpeg。
2. 切片边界只做快速关闭和本地原子移交，不在 RTP 线程执行 `fsync`、SHA256 或 NAS 复制。
3. 后台 worker 刷盘、计算 SHA256、复制到 NAS 隐藏目录、逐文件校验，最后原子改名并写 `audio_ready.json`。

NAS 暂时不可用时，本地 staging 保留待上传片段并持续重试。待上传最老文件达到 7 天，或本地空闲空间低于配置阈值时，系统停止生成新音频片段并报警，不删除旧文件；实时 RTP、唤醒和视频链路不受影响。NAS 文件默认永久保留，不自动删除。

## 6. 管理接口

接收端音频归档管理服务只监听 `127.0.0.1:18083`，Web Monitor 在局域网内代理以下接口：

```text
GET  /api/audio/status
POST /api/audio/start-all
POST /api/audio/stop-all
POST /api/audio/start-sender?sender_id=<sender_id>
POST /api/audio/stop-sender?sender_id=<sender_id>
```

start/stop 是调试开关，只控制归档。服务重启后按默认配置恢复全天归档。

状态重点字段：

```json
{
  "storage_blocked": false,
  "pending_segments": 0,
  "pending_bytes": 0,
  "nas_available": true,
  "streams": [
    {
      "sender_id": "lubancat-52d2ef0c",
      "enabled": true,
      "recording": true,
      "received_packets": 123456,
      "clock_sync_valid": true
    }
  ]
}
```

Web Monitor 的“音频”入口提供全部和单 sender 的暂停、恢复及 RTP 健康状态。

## 8. 2026-08-20 验证

真实接收端 FFmpeg/FFprobe 验证结果：

1. 4 秒高频切片连续发布，完整片段 FFprobe 时长约 `4.0065 s`，解码时间轴为 4 秒。
2. 有 RTP 的片段记录到 `186/200` 实包和 `14/200` 静音补包，时间轴未缩短。
3. RTP 线程在切片后缓冲回到 0，刷盘/哈希/NAS 发布位于后台 worker。
4. `audio_ready.json` 最后生成，文件大小和 SHA256 校验通过后才删除本地 staged 目录。
5. 曾尝试“本机 UDP 转发给 FFmpeg 再封装”，出现 0 字节输出和边界收尾阻塞，已废弃，不是当前实现。
