# 录制缺帧、断流的原因分析与修复说明

更新时间：2026-09-08。本文时间均为北京时间（UTC+08:00）。

## 1. 结论

下游反馈的 `2026-09-08/112121` 批次确实缺少 RGB 帧。
复查 NAS 上的四份 `frames.csv` 后，间断时间、视频帧索引与反馈一致。
这不是把时间戳换一列或调整播放速度就能修复的问题，也不是这次 MP4 无法解码的问题。

已确认的软件放大机制是：

```text
媒体链路开始积压
  -> sender 把数据写入 TCP 内核缓冲区，仍显示发送约 30 FPS
  -> receiver 实际收到的是几十秒前的帧
  -> sender 遇到写不动的包，5 秒后放弃旧 TCP 并重连
  -> receiver 让新会话接管，关闭尚未读完的旧会话
  -> 旧连接缓冲中的完整历史帧来不及进入录制文件
  -> 新连接等关键帧恢复，CSV 和视频中留下真实缺口
```

**不能把“写入 sender 的 TCP 缓冲区成功”当作“receiver 已收到并录下”。**

52d2ef0c 还叠加了晚于该切片起点上线、启动时间异常、RGB/Depth 多次断连，不能只用同一个 RGB 重连问题解释全部缺录。

## 4. 哪些判断已证实，哪些还需要现场验证

已证实：发送端采集仍在运行；到接收端的媒体积压达几十秒；原重连策略会关闭有积压的旧连接并放大缺帧；52d2ef0c 存在晚到、异常初始时间及双流断连。

尚未完全证实：最初积压究竟由哪一个 AP 的无线重传、空口争用、链路拥塞，或接收端短时调度停顿触发。当时没有同步保存各跳抓包、TCP 重传和逐秒线程栈，不能事后把唯一物理原因说死。

接收端历史 `sar` 的 11:20～11:30 十分钟平均值为 CPU 空闲约 43%、I/O 等待约 0.64%，内存可用约 8.5 GB。这些数据不支持“持续 CPU/内存耗尽或 NAS 写盘完全堵死”，但十分钟平均值也不能排除秒级尖峰。

## 5. 代码改动

修复提交：`ccd3981`。测试检查修正：`8543f1d`。

### 5.1 主媒体 TCP 保留未完成包

- 仅针对启用 `recording_buffer.enabled` 的 RGB/Depth 主媒体。
- TCP 暂时不可写时，保存当前包的字节偏移、保持原连接。
- 一次发送调用约每 100 ms 让出控制，发送线程保留同一个包及其内存所有者，之后从正确字节位置继续。
- 等待续传不计作一次实际丢帧，不触发 RGB 关键帧丢弃保护。
- 即使队列中其他帧触发保护，也必须先把已发了一部分的当前包发完，不能破坏 TCP 包边界。
- 实际断连、连接目标变化或单包持续受阻达到 60 秒时，仍走错误恢复；不会无限阻塞。
- 预览与拍照通道不采用这一主媒体保留策略，避免改变既有低延迟预览和快照重试语义。

保留 receiver 的新旧会话隔离，避免历史上出现的旧帧回灌、帧号倒退问题；修复点是减少不必要的重连，而不是让新旧会话随意混写。

### 5.2 Receiver 不因一次 2 秒读超时丢掉半包

原有 socket 的 2 秒超时改作停机轮询周期。暂时超时时保留已读字节，继续等待同一包；无进展上限为 60 秒。进程停止或对端确实关闭时仍退出。

### 5.3 每个流单独提供接收健康信息

`GET /api/status` 的每个 camera 增加：

| 字段 | 含义 |
| --- | --- |
| `rgb_receive_age_ms` | 距最后一个完整 RGB 包到达多久；未收到为 -1 |
| `depth_receive_age_ms` | 距最后一个完整 Depth 包到达多久；未收到为 -1 |
| `rgb_receive_delay_us` | 最近 RGB 的接收时间减全局采集时间；时钟无效或结果为负时为 -1 |
| `depth_receive_delay_us` | 同上，针对 Depth |

接收间隔或采集至接收延迟超过 500 ms 时，记录限频告警 `media arrival delayed`。注意延迟字段是“最近一包”的值，判断断流要同时看 age；一条 Depth 心跳不能再代替 RGB 的健康情况。

### 5.4 启动校时和预览隔离补强

旧设备的 systemd 服务有的直接运行 `sender_watchdog.sh`，绕过了新安装器的 chrony 等待。本次把有界校时等待补到 watchdog 的实际启动入口：相机初始化前尝试等待时间校准，最长约 33 秒；超时明确记录降级，不强制停止离线采集。

这减少了主机带错误初始日期启动采集的风险，但不把它当成 52d2ef0c 的现场根因已经完全验证。

预览解码器的 `active()` 改为读取原子运行状态，不再等待持有 FFmpeg 管道写锁的预览线程，减少录制接收线程被预览反压牵连的机会。

### 5.5 测试不再漏看工作线程创建的 FFmpeg

原测试只读取 `/proc/<pid>/task/<主线程>/children`。现在遍历所有线程的 children，真实检查预览子进程和遗留录制文件句柄；未删除或放宽原来的文件句柄检查。

- 相同“接收方停读 6 秒”用例：旧 sender 代码失败，提示连接被关闭；新代码通过。

- Receiver 的半包测试：分别在包头、负载中停顿 2.5 秒，之后完整接收一个包，期间 admin API 仍响应。
- ARM sender：8 项测试通过。
- ARM receiver：28 项通过，但本机没有 ffmpeg/ffprobe，部分媒体落盘测试实际跳过，不能据此声称落盘验证完成。

## 9. 仍然存在的边界

系统仍使用有界内存队列和 TCP，不是具备逐帧落盘确认与断电持久重放的无限可靠消息系统。当前一些 sender 配置为每流 900 帧队列，约 30 秒；内核缓冲还会额外容纳数据，但不能把这个容量当作固定保障。

如果长期平均带宽低于产出、队列耗尽、设备断电、USB 断开、TCP 真正失败或超出本次保留上限，仍可能缺帧。本修复不增加无线带宽，也不承诺在这些条件下完整录制。要进一步承诺断电恢复或更长中断补传，需要单独设计 sender 本地缓存和 receiver 接收/落盘确认协议。
