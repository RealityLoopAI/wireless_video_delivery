## 编码和曝光检查

日志中的编码调用均值约 0.116 ms，但它是异步提交调用耗时，不是完整编码管线耗时。
CSV 中编码开始到输出平均约 33.514 ms，不能据此认定吞吐跟不上，因为管线可以并行处理不同帧。
SDK 系统时间到应用取帧平均约 0.171 ms，P99 约 1.941 ms，最大约 18.773 ms；没有看到此处长时间排队的证据。
但 SDK 系统时间不一定是物理曝光开始，不能用这个差值证明底层没有缓冲。

同一进程启动日志确认：Orbbec SDK 后端，SV1301S_U3，序列号 AY2M54301VE，USB3.0；自动曝光设置及回读 false，曝光 312，增益 0。
因此启动时不是自动曝光模式。逐帧曝光元数据未提供，不能证明整个异常时段相机内部行为绝无变化。
该录像时段内核日志查询未发现 USB reset、UVC error 或热降频记录，缺少报错也不能排除底层丢帧。

## 帧号解释的边界

实际路径使用 `color->index()`，见 `01_sender_linux/src/detail/camera_capture.inl` 和 `camera_support.inl` 的 `record_rgb_input()`。
仓库另有 V4L2 路径使用 `next_frame_id_++`，但本次运行不是那条路径，不能拿它解释 SDK 帧号。
排查中曾先读到 V4L2 路径，已在确认实际后端后纠正。
官方 API 将该字段描述为 frame index，并未在这份接口说明中保证它等同于物理传感器曝光计数：[Orbbec SDK Frame API](https://orbbec.github.io/OrbbecSDK/doc/api/English/Frame_8h.html)。
所以连续 SDK 帧号可以支持“应用已见帧连续交付”的判断，不能单凭它排除 SDK 之前漏帧。

## 下一步诊断

1. 增加或利用 SDK/底层 UVC 的原始序号、回调时间及驱动错误标志，与现有 SDK 帧号对比。
2. 同步采集 SDK 回调到应用取帧的队列和线程调度延迟，保留按秒统计及异常窗口。
3. 有空闲维护窗口时，用相同档位、曝光做纯采集对照，排除编码/网络参与因素；再分别比较带编码和带发送。
4. 不通过复制帧、插帧或重写时间戳来把计数填成 27,000；那会掩盖数据集真实时间轴。
