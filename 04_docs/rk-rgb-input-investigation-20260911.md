## 帧号解释的边界

实际路径使用 `color->index()`，见 `01_sender_linux/src/detail/camera_capture.inl` 和 `camera_support.inl` 的 `record_rgb_input()`。
仓库另有 V4L2 路径使用 `next_frame_id_++`，但本次运行不是那条路径，不能拿它解释 SDK 帧号。
排查中曾先读到 V4L2 路径，已在确认实际后端后纠正。
官方 API 将该字段描述为 frame index，并未在这份接口说明中保证它等同于物理传感器曝光计数：[Orbbec SDK Frame API](https://orbbec.github.io/OrbbecSDK/doc/api/English/Frame_8h.html)。
所以连续 SDK 帧号可以支持“应用已见帧连续交付”的判断，不能单凭它排除 SDK 之前漏帧。

本轮 DQBUF 3601 次，首末跨度约 29.9872 fps，驱动 sequence 共缺 4 个编号，分三处：

| 1013774 -> 1013776 | 835939.826479 | 线程唤醒后等待约 13.468 ms，随后从 Xorg 切入 |

第二处原始事件：835934.812919 从取帧线程切到 Xorg，835934.829084 切回，
835934.829114 DQBUF，835934.829251 QBUF；后续缺失编号 1013625。
第三处原始事件：835939.812968 唤醒，835939.826436 从 Xorg 切入，

DQBUF 到 QBUF 平均 0.102 ms、最大 2.657 ms。没有持续 CPU 吞吐不够的证据，

Linux v5.10 上游 UVC 实现中，FID 变化会推进 sequence，即使没有可用缓冲区，

[uvc_video.c](https://github.com/torvalds/linux/blob/v5.10/drivers/media/usb/uvc/uvc_video.c)。
本机是厂商 5.10.209 内核，上游源码只能作为机制依据，不是本机逐行一致性证明。

### 判断与修复边界

高置信度观察：底层没有多缓冲轮转，且两次交付缺口与 Xorg 引起的调度延迟紧邻。
推断：单缓冲交付放大了调度抖动，是可优化的软件风险，而非足以判定相机硬件损坏。
仍未解释第一次两编号缺口和历史全部 51 帧差额，不能宣称全部根治。

优先修复方向是验证 SDK 初始化/归还所有缓冲区的行为，让多缓冲真正工作，
并以相同曝光、档位、真实驱动序号做前后对照；调高线程优先级最多是缓解，不能代替缓冲修复。
不能在运行中的 SDK 文件描述符上擅自补 QBUF，因尚未确认 SDK 是否按实际返回 index 取对应映射，
贸然入队其他缓冲区可能引入错帧。
仓库自有 `V4L2MjpegCapture` 已有四缓冲逐个入队逻辑，但不是当前 SDK 后端，
直接切换还需验证 RGBD 配对、时间戳及色彩控制兼容性。
旧 `40_Orbbec_V4L2_UVC启动修复_2026-06-26.md` 记录过此型号使用 LibUVC 卡启动，
因此这次没有直接切换 LibUVC 或盲目升级 SDK。

## 第三轮：定位 SDK 初始化实现

对实际加载的 ARM64 `libOrbbecSDK.so.1.10.27` 做静态反汇编，没有修改该文件或进程内存。

库已去除内部符号，objdump 显示的邻近导出符号名称不是准确函数名；以下以指令地址、
ioctl 请求码、参数结构偏移及分支为依据。

### 实现证据

1. `0x1b5298` 到 `0x1b5344`：RGB QUERYBUF/mmap 初始化遍历返回的缓冲区，最多四个，
   index 来自循环变量，并把映射按 index 存入表中。
2. `0x1b2e04` 到 `0x1b2e40`：采集线程初始化构造零初始化的 `v4l2_buffer`，
   type=VIDEO_CAPTURE、memory=MMAP、index=0，仅调用一次 `VIDIOC_QBUF` (`0xc058560f`)。
   随后进入接收循环，没有初始 index=1/2/3 的入队循环。
3. `0x1b3080` 到 `0x1b30b0`：后续取帧通过返回 index 选择映射，
   `0x1b311c` 到 `0x1b3130` 归还取回的缓冲区。因此开始只入队零号，就会一直只轮转零号。
4. `0x1acc28` 的 ioctl 包装只做 EINTR/EAGAIN 重试，不会代为把其他缓冲区入队。

这与前两轮 QUERYBUF 和 trace 的实际状态吻合，确认当前 SDK 实现存在多缓冲未启用的问题。
它可以解释对短暂调度延迟的脆弱性，但仍不能证明历史全部缺口都只有这一原因。
反汇编片段：`08_reports/rk-rgb-input-investigation-20260911/sdk-v1-buffer-disassembly.txt`。

官方开源 SDK v2 的 `captureLoop()` 已在启动处按 index 遍历多个缓冲区逐个 QBUF：
[ObV4lUvcDevicePort.cpp](https://github.com/orbbec/OrbbecSDK_v2/blob/main/src/platform/usb/uvc/ObV4lUvcDevicePort.cpp)。
这里只把它作为正确缓冲初始化的参照，不代表 v2 可直接替代本机 SDK v1。
本次获取的参照源文件 SHA256：`fbbef06861ddfdd51f235cae65ce3f8cc25b0366710d4198a6e1011ee488ff24`。
