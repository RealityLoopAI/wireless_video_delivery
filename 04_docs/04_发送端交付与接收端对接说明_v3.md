## 3. 状态通道

状态通道使用 UDP。

每个 UDP datagram 是一条 UTF-8 JSON 消息，发送端当前会在 JSON 后追加一个换行符 `\n`。接收端解析时可以先 trim 空白字符。

消息类型遵循：

```text
sender_hello
camera_announce
heartbeat
camera_offline
event
```

字段语义以 `04_docs/03_中间传输数据格式_v3.md` 为准。

当前实现中：

1. 启动后发送 `sender_hello`。
2. RGB 和 Depth 都拿到帧后发送 `camera_announce`。
3. 默认每 1000 ms 对每路相机分别发送一条带 top-level `camera_id` 的 `heartbeat`，接收端据此刷新对应 `<sender_id>_<camera_id>` 的 `last_status_us` / `status_live`。
4. 编码器失败、网络失败、热插拔失败或超过热插拔路数上限等状态写入日志，并通过 `event` 上报。

## 4. 媒体通道

媒体通道使用 TCP。TCP 流中连续发送多个媒体 packet。

发送端使用非阻塞 TCP。配置项 `transport.send_timeout_ms` 控制一个媒体包在 TCP 背压下允许占用发送路径的最长时间，默认配置为 80 ms；`transport.send_buffer_bytes` 是发送端请求的 socket 发送缓冲大小，RK3588 现场配置为 4 MiB，最终有效值仍受系统 `net.core.wmem_max` 限制。当 socket 已有积压且新包无法完整进入发送队列时，发送端会在写入前丢弃该完整包并保留 TCP 连接；如果已经写入了半包后仍然超时，则关闭连接并重连，保证接收端不会在旧 TCP 流内继续解析损坏包边界。

每个 packet 结构：

```text
固定头 94 字节
sender_id bytes
camera_id bytes
codec_or_compression bytes
payload bytes
```

接收端需要循环读取：

1. 先读取 94 字节固定头。
2. 校验 magic、header_version、header_size。
3. 根据 `sender_id_len`、`camera_id_len`、`codec_len` 读取 3 段字符串。
4. 根据 `payload_size` 读取 payload。
5. 处理完一个 packet 后继续读下一个 packet。

## 5. 固定头格式

固定头使用小端序。

```text
offset  size  type    field
0       4     uint32  magic
4       2     uint16  header_version
6       2     uint16  header_size
8       1     uint8   stream_type
9       1     uint8   reserved0
10      4     uint32  flags
14      2     uint16  sender_id_len
16      2     uint16  camera_id_len
18      2     uint16  codec_len
20      8     uint64  frame_id
28      8     uint64  timestamp_us
36      8     uint64  system_timestamp_us
44      8     uint64  pair_id
52      4     uint32  width
56      4     uint32  height
60      2     uint16  pixel_format
62      8     uint64  payload_size
70      8     uint64  uncompressed_size
78      16    bytes   reserved
```

固定值：

```text
magic = 0x33565747
magic bytes = 47 57 56 33
magic ascii = "GWV3"
header_version = 1
header_size = 94
```

## 6. 枚举值

`stream_type`：

```text
1 = rgb
2 = depth_raw
```

`pixel_format`：

```text
1 = encoded_video
2 = depth_u16
```

`flags`：

```text
bit 0 = key_frame
bit 1 = dropped_before
bit 2 = end_of_segment_hint
bit 3 = has_system_timestamp
```

当前实现会设置 `has_system_timestamp`。

## 7. RGB Payload

RGB packet：

```text
stream_type = 1
pixel_format = 1
codec_or_compression = h264
payload = H.264 byte-stream / AU
```

发送端当前编码路线：

```text
Orbbec RGB MJPG -> OpenCV decode BGR -> GStreamer mpph264enc -> h264parse -> TCP media packet
```

接收端建议：

1. 按 H.264 Annex B byte-stream 处理。
2. 录制时优先直接封装到 MP4/MKV，不要重编码。
3. 预览时再解码。

## 8. Depth Payload

Depth packet：

```text
stream_type = 2
pixel_format = 2
codec_or_compression = none 或 zlib
payload = uint16 depth_raw 一整帧，或 zlib 压缩后的 uint16 depth_raw
uncompressed_size = width * height * 2
```

当前实测规格：

```text
width = 640
height = 400
camera_profile_format = y12
uncompressed_size = width * height * 2 = 512000 bytes
depth_scale = 1
```

2026-06-01 现场枚举确认 `SV1301S_U3 / AY2MC31010W` 最高 Depth profile 为 `1280x800@30 y11/y12`。默认双路配置保留 `640x400@30 y12` 作为稳定发送档；`06_configs/sender_rk3588-01_cam02_depth_max.json` 仅用于单路最高 Depth 压力和画质验证。最高 Depth 测试档的 Depth `uncompressed_size` 为 `1280 * 800 * 2 = 2048000` bytes；2026-06-05 实测 zlib 后 Depth 网络约 62.45Mbps。

当 `codec_or_compression = none` 时，`payload_size = uncompressed_size`。

当 `codec_or_compression = zlib` 时：

1. `payload_size` 是压缩后的字节数。
2. `uncompressed_size` 是解压后的原始深度字节数。
3. 接收端必须先用 zlib 解压到 `uncompressed_size`，再按 `uint16 little-endian` 解析。

`depth_scale` 由 `camera_announce.depth_profile.depth_scale` 提供。

## 9. 接收端最小实现建议

接收端首版可以先实现以下最小闭环：

1. UDP `50011` 打印并保存状态 JSON。
2. TCP `50010` accept 一个发送端连接。
3. 按 94 字节固定头解析媒体 packet。
4. 使用状态通道或媒体包中的实际 `sender_id` 与 `camera_id` 作为相机唯一标识；当前 RK3588 配置示例为 `sender_id=orangepi5pro-66-133`、`camera_id=cam01/cam02`。
5. RGB payload 写入临时 `.h264` 文件，验证可被 FFmpeg 解码。
6. Depth payload 在 `codec_or_compression=zlib` 时先解压，再按帧写入临时 raw 文件，或写入 MKV/自定义无损容器。
7. 根据 `frame_id`、`timestamp_us` 记录逐帧索引。

## 10. 发送端运行方式

构建：

```bash
cmake -S . -B 12_build
cmake --build 12_build -j4
```

配置校验：

```bash
./12_build/bin/gemini_sender --config 06_configs/sender_rk3588-01_two_cameras.json --validate-config
```

本机采集验证，不发送、不预览：

```bash
./12_build/bin/gemini_sender --config 06_configs/sender_rk3588-01_one_camera.json --run-seconds 5 --no-preview --no-send
```

后台启动：

```bash
./05_tools/start_sender.sh
```

所有启动脚本都会先执行 `05_tools/sender_preflight.sh`，在终端显示发送端 ID、相机 ID、接收端 IP/端口、RGB/Depth profile、编码器、Depth 压缩、预览配置、日志目录、路由和 Wi-Fi 链路信息。预检失败时输出中文错误并停止启动。

状态查看：

```bash
./05_tools/status_sender.sh
```

停止：

```bash
./05_tools/stop_sender.sh
```

## 11. 已知限制

1. 传输协议是当前首版约定：状态 UDP、媒体 TCP。文档原需求没有写死协议，后续可替换为 SRT/RTP 等。
2. 当前实现的 Depth 压缩方式为 `none` 和 `zlib`，尚未实现 LZ4/Zstd。
3. 当前 RGB 输入使用相机 MJPG，再硬编成 H.264；1080p@30 已在本机启动验证。
4. 当前只按一台相机 `cam02` 配置验证。
5. 接收端未启动时，发送端会继续采集，但媒体 TCP 会报 `Connection refused` 并周期重试。
6. Orbbec SDK 停流时会输出若干 USB timeout warning，当前观察为 SDK 退出阶段日志，不影响本次采集验证结果。
