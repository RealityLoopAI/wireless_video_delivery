# RTP/UDP RGB 预览拆通道实现说明

日期：2026-06-18

## 本次实现范围

本次先落地第一阶段：只把低码率 Web RGB 预览流 `rgb_preview` 从媒体 TCP 中拆到独立 UDP 通道。

- 状态心跳仍是 UDP `50011`。
- 主媒体录制链路仍是 TCP `50010`，继续承载 `rgb` 和 `depth_raw`。
- Web RGB 预览新增 UDP `50012`，只承载 `rgb_preview`。
- 接收端收到 UDP `rgb_preview` 后只更新网页预览，不写 NAS，不改变下游录制文件格式。

## 配置项

发送端：

```json
"web_rgb_preview": {
  "enabled": true,
  "max_width": 640,
  "max_height": 360,
  "fps": 30,
  "bitrate_bps": 500000,
  "udp_enabled": true,
  "udp_port": 50012,
  "udp_mtu_bytes": 1200
}
```

接收端：

```json
"preview_udp_enabled": true,
"preview_udp_bind_ip": "0.0.0.0",
"preview_udp_port": 50012
```

## 数据流

发送端继续用独立低码率 H.264 编码器生成 `StreamType::rgb_preview`。当 `udp_enabled=true` 时：

1. `rgb_preview` 不再写入媒体 TCP。
2. 发送端按 `udp_mtu_bytes` 分片，每片带工程内 RTP-style 头。
3. 接收端按发送端地址和 sequence 重组。
4. 重组完成后解析为原有 `MediaPacket`，进入现有 RGB 预览解码路径。

丢包处理：1 秒内未收齐的预览帧直接丢弃，等待下一帧或下一 IDR。这样网络抖动表现为预览丢帧，而不是 TCP 队头阻塞导致整条预览链路卡死。

## 当前取舍

优势：

- Depth 大包堵塞 TCP 时，低码率 RGB Web 预览仍有独立 UDP 通道。
- 不改变 NAS 落盘和下游 `frames.csv` 字段。
- 可按发送端逐步启用，便于现场灰度验证。

限制：

- 当前是工程内 RTP-style 分片头，不是完整 RFC RTP/H264 payload。
- UDP 预览不保证每帧必达，正式录制仍以 TCP 主媒体流为准。
- 主 RGB/Depth 录制链路仍可能 TCP 背压，后续要继续拆 RGB 主流或 Depth 通道。

## 验收点

1. 接收端状态 `/api/status` 能看到 `preview_udp_enabled=true` 和 `preview_udp_port=50012`。
2. 发送端日志中 `rgb_preview_sent_packets_s` 接近配置 FPS。
3. 树莓派 TCP `Send-Q` 堵塞时，网页 RGB 预览不应长期冻结。
4. NAS 录制目录中不应新增 `rgb_preview` 录制文件，`frames.csv` 格式保持兼容。
