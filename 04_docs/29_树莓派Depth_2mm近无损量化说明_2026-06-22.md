# 树莓派 Depth 2mm 近无损量化说明

日期：2026-06-22

## 背景

树莓派 Gemini305 当前使用 RGB `1280x800@30`、Depth `1280x800@30`。现场实测中，Depth 相机采集可以稳定接近 30fps，但发送端经过 zlib 压缩后实际发送通常只有约 18-23fps，接收端 10 秒计数约为 RGB 29.9fps、Depth 20.0fps。

主要瓶颈不在 NAS 空间，也不在相机采集，而在树莓派端 Depth 压缩/发送负载和 Depth 数据量。硬件环境暂不调整时，需要降低 Depth payload 的熵和码率。

## 实验方案

新增发送端配置项：

```json
"depth_transport": {
  "compression": "rvl",
  "quantization_step_mm": 2
}
```

含义：

- `quantization_step_mm=0`：默认，不做量化。
- `compression=rvl`：使用面向 Depth 图的轻量差分/游程/变长编码，降低 CPU 压缩开销。
- `quantization_step_mm=2`：发送端在压缩前把非零 `uint16` Depth 值按 2mm 步长四舍五入。
- 无效深度值 `0` 保持为 `0`。
- 帧尺寸、帧率配置、`frame_id`、设备时间戳、系统时间戳都不改变。
- 接收端解压后仍然得到 `uint16 little-endian` Depth 帧，NAS 中 Depth 仍按 `gray16le`/FFV1 MKV 写入。

## 对下游的影响

下游读取方式不变，仍按原来的 `depth.mkv`、`frames.csv`、`meta.json` 使用。

差异是 Depth 数值精度：

- 原始值约按 1mm 粒度变化。
- 量化后按 2mm 粒度变化。
- 最大绝对误差约 1mm。

这不会改变 RGBD 空间对齐关系，也不会改变相机内参外参；只会让深度 Z 值略微规整。对可视化和一般 RGBD 对齐应可接受，但如果下游做亚毫米级几何分析，需要确认误差预算。

发送端 `camera_announce.depth_profile` 会带 `compression=rvl` 以及：

```json
"quantization_step_mm": 2,
"quantization_max_error_mm": 1.0
```

接收端 `meta.json` 中也会保留 `camera_announce_raw`，可追溯本段录制使用的深度量化参数。

## 现场实测结论

2026-06-22 当前硬件和 Wi-Fi 环境下，测试结果如下：

- 原 `zlib`：Depth 采集约 30fps，接收端 Depth 约 20fps。
- `zlib + 2mm`：Depth 码率下降到约 75-100Mbps，但接收端 Depth 约 14fps，未达标。
- `rvl + 2mm`：接收端短时间收到 RGB/Depth 包后主媒体连接断开，树莓派 Wi-Fi/SSH 随后不可达，不能作为默认方案。
- `qdelta + 2mm`：CPU 开销很低，但单帧 payload 接近原始大小，约 2.05MB/帧，TCP backpressure 严重，接收端 10 秒 Depth 增量为 0，未达标。

因此当前仓库默认配置仍保持稳定的 `compression=zlib`，RVL/qdelta 编解码代码只作为后续实验能力保留。要求 Depth `1280x800@30` 完整落盘时，当前软件方案尚未验证通过。

## 验收指标

改动部署后重点看发送端日志：

```text
depth_input_fps
depth_sent_fps
depth_mbps
depth_compress_avg_ms
depth_send_failures
```

目标：

- `depth_input_fps` 维持约 30fps。
- `depth_sent_fps` 尽量接近 30fps。
- `depth_mbps` 相比 zlib 原方案约 120-150Mbps 明显下降。
- `depth_compress_avg_ms` 相比 zlib 原方案约 32-34ms 下降。
- `depth_send_failures` 不持续增长。

接收端验收：

1. `/api/status` 中 `depth_packets` 10 秒增量接近 300。
2. 正常停止录制后 `depth.mkv` 可打开。
3. `frames.csv` 中 Depth 帧数和时间戳连续性满足下游同步脚本要求。

## 风险和回退

如果 RVL + 2mm 量化后 Depth 仍不能接近 30fps，说明瓶颈可能还包括树莓派 CPU、TCP 主链路、接收端处理节奏。后续可继续比较：

- 4mm 量化。
- Depth 独立 UDP/RTP 实验通道，接收端按完整帧重组，坏帧丢弃并统计。
- 如果系统允许安装开发包，再比较 LZ4 或 zstd 低等级压缩。

回退方式：把 `depth_transport.compression` 改回 `zlib`，并把 `depth_transport.quantization_step_mm` 改回 `0` 或删除该字段。
