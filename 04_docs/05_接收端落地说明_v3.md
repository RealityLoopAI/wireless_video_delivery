# 接收端落地说明 v3

## 1. 当前实现范围

接收端已经落地为两个进程：

1. `gemini_receiver`：C++ 核心接收与录制服务。
2. `09_web_monitor/server.py`：FastAPI Web/REST 监控服务。

C++ 服务负责：

1. UDP `50011` 接收发送端状态 JSON。
2. TCP `50010` 接收媒体二进制 packet。
3. 本地 HTTP `127.0.0.1:18080` 提供状态和录制控制。
4. 按 `/home/fz/Desktop/nas/<camera_key>/<YYYY-MM-DD>/<HHMMSS>/` 写录制切片。
5. RGB 不重编码封装为 `rgb.mp4`，并保留 `rgb_debug.h264`。
6. Depth 按 `gray16le` 输入 FFmpeg，封装为 `depth.mkv + FFV1`，并保留 `depth_debug.raw`。
7. 生成 `meta.json` 和 `frames.csv`。

FastAPI 服务负责：

1. 提供浏览器页面。
2. 转发 REST 控制到 C++ 本地管理接口。
3. 默认监听 `0.0.0.0:8080`。

## 2. 启动方式

```bash
./05_tools/start_receiver.sh
```

状态：

```bash
./05_tools/status_receiver.sh
```

停止：

```bash
./05_tools/stop_receiver.sh
```

Web 页面：

```text
http://127.0.0.1:8080
```

在当前机器上已经验证：

2. `gemini_receiver` 可编译运行。
3. FastAPI Web 可启动。

## 5. 当前发现的问题

真实发送端当前 RGB 媒体包只有 H.264 SPS/PPS 头，未收到可封装的视频 slice，因此 `rgb.mp4` 为空，`ffmpeg.log` 会记录 `missing picture` / `dimensions not set`。

接收端已经保留 `rgb_debug.h264` 旁路文件。下一步应在发送端侧排查 GStreamer `mpph264enc` 实际输出，重点检查：

1. `appsrc` 时间戳是否被硬件编码器接受。
2. `mpph264enc` 是否实际输出 IDR/P/B slice。
3. `appsink` 拉取超时时间是否过短。
4. 是否需要增加 x264 软件 fallback。

Depth 录制链路已经闭环。
