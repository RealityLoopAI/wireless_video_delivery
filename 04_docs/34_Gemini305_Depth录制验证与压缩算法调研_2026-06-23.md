# Gemini305 Depth 录制验证与压缩算法调研

日期：2026-06-23

## 1. 当前结论

当前 Orange Pi Gemini305 正式运行配置先保持：

```text
sender:   orangepi5pro-d12a4719 / 192.168.66.133
receiver: fz-Standard-PC-i440FX-PIIX-1996 / 192.168.66.196
camera:   Orbbec Gemini305
RGB:      1280x800@30 MJPG -> H.264
Depth:    1280x800@30 Y16 -> pq8zlib + 4mm
media:    TCP 50010
preview:  UDP 50012 low bitrate preview
```

`pq8zlib + 4mm` 是当前 Gemini305 专用的精度优先低码率方案。Gemini305 官方工作范围约 `4-100cm`，`4mm * 255 = 1020mm` 可以覆盖该相机有效深度范围。未来如果换成长距离深度相机，不能直接复用 q8 + 4mm，需要按相机最大有效深度重新评估。

## 4. Web Depth 伪彩范围修正

2026-06-23 现场发现 Web Depth 伪彩预览颜色异常，画面几乎被压成同一色系。排查结果：

```text
当前相机: orangepi5pro-d12a4719_cam01 / Gemini305
当前 Depth: 1280x800@30 Y16 -> pq8zlib + 4mm
announce depth_scale: 0.1
q8 4mm 最大可表示深度: 4mm * 255 = 1020mm
原 Web Gemini305 伪彩范围: 250-6500mm
修正后 Web Gemini305 伪彩范围: 40-1000mm
```

原来的 `250-6500mm` 范围过宽，和 Gemini305 官方约 `4-100cm` 工作范围不匹配，也和当前 `q8 4mm` 的最大可表示深度不匹配，导致有效深度被压在很窄的颜色区间里。修正后只影响 Web 预览的伪彩显示，不改变发送端压缩、接收端落盘、`depth.mkv`、`frames.csv` 或时间戳。

## 5. 已验证或已实现的项目内方案

| 方案 | 精度 | 典型表现 | 当前结论 |
| --- | --- | --- | --- |
| `none` | 无损 | `1280x800@30` 原始约 `491.52Mbps` | Wi-Fi 压力太大，只适合有线或调试 |
| `zlib` | 无损或量化后无损 | 码率低，但 CPU 消耗大 | 高分辨率 30fps 容易压缩跟不上 |
| `lz4` | 无损或量化后无损 | CPU 低、帧率高，码率高 | 可救实时性，但 Wi-Fi 余量小 |
| `rvl` | 可无损/可量化 | Depth 专用，理论适合深度图 | 当前实现压缩耗时偏高，未达 30fps |
| `qdelta` | 量化后有损 | 理论上适合平滑深度图 | 当前效果不如 `pq8zlib` |
| `plz4` | 量化后有损 | 分块并行，能接近 30fps | 4mm 时码率约 137-190Mbps，仍偏高 |
| `pzlib` | 量化后有损 | 保留 16-bit 全量程 | 码率较低但仍不稳定达 30fps |
| `q8lz4` | 8-bit 深度 index | 快，但码率仍较高 | 可保留作低 CPU 实验 |
| `q8zlib` | 8-bit 深度 index | 码率低，单线程压缩接近单帧预算 | 被 `pq8zlib` 替代 |
| `pq8zlib` | 8-bit 深度 index | 分块并行 zlib，当前约 24-44Mbps | 当前 Gemini305 正式方案 |

## 6. 市面成熟压缩算法与后续尝试顺序

### 6.1 最值得优先尝试

1. `pq8zstd + 4mm`

   Zstandard 是成熟的通用无损压缩算法，压缩等级可调，通常比 zlib 有更好的速度/压缩率折中。对本工程最直接的下一步是保持当前 q8 深度 index 不变，把每块的 zlib 替换为 zstd level 1-3，目标是降低 CPU 或进一步降低码率。

   风险：接收端要新增 zstd 解码依赖；不同设备需要确认 `libzstd` 可部署。

2. `pq8lz4 + 4mm`

   LZ4 是成熟高速无损压缩算法，优势是极低延迟。它可能把 Depth 压缩时间从约 20ms 进一步降下来，但码率大概率高于 zlib/zstd。

   风险：如果码率回到 100Mbps 级别，Wi-Fi/TCP 稳定性可能又变差。

3. temporal delta + periodic keyframe + zstd/lz4

   深度视频相邻帧通常变化小，可以用前一帧作为预测，只发送 delta 或变化块，再周期性插入关键帧。成熟视频编码器本质上也在利用这个思路。

   风险：实现复杂度高，必须处理丢包、断线重连、关键帧恢复和录制可追溯性；当前 TCP 主链路可靠，但重连后仍需要完整 keyframe。

### 6.2 可作为中期路线

| 算法/路线 | 成熟度 | 适合点 | 不适合点 |
| --- | --- | --- | --- |
| Zstandard | 成熟通用库 | 替代 zlib；适合 q8 index、分块并行、可调等级 | 需要接收端依赖 |
| LZ4 | 成熟通用库 | 极低延迟；适合 CPU 紧张但网络有余量 | 压缩率通常不如 zlib/zstd |
| zlib/DEFLATE | 成熟通用库 | 依赖最普遍；当前已用 | 速度/压缩率折中不如 zstd |
| Brotli | 成熟通用库 | 静态内容压缩率好 | 实时视频帧压缩延迟通常不划算 |
| RVL | Depth 专用 | 面向深度图，结构简单，理论上很合适 | 当前实现还需并行化/优化，否则高分辨率 30fps 不够 |
| FFV1 | 成熟无损视频编码 | 很适合接收端落盘归档，当前 depth.mkv 已用 | 不适合作为发送端实时无线编码的首选，CPU/延迟压力更高 |
| H.265/HEVC 10-bit/12-bit | 成熟视频编码 | 码率可能很低，可利用时域预测 | 深度值要映射到视频像素，需防止色彩范围、量化和滤波破坏深度语义；硬编支持不确定 |
| AV1 10-bit/12-bit | 成熟开放视频编码 | 压缩率强 | 软件编码太重，实时端不优先 |
| JPEG XL | 成熟图像格式 | 支持高位深、无损/近无损 | 实时流式生态和硬件支持弱 |
| PNG | 成熟图像格式 | 16-bit 深度兼容性好 | 单帧实时压缩太慢，容器开销也不适合 30fps |
| Draco / mesh compression | 成熟几何压缩 | 适合点云/网格归档或离线传输 | 不适合当前按像素 RGBD 帧同步录制 |

### 6.3 不建议立即做的路线

- 不建议马上把 Depth 直接编码成普通 H.264 8-bit 灰度视频。这样码率低，但深度数值语义会被视频量化、色彩范围、去块滤波和运动补偿破坏。
- 不建议在还没做关键帧/重同步机制前上强时域预测。只要中间丢一帧，后续帧可能全依赖错误参考帧。
- 不建议继续单纯增大 TCP buffer 作为主要优化手段。它能缓解短抖动，但不能降低真实链路负载，反而会增加延迟和故障恢复时间。

## 7. 推荐后续实验计划

1. 基线保持 `pq8zlib + 4mm`，继续做长时间录制和下游 RGBD 对齐验证。
2. 新增 `pq8zstd + 4mm`，只替换压缩内核，不改变 wire format 的深度语义。
3. 对比 `pq8zlib` 与 `pq8zstd`：

```text
depth_sent_fps
depth_mbps
depth_compress_avg_ms
sender CPU
receiver CPU
TCP Send-Q / Recv-Q
frames.csv 单调性
depth.mkv 可读帧数
下游对齐结果
```

4. 如果 zstd 无明显收益，再试 `pq8lz4 + 4mm`，目标是换取更低 CPU。
5. 只有在 q8 系列不能满足长期稳定时，再做 temporal delta + keyframe。
