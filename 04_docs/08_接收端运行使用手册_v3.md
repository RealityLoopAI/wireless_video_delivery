# 接收端运行使用手册 v3

更新时间：2026-06-05

本文档说明 Ubuntu 接收端的启动、停止、状态检查、录制控制、NAS 落盘和 Orbbec 兼容导出。

## 1. 适用范围

接收端运行在 Ubuntu x86_64 主机上，负责：

- 监听发送端 UDP 状态包和 TCP 媒体包。
- 提供 C++ 本地管理 API。
- 提供 Web 监控页面。
- 控制录制并写入 NAS。
- 将录制 segment 离线导出为下游 Orbbec 兼容交付目录。

## 2. 默认配置

配置文件：

```text
06_configs/receiver_ubuntu-01.json
```

当前默认端口：

```text
media tcp: 50010
status udp: 50011
admin http: 127.0.0.1:18080
web: 0.0.0.0:8080
```

当前默认 NAS 根目录：

```text
/home/fz/Desktop/nas
```

## 3. 一键启动、停止、状态

启动：

```bash
./05_tools/start_receiver.sh
```

停止：

```bash
./05_tools/stop_receiver.sh
```

查看状态：

```bash
./05_tools/status_receiver.sh
```

如果要使用非默认配置：

```bash
./05_tools/start_receiver.sh 06_configs/receiver_ubuntu-01.json
./05_tools/status_receiver.sh 06_configs/receiver_ubuntu-01.json
```

启动脚本会自动：

1. 检查 `cmake`、`g++`、`ffmpeg`、`python3`。
2. 编译 `gemini_receiver`。
3. 创建 Web 监控 Python venv。
4. 优先通过 `systemd --user` 启动 C++ 接收端。
5. 优先通过 `systemd --user` 启动 Web 监控服务。
6. 启动前检查并轮转过大的接收端日志。

当前推荐先安装持久化自启动服务：

```bash
./05_tools/install_receiver_autostart.sh
```

安装后会创建并启用以下用户服务：

```text
gwv3-gemini-receiver.service
gwv3-web-monitor.service
gwv3-receiver-log-rotate.timer
```

服务特性：

- 接收端或 Web 异常退出后由 systemd 自动重启。
- 接收端和 Web 不再挂在终端 scope 下，避免终端被 OOM 清理时把接收端一起杀掉。
- 接收端服务设置 `MemoryHigh=3G`、`MemoryMax=4G`。
- Web 服务设置 `MemoryHigh=384M`、`MemoryMax=512M`。
- 日志轮转 timer 每 10 分钟检查一次日志文件，超过 256MB 自动归档。

如果要卸载自启动服务：

```bash
./05_tools/uninstall_receiver_autostart.sh
```

如果要求机器开机后未登录桌面也自动启动，需要额外启用 user linger：

```bash
sudo loginctl enable-linger fz
```

如果不启用 linger，服务会在用户登录后自动启动。

## 4. Web 页面

默认访问：

```text
http://127.0.0.1:8080
```

页面能力：

- 查看发送端在线状态。
- 查看 RGB/Depth packet 和字节计数。
- 左侧主画面同时查看 RGB 和 Depth 实时预览。
- 右侧查看除主画面外其他在线相机的 RGB/Depth 预览。
- 点击右侧卡片切换主画面。
- 全局开始/停止录制。
- 单相机开始/停止录制。
- 相机自命名、本路文件名前缀、当前保存目录和高级状态位于底部折叠设置区。

## 6. NAS 落盘目录

每段录制写入：

```text
<nas_root>/<sender_id>_<camera_id>/<YYYY-MM-DD>/<HHMMSS>/
```

典型文件：

```text
rgb.mp4
depth.mkv
frames.csv
calibration.json
meta.json
ffmpeg.log
rgb_debug.h264
depth_debug.raw
```

格式细节见：

```text
04_docs/06_接收端当前存储格式说明_v3.md
```

如果后续需要生成 RGB 坐标系下的 aligned depth，可在录制完成后运行：

```bash
python3 05_tools/align_depth_to_rgb.py <segment_dir>
```

该命令会读取同一 segment 的 `depth.mkv` 和 `calibration.json`，输出 `depth_aligned_to_rgb.mkv`。脚本会校验 RGB/Depth 内参与当前视频/profile 尺寸一致，并拒绝 D2C 外参缺失或全 0 的数据。

## 7. Orbbec 兼容导出

如果下游工程师能直接读取 RGB 和 Depth 录像，推荐只导出 Orbbec 风格的 JSON/CSV/预览文件，不默认展开逐帧 PNG。

导出命令：

```bash
./05_tools/export_orbbec_delivery.py <segment_dir> --overwrite
```

示例：

```bash
./05_tools/export_orbbec_delivery.py \
  /home/fz/Desktop/nas/orangepi5pro-b439137c_cam02/2026-05-11/180433 \
  --overwrite
```

默认输出：

```text
<segment_dir>/orbbec_delivery/<session_name>/
```

如果下游强制要求逐帧 `uint16 PNG`：

```bash
./05_tools/export_orbbec_delivery.py <segment_dir> --export-depth-png --overwrite
```

详细说明见：

```text
04_docs/07_Orbbec交付导出说明_v3.md
```

## 8. 录制帧率分析

接收端录制时会按前几帧真实到达间隔估算封装帧率，并写入 `meta.json` 的 `rgb_record_fps` / `depth_record_fps`。

如果本地播放感觉帧率低，不要只看播放器显示的标称 fps，应同时分析 `frames.csv` 里的真实到达帧率。

分析命令：

```bash
./05_tools/analyze_segment_fps.py <segment_dir>
```

示例：

```bash
./05_tools/analyze_segment_fps.py \
  /home/fz/Desktop/nas/orangepi5pro-b439137c_cam02/2026-05-12/102013
```

重点看：

- `media`：文件封装后的编码、分辨率、标称 fps、码率。
- `arrival`：接收端真实收到的 RGB/Depth 帧率。
- `intervals`：帧间隔抖动，`p95` 和 `>50ms` 越大，播放观感越卡。

## 9. 常见问题

### 9.1 Web 页面打不开

先执行：

```bash
./05_tools/status_receiver.sh
```

确认 C++ 接收端和 Web 监控都在运行。如果管理接口不可用，查看：

```text
08_reports/receiver_logs/receiver.log
08_reports/receiver_logs/receiver_stdout.log
08_reports/receiver_logs/web_stdout.log
```

### 9.2 没有 RGB 预览

RGB 预览依赖发送端持续输出可解码 H.264 帧。接收端刚启动后需要等到新的关键帧或完整帧进入预览解码器。

### 9.3 录制目录没有 `rgb.mp4`

可能录制时长过短，或者发送端没有输出可封装的 H.264 视频帧。检查 `ffmpeg.log` 和 `rgb_debug.h264`。

### 9.4 Depth CSV 的 `pair_delta_ms` 很大

RGB 和 Depth 的 SDK timestamp 可能不是同一时间基准。后续对齐应优先使用新增的 `*_system_timestamp_us` 字段和接收端 `local_time_us`。

### 9.5 播放器帧率和观感不一致

接收端会按实测到达帧率封装录像，避免把十几帧的源流强行标成 30fps 导致本地播放速度异常。真实流畅度仍取决于发送端实际送达帧率。用 `analyze_segment_fps.py` 检查 `arrival fps`；如果 `arrival fps` 只有十几帧，应优先排查发送端采集、编码、Depth 压缩、预览和网络链路。

### 9.6 接收端突然全部停止

先执行：

```bash
./05_tools/status_receiver.sh
```

如果 C++ 接收端和 Web 都不在，检查 systemd 日志：

```bash
journalctl --user -u gwv3-gemini-receiver.service -u gwv3-web-monitor.service --since "1 hour ago" --no-pager
journalctl --since "1 hour ago" --no-pager | grep -Ei "oom|killed|gwv3|gemini|receiver"
```

2026-06-04 现场出现过一次 `systemd-oomd` 因内存压力杀掉终端 scope，导致接收端、Web 和 ffmpeg 预览进程一起退出。2026-06-05 已通过 systemd 用户服务、自动重启、内存上限和日志轮转加固。

### 9.7 Web 预览 CPU 高

当前 RGB 预览链路使用 ffmpeg 解码 H.264 到 MJPEG 图片流：

```text
ffmpeg -f h264 -i pipe:0 -vf fps=10,scale=640:-2 -q:v 3 -f image2pipe -vcodec mjpeg pipe:1
```

主画面 RGB 为高清预览，缩略图 RGB 为 640 宽预览。Depth 预览由接收端生成伪彩图片。

录制保存 `rgb.mp4` 使用 H.264 copy 封装，不需要 RGB 解码；CPU 压力主要来自网页预览，不是录像保存。

### 9.8 ffmpeg 预览是否使用硬件解码

当前未启用硬件解码。现场 x86 接收端环境检测结果：

- ffmpeg 编译支持 `vaapi`、`qsv`、`cuda` 等接口。
- 当前机器显示为虚拟显卡 `Device 1234:1111`。
- 未发现 NVIDIA 设备。
- `/dev/dri` 未看到常见的 `renderD128`。
- 未安装 `vainfo`，VAAPI 能力无法验证。

因此当前环境不适合直接开启 `-hwaccel vaapi/qsv/cuda`。如果要启用硬解，需要先确认接收端有真实 GPU/核显或虚拟机 GPU 直通，再调整 `RgbPreviewDecoder` 的 ffmpeg 参数。

## 10. 稳定运行建议

推荐配置：

```bash
./05_tools/install_receiver_autostart.sh
./05_tools/status_receiver.sh
```

关键检查项：

- `systemctl --user is-enabled gwv3-gemini-receiver.service gwv3-web-monitor.service gwv3-receiver-log-rotate.timer` 应返回 `enabled`。
- `systemctl --user status gwv3-gemini-receiver.service gwv3-web-monitor.service` 应显示 `active (running)`。
- `/proc/<receiver_pid>/cgroup` 应包含 `gwv3-gemini-receiver.service`，而不是 `vte-spawn-*.scope`。
- `08_reports/receiver_logs/web_stdout.log` 不应持续快速增长；Web 已默认使用 `--no-access-log`。
- `08_reports/receiver_logs/receiver.log` 的 heartbeat/status 日志已限频，常规状态不应每秒刷屏。
