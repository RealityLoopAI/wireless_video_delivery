# Web RGB 低码率独立预览流说明

日期：2026-06-15

## 背景

现场接收端网页预览出现 RGB 延迟和卡顿。检查网络连接后发现，浏览器预览原来直接消费接收端缓存的主 RGB H.264 流。主 RGB 流用于录制和下游处理，典型配置为 `1920x1080@30`、约 `12Mbps`。多发送端同时打开网页预览时，接收端到浏览器的 TCP 连接容易产生发送队列积压，表现为网页画面越来越慢、延迟变大。

这类卡顿不一定说明发送端到接收端的媒体链路已经堵塞。现场看到的主要压力在接收端 Web 预览输出侧，尤其是多路浏览器预览同时打开时。

## 改动目标

1. 不降低原始 RGB 录制质量。
2. 不降低发送端 RGB/Depth 主链路帧率。
3. 网页 RGB 预览保持 30fps，但允许降低预览码率和画质。
4. 旧发送端仍能被接收端预览，不能因为协议扩展直接不可用。

## 协议扩展

在 `03_common_core/include/gwv3_common/protocol.hpp` 中新增媒体流类型：

```cpp
enum class StreamType : uint8_t {
    rgb = 1,
    depth_raw = 2,
    rgb_preview = 3,
};
```

含义：

- `rgb`：主 RGB H.264 流，继续用于录制、下游处理和高质量数据传输。
- `depth_raw`：Depth 数据流，逻辑不变。
- `rgb_preview`：新增的 Web 预览专用 RGB H.264 流，只用于实时网页预览，不参与录制落盘。

## 发送端改动

发送端每路相机现在可以额外创建一个 Web RGB preview encoder。默认配置在 `AppConfig::web_rgb_preview` 中：

```cpp
enabled = true
max_width = 1920
max_height = 1080
fps = 30
bitrate_bps = 1200000
```

当前默认没有把预览缩到 `640x360`，而是保持输入 RGB 尺寸并把码率降到约 `1.2Mbps`。原因是现场双路 RK3588 测试时，增加缩放链路会带来额外解码、缩放和编码负担，预览帧率会从 30fps 掉到约 23-25fps。保持 `1920x1080` 低码率后，网页预览画质会下降，但帧率更接近 30fps，CPU/GPU 负担也更稳定。

发送端状态日志新增以下字段：

- `rgb_preview_sent_packets_s`
- `rgb_preview_mbps`
- `rgb_preview_send_avg_ms`
- `rgb_preview_send_failures`

发送端 heartbeat 新增以下字段：

- `rgb_preview_mbps`
- `rgb_preview_fps`
- `rgb_preview_width`
- `rgb_preview_height`

## 接收端改动

接收端为每路相机分别缓存两条 RGB H.264 流：

- `rgb_stream`：主 RGB 流。
- `rgb_preview_stream`：新增的低码率 Web 预览流。

`/api/preview/rgb-h264` 的选择逻辑：

1. 如果 `rgb_preview_stream` 新鲜可用，优先输出 `rgb_preview`。
2. 如果发送端还没有升级、没有 `rgb_preview`，自动回退输出主 `rgb`。
3. 响应头增加 `X-GWV3-Rgb-Stream`，用于现场确认实际使用的是 `preview` 还是 `main`。

接收端收到 `rgb_preview` 后只更新预览缓存和状态字段，不写入录制文件，也不计入主 RGB 包计数。这样不会改变 NAS 落盘格式，也不会影响下游读取主 RGB 和 Depth。

Web Monitor 页面仍访问：

```text
/api/preview/rgb-video?sender_id=<sender_id>&camera_id=<camera_id>
```

Web Monitor 内部会从接收端本机管理口读取：

```text
http://127.0.0.1:18080/api/preview/rgb-h264
```

所以外部直接访问 `http://<receiver>:8080/api/preview/rgb-h264` 返回 404 是正常的；浏览器应该走 `rgb-video`。

## 现场部署状态

截至 2026-06-15，本次已升级并重启：

- 接收端：`fz-Standard-PC-i440FX-PIIX-1996 / 192.168.66.196`
- 本机发送端：`rk3588-ubuntu / 192.168.66.85`
- Orange Pi 发送端：`orangepi5pro-b439137c / 192.168.66.206`
- Orange Pi 发送端：`orangepi5pro-c973b736 / 192.168.66.133`
- 树莓派发送端：`raspberrypi-01 / 192.168.66.210`，Gemini305 V4L2 分支，`1280x800@30 RGB + 320x200@30 Depth`

树莓派 Gemini305 V4L2 分支已同步本改动。接收端确认该路 `/api/preview/rgb-h264` 响应头为 `X-GWV3-Rgb-Stream: preview`，状态接口显示 `rgb_preview_width=1280`、`rgb_preview_height=800`。该路网页预览流典型为 `1.1-1.4Mbps`，主 RGB 流仍保持约 `6Mbps`，Depth 约 `15-16Mbps`。

树莓派现场还发现两个额外问题：

1. 重复 watchdog：同一仓库会被外部启动路径重复拉起，两个 `gemini_sender` 抢同一个 `/dev/video6`，导致一路正常发送、一路持续 `VIDIOC_S_FMT failed ... Device or resource busy`。`05_tools/sender_watchdog.sh` 已增加 `12_build/sender.lock` 文件锁；重复启动会记录 `another sender watchdog is already running` 并退出。`05_tools/stop_sender.sh` 已增加残留 watchdog 清理。
2. 发送缓冲上限过低：树莓派 `net.core.wmem_max` 原来只有 `1048576`，导致配置里的 `transport.send_buffer_bytes=4194304` 实际只能得到约 `1MB` 用户态发送容量，日志表现为 `media TCP packet dropped under backpressure ... capacity_bytes=1048576`。现场已写入 `/etc/sysctl.d/99-gwv3-network-buffers.conf` 并应用：

```text
net.core.wmem_max = 8388608
net.core.wmem_default = 1048576
net.core.rmem_max = 16777216
net.core.rmem_default = 1048576
```

重启树莓派发送端后，`ss -tinmp` 确认该路媒体 socket 为 `tb8388608`，连续观察未再出现新的 backpressure 丢包。

## 验证结果

接收端本机管理口验证：

```bash
curl -sD - 'http://127.0.0.1:18080/api/preview/rgb-h264?sender_id=rk3588-ubuntu&camera_id=cam01' -o /dev/null
```

升级后的发送端返回：

```text
X-GWV3-Rgb-Stream: preview
```

树莓派 Gemini305 V4L2 分支返回：

```text
X-GWV3-Rgb-Stream: preview
```

`/api/status` 中，RK3588/Orange Pi 设备的 `rgb_preview_width/rgb_preview_height` 为 `1920x1080`，树莓派 Gemini305 为 `1280x800`，并且 `rgb_preview_age_ms` 持续保持新鲜。发送端日志中，典型预览流约为每路 `1.0-1.4Mbps`、接近 `30fps`。

现场检查 TCP 队列时，已升级设备的 Web 预览流量明显下降。多数接收端 Web 预览长连接的 `Send-Q` 可保持为 0；如果浏览器端存在旧页面、后台页面或慢客户端，仍可能看到某条 `8080` 连接出现 `Send-Q` 积压。此时积压位于接收端到浏览器的输出侧，关闭或刷新浏览器页面、重启 Web Monitor 后会释放旧连接。现场还发现旧 ffmpeg 预览子进程可能拖住 Web Monitor 停止流程，因此 `install_receiver_autostart.sh` 生成的 Web Monitor systemd 服务已增加 `KillMode=mixed`、`TimeoutStopSec=5s`、`SendSIGKILL=yes`，后续重启时会更快清理旧预览进程。发送端到接收端 `50010` 媒体连接偶发几十到一百多 KB 队列，属于瞬时波动，不是之前网页预览持续积压的状态。

## 后续优化方向

如果后续仍希望进一步降低网页预览带宽，可以考虑：

1. 将 Web 预览从当前 fragmented MP4 代理改成更标准的视频流方案，例如 WebRTC 或低延迟 HLS/LL-HLS。
2. 在发送端增加真正的预览帧率控制和可选缩放策略，但要以现场 RK3588 双路 30fps 压测为准。
3. 在 Web 页面增加每路实际使用流类型显示，例如 `preview/main`，便于现场排查。
4. 将树莓派上的 `/etc/sysctl.d/99-gwv3-network-buffers.conf` 同步到其他发送端，保证 `send_buffer_bytes=4194304` 能真正生效。
