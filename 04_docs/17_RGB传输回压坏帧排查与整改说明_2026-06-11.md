# RGB 传输回压坏帧排查与整改说明

日期：2026-06-11

## 背景

现场三路录制包含：

- `raspberrypi-01_cam01`
- `rk3588-ubuntu_cam01`
- `rk3588-ubuntu_cam02`

用户反馈新拍视频里坏帧较多，主要集中在另一个发送端，即 `raspberrypi-01_cam01`。排查对象为接收端 NAS 目录和树莓派发送端日志。

## 现象与证据

异常录制段：

```text
/home/fz/Desktop/nas/raspberrypi-01_cam01/2026-06-11/141402
```

该段接收端 `meta.json` 统计：

```text
segment_start_us=1781158442777660
segment_end_us=1781158536046864
rgb_frames=929
rgb_actual_fps=9.969
rgb_record_fps=30.042
rgb_target_duration_sec=93.084
rgb_retime_scale=3.013
```

也就是说，该段真实录制时间跨度约 93 秒，但 RGB 实际只到达约 10fps。接收端按约 30fps 建立 MP4 时，播放时长被压到约 30.7 秒，导致肉眼看到画面卡顿、时间戳和画面不同步。

接收端日志在同一时间连续出现：

```text
media client disconnected from=192.168.66.210 ... reason=connection closed while reading payload
```

树莓派发送端日志在同一时间连续出现：

```text
media TCP packet dropped under backpressure pending_bytes~=4MB capacity_bytes=4194304
rgb_sent_packets_s=4.99
depth_sent_fps=4.00
rgb_send_failures>0
depth_send_failures>0
```

同时树莓派采集侧仍保持：

```text
rgb_input_fps~=30
depth_input_fps~=30
rgb_corrupt_jpeg_frames=0
```

结论：这次坏帧不是相机原始 RGB MJPEG 坏帧，也不是 USB 采集掉到低帧率，而是媒体 TCP 传输发生回压后主动丢包和重连。

## 根因

### 1. H.264 参考帧链断裂

当前 RGB 使用 H.264。发生 TCP 回压时，发送端可能丢掉一个或多个 RGB H.264 packet。若丢掉的是 P 帧，后续 P 帧仍依赖已经缺失的参考帧，接收端解码就可能出现花屏、破块或短时间坏帧，直到下一个 IDR 关键帧恢复。

### 2. 接收端写 NAS 的压力过高

接收端 `nas_root=/home/fz/Desktop/nas` 实际挂载到网络共享：

```text
//192.168.66.149/video_database
```

异常排查时配置开启了：

```json
"write_debug_h264": true,
"write_debug_depth_raw": true
```

正式录制时如果继续开启，会同时写：

- `rgb.mp4`
- `rgb_debug.h264`
- `depth.mkv`
- `depth_debug.raw`
- `frames.csv`
- `rgb_recorded_frames.csv`

其中 `depth_debug.raw` 体积最大，长录会快速达到 GB 级。接收端同一时间要接收多个发送端 TCP、运行多个 ffmpeg、再通过 SMB 写网络 NAS，容易触发发送端 TCP 发送缓存堆满。

## 本次整改

### 发送端

新增 RGB 关键帧恢复保护：

1. 任意 RGB 媒体包发送失败或因 TCP 回压被丢弃时，标记该 camera 进入 `waiting_for_keyframe` 状态。
2. 在该状态下，后续非 IDR H.264 帧不再发送。
3. 等待下一帧 IDR 到来，成功恢复发送后清除状态。

这样可以避免“丢了一个 P 帧后继续发送一串依赖坏参考帧的 P 帧”，把坏帧影响限制到一次回压后的短窗口。

涉及文件：

```text
01_sender_linux/src/main.cpp
```

### 接收端

正式配置默认关闭大体量 debug/raw 落盘：

```json
"write_debug_h264": false,
"write_debug_depth_raw": false
```

同时接收端代码默认值也改为 false，避免某台设备漏配字段时又默认打开。

涉及文件：

```text
02_receiver_linux/src/main.cpp
06_configs/receiver_ubuntu-01.json
02_receiver_linux/README.md
```

## 使用建议

正式录制时保持：

```json
"write_debug_h264": false,
"write_debug_depth_raw": false
```

只有在排查编码边界、MP4 修复、深度原始值问题时，才临时打开 debug 文件。打开后应缩短录制时间，并优先写本地盘，不建议直接长时间写网络 NAS。

如果后续仍出现回压，应优先检查：

1. 接收端 CPU 和 `ffmpeg` 进程数量。
2. 接收端 `/home/fz/Desktop/nas` 是否仍为网络共享。
3. 接收端 `iowait`、SMB 写入延迟和网卡 TCP RTT。
4. 发送端日志中的 `media TCP packet dropped under backpressure` 和 `rgb_send_failures`。

## 当前边界

本次整改能降低坏帧扩散和 NAS 写入压力，但不能消除所有网络拥塞。如果无线链路或网络 NAS 持续拥塞，仍会发生降帧。此时应降低总码率、减少同时录制路数，或将接收端先写本地 SSD，录完再异步同步到 NAS。

## 现场补充：RK 本机 cam01 USB3 深度枚举失败

2026-06-11 15:10 左右，在 RK 本机重新验证双路发送时，`rk3588-ubuntu_cam01` 仍无法上线。接收端状态显示：

```text
rk3588-ubuntu_cam01 live False
last_error=No required type sensor found! sensorType: OB_SENSOR_DEPTH
```

本机发送端日志同步出现：

```text
camera reconnect failed camera_id=cam01 error=No required type sensor found! sensorType: OB_SENSOR_DEPTH
```

进一步停止发送端并只对 cam01 所在 USB 路径做软重枚举：

```text
cam01 RGB:   9-1.1, serial=AY2M54302ZH
cam01 Depth: 10-1.2
```

结果 RGB 功能能重新枚举，但 USB3 深度功能无法重新上线。内核日志显示：

```text
usb 10-1.2: Device not responding to setup address
usb 10-1.2: device not accepting address, error -71
usb 10-1-port2: unable to enumerate USB device
```

结论：这是 cam01 的 USB3 深度链路在内核层枚举失败，不是发送端进程占用，也不是本次 H.264 传输保护逻辑导致。软件重启发送端无法恢复该状态，需要物理处理：

1. 重新插拔 cam01 的 USB3 线。
2. 优先更换 USB3 线或换到另一个独立 USB3 口。
3. 插回后先确认 `lsusb -t` 中 cam01 同时出现 USB2 RGB 和 USB3 Depth，再启动发送端。

cam02 在同一轮验证中可正常采集：

```text
rgb_input_fps~=30
depth_input_fps~=30
rgb_corrupt_jpeg_frames=0
```
