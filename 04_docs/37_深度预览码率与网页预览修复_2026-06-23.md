# 深度预览码率与网页预览修复记录

日期：2026-06-23

## 背景

现场三路 RGBD 发送时，网页预览出现过以下问题：

- 浏览器提示 WebCodecs 不可用后，RGB 预览回退链路延迟高、画面比例异常。
- 小窗口或主画面偶发不刷新。
- Gemini305 深度伪彩偏蓝或映射不对。
- 深度传输码率高时，发送端 TCP 队列回压，RGB 帧率被拖低。

本次目标是先恢复网页预览可用性和深度伪彩正确性，同时保留后续继续优化深度压缩的入口。

## 发现的问题

### 1. WebCodecs fallback 路径不适合现场预览

网页端在 WebCodecs 不可用时曾尝试走 MP4/H.264 fallback。这个路径会引入较高缓冲延迟，并且依赖接收端额外的 ffmpeg/remux 进程。现场表现为：

- RGB 延迟明显；
- 画面比例异常；
- 浏览器刷新或切换主画面后可能残留进程；
- 小窗口帧率不稳定。

### 2. 接收端 RGB 预览源切换导致 decoder 重启

接收端同时存在主 RGB 流和独立 `rgb_preview` 流时，JPEG 预览 fallback 会根据最近更新时间在两个源之间切换。源切换会导致解码器重启，表现为网页预览卡顿、404 或画面停住。

### 3. `pq8zlib` 深度量化 raw step 固定为 1

`pq8zlib` 会把 16bit 深度压到 8bit 后再 zlib 压缩。之前 raw step 固定为 1，等价于最大只能表达 255 个 raw 单位。

对 Gemini305 这类 `depth_scale=0.1mm/raw` 的相机，最大可表达深度只有约 25.5mm；对 `depth_scale=1.0mm/raw` 的相机，也只有约 255mm。这会让正常深度值在接收端被截断，伪彩映射几乎全落在低值区间。

## 本次修复

### 1. 禁用 MP4 RGB fallback

`09_web_monitor/server.py` 中 `/api/preview/rgb-video` 改为返回 410，网页端刷新后不再使用 MP4 fallback。WebCodecs 不可用时，网页回退到 JPEG still preview。

这样牺牲了浏览器端视频解码路径，但降低了延迟和进程残留风险，更适合当前现场调试。

### 2. 固定 RGB JPEG fallback 的有效源

`02_receiver_linux/src/main.cpp` 增加 `last_rgb_preview_packet_us`，接收端用独立 `rgb_preview` 包时间判断预览流是否可用，避免主 RGB 与预览 RGB 反复切换。

### 3. 增加深度量化步长配置

发送端新增：

```json
"depth_transport": {
  "compression": "pq8zlib",
  "quantization_step_mm": 10
}
```

代码会根据 SDK 的 `depth_scale` 把毫米级量化步长转换成 raw step。例如：

- `depth_scale=1.0mm/raw`，`quantization_step_mm=10` 时 raw step 为 10。
- `depth_scale=0.1mm/raw`，`quantization_step_mm=10` 时 raw step 为 100。

这样 `pq8zlib` 的 8bit 值可以覆盖到约 2.55m 量级，深度伪彩不再因为表达范围过小而整体偏蓝。

### 4. 保留其他深度压缩实验入口

本次代码中保留了 `qdelta` 和 `pq12zlib` 的实现入口，便于后续继续测试更高精度或更低码率的深度编码方案。当前现场实跑仍以 `pq8zlib` 为主。

## 4mm 与 10mm 的取舍

之前 `pq8zlib + 4mm` 现场观感确实更细，深度可视化也更接近原始深度。但在当前组合下需要注意：

- 当前深度档位是 `1280x800@30`，比低分辨率深度流压力大很多。
- OrangePi 当前 Wi-Fi 发送速率会波动，深度码率一高就容易产生发送队列回压。
- 4mm 比 10mm 保留更多深度细节，通常也会让压缩后码率升高。
- 回压一旦出现，RGB 也会被拖慢，表现为网页 RGB 延迟和帧率下降。

因此当前建议：

- 稳定性优先：先用 `pq8zlib + 10mm`。
- 近距离深度细节优先，且网络余量足够：可回到 `pq8zlib + 4mm` 做单独验收。
- 如果要求 1mm 到 4mm 精度、30fps、低码率同时满足，后续应继续做专用深度编码，而不是只靠 `pq8zlib` 参数硬调。

## 当前现场档位

本机 `rk3588-ubuntu` 双路：

```text
cam01/cam02
RGB:   1280x720@30, MJPG -> H.264, 约 12Mbps/路
Depth: 1280x800@30, pq8zlib, 当前默认 10mm 量化
曝光:  手动 exposure=312, gain=80
```

OrangePi `orangepi5pro-d12a4719` 单路 Gemini305：

```text
cam01
RGB:   1280x800@30, MJPG -> H.264, 约 6Mbps
Depth: 1280x800@30, pq8zlib, 当前 10mm 量化
曝光:  自动曝光默认参数
网络:  666666-5G
```

最近一次接收端采样：

```text
orangepi5pro-d12a4719_cam01 rgb_fps 22.9 rgb_mbps 4.8 depth_fps 25.9 depth_mbps 58.5
rk3588-ubuntu_cam01         rgb_fps 30.9 rgb_mbps 12.4 depth_fps 18.9 depth_mbps 12.7
rk3588-ubuntu_cam02         rgb_fps 30.9 rgb_mbps 12.4 depth_fps 17.3 depth_mbps 11.8
```

结论：RGB 主链路已明显恢复；深度全分辨率传输仍是主要瓶颈。OrangePi 深度码率最高，网络波动时会优先影响这一路 RGB。

## 后续建议

1. 继续把网页预览与录制主链路隔离，预览只做低码率、低延迟、可丢帧显示。
2. 深度传输继续做专用编码，候选方向包括 RVL、delta + entropy coding、分块并行、12bit packing、深度 PNG/Zstd、专用 ROI/无效值 run-length。
3. 对 4mm 做独立 A/B 测试：同一网络、同一分辨率、同一预览状态下比较 RGB fps、Depth fps、TCP backlog、接收端落盘完整性。
4. 录制优先场景仍建议关闭网页预览或只保留单主画面预览，避免预览负载影响落盘。
