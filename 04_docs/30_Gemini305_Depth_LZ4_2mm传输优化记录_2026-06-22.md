# Gemini305 Depth LZ4 2mm 传输优化记录

日期：2026-06-22

## 1. 背景

现场设备 `orangepi5pro-d12a4719` 更换为 Orbbec Gemini305 后，目标档位为：

```text
RGB   1280x800@30 MJPG
Depth 1280x800@30 Y16
接收端 192.168.66.196
状态通道 UDP 50011
媒体通道 TCP 50010
Web 预览 UDP 50012
```

Depth 原始数据量约为：

```text
1280 * 800 * 16bit * 30fps = 491.52 Mbps
```

在 Wi-Fi 链路上直接发送压力过大，因此本轮重点尝试 Depth 专用压缩，并保持下游落盘仍为 `uint16 gray16le` 深度帧。

## 2. 本轮改动

发送端：

- 新增 `depth_transport.compression = "lz4"` 支持。
- 运行时动态加载 `liblz4.so.1`，使用 `LZ4_compress_fast` 压缩深度 payload。
- `sender_hello` capabilities 增加 `lz4`。
- 修复压缩分支判断，`qdelta` 和 `lz4` 不再误走未压缩发送路径。
- 当前配置文件：`06_configs/sender_orangepi5pro-d12a4719_gemini305.json`。

接收端：

- 新增 `lz4` 深度包解码。
- 运行时动态加载 `liblz4.so.1`，使用 `LZ4_decompress_safe` 恢复深度 payload。
- 解码后继续按原始 `uint16` 深度写入视频和 `frames.csv`，下游文件接口不变。

当前关键配置：

```json
{
  "transport": {
    "media_protocol": "tcp",
    "send_buffer_bytes": 33554432
  },
  "depth_transport": {
    "compression": "lz4",
    "quantization_step_mm": 2
  },
  "rgb_profile": {
    "width": 1280,
    "height": 800,
    "fps": 30,
    "format": "mjpg"
  },
  "depth_profile": {
    "width": 1280,
    "height": 800,
    "fps": 30,
    "format": "y16"
  }
}
```

注意：当前 `lz4` 路径主要解决实时吞吐，实际压缩后深度码率仍明显高于 `zlib` 和 `rvl`；它的优势是 CPU 延迟更低，更容易接近 30fps。

## 3. 压缩方案实测对比

| 方案 | 现象 | 结论 |
| --- | --- | --- |
| `qdelta + 2mm` 修复前 | 实际接近原始大包，单帧约 2.05MB，TCP 快速堆积 | 不可用，已修复误走未压缩分支的问题 |
| `qdelta + 2mm` 修复后 | 接收端约 16fps，Depth 约 129Mbps | 码率较低，但实时性不够 |
| `rvl + 2mm` | Depth 约 11-12fps，约 63-69Mbps | 码率最低，但 CPU 压缩瓶颈明显 |
| `zlib + 2mm` | Depth 约 22-23fps，约 99-104Mbps | 稳定性较好，但达不到 30fps |
| `lz4 + 2mm` | Depth 约 29.9-31fps，约 210-249Mbps | 当前最接近 30fps，但无线余量较小 |

## 5. 风险和结论

当前 `lz4 + 2mm` 可以在接收端看到接近 30fps 的 RGB 和 Depth，且最新短窗口正常。但是这不是一个余量很大的方案：

- Depth 码率仍有约 210-249Mbps。
- Wi-Fi 标称 433Mbps，但实际可用吞吐会随干扰、重传、AP 调度和接收端处理抖动下降。
- 日志中曾出现 `bulk media TCP packet dropped under backpressure`，说明 TCP 发送队列会在突发抖动时顶到阈值。
- 当前媒体仍走 TCP，队头阻塞会让 Depth 的突发大包影响整体实时性。

因此当前结论是：

```text
如果优先保持 1280x800 Depth 采集 30fps，当前首选 lz4 + 2mm。
如果优先绝对少丢包和长时间稳定，zlib + 2mm 更稳但只能约 22-23fps。
如果后续必须同时满足 30fps 和长时间零背压，应继续做媒体链路拆分或 UDP/RTP 化。
```

## 6. 后续优化方向

1. 将 RGB、Depth 拆为独立媒体连接，避免 Depth 队列阻塞 RGB。
2. 将 Depth 从 TCP 迁移到 UDP/RTP 或自定义 UDP 分片，并在接收端按帧号和时间戳重组。
3. 增加 Depth 帧级优先级策略：网络抖动时丢旧 Depth，保留最新 RGB/Depth 时间戳一致性。
4. 如果下游允许，可进一步放大量化步长，例如 4mm 或 5mm，换取更低码率。
5. 优先把高码率 Gemini305 发送端放到更近的 AP/CPE，或改有线链路。
