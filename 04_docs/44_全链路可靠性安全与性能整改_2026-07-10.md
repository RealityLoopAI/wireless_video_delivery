# 全链路可靠性、安全与性能整改

日期：2026-07-10

## 目标

本轮不是改相机档位或传输协议，而是系统审查 sender、receiver、录制、Web、CLOCK_SYNC 和部署路径，修复会造成崩溃、内存失控、错误时间轴、录制损坏、管理超时和版本漂移的问题。

## 已修复问题

### 发送端

1. SDK RGB/Depth 帧在 `waitForFrames()` 返回后立即绑定设备时间、系统时间、host capture 时间和同一 FrameSet 的 `pair_id`，不再到编码或发送阶段临时取帧时间。
2. SDK 异常时间戳会按 host capture 时间校验，处理零值、明显偏离和倒退；V4L2 使用内核 buffer 时间映射到系统 epoch。
3. RGB、Depth、预览使用独立有界队列和字节上限；正式数据可重试，预览允许丢帧，避免无限积压导致 OOM。
4. Depth 原始帧通过 SDK payload owner 延长生命周期，减少整帧复制；TCP 使用 `sendmsg` 分散写，避免重新拼接 header 和 payload。
5. 相机、编码、压缩、发送线程增加顶层异常边界和 RAII join；热插拔失败进入重连，不再因未捕获异常 `terminate`。
6. 退出时先停止采集，再限时排空压缩和正式媒体队列，降低突然退出导致的尾帧损失。
7. 配置改为严格 JSON 解析，限制身份、IP、档位、队列、码率和数值范围。

### 接收端

1. TCP/UDP 媒体元数据在分配 payload 前校验；限制 payload、图像尺寸、codec、身份和字符串长度。
2. UDP 分片按来源、类型和序号隔离，限制活动 assembly 数量、总内存、单包大小和 chunk 数，拒绝重叠/非连续分片。
3. Depth 解压改为全进程共享的固定线程池，不再每帧创建线程，也不会随多个连接成倍膨胀。
4. 媒体/admin 客户端线程和 ffmpeg preview decoder 全部托管并 join，移除 detached thread、fd 重用和 double-close 风险。
5. 监听端口增加启动 readiness 检查；端口冲突时进程直接失败，不再出现服务 active 但实际未监听。
6. `/api/status` 使用短锁和缓存，预览解码、JPEG/Depth 伪彩等重处理移出全局状态锁，降低 `receiver admin unavailable: timed out`。

### 录制

1. 每路相机使用可靠有界录制队列，并设置全局总内存上限；队列压力不再无界占用内存。
2. 开始录制检查 NAS 目录、可写性和最小剩余空间；运行中持续检查空间并在写失败后暂停该路输入、保留错误状态。
3. CSV 每 30 行 flush，并检查写入错误；段创建中途失败会完整回滚文件和 pipe 状态。
4. RGB 始终写 H.264 恢复旁路。MP4 pipe 失败不再在同一目标文件上覆盖重开，结束后校验并按需自动恢复。
5. Depth 使用独立 part 文件，校验有效 part 后再 rename/concat；无效 part 保留用于排查。
6. 停止录制异步收尾，禁止收尾未完成时重复 start/stop；状态明确区分 accepting、active、finalizing。
7. 保持 fragmented MP4 实时写法；正常结束后在临时文件中单次无损重封装为普通 MP4，校验成功后原子替换，不做 faststart 二次搬运。最终用真实解码 seek 测试验证可读与可定位。

### 时间轴和配对

1. CLOCK_SYNC 绑定响应来源 IP/端口，严格解析 JSON，过滤负延迟、高延迟、超大跳变和异常数值。
2. offset 使用低 delay 样本中位数和 EWMA；drift 使用低 delay 样本线性回归并限制在合理范围。
3. health/model timeout 使用本机单调时钟或 receiver 接收时间，不受系统时间回拨影响。
4. `global_timestamp_us` 只映射带有效 sender 系统时间的媒体包；模型无效或结果明显偏离 receiver 时降级并写 `clock_sync_valid=0`。
5. 同一 SDK FrameSet 的 RGB/Depth 写同一非零 `pair_id`；Depth 人工 remap 时不伪造配对关系。

### 安全和部署

1. Web `/api/*` 默认需要随机访问令牌和 HttpOnly Cookie；令牌不进入仓库。
2. C++ admin 强制监听 `127.0.0.1`；Web H.264 stream 限制并发客户端数。
3. sender/status/media 按 sender_id 绑定来源 IP，拒绝在线期间的身份冲突；协议身份禁止路径字符。
4. 进程上报 `build_commit`、`build_dirty` 和代码内容 `build_source_hash`；测试构建输出到自己的 build 目录，不会覆盖正式二进制。
5. 增加配置测试和接收端故障注入测试，覆盖端口冲突、恶意 UDP 分片、压缩布局、认证、录制收尾、CLOCK_SYNC 和优雅退出。

## 运行边界

1. 媒体和状态协议仍以可信局域网为前提，没有端到端加密和消息级共享密钥；跨不可信网络前必须加 VPN/TLS 或协议认证。
2. Web 当前是 HTTP，令牌不能抵抗同网段抓包；生产环境应由 HTTPS 反向代理承载。
3. 无硬件触发/同步线时，CLOCK_SYNC 只能统一主机时间，不能让不同传感器同时曝光。
4. NAS 掉线、USB 供电不足、Wi-Fi 物理丢包和相机固件故障只能检测、限损和恢复，软件不能保证零丢帧。
5. 正式部署必须在每种 ARM 架构本机编译，并用状态中的 commit/dirty 核对，不应复制其他架构二进制。

```bash
cmake -S . -B 12_build -DGWV3_BUILD_SENDER=ON -DGWV3_BUILD_RECEIVER=ON
cmake --build 12_build -j2
ctest --test-dir 12_build --output-on-failure
```
