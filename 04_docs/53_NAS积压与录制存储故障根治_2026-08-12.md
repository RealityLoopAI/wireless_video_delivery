# NAS 积压与录制存储故障根治

## 1. 现象与根因

下游报告的 session `1786436322738206` 发生于 2026-08-11 16:18--17:21，早于统一分片版本部署。直接复核 `frames.csv` 发现：

1. 首片不是简单的 MP4 duration 计算问题。
2. `ab748372`、`f022c4`、`fe0ec3fe` 的 RGB 在同一时段各缺失约 98--99 秒。
3. 其他路由的 RGB 或 Depth 也在相同时段中断。
4. CSV 首尾时间仍覆盖 15 分钟，但实际帧数减少；30 FPS CFR 容器会把无帧时间压掉。

共同中断指向 receiver 共享 I/O/网络资源，不是六台相机各自同时故障。

旧 uploader 同时对 6 路活动分片以 4 MiB 小块增量镜像，频繁计算哈希、切换文件和更新 CIFS 状态。分片关闭时镜像复用率仅约 15--37%，仍需要读回校验并复制大部分数据。这造成本地机械盘随机 I/O 抖动和重复网络写入。

## 2. 修复

### 2.1 录制故障状态机

1. 开始录制前检查 `min_free_disk_bytes + 2 GiB` 恢复余量。
2. 录制中任一路触发本地空间保留线时，只有第一个故障线程会原子地请求全局 `stop-all`。
3. 所有路停止接收录制数据、异步收尾，接口进入 `recording_state=faulted`。
4. 保留故障 session、时间、首发相机和原因。
5. 取消“空间恢复后在原 session 内静默续录”，避免下游把中间大缺口当成完整数据。

### 2.2 NAS 搬运

1. 默认关闭多路活动增量镜像。
2. 已关闭分片按老到新搬运；录制时保持 1 个 worker，空闲时使用 2 个 worker 快速清理积压。
3. 大于等于 64 MiB 的文件使用 `dd iflag=direct` 避免污染 receiver 页缓存；保留暂停、取消、进度和失败回退。
4. 小文件和不支持 direct I/O 的文件系统仍使用 Python 缓冲复制。
5. 目标不是占满 NAS，而是稳定高于六路实际产出速率并保护实时录制。

## 3. 实测数据

| 路径 | 实测速率 |
| --- | ---: |
| NAS 本身零数据单流写入 | 远高于业务需求，不是介质上限 |
| 本地盘冷读 + `dd iflag=direct` + NAS | 约 172 Mbps |
| 两路 direct 并发聚合 | 约 187 Mbps，但 I/O pressure 更高 |
| Python 缓冲单流 | 约 58 Mbps |
| `sendfile` | 约 98 Mbps |
| 部署后 uploader 实际监测 | 约 147--151 Mbps |
| 六路录制产出 | 约 85 Mbps |

录制时单 direct worker 避免本地盘寻道竞争；停录后启用双 worker，优先缩短 NAS 完整可见时间。若录制中暂存盘进入高水位，也会临时升到配置的 2 个 worker，以避免触发硬保留线。

## 4. 运维判定

1. 不能只看 `recording_all`；应优先看 `recording_state` 和 `recording_faulted`。
2. `record_queue_total_bytes` 应长期接近 0。
3. `recording_uploader.pending_bytes` 可在分片轮转时阶梯上升，但长期斜率必须下降。
4. `nas_write_recent_mbps` 是短窗口值，文件切换、fsync 和发布阶段可短暂为 0；需结合 `pending_bytes` 趋势。
5. NAS 真正可见仍按 session + route + segment + ready marker 判断。
