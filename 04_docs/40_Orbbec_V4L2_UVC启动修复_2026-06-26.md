# Orbbec V4L2 UVC 启动修复说明

日期：2026-06-26

## 背景

本机 RK3588 发送端更换/重新插拔 Orbbec 相机后，`cam01` 能枚举到深度设备，但发送端长期停留在 0fps，receiver 侧显示 `camera startup pending`。此时当前实际在线设备为：

- 深度设备：`2bc5:0614`，`SV1301S_U3`，序列号 `AY2M54302ZH`，USB3.0。
- RGB UVC：`2bc5:0511`，同序列号 `AY2M54302ZH`，USB2.0 UVC。

`cam02` 当前未插入，配置里仍保留 `AY2MC31010W`，因此 `cam02 configured camera not found` 是预期状态，不应阻塞 `cam01`。

## 根因

Orbbec SDK 默认配置中 `LinuxUVCBackend` 使用 `LibUVC`。在当前 `SV1301S_U3` 相机上，LibUVC 路径会接管/解绑 Linux kernel `uvcvideo`，随后 SDK `pipeline.start()` 卡住；异常退出后 RGB UVC 接口还可能保持未绑定状态，导致 `/dev/video21`/`/dev/video22` 消失。

验证现象：

- `lsusb -t` 可看到 RGB UVC 设备，但接口 `Driver=` 为空。
- `v4l2-ctl --list-devices` 看不到 Orbbec RGB UVC 节点。
- SDK 探针 color-only 也卡住，并打印 `Current device does not support frame sync`。
- 重新绑定 `uvcvideo` 后，用 `v4l2-ctl` 直接采 `1280x720@30 MJPG` 正常。

## 修复

1. 新增仓库根目录 `OrbbecSDKConfig_v1.0.xml`，固定：
   - `FrameSync=false`
   - `LinuxUVCBackend=V4L2`
2. CMake 优先复制仓库根目录的 SDK 配置到 `12_build/bin`，避免后续构建回退到 SDK 默认 `LibUVC`。
3. 新增 `05_tools/orbbec_runtime_guard.sh`：
   - 启动前同步 `OrbbecSDKConfig_v1.0.xml` 到当前工作目录。
   - 启动前检查 Orbbec UVC 接口，发现未绑定时自动绑定到 `uvcvideo`。
4. `start_sender.sh` 和 `sender_watchdog.sh` 都接入 runtime guard，保证手动启动和 watchdog 重启路径一致。
5. 发送端相机启动顺序调整：
   - `frame_aggregate_mode=disable` 时不再调用 `setFrameAggregateOutputMode()`。
   - RGB 曝光/增益控制改为 pipeline 成功启动后下发，避免启动前占用 UVC。
6. `orbbec_fps_probe` 增加可配置 RGB/depth 档位和格式，后续可直接复现目标组合。

## 验证结果

SDK 探针：

- `1280x720@30 MJPG` color-only：稳定约 30fps。
- `1280x720@30 MJPG + 1280x800@30 Y12` RGBD：稳定约 30fps。

正式发送端：

- `rk3588-ubuntu_cam01` 已恢复 `live=true`。
- RGB 输入/发送：约 `29.9-30.9 fps`。
- Depth 输入/发送：约 `29.9-30.9 fps`。
- RGB 发送码率：约 `12 Mbps`。
- Depth 发送码率：约 `22-23 Mbps`。
- `send_failures=0`，`wait_timeouts=0`。
- 手动曝光生效：`auto_exposure=0`，`exposure=312`，`gain=80`。

## 未完成/注意项

- 当前只插入一路相机，`cam02` 离线是物理未接入导致。
- `Current device does not support frame sync` 仍会在读取 profile 时由 SDK 打 warning，但 V4L2 后端下不再阻塞采集。
- receiver 当前主预览仍选择 OrangePi 设备，本机 `rk3588-ubuntu_cam01` 主预览未设为主画面；这不影响媒体收包和录制。
- 当前 CPU 主要消耗来自本机 sender 的深度压缩和发送，约 `140%` 单进程 CPU；系统整体仍有约 `70%` idle。
