# 中间传输数据格式规范 v3

## 1. 文档定位

本文档定义 3.0 发送端与接收端之间的数据格式，用于解耦发送端和接收端开发。

本文档只规定数据结构、字段名、字段语义、时间戳语义和版本规则，不写死底层网络协议。

底层网络协议可以在后续实测后选择 SRT、UDP/RTP、TCP、自定义 UDP/TCP 组合或其他方案。无论底层协议如何变化，发送端和接收端都必须遵守本文档定义的数据格式。

## 2. 总体原则

1. 数据方向只定义发送端到接收端。
2. 接收端不通过本文档定义的格式向发送端下发控制命令。
3. 录制开始/停止只发生在接收端内部和 REST API，不通知发送端。
4. 小消息使用 JSON。
5. RGB/Depth 大数据使用二进制帧头 + 二进制 payload。
6. 字段名全部使用英文。
7. 文档说明使用中文。
8. 协议 ID 字段只允许 ASCII 字母、数字、下划线 `_`、短横线 `-`。

## 3. 版本规则

所有 JSON 消息必须包含：

```json
{
  "protocol_version": "3.0",
  "message_type": "heartbeat"
}
```

媒体二进制帧头必须包含：

```text
header_version
```

版本兼容原则：

1. 主版本不一致时，接收端可以拒绝接收。
2. 次版本新增字段时，接收端应忽略未知字段。
3. 必填字段缺失时，接收端应拒绝该消息或该帧，并记录错误。

## 4. ID 规则

### 4.1 sender_id

1. 最大 64 字节。
2. 只允许 ASCII 字母、数字、下划线 `_`、短横线 `-`。
3. 不允许中文。
4. 不允许空格。
5. 不能为空。

### 4.2 camera_id

1. 最大 64 字节。
2. 只允许 ASCII 字母、数字、下划线 `_`、短横线 `-`。
3. 不允许中文。
4. 不允许空格。
5. 不能为空。

### 4.3 camera_key

接收端默认使用以下规则生成 `camera_key`：

```text
<sender_id>_<camera_id>
```

`camera_key` 用于录制目录，不由发送端直接决定。

## 5. 时间戳规则

### 5.1 timestamp_us

1. 所有媒体帧必须包含 `timestamp_us`。
2. 单位为微秒。
3. 优先使用相机/SDK 提供的帧时间戳。
4. 如果同时存在硬件时间戳和系统时间戳，应在字段中区分。
5. 发送端必须保持同一路相机内 RGB/Depth 时间戳可用于配对。

### 5.2 system_timestamp_us

可选字段。

含义：

1. 发送端系统时间戳。
2. 单位为微秒。
3. 可用于日志和粗略排序。
4. 不作为跨发送端严格同步依据。

### 5.3 跨相机同步

1. 3.0 不要求跨摄像头严格同步。
2. 3.0 不要求跨发送端严格同步。
3. 不要求硬件同步或 PTP。
4. 接收端只保证每一路内部 RGB/Depth 的配对关系可追踪。

## 6. JSON 消息格式

### 6.1 通用字段

所有 JSON 消息都应包含：

```json
{
  "protocol_version": "3.0",
  "message_type": "sender_hello",
  "sender_id": "sender01",
  "timestamp_us": 1715230000000000
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `protocol_version` | string | 是 | 协议版本 |
| `message_type` | string | 是 | 消息类型 |
| `sender_id` | string | 是 | 发送端 ID |
| `timestamp_us` | uint64 | 是 | 发送端生成消息时间 |

## 7. sender_hello

发送端启动后发送一次。

示例：

```json
{
  "protocol_version": "3.0",
  "message_type": "sender_hello",
  "sender_id": "sender01",
  "timestamp_us": 1715230000000000,
  "sender_version": "3.0.0",
  "host_name": "orangepi-01",
  "os": "linux",
  "arch": "aarch64",
  "capabilities": {
    "rgb_encoding": ["h264", "h265"],
    "depth_compression": ["none", "lz4", "zstd"],
    "local_preview": true
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `sender_version` | string | 是 | 发送端程序版本 |
| `host_name` | string | 否 | 主机名 |
| `os` | string | 否 | 操作系统 |
| `arch` | string | 否 | CPU 架构 |
| `capabilities` | object | 是 | 发送端能力 |

## 8. camera_announce

每个相机上线时发送。相机 profile 或标定发生变化时也应重新发送。

示例：

```json
{
  "protocol_version": "3.0",
  "message_type": "camera_announce",
  "sender_id": "sender01",
  "camera_id": "cam01",
  "timestamp_us": 1715230001000000,
  "device": {
    "vendor": "orbbec",
    "model": "Gemini",
    "serial_number": "SN123456",
    "uid": "usb-001",
    "firmware_version": "3.0.18",
    "connection_type": "USB3"
  },
  "rgb_profile": {
    "width": 1920,
    "height": 1080,
    "fps": 30,
    "pixel_format": "rgb",
    "codec": "h264"
  },
  "depth_profile": {
    "width": 640,
    "height": 576,
    "fps": 30,
    "pixel_format": "uint16",
    "compression": "zstd",
    "depth_scale": 0.1
  },
  "calibration": {
    "available": true,
    "source": "orbbec_sdk",
    "data": {}
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `camera_id` | string | 是 | 相机 ID |
| `device` | object | 是 | 设备信息 |
| `rgb_profile` | object | 是 | RGB 当前输出规格 |
| `depth_profile` | object | 是 | Depth 当前输出规格 |
| `calibration` | object | 是 | 标定信息 |

`calibration.data` 的具体结构可根据 Orbbec SDK 实际输出展开，但必须能保存 RGB 内参、Depth 内参、外参、畸变参数和 `depth_scale`。

## 9. heartbeat

发送端周期性发送。当前发送端按相机逐路发送 heartbeat，每条消息带 top-level `camera_id`，以兼容接收端按 `<sender_id>_<camera_id>` 刷新 `last_status_us` / `status_live` 的实现。

示例：

```json
{
  "protocol_version": "3.0",
  "message_type": "heartbeat",
  "sender_id": "sender01",
  "camera_id": "cam01",
  "timestamp_us": 1715230002000000,
  "uptime_ms": 120000,
  "online": true,
  "rgb_fps": 29.8,
  "depth_fps": 29.7,
  "rgb_encoding": "h264",
  "depth_compression": "zstd",
  "rgb_dropped_frames": 0,
  "depth_dropped_frames": 1,
  "hardware_encoder": true,
  "last_error": ""
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `uptime_ms` | uint64 | 否 | 发送端运行时间 |
| `camera_id` | string | 是 | 当前 heartbeat 对应的相机 ID |
| `online` | bool | 是 | 当前相机是否在线 |
| `rgb_fps` / `depth_fps` | number | 否 | 从进程启动累计计算的 RGB / Depth 平均帧率 |
| `rgb_measured_fps` / `depth_measured_fps` | number | 否 | 最近性能窗口测得的 RGB / Depth 帧率 |
| `rgb_mbps` / `depth_mbps` | number | 否 | 最近性能窗口测得的发送码率 |

## 10. camera_offline

相机掉线时发送。

示例：

```json
{
  "protocol_version": "3.0",
  "message_type": "camera_offline",
  "sender_id": "sender01",
  "camera_id": "cam01",
  "timestamp_us": 1715230003000000,
  "reason": "device_disconnected"
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `camera_id` | string | 是 | 相机 ID |
| `reason` | string | 是 | 离线原因 |

## 11. event

发送端异常或重要状态变化时发送。

示例：

```json
{
  "protocol_version": "3.0",
  "message_type": "event",
  "sender_id": "sender01",
  "camera_id": "cam01",
  "timestamp_us": 1715230004000000,
  "level": "warning",
  "event_code": "depth_missing",
  "message": "Depth stream timeout",
  "details": {
    "timeout_ms": 1000
  }
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `camera_id` | string | 否 | 相机 ID，sender 级事件可为空 |
| `level` | string | 是 | `info` / `warning` / `error` |
| `event_code` | string | 是 | 事件码 |
| `message` | string | 是 | 人可读说明 |
| `details` | object | 否 | 附加信息 |

## 12. 媒体帧格式

媒体帧用于发送 RGB 和 Depth 大数据。

媒体帧结构：

```text
固定长度二进制帧头
可变长度 sender_id
可变长度 camera_id
可变长度 codec_or_compression
二进制 payload
```

## 13. 媒体帧头字段

固定帧头应至少包含以下字段。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `magic` | uint32 | 是 | 固定魔数，用于识别帧 |
| `header_version` | uint16 | 是 | 帧头版本 |
| `header_size` | uint16 | 是 | 固定头长度 |
| `stream_type` | uint8 | 是 | 1=RGB，2=Depth |
| `flags` | uint32 | 是 | 标志位 |
| `sender_id_len` | uint16 | 是 | sender_id 字节长度 |
| `camera_id_len` | uint16 | 是 | camera_id 字节长度 |
| `codec_len` | uint16 | 是 | codec/compression 字符串长度 |
| `frame_id` | uint64 | 是 | 该流内帧号 |
| `timestamp_us` | uint64 | 是 | 帧时间戳 |
| `system_timestamp_us` | uint64 | 否 | 发送端系统时间戳，无则为 0 |
| `pair_id` | uint64 | 否 | RGB/Depth 配对 ID，无则为 0 |
| `width` | uint32 | 是 | 图像宽 |
| `height` | uint32 | 是 | 图像高 |
| `pixel_format` | uint16 | 是 | 像素格式枚举 |
| `payload_size` | uint64 | 是 | payload 字节数 |
| `uncompressed_size` | uint64 | 否 | 解压后字节数，无压缩时可等于 payload_size |
| `reserved` | bytes | 否 | 预留字段 |

实际 C++ 结构体定义应固定字节序和对齐方式。建议使用网络字节序或明确规定小端格式，避免不同平台解析歧义。

## 14. stream_type

`stream_type` 取值：

| 值 | 名称 | 说明 |
| --- | --- | --- |
| 1 | `rgb` | RGB 编码视频帧 |
| 2 | `depth_raw` | 原始 Depth 帧 |

首版不把 `depth_color` 作为正式媒体流。

`depth_aligned_to_rgb` 是可选产物，不作为首版必传流。

## 15. pixel_format

建议取值：

| 值 | 名称 | 说明 |
| --- | --- | --- |
| 1 | `encoded_video` | H.264/H.265 编码视频 |
| 2 | `depth_u16` | uint16 原始深度 |

如果后续增加新格式，必须增加枚举并更新本文档。

## 16. RGB 媒体帧

RGB 媒体帧要求：

1. `stream_type = 1`。
2. `pixel_format = encoded_video`。
3. `codec_or_compression` 为 `h264` 或 `h265`。
4. payload 是发送端编码后的 H.264/H.265 数据。
5. 接收端应优先直接封装为 `rgb.mp4`。
6. 接收端只为网页预览解码。

RGB 帧不允许发送原始 1080p RGB 图像作为首版主路径。

## 17. Depth 媒体帧

Depth 媒体帧要求：

1. `stream_type = 2`。
2. `pixel_format = depth_u16`。
3. 原始数据类型为 `uint16`。
4. payload 是一整帧 `depth_raw`。
5. `codec_or_compression` 可为 `none`、`lz4`、`zstd`。
6. 禁止默认有损压缩。
7. `uncompressed_size` 必须填写。
8. Depth 的 `depth_scale` 由 `camera_announce` 提供，必要时也可在扩展字段中重复携带。

## 18. pair_id

`pair_id` 用于 RGB 与 Depth 的可选配对。

规则：

1. 如果发送端能明确判断某 RGB 帧和某 Depth 帧是一组，则两帧填写相同 `pair_id`。
2. 如果发送端不能明确配对，`pair_id = 0`。
3. 接收端在 `pair_id = 0` 时按最近时间戳生成配对关系。
4. 不强制 RGB/Depth 一一对应。

## 19. flags

`flags` 用于记录帧属性。

建议定义：

| 位 | 名称 | 说明 |
| --- | --- | --- |
| 0 | `key_frame` | RGB 视频关键帧 |
| 1 | `dropped_before` | 发送端已知前面发生过丢帧 |
| 2 | `end_of_segment_hint` | 可选，提示切片边界 |
| 3 | `has_system_timestamp` | `system_timestamp_us` 有效 |

未定义位必须置 0。

## 20. 事件码建议

建议事件码包括：

| event_code | 说明 |
| --- | --- |
| `camera_connected` | 相机上线 |
| `camera_disconnected` | 相机掉线 |
| `rgb_missing` | RGB 流缺失 |
| `depth_missing` | Depth 流缺失 |
| `encoder_init_failed` | 编码器初始化失败 |
| `hardware_encoder_fallback` | 硬件编码失败，切到软件编码 |
| `network_send_failed` | 网络发送失败 |
| `receiver_unreachable` | 接收端不可达 |
| `frame_drop` | 发送端丢帧 |
| `profile_changed` | 采集规格变化 |

## 21. 接收端处理要求

接收端收到数据后必须：

1. 校验协议版本。
2. 校验 `sender_id` 和 `camera_id` 合法性。
3. 检测 ID 冲突。
4. 根据 `sender_hello` 建立发送端状态。
5. 根据 `camera_announce` 建立相机状态。
6. 根据 `heartbeat` 更新在线状态。
7. 根据 RGB 帧写入或预览 RGB。
8. 根据 Depth 帧写入或预览 Depth。
9. 根据 `pair_id` 或时间戳生成 RGB/Depth 配对关系。
10. 根据 `event` 更新网页和日志状态。

## 22. 未定项

以下内容不在本文档中写死：

1. 底层网络协议。
2. 媒体端口。
3. 状态消息端口。
4. RGB 最终使用 H.264 还是 H.265。
5. Depth 最终使用 `none`、`lz4`、`zstd` 或其他无损压缩方式。
6. 二进制帧头最终 C++ struct 的字节对齐细节。
7. Web 预览最终实现路线。

这些内容需要现场实测或实现阶段评审后确认。
