# 音响循环、录音与拍照异常排查修复

## 1. 目的与结论

本次针对 `2026-08-27` 的 9 小时 42 分长测报告和同时段设备日志进行排查。确认的主问题不是摄像头持续停流，而是以下故障链：

1. Wi-Fi/AP 在 `04:00-04:05` 发生多次断开和频道变化，两台发送端到接收端的音频、媒体、状态和拍照结果传输同时中断。
2. 发送端将“网络不可达”当成进程故障，达到计数阈值后退出，再被 systemd 拉起，把一次网络抖动放大成重复采集重启。
3. 接收端只看到音频 RTP 缺失，无法区分“网络断开”和“发送端麦克风真停止”，因而发出 `rebuild_capture`；发送端原先无条件重建 ALSA 采集，导致网络恢复后又人为制造一次音频空窗。
4. 唤醒后“拍照”的最短解码时长为 `0.45s`，短促发音可能在 ASR 前被当作过短片段跳过。
5. 发送端停止期间留下的拍照请求，恢复后可能被延迟执行，对应报告中停止后仍出现拍照的风险。

本轮修复了代码可控的放大因素，但 AP 掉线本身仍需要通过固定非 DFS 5 GHz 信道等方式处理。软件无法补回在无网络期间从未到达接收端的媒体包。

## 2. 证据链

### 2.1 04:00-04:05 集中异常

`lubancat-e8cc0cb3` 上一次启动的 NetworkManager 日志显示：

- AP `土著拯救器-5G`，BSSID `fe:83:c6:46:82:e6`，在 `04:00:14`、`04:01:44`、`04:03:09`、`04:04:38` 断开，原因码为 `4`。
- 备用网络 `666666-5G` 在该时段多次关联失败。
- AP 频率出现 `5300 -> 5280 -> 5320 -> 5220 -> 5280 MHz` 变化。这与自动选频、DFS 避让或 AP 重启的表现一致，最终类型需配合 AP 日志确认。

同时发送端日志显示：

- 摄像头采集仍约为 `30 FPS`，相机 `disconnects=0`。
- media/status/clock/photo 发送同时返回 `Network is unreachable`。
- 部署单元中的媒体中断阈值为 30 个采样周期，达到后进程退出，导致同一时段反复重启。

接收端的音频 `partial`、长时间无输入、视频分段中断与上述无线断开时间重合，因此该窗口的首要原因是网络/AP，代码的错误重启策略放大了影响。

### 2.2 07:19 与 09:44 异常

- `07:19` 两路音频数据接收基本完整，但播放声音缺失或失真，两台相机同时漏拍。更符合共享声源、播放或识别链路异常，不是两台摄像头同时停流。
- `09:44` 音频周期存在，但日志中没有对应的 `rgb snapshot request queued`。请求在进入相机队列之前就没有形成，不是 NAS 上传或 JPEG 落盘丢失。
- 三连拍在同一秒内会产生 `.jpg`、`_001.jpg`、`_002.jpg`；目录冲突时会产生 `HH-MM-SS_001` 目录。这是正常命名策略，不能单独作为重复拍照证据。

## 3. 代码修复

### 3.1 网络中断不再重启整个 sender

涉及文件：

- `01_sender_linux/include/gwv3_sender/media_outage_guard.hpp`
- `01_sender_linux/src/main.cpp`
- `05_tools/start_sender.sh`
- `05_tools/start_sender_preview.sh`
- `05_tools/systemd/gwv3-gemini-sender-*.service`

调整如下：

- `GEMINI_SENDER_MEDIA_OUTAGE_RESTART_SAMPLES` 默认由启用阈值改为 `0`，`0` 表示禁止仅因为媒体网络发送失败而退出进程。
- 网络断开时，采集和编码继续运行，有界队列仍按既有策略丢弃过旧数据，网络恢复后从最新帧继续传输。
- USB 拔出、SDK 枚举失败、相机采集长时间零帧等真实采集故障的检测和恢复保持不变。
- 保留环境变量，必要时可显式设为大于 `0` 的阈值，但无线网络环境不建议启用。

### 3.2 音频采集重建改为发送端二次确认

涉及文件：

- `12_apps/xiaohuan_voice_photo/audio_capture_recovery.py`
- `12_apps/xiaohuan_voice_photo/vosk_wake.py`
- `12_apps/xiaohuan_voice_photo/run_wake_service.sh`
- `05_tools/audio_archive_receiver.py`

新流程：

1. 接收端 RTP 超时后生成唯一 `request_id`，请求中带上原因、请求时间和最后收包时间。
2. 发送端 UDP gate 持续记录本地 ffmpeg/ALSA 输出的最后包时间，即使播放期间暂停对外转发，也仍然更新该状态。
3. 本地包龄小于 `2.0s` 时，说明采集正常，拒绝重建并回报 `local_capture_healthy`。
4. 本地包确实超时或从未产生时，才接受重建；重复请求和已有待处理请求会被去重。
5. 发送端通过 timing UDP 回报 `audio_capture_control_result`，接收端状态增加 `rebuild_accepted`、`rebuild_ignored`、`last_rebuild_result`、`last_rebuild_request_id` 等诊断字段。

这个改动保留了真实麦克风停止时的自恢复，同时避免将网络断开误当成音频硬件故障。

### 3.3 拍照指令和过期请求

- 唤醒后拍照指令的 `photo_decode_min_seconds` 由 `0.45s` 调整为 `0.30s`，降低短促“拍照”在 ASR 前被过滤的概率。
- 命令仍在唤醒后窗口和拍照受限词表中识别，没有改为任意语音触发。
- sender 读取拍照请求时检查 `requested_at_unix_us`，超过 `30s` 的历史请求会写入 `timeout` 结果并删除，不再在进程恢复后延迟拍摄。
- 拍摄时间在当前时间 `30s` 之后或请求时间异常超前时，也会返回错误结果，不再静默丢弃。
- 识别片段、低质量跳过、唤醒命中、指令分类和拍照完成日志增加带时区的毫秒级时间，便于与音频、照片和网络日志交叉定位。

## 5. 部署与验收

发送端为 ARM 设备，应从同一 commit 在各设备本机编译，不要在不同 SoC 之间直接复制 C++ 二进制。

1. 确认接收端没有录制任务，再停止和替换服务。
2. 在每台 sender 同步源码，本机编译 `gemini_sender`，安装对应的 systemd 单元并执行 `daemon-reload`。
3. 同步语音目录中的 `audio_capture_recovery.py`、`vosk_wake.py`、`run_wake_service.sh`，重启语音服务。
4. 接收端同步 `audio_archive_receiver.py`，重启音频归档服务。
5. 断开 sender Wi-Fi 10-20 秒再恢复，验收 sender 进程 PID 不变，摄像头采集不重启，媒体传输自动恢复。
6. 在网络抖动但本地音频正常的情况下，接收端状态应看到 `rebuild_ignored` 增加、`last_rebuild_result=local_capture_healthy`，发送端不重开 ALSA。
7. 真正停止本地音频生产进程时，应看到 `rebuild_accepted` 增加，且采集可恢复。
8. 做一次至少 2 小时循环测试，同时检查照片间隔、`wake_runtime.log`、音频 `audio_meta.json` 和网络断开日志。

## 6. AP 和网络处理建议

代码修复只能减小网络故障的放大效应，不能修复 AP 自身掉线。建议：

- 5 GHz 固定使用非 DFS 信道 `36/40/44/48` 之一，关闭自动选频和定时“网络优化”。
- 关闭会主动踢出客户端的智能漫游、双频合一和负载均衡，或为固定发送端做白名单。
- 禁用 sender WLAN 省电，固定目标 BSSID，避免网络之间来回切换。
- 保留 AP 日志，重点检查 `04:00` 是否存在 DFS 雷达规避、调度重启、自动选频或 DHCP 异常。
- 长测时同时采集 `journalctl -u NetworkManager`、`iw dev wlan0 link`、ping 丢包率和 AP 日志，不要只根据录制文件反推网络。

## 7. 仍然存在的边界

### 7.1 长时间网络断开时仍会丢数据

当前主媒体队列是内存有界队列，常用配置约为 30 秒，可配上限约为 60 秒；音频归档使用 RTP/UDP，没有确认和重传。因此：

- 短时网络抖动可以自动恢复，且本轮修复后不会再因网络错误重启采集。
- 类似 5 分钟的中断期间，接收端从未收到的 RGB、Depth 和音频不可能由现有代码事后还原。
- 如产品要求在数分钟断网中仍不丢帧，需要新增 sender 本地持久化 spool、接收确认、断点回传、去重和分段合并协议。这是一个独立的可靠传输功能，不应通过无限扩大内存队列实现。

### 7.2 外部声源无法由单机软件保证

两台设备同时漏拍且音频数据完整时，仍可能是外部循环播放或环境声学问题。新日志可以明确区分“没有形成语音片段”、“片段被质量门限跳过”、“ASR 未命中”和“已进队但相机未完成”，但不能替代外部播放设备的健康监测。

## 8. 快速排查表

| 现象 | 先看什么 | 判断 |
|---|---|---|
| RGB/Depth/音频/状态同时中断 | NetworkManager、AP 日志、`Network is unreachable` | 网络/AP 问题 |
| 相机继续 30 FPS，但发送失败 | sender perf 日志 | 传输中断，不应重启相机 |
| 接收端音频缺失，`last_rebuild_result=local_capture_healthy` | 音频归档 status | 发送端采集正常，中间网络异常 |
| `rebuild_accepted` 增加 | sender 重建日志和 ALSA | 本地音频生产确实停滞 |
| 有声音但无拍照请求 | `segment` / `skipped low_quality` / ASR 文本 | 语音切段或识别未命中 |
| 有 `rgb snapshot request queued` 但 NAS 无照片 | snapshot result、receiver photo uploader | 相机编码、上传或 NAS 阶段 |
| 恢复后出现历史拍照 | `snapshot request expired before sender queue` | 过期请求已被拒绝，不应再实拍 |
