# 本机 RGB 四缓冲混合采集修复与短测

## 结论与发布边界

2026-09-11，为本机 SV1301S_U3 增加默认关闭的 `native_rgb_capture`。
RGB 使用原生 V4L2 四缓冲，Depth 保持 Orbbec SDK；复用原有编码、压缩、媒体传输和录制路径。
本次仅在本机临时二进制上试运行，未修改生产配置、生产二进制或其他设备。
测试完成后已恢复 `gwv3-gemini-sender.service` 原版本。

这是针对已确认缓冲区使用缺陷的实验修复，不是全系统零缺帧保证。
前序证据见 [本机 RGB 输入调查](rk-rgb-input-investigation-20260911.md)。
SDK 1.10.27 的 V4L2 路径分配四缓冲，却仅将索引 0 加入初始采集队列；
已有调度追踪说明单缓冲会增加调度延迟造成采集空档的风险，但不能解释所有现场间断。
检查 1.10.35 二进制仍存在同类初始入队行为，未将升级 SDK 当成修复。

## 改动

- RGB 在 `VIDIOC_DQBUF` 成功后立即绑定主机系统时间，再交给现有编码时序结构。
- SDK 外部帧包装持有缓冲区生命周期，最后一个引用释放时归还 V4L2，避免提前归还导致错帧。
- 不新增该包装边界的整帧复制；不代表整个编码/发送链路实现零拷贝。
- 校验驱动缓冲索引、长度和错误标志；归还失败进入已有故障恢复流程。
- Depth 使用独立 SDK 回调和容量 32 的有界 inbox；初始化完成前不积累帧。
- inbox 溢出显式触发恢复，不静默吞掉故障，也不承诺任意长阻塞下不丢帧。
- 增加配置约束、inbox 并发/生命周期/启动门控测试、SDK 外部帧所有权测试。

SDK 外部 MJPG 工厂返回通用 VIDEO 类型，直接 `as<ColorFrame>()` 会失败。
测试先复现该失败，随后使用 SDK 公开的 `ColorFrame(Frame&)` 包装构造，验证指针未复制、尺寸正确、最后引用释放时回调执行。

## 时间戳和兼容限制

原配置不包含此字段时行为不变。仅在单个 camera 配置中显式设置：

```json
{"native_rgb_capture": true}
```

还必须满足：`capture_backend=orbbec_sdk`、`device_model=SV1301S_U3`、RGB MJPG、Depth 开启、
`frame_aggregate_mode=disable`、无旋转、软件自适应曝光关闭。运行时再次核对实际型号。
当前仅验证 SDK 1.10.27 ARM64；其他 SDK/架构未验收，不支持包装接口的构建在启用时明确报错。

实验 RGB 的 `timestamp_us=0`，因为本路径没有可验证的相机设备时钟；
`frame_system_timestamp_us` 来自主机出队时刻，经已有时钟归一化逻辑处理。
`sender_capture_host_timestamp_us` 保留原始出队主机时间，`global_timestamp_us` 仍由接收端映射。
出队时间不是曝光开始时间，缓冲和线程调度仍可能给内容对齐带来误差。
驱动时间戳与 sequence 仅作为日志诊断，不能把 sequence 跳号直接当成物理曝光丢帧数。

混合采集的 RGB/Depth 不再属于同一个 SDK FrameSet，因此 `pair_id=0`，配对有效标志为 false。
不得伪造硬件配对，也不得用于要求非零 pair_id 的下游流程；这种下游应保持原模式。
SDK 帧级曝光等诊断元数据在实验 RGB 路径中不提供，不能把空值解释成自动曝光。
生产曝光配置未更改。媒体协议、接收端和 NAS 发布逻辑未改。

## 实际测试

独立构建目录 `/tmp/wvd-native-rgb-build`，未覆盖 `12_build`。
最终代码 sender CTest **25/25 通过，24.42 秒**。仅指该构建的 sender 测试集，不是全仓/全设备验收。

第一轮约两分钟 RGBD 试运行发现初始化期 Depth 积累约 20 帧，随后增加 inbox 启动门控。
第二轮约 127 秒运行，在其中单独录制本机 cam01；其余相机未启动测试录制。
录制位置：`rk3588-ubuntu_cam01/2026-09-11/110510`。

|---|---:|---:|
| 档位 | 1920x1080@30 | 320x200@30 |
| 录制窗口 | 41.265652 秒 | 41.265652 秒 |
| CSV/媒体帧数 | 1238 | 1241 |
| CSV 最大全局时间间隔 | 42.270 ms | 41.849 ms |
| 超过 50ms 的 CSV 间隔 | 0 | 0 |
| 全局时间戳倒退 | 0 | 0 |
| 无效 clock_sync 行数 | 0 | 0 |
| 完整解码 | 通过 | 通过 |

RGB 视频索引为 0..1237，所有 RGB 行的采集主机时间与 frame_system_timestamp_us 一致。
NAS `ready=true`、`recording_quality_status=complete`。
这些数量允许实际相机帧率和窗口边界产生少量差异，不能把理论 30fps 当成绝对帧计数器。

第二轮 ftrace 无环形覆盖，3790 次 DQBUF，四个索引的次数分别为 948、948、947、947。
启动最初两帧的驱动时间有一次 252.018ms 间隔；其后未发现超过 50ms 的驱动时间间隔。
不能把包含启动过程的整段试运行写成绝对无间隔。

测试中遇到 TCP 背压，采集仍接近 30fps，本次录制最终完整到达；背压根因未在此修复。
默认 `ffmpeg -f null` 检查曾出现输出 DTS 取整警告；直接 ffprobe 检查两个源文件 PTS 均递增。
使用 `-fps_mode passthrough -enc_time_base 1:1000000` 完整解码两文件，退出码均为 0，stderr 为空。
这证明文件可解码，不替代画面内容重复帧检查或多机内容级同步验证。

## 回退与下一步验收

实验开关恢复 false/删除字段，重启 sender 即回原采集路径。本次已恢复原服务和原二进制。
测试二进制标识为基于 `9652df373f6f` 的 dirty build，不是归档提交之后重编译的发布版本。

永久部署前还需同场景对照至少 15 分钟和长时间录制，覆盖 CPU/网络压力、USB 热插拔、队列溢出和退出恢复。
还需验证主机出队时间对跨相机内容对齐的影响、RGBD 配对下游兼容性。
不扩大到其他型号，不因短测通过宣称长期少帧已根治。
当前原服务恢复后 RGB/Depth 均约 30fps，但仍能观察到偶发 TCP 背压告警。
