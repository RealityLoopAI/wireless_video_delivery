# 多路实时音频 RTP 接口

## 1. 用途

LubanCat 和 OrangePi 开机后持续把麦克风音频发送给 Windows 电脑。接收端无需先启动；它上线后直接监听固定 UDP 端口即可。

这条 RTP 链路只承载连续音频，不发送唤醒事件。“你好小环”、“我在”和“拍照”仍由设备本机处理。非拍照命令不再通过旧 HTTP 接口上传。

## 2. 固定端点

| 发送设备 | sender ID | 目标 IP | UDP 端口 | RTP PT | SSRC |
|---|---|---|---:|---:|---:|
| LubanCat | `lubancat-52d2ef0c` | `192.168.66.32` | `50030` | `111` | `1389555468` (`0x52D2EF0C`) |
| OrangePi | `orangepi5pro-d12a4719` | `192.168.66.32` | `50031` | `111` | `3509208857` (`0xD12A4719`) |
| LubanCat | `lubancat-e8cc0cb3` | `192.168.66.32` | `50032` | `111` | `3322710864` (`0xC60C8B50`) |

Windows 防火墙需允许入站 UDP 50030 至 50032。

同一个已编码 RTP 包还会复制给 `192.168.66.196` 的同端口用于全天归档。该复制不做第二次 Opus 编码，不改变 Windows 的实时接收方式。

## 3. 媒体参数

- 封装：RTP over UDP
- 编码：Opus CBR
- 码率：32 kbit/s/路
- 声道：单声道
- 每包时长：20 ms
- RTP clock rate：48000 Hz
- 麦克风原始内容采样率：16000 Hz，发送分支会重采样到 Opus/RTP 规定的 48000 Hz
- RTP Payload Type：111（动态 PT）
- 不加密、不鉴权、不重传

网络预算不能只按32 kbit/s 编码码率计算。加上 RTP/UDP/IP 及二层开销后，每路通常约 50~70 kbit/s，两路远低于现有视频链路负载。

## 4. SDP 描述

LubanCat (`lubancat-52d2ef0c.sdp`):

```sdp
v=0
o=- 0 0 IN IP4 192.168.66.32
s=lubancat-52d2ef0c audio
c=IN IP4 192.168.66.32
t=0 0
m=audio 50030 RTP/AVP 111
a=rtpmap:111 opus/48000/1
a=recvonly
```

OrangePi (`orangepi5pro-d12a4719.sdp`):

```sdp
v=0
o=- 0 0 IN IP4 192.168.66.32
s=orangepi5pro-d12a4719 audio
c=IN IP4 192.168.66.32
t=0 0
m=audio 50031 RTP/AVP 111
a=rtpmap:111 opus/48000/1
a=recvonly
```

## 5. Windows 接收建议

下游 Python 程序建议使用 GStreamer 或 FFmpeg/PyAV 分别绑定各 UDP 端口，按 PT 111 解封装并用 Opus 48000 Hz 单声道解码。每路必须使用独立 socket/解码器，不要按包到达顺序混在一起。

FFmpeg 监听示例：

```powershell
ffplay -protocol_whitelist file,udp,rtp -fflags nobuffer -flags low_delay -i lubancat-52d2ef0c.sdp
ffplay -protocol_whitelist file,udp,rtp -fflags nobuffer -flags low_delay -i orangepi5pro-d12a4719.sdp
```

GStreamer 监听示例：

```powershell
gst-launch-1.0 udpsrc port=50030 caps="application/x-rtp,media=audio,encoding-name=OPUS,clock-rate=48000,channels=1,payload=111" ! rtpjitterbuffer latency=100 drop-on-latency=true ! rtpopusdepay ! opusdec ! audioconvert ! audioresample ! autoaudiosink
```

其他路把 `port=50030` 改为 `50031` 或 `50032`。Python 中若要获取 PCM，将 `autoaudiosink` 换为 `appsink`。

## 6. 运行边界

1. UDP 可能丢包或乱序，接收端应配置 60~150 ms jitter buffer，不要用 TCP 式无限等待。
2. 发送设备在本机播放“我在”或“叮”时仍继续推流和关键词识别，因此下游可能听到环境中的音箱声。当前依赖麦克风设备自带回声消除。
3. 目标 PC 不在线不会阻塞发送端；上线后从当前 RTP 包开始接收。
4. RTP 序列号、时间戳和 SSRC 用于检测丢包、排序和区分设备；不要用 UDP 到达时间代替 RTP 时间戳。

## 7. 健康检查

发送端日志应出现：

```text
audio_stream=true
audio_stream_target=192.168.66.32:50030 ... bitrate=32000 pt=111 ...
audio_stream_playback_policy=continuous
speech_playback_mode=asynchronous continuous_capture=true
utterance_forward=false
```

若 Windows 收不到，先检查 Windows 防火墙、监听端口和设备到 `192.168.66.32` 的路由，再检查 RTP PT/端口是否与本文一致。
