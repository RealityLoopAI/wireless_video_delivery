# RGB 普通 MP4 兼容收尾

> 历史说明：本文记录 2026-07-14 在 receiver finalizer 内完成普通 MP4 转换的阶段实现。2026-07-21 起，该全文件操作已移到独立 uploader，并在本地 staging 完成后原子发布 NAS。2026-07-24 起，实时 fragmented MP4 不再生成 `global_sidx`，避免关闭时扫描和回写长文件；当前操作以 [48_本地暂存与NAS可靠发布_2026-07-21.md](48_本地暂存与NAS可靠发布_2026-07-21.md) 和 [49_长录制完整性与收尾性能整改_2026-07-24.md](49_长录制完整性与收尾性能整改_2026-07-24.md) 为准。

日期：2026-07-14

## 问题

最新 RGB 文件具备 `moov`、全局 `sidx` 和尾部 `mfra`，`ffprobe` 可读取、ffmpeg 也能随机 seek，但部分 Windows 播放器仍不能拖动进度条。文件本身没有缺帧或缺 `moov`，根因是播放器对 fragmented MP4 的索引支持不完整。

## 最终方案

接收端采用两阶段封装：

1. 录制期间写 `frag_keyframe + empty_moov + default_base_moof + global_sidx` 的 fragmented MP4，降低异常断电或进程退出导致整段不可读的风险。
2. 自动轮转或正常停止后，在全局单线程异步录制收尾 worker 中用 ffmpeg `-c:v copy` 生成 `rgb_seekable.tmp.mp4`，不重新编码。
3. 校验输出 duration 与源文件一致，并确认顶层存在 `moov` 且不存在 `moof`。
4. 只有校验成功才在同目录原子替换正式 `rgb.mp4`。
5. 转换失败时保留原 fragmented MP4 和 `rgb_debug.h264`，不发布虚假的完成状态。
6. receiver systemd 使用 `KillMode=mixed`，停止时 SIGTERM 只先发给主进程，避免 `control-group` 同时杀掉录制 ffmpeg、破坏 RGB/Depth 正常写尾。
7. RGB 预览 decoder 停止时先回收 ffmpeg 子进程，再等待 pipe reader 线程，避免 reader 阻塞使 receiver 长时间停在 `deactivating`。
8. 自动轮转先启动并切换新切片，旧切片随后进入有界后台队列；录制线程不再同步等待旧切片重封装。
9. 所有相机共用一个串行收尾 worker，避免多路长文件同时读写 NAS 引发 I/O 压力、媒体队列增长和 OOM。
10. 待收尾切片数受 `record_finalize_max_pending_segments` 限制；达到上限时延后轮转但保持当前切片连续写入。

## 取舍

转换不会损失画质，也不会改变视频帧顺序，但需要额外读取和写入一次 RGB 文件。为避免 `+faststart` 再做一次大文件搬运，普通 MP4 的 `moov` 保留在文件尾。录制停止接口仍是异步的，网页和管理 API 不应被阻塞；长切片结束后必须等待 `/api/status` 中 `record_finalize_outstanding_segments=0` 且所有 `record_finalizing=false` 再重启或断电。

## 验证标准

1. 最终 `rgb.mp4` 顶层有 `ftyp`、`mdat`、`moov`，没有 `moof`。
2. `ffprobe` 能读取 H.264、duration 和帧数。
3. ffmpeg 能从中间和接近结尾位置随机 seek 并解码一帧。
4. 目录不存在残留 `rgb_seekable.tmp.mp4`。
5. `recording_ready.json` 只在媒体、CSV 和元数据全部收尾完成后发布。
