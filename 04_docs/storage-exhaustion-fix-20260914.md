# NAS 容量耗尽与接收端暂停修复报告

日期：2026-09-14，北京时间。对应证据：`storage-exhaustion-evidence.txt`。

## 一、原因已经明确

下游提供的宿主机证据补齐了此前报告的缺口：录像 `/volume1/video_database` 和接收端虚拟磁盘 `/volume1/@kvm/...qcow2` 共用 NAS 的 `/volume1`。

2026-09-12 04:07:18 内核返回 CIFS ENOSPC；随后视频和音频上传失败。下游只读查询记录虚拟机为 `paused (I/O error)`，磁盘错误为 `vda: no space`。这不是“没有开放相机”，而是同一底层卷写满，将录制故障扩大成整个接收端不可用。

04:18 附近是最后日志和磁盘更新时间，不是已精确确定的暂停时间。错误重试次数也不等于丢失文件数。本次未读取下游 Windows 上的完整原始日志，所附 SHA-256 未重新校验；原因判断依据其证据摘录及本机已核实的内核 ENOSPC。

本次重新登录 NAS，确认 `/volume1` 为 ext4，虚拟机目前 `running (booted)`。此前 10:30 的启动已经恢复了服务，本次没有再次重启虚拟机。

## 二、原有保护为什么没有挡住

1. 接收端主要检查 guest 内部 staging 文件系统。guest 还有空闲逻辑块，不代表承载 qcow2 的宿主卷还能分配物理空间。
2. 音频原有 NAS 低空间检查只打印 warning，仍然继续发布文件。
3. 视频上传缺少一致的 NAS 保留空间入口和运行中检查，直到写入返回 ENOSPC 才重试。
4. 释放 NAS 容量不会自动解除 libvirt 的 I/O 暂停。必须检查虚拟机和服务，不能只看 NAS 剩余容量。

## 三、本次修复

### 应用层

- 视频上传增加 `nas_min_free_mb`，低空间时暂停新任务；运行中的复制通过既有 pause 回调检查容量，返回明确 ENOSPC 并保留本地数据供重试。
- 音频发布由“只报警”改为低空间拒绝发布，每个文件复制前复查。照片上传也增加容量准入检查。
- NAS 后台挂载管理器将 `free_bytes` 写入本地状态文件。接收端只读这个本地快照，不在媒体或管理接口线程上执行 NAS 容量查询。
- 接收端增加可选 `shared_nas_min_free_mb`：仅对“系统盘和 NAS 共享底层卷”的现场启用。低空间时现有录制存储故障路径受控收尾并阻止新录制；启动预检另有 2 GiB 余量。容量不足、快照过期、路径不匹配或快照缺失均不能放行。
- 音频本地采集的存储保护也读取共享底层卷快照。独立系统盘部署默认不启用共享卷检查，保留 NAS 离线时本地缓存的原有行为。
- 不改 RGB/Depth 编码、时间戳、CSV、ready 发布契约，不删除或伪造历史数据。

### 宿主机兜底

NAS 新增 `gwv3-nas-vm-capacity-guard.timer`，约每 15 秒检查一次底层容量。低于阈值时核实指定 VM 磁盘确实在该卷，然后请求 `virsh shutdown` 正常关机。

不执行 `destroy`、强制重置或自动 `resume`。已经暂停的 VM 提示人工恢复，不擅自让旧录制继续。guard 的状态在 `/var/lib/gwv3/vm-capacity-status.json`。

该 unit 固定了本现场的卷和 VM UUID，不是可盲目用于所有 NAS 的通用配置。其他现场部署前必须核对卷、磁盘路径和 UUID。

## 四、本现场阈值

| 条件 | 行为 |
| --- | --- |
| NAS 剩余低于 120 GiB | 暂停新音视频/照片上传，运行中的视频复制检查失败后保留本地重试 |
| 共享底层卷低于 100 GiB，或其监测状态失效 | 接收端不允许新录制，已有录制走存储保护；音频采集进入存储阻止状态 |
| NAS 底层卷低于 50 GiB | 宿主机请求接收端 VM 正常关机，作为最后兜底 |
| 空间恢复 | 上传自动重试；不自动发起新视频录制。VM 若关机/暂停，需要运维核实后恢复 |

生产接收端 `/etc/gwv3/receiver.json`：

```json
{"nas_min_free_mb": 122880, "shared_nas_min_free_mb": 102400}
```

音频 `/etc/gwv3/audio_archive_receiver.json` 同步上述两个值，并读取 `/run/gwv3/nas-mount-status.json`。通用上传默认保留 10 GiB，共享卷保护默认关闭；本现场显式提高阈值。

这是策略保留量，不是文件系统硬配额，不承诺绝不会越过阈值：有在途复制、缓存、收尾和其他进程写入。故意留较大余量用于安全收尾。

### 运维步骤

1. 停止继续向同一卷大量写入，扩容或按既有留存规则处理可删除数据。不得删除未确认交付的 staging 或随意操作 qcow2。
2. NAS 剩余恢复到高于 120 GiB，并核查存储池、共享配额和文件系统状态。
3. 宿主机执行只读检查：

```bash
virsh -r -c qemu:///system domstate 9e268f60-b0a2-46c2-a8f4-2671bcc1b8f8 --reason
virsh -r -c qemu:///system domblkerror 9e268f60-b0a2-46c2-a8f4-2671bcc1b8f8
df -h /volume1
cat /var/lib/gwv3/vm-capacity-status.json
```

4. 如果已关机，在 NAS 虚拟机管理页正常启动。如果是 I/O 暂停，先确认错误已解除再由运维恢复；恢复后立即检查是否仍有旧录制会话，停止旧会话并等待修复/补传，不自动开始新任务。不要直接强制断电。
5. 接收端确认 NAS 状态 `ready=true`、`free_bytes` 和更新时间正常；确认 receiver、uploader、audio 服务正常。
6. 查看 `/api/status` 的 pending 队列是否下降、错误是否消失。队列为零后，再检查目标目录的 ready 标记和质量状态；需要逐帧完整性验收的数据仍按 CSV 核对，不能仅以队列清空判定内容无缺失。
7. 运维确认后手动开始下一次录制。

## 七、回退与边界

上线备份目录：`/home/loop/storage-fix-backup-20260914`，包含旧二进制、旧上传/音频/照片脚本、旧挂载管理器和原配置。

回退前确认录制及收尾空闲，再停止相关服务，恢复备份及配置，重启挂载管理器和应用服务。共享卷保护配置与新挂载管理器必须配套回退，否则旧状态不含容量字段，新接收端将拒绝录制。

宿主机 guard 可通过停止并禁用对应 timer 回退；但回退后重新暴露共享卷耗尽风险。

真正隔离仍需将 VM 系统盘迁到独立存储，或为录像建立可执行的独立配额/独立卷。本次没有移动 VM 磁盘或重分区。其他 NAS 客户端若继续无限写入，或 guest 不响应 ACPI 关机，软件阈值不能代替物理隔离；没有宣称完成硬件级根治。
