# Gemini Wireless Video v3 接收端当前存储格式说明

更新时间：2026-06-16

本文档说明当前无线接收端实际落盘的数据格式，供下游数据处理工程对接使用。

## 1. 总体结论

当前接收端采用“实时主存储格式”：

- RGB：`rgb.mp4`，发送端 H.264 码流在接收端直接封装为 MP4，不重新编码。
- Depth：`depth.mkv`，接收端将 depth uint16 原始帧写入 FFV1/Matroska，保持无损。
- 索引：`frames.csv`，记录每个媒体包到达接收端后的帧号、时间戳、尺寸、payload 大小，并合并 RGB 视频帧序号。
- 元数据：`meta.json`，记录 segment 基础信息和相机 announce 原始 JSON。
- 标定：`calibration.json`，按 segment 展开保存设备信息、RGB/Depth profile、RGB/Depth 内参、畸变参数、Depth -> RGB 外参和离线对齐产物约定。
- 对齐产物：接收端录制结束后不会自动生成；如需 RGB 坐标系下的 Depth，可手动运行离线脚本生成 `depth_aligned_to_rgb.mkv` 和 `depth_aligned_to_rgb.json`。
- Debug/恢复：接收端录制期间会写 `rgb_debug.h264` 作为 RGB MP4 修复旁路；`write_debug_h264=false` 时，`rgb.mp4` 通过最终校验后自动删除该旁路，失败时保留用于人工排查或重封装。`depth_debug.raw` 仍只在配置开启时保留。
- 文件名：REST 可按单路相机设置文件名前缀；为空时保持 `rgb.mp4` / `depth.mkv` 等默认文件名。

当前格式优先保证实时录制稳定性和完整性。它不是逐帧 PNG 目录格式，但可以从当前主存储格式离线导出 PNG/CSV/JSON 交付格式。

## 2. 目录结构

录制根目录由接收端配置 `nas_root` 决定，当前为：

```text
/home/fz/Desktop/nas
```

每路相机按以下规则创建目录：

```text
<nas_root>/<storage_key>/<YYYY-MM-DD>/<HHMMSS>/
```

`storage_key` 优先使用 REST 设置的相机自命名 `camera_name`；未设置时使用原始 `<sender_id>_<camera_id>`。

示例：

```text
/home/fz/Desktop/nas/orangepi5pro-b439137c_cam02/2026-05-11/162546/
├── rgb.mp4
├── depth.mkv
├── frames.csv
├── calibration.json
├── meta.json
├── ffmpeg.log
├── rgb_debug.h264        # MP4 校验失败时保留；write_debug_h264=true 时总是保留
└── depth_debug.raw       # 可选，取决于 write_debug_depth_raw
```

如果该路相机本次录制使用文件名前缀 `test01_`，目录下所有文件都会加前缀：

```text
/home/fz/Desktop/nas/front_left/2026-05-18/162546/
├── test01_rgb.mp4
├── test01_depth.mkv
├── test01_frames.csv
├── test01_calibration.json
├── test01_meta.json
├── test01_ffmpeg.log
├── test01_rgb_debug.h264
└── test01_depth_debug.raw
```

## 3. 文件说明

| 文件 | 是否必有 | 格式 | 说明 |
|---|---:|---|---|
| `rgb.mp4` | 是，有 RGB 时 | MP4 / H.264 | 接收端直接封装发送端 H.264 码流，`-c:v copy`，不解码不重编码。 |
| `depth.mkv` | 是，有 Depth 时 | Matroska / FFV1 / `gray16le` | 接收端将 depth uint16 原始帧写入 FFV1，无损压缩。 |
| `frames.csv` | 是 | CSV | 每个 RGB/Depth 媒体包一行，用于索引帧号、时间戳、尺寸、payload 大小；RGB 行中同时给出是否写入 `rgb.mp4` 以及对应视频帧序号。 |
| `meta.json` | 是 | JSON | segment 级元数据。录制开始和结束都会写入。 |
| `calibration.json` | 是 | JSON | segment 级标定展开文件，供后续离线生成 `depth_aligned_to_rgb`。 |
| `depth_aligned_to_rgb.mkv` | 可选 | Matroska / FFV1 / `gray16le` | Depth 投影到 RGB 坐标系后的结果，分辨率与 RGB 一致。 |
| `depth_aligned_to_rgb.json` | 可选 | JSON | 对齐产物 sidecar，记录输出分辨率、帧数、fps、深度 scale 和标定文件。 |
| `ffmpeg.log` | 是 | text | `rgb.mp4` / `depth.mkv` 封装过程中的 FFmpeg 日志。 |
| `rgb_debug.h264` | 可选 | Annex B H.264 | RGB MP4 修复旁路。录制期间同步写入与 `rgb.mp4` 输入一致的 H.264 码流；最终校验成功且 `write_debug_h264=false` 时自动删除，失败时保留。 |
| `depth_debug.raw` | 可选 | raw uint16 little-endian | 解压后的 depth 原始帧连续拼接，无文件头。 |

注意：如果设置了文件名前缀，以上文件名均会变为 `<prefix><原文件名>`；实际文件名以 `meta.json` 中对应字段为准。

## 4. RGB 视频格式

`rgb.mp4` 的内容来自发送端硬件编码后的 H.264 流。

当前链路：

```text
Orbbec RGB → 发送端 Rockchip/GStreamer H.264 硬编码 → TCP → 接收端 MP4 封装
```

接收端封装方式：

```text
ffmpeg -fflags +genpts -r <estimated_rgb_record_fps> -f h264 -i pipe:0 \
  -c:v copy -movflags +frag_keyframe+empty_moov+default_base_moof \
  -flush_packets 1 rgb.mp4
```

特性：

- 分辨率由发送端 RGB profile 决定。
- 当前最新发送端 preset 可输出 `1920x1080`。
- 接收端会先采样前几帧到达间隔，再按估算的实际到达帧率封装，写入 `meta.json` 的 `rgb_record_fps`。
- 播放流畅度由发送端实际送达帧率决定；如果实际只有十几帧，接收端不会插帧伪造 30fps。
- 接收端不会把 RGB 解码成 BGR 后再编码，因此不会额外引入转码损失。
- RGB 使用 fragmented MP4，`moov` 在文件头部，媒体数据按 fragment 落盘，降低 NAS/CIFS 收尾阶段异常导致整段缺 `moov` 的风险。
- MP4 容器内部 PTS 由 ffmpeg 根据输入帧率生成或 retime，不作为跨相机同步依据。
- 下游按 `rgb.mp4` 第 N 帧取图时，必须在 `frames.csv` 中筛选 `stream_type=rgb` 且 `rgb_recorded=1`，再用 `rgb_video_frame_index` 找对应 `frame_system_timestamp_us`。
- 如果下游需要逐帧 RGB 图像，正常情况下从 `rgb.mp4` 离线抽帧；只有 MP4 封装失败或配置显式保留 debug 时才使用 `rgb_debug.h264`。

示例探测结果：

```text
codec_name=h264
width=1920
height=1080
pix_fmt=yuv420p
avg_frame_rate=14909/1000
```

## 5. Depth 数据格式

### 5.1 `depth.mkv`

`depth.mkv` 是当前推荐下游读取的 depth 主文件。

编码方式：

```text
raw uint16 depth frame → ffmpeg rawvideo gray16le → FFV1 → Matroska
```

接收端写入命令：

```text
ffmpeg -f rawvideo -pixel_format gray16le -video_size <W>x<H> \
  -framerate <estimated_depth_record_fps> -i pipe:0 -c:v ffv1 -level 3 depth.mkv
```

特性：

- 像素格式：`gray16le`
- 每像素：16-bit unsigned depth
- 当前常见尺寸：`640x400`
- 编码：FFV1，无损
- 容器：Matroska
- 接收端会先采样前几帧到达间隔，再按估算的实际到达帧率封装，写入 `meta.json` 的 `depth_record_fps`。
- 配置项 `depth_fps` 只作为估算失败时的兜底值，不再强制把所有录像写成固定 30fps。

示例探测结果：

```text
codec_name=ffv1
width=640
height=400
pix_fmt=gray16le
```

### 5.2 网络 zlib 压缩与落盘格式

发送端可以将 Depth payload 用 `zlib` 压缩传输。

接收端处理逻辑：

```text
TCP payload(zlib) → 接收端 zlib 解压 → depth.mkv / depth_debug.raw
```

因此，无论网络层是 `none` 还是 `zlib`，落盘后的 `depth.mkv` 和 `depth_debug.raw` 都表示解压后的 uint16 depth 数据。

### 5.3 `depth_debug.raw`

`depth_debug.raw` 是连续拼接的原始 depth 帧：

```text
frame0 uint16le + frame1 uint16le + frame2 uint16le + ...
```

没有文件头。读取时必须从 `meta.json` 或 `frames.csv` 获取 width/height。

单帧字节数：

```text
depth_width * depth_height * 2
```

例如 `640x400` 单帧为：

```text
640 * 400 * 2 = 512000 bytes
```

## 6. `frames.csv` 字段说明

当前 CSV header：

```csv
local_time_us,stream_type,rgb_frame_id,rgb_timestamp_us,depth_frame_id,depth_timestamp_us,pair_id,pair_delta_ms,width,height,payload_size,packet_system_timestamp_us,rgb_system_timestamp_us,depth_system_timestamp_us,frame_id,timestamp_us,frame_system_timestamp_us,rgb_exposure_us,rgb_gain,rgb_auto_exposure,rgb_actual_fps,rgb_frame_interval_us,codec_or_compression,rgb_recorded,rgb_video_frame_index,rgb_recorded_payload_size
```

字段说明：

| 字段 | 类型 | 单位 | 说明 |
|---|---|---:|---|
| `local_time_us` | uint64 | us | 接收端写入该行时的系统时间，Unix epoch microseconds。 |
| `stream_type` | string | - | 当前行对应的媒体包类型：`rgb` 或 `depth`。 |
| `rgb_frame_id` | uint64 | - | 最近一帧 RGB 的发送端帧号。当前行是 depth 时也会带上最近 RGB 帧。 |
| `rgb_timestamp_us` | uint64 | us | 最近一帧 RGB 的发送端设备/SDK 时间戳。 |
| `depth_frame_id` | uint64 | - | 最近一帧 Depth 的发送端帧号。当前行是 rgb 时也会带上最近 Depth 帧。 |
| `depth_timestamp_us` | uint64 | us | 最近一帧 Depth 的发送端设备/SDK 时间戳。 |
| `pair_id` | uint64 | - | 协议预留的配对 ID，当前发送端通常为 `0`。 |
| `pair_delta_ms` | double | ms | 最近 RGB/Depth 时间戳差值。当前接收端优先用 `rgb_system_timestamp_us` / `depth_system_timestamp_us` 计算，缺失时才回退 `timestamp_us`。严格对齐仍建议下游按 `frame_system_timestamp_us` 做最近邻配对。 |
| `width` | uint32 | px | 当前媒体包宽度。 |
| `height` | uint32 | px | 当前媒体包高度。 |
| `payload_size` | uint64 | bytes | 当前媒体包 payload 字节数。Depth 落盘前会被解压，CSV 记录的是写入 segment 的 packet 大小。 |
| `packet_system_timestamp_us` | uint64 | us | 当前媒体包协议头中的发送端 system timestamp。 |
| `rgb_system_timestamp_us` | uint64 | us | 最近一帧 RGB 的发送端 system timestamp。 |
| `depth_system_timestamp_us` | uint64 | us | 最近一帧 Depth 的发送端 system timestamp。 |
| `frame_id` | uint64 | - | 当前行对应流自己的帧号。RGB 行为 RGB frame id，Depth 行为 Depth frame id。 |
| `timestamp_us` | uint64 | us | 当前行对应流自己的设备/SDK timestamp。 |
| `frame_system_timestamp_us` | uint64 | us | 当前行对应流自己的发送端 system timestamp。跨相机对齐优先读此列。 |
| `rgb_exposure_us` | int32 | us | 最近一帧 RGB 的曝光时间；发送端或 SDK 不提供时为空。 |
| `rgb_gain` | int32 | - | 最近一帧 RGB 的增益；发送端或 SDK 不提供时为空。 |
| `rgb_auto_exposure` | int32 | - | 最近一帧 RGB 是否自动曝光：`0` 关闭，`1` 开启；未知时为空。 |
| `rgb_actual_fps` | int32 | fps | SDK metadata 上报的 RGB 实际帧率；当前部分 Orbbec 设备不提供时为空。 |
| `rgb_frame_interval_us` | int64 | us | 当前 RGB 包与上一 RGB 包的 `frame_system_timestamp_us` 差值。重复包或重复帧时可能为 `0`。 |
| `codec_or_compression` | string | - | 当前行对应媒体包的编码或压缩方式。RGB 通常为 `h264`，Depth 落盘前解压后通常为 `none`。 |
| `rgb_recorded` | int | - | 仅 RGB 行有效。`1` 表示该 RGB 包实际写入 `rgb.mp4`，`0` 表示该 RGB 包未形成视频帧；Depth 行为空。 |
| `rgb_video_frame_index` | uint64 | - | 仅 `rgb_recorded=1` 时有效。从 `0` 开始，对应下游从 `rgb.mp4` 顺序解码得到的帧序号。 |
| `rgb_recorded_payload_size` | uint64 | bytes | 仅 `rgb_recorded=1` 时有效，表示实际写入 `rgb.mp4` 输入码流的 H.264 payload 字节数。 |

注意：

- 当前 CSV 是“媒体包索引”，不是严格的一行一组 RGBD 同步帧。
- `frames.csv` 的第 N 个 RGB 行不保证等于 `rgb.mp4` 的第 N 帧；录制起始阶段不可解码 H.264 包、编码器输出重复包或封装丢弃都会打破这个假设。
- 对应 `rgb.mp4` 视频帧时，必须筛选 `stream_type=rgb && rgb_recorded=1`，再用 `rgb_video_frame_index` 与视频帧序号匹配。
- 旧的 `rgb_*` / `depth_*` 字段会保留，用于快速查看当前 pair 双侧参考信息。
- 新增的统一字段 `frame_id` / `timestamp_us` / `frame_system_timestamp_us` / `codec_or_compression` 只描述当前行自己的帧，便于下游按单流读取。
- 如果下游需要严格 RGBD 配对，应优先使用 `pair_id`、`frame_system_timestamp_us`、`timestamp_us` 做二次对齐。
- `*_system_timestamp_us` 和 `frame_system_timestamp_us` 来自发送端系统时间，后续比 RGB/Depth SDK timestamp 更适合做跨流时间线对齐。
- `pair_delta_ms` 使用发送端 system timestamp 后可作为同一发送端 RGB/Depth 近似时间差参考；跨发送端 RGB 对齐仍应直接读取每行 `frame_system_timestamp_us` 做最近帧匹配。

## 7. RGB 视频帧索引使用方式

`frames.csv` 同时承担媒体包级日志和 RGB 视频帧级索引。下游做跨相机 RGB 画面对齐时，不应从 `frames.csv` 的第 N 个 RGB 行推断视频帧号，而应按以下规则读取：

```text
stream_type == "rgb" && rgb_recorded == 1
```

筛选后的 `rgb_video_frame_index` 从 `0` 连续递增，对应 `rgb.mp4` 顺序解码得到的帧序号；同一行的 `frame_system_timestamp_us` 是该视频帧的发送端系统时间戳，跨相机 RGB 同步优先使用该列。

| `depth_target_duration_sec` | Depth 按实际到达时间计算出的目标时长。 |

| `write_debug_depth_raw` | 是否写入 depth raw debug 旁路文件。 |

注意：如果接收端进程重启后立刻开始录制，且新的 `camera_announce` 尚未再次收到，`camera_announce_raw` 可能为空。下游强依赖标定时，应要求录制前确认已收到 announce，或后续将相机 announce 做持久缓存。

## 9. `calibration.json` 字段说明

`calibration.json` 是 `camera_announce` 的 segment 级展开文件，避免下游只依赖 `meta.json` 中被转义的 `camera_announce_raw` 字符串。

示例：

```json
{
  "schema": "gemini_calibration_v1",
  "sender_id": "orangepi5pro-b439137c",
  "camera_id": "cam02",
  "camera_key": "orangepi5pro-b439137c_cam02",
  "camera_name": "front_left",
  "storage_key": "front_left",
  "file_prefix": "test01_",
  "segment_start_us": 1778487946853997,
  "segment_end_us": 1778487948978256,
  "closed": true,
  "announce_timestamp_us": 1778487946800000,
  "alignment_mode": "raw_depth_to_rgb_offline",
  "depth_master": "depth_raw",
  "aligned_depth": {
    "generated": false,
    "target": "rgb",
    "output_file": "test01_depth_aligned_to_rgb.mkv",
    "method": "offline"
  },
  "device": {},
  "rgb_profile": {},
  "depth_profile": {},
  "calibration": {
    "available": true,
    "source": "orbbec_sdk",
    "data": {
      "depth_intrinsic": {},
      "rgb_intrinsic": {},
      "depth_distortion": {},
      "rgb_distortion": {},
      "d2c_transform": {},
      "is_mirrored": false
    }
  },
  "camera_announce_raw": ""
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `schema` | 当前固定为 `gemini_calibration_v1`。 |
| `sender_id` / `camera_id` / `camera_key` | 与 `meta.json` 一致，用于定位相机来源。 |
| `segment_start_us` / `segment_end_us` / `closed` | 与 `meta.json` 一致，用于确认该段标定对应的录像范围。 |
| `announce_timestamp_us` | 发送端生成 `camera_announce` 的时间戳。缺失时为 `0`。 |
| `alignment_mode` | 当前为 `raw_depth_to_rgb_offline`，表示实时录制仍保存原始 Depth，空间对齐由离线脚本生成。 |
| `depth_master` | 当前固定为 `depth_raw`，即 `depth.mkv` 是深度母版。 |
| `aligned_depth` | aligned depth 的状态和约定输出文件名。录制阶段通常 `generated=false`；如果手动对齐成功，会更新为 `generated=true` 并记录 sidecar、帧数、分辨率、fps。 |
| `device` | 发送端 `camera_announce.device` 原样展开。 |
| `rgb_profile` / `depth_profile` | 发送端当前 RGB/Depth 输出 profile。`depth_profile.depth_scale` 用于把 uint16 深度值换算成实际距离。 |
| `calibration` | 发送端 Orbbec SDK 标定输出，包含 RGB/Depth 内参、畸变参数和 Depth -> RGB 外参。发送端只有在 RGB 内参、Depth 内参和 D2C 外参均有效时才置 `available=true`。 |
| `camera_announce_raw` | 原始 announce JSON 备份。 |

如果录制开始时尚未收到 `camera_announce`，`device`、`rgb_profile`、`depth_profile` 会为空对象，`calibration.available=false`。下游强依赖空间对齐时，应检查 `calibration.available=true` 且 `calibration.data` 字段完整。离线对齐脚本还会校验 RGB/Depth 内参尺寸必须与当前视频/profile 一致，并拒绝 D2C 外参全 0 的 segment，避免生成无效的 aligned depth。

手动生成 aligned depth：

```bash
05_tools/run_align_depth_to_rgb.sh <segment_dir>
```

该脚本读取 `depth.mkv` 和同一 segment 的 `calibration.json`，输出 `depth_aligned_to_rgb.mkv` 和 `depth_aligned_to_rgb.json`，并把 `calibration.json.aligned_depth.generated` 更新为 `true`。对齐方法是把 Depth 像素按 Depth 内参反投影到 3D，再使用 `d2c_transform` 投到 RGB 坐标系；同一 RGB 像素有多个 Depth 点时保留最近深度。该产物是手动离线结果，不改变实时录制母版 `depth.mkv`。如果 Orbbec SDK 仅提供某个分辨率组合的完整标定，应使用该已标定组合录制或补齐目标分辨率对应的内参/外参后再对齐。

## 10. 当前格式与下游 PNG 方案的差异

| 项目 | 当前接收端格式 | 下游方案 |
|---|---|---|
| RGB 视频 | `rgb.mp4`，H.264 copy，不重编码 | `camera_00_<serial>_rgb_<W>x<H>_<fps>fps.mp4` |
| Depth 主数据 | `depth.mkv`，FFV1 gray16le，无损 | `depth_png/*.png`，逐帧 uint16 PNG |
| Depth 预览视频 | 当前仅 Web 实时预览，不落盘为 preview MP4 | `camera_00_<serial>_depth_preview_<fps>fps.mp4` |
| 元数据 | `meta.json` + `calibration.json`，segment 级 | `session.json` + 相机级 JSON |
| CSV | `frames.csv`，媒体包级索引 | `camera_00_<serial>_depth_frames.csv`，Depth PNG 帧索引 |
| 目录组织 | `<sender>_<camera>/<date>/<time>/` | `<session_name>/camera_00_*` |
| 时间戳 | 发送端 timestamp + 接收端 local_time | planned / emit / source 三层时间戳 |
| 多相机 | 每路相机独立目录 | 同一 session 下多个 camera 文件组 |

## 11. 给下游工程师的读取建议

### 11.1 如果可接受当前主格式

建议直接读取：

- RGB：用 FFmpeg / OpenCV / PyAV 读取 `rgb.mp4`
- Depth：用 FFmpeg / PyAV 读取 `depth.mkv` 的 `gray16le` 帧
- 时间索引：读取 `frames.csv`
- 元数据：读取 `meta.json`
- 标定/空间对齐：读取 `calibration.json`

这种方式文件数量少，适合 NAS 和长时间录制。

### 11.2 如果必须使用逐帧 PNG

建议不要实时替代当前主格式，而是在录制结束后做离线导出：

```text
depth.mkv → depth_png/*.png
frames.csv + meta.json + calibration.json → session.json / camera json / depth_frames.csv
```

原因：

- 逐帧 PNG 会产生大量小文件，对 NAS 和文件系统压力明显更大。
- 实时写 PNG 会增加 CPU 和 IO 抖动，影响接收端稳定性。
- 当前 `depth.mkv` 是无损主文件，足以作为导出源。

### 11.3 需要下游确认的问题

下游工程需要明确以下数据契约：

1. 是否能直接读取 `depth.mkv` 的 FFV1/gray16le。
2. 是否强制要求逐帧 `uint16 PNG`。
3. 是否接受保留实测到达帧率，还是需要离线重采样成固定 `15fps` / `30fps`。
4. 是否需要严格 RGBD 同步帧，还是可接受后处理按 timestamp 对齐。
5. 是否强依赖相机标定、serial、depth scale。
6. 是否要求所有相机落在同一个 session 目录。

## 12. 推荐后续改造

推荐保留当前格式作为主存储格式，再新增一个导出模式：

```json
{
  "delivery_export": {
    "enabled": true,
    "format": "orbbec_multi_rgbd_v1",
    "depth_png": true,
    "depth_preview_mp4": true,
    "session_json": true,
    "camera_json": true
  }
}
```

推荐分层：

```text
实时录制层：rgb.mp4 + depth.mkv + frames.csv + meta.json + calibration.json
交付导出层：session.json + camera json + depth_png + depth_frames.csv + depth_preview.mp4
```

这样可以同时满足：

- 实时接收和录制稳定。
- NAS 写入压力可控。
- 下游可以拿到他们熟悉的 PNG/CSV/JSON 目录结构。
- 后续多相机扩展时可生成统一 session。
