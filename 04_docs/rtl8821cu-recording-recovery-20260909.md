# LubanCat 录制缺帧的无线驱动对照与恢复

日期：2026-09-09。本文与 `recording-backlog-deployment-20260909.md` 连续阅读。
本文不是“全部问题已经根治”的声明；以下区分实测、推断和待验收项。

## 1. 症状与定位

`lubancat-52d2ef0c` 的相机输入接近 30 FPS，但 RGB/Depth 发送队列持续积压，
随后覆盖旧帧并触发 H.264 IDR 恢复。接收端和 NAS 队列当时没有对应积压。
原先的软件修复抑制了隐藏 TCP 队列、重复关键帧请求和错误录制验收，
但没有恢复这台设备的持续上行能力。

本轮在相同设备、相同 TP-LINK 5 GHz AP、保持其他发送端运行的条件下，
暂停该机采集，以独立 TCP 接收脚本测试，避免把编解码、NAS 或 CSV 算作网络吞吐。
测试发送脚本每次发送 2500 字节，按单调时钟间隔发送，阻塞后不突发追赶。
脚本调度本身有开销，所以目标速率不是实测速率或链路极限。

| 驱动/试验 | 目标 | 实际接收 | 实测均值 | 结果 |
| --- | --- | --- | --- | --- |
| 原 `rtw88_8821cu` | 8 Mbps | 12 MB / 20.123 s | 4.77 Mbps | 未跟上目标 |
| 原 `rtw88_8821cu` | 12 Mbps | 7.799 MB / 32.250 s | 1.93 Mbps | 到时间上限仍未传完目标 18 MB |
| 新版 rtw88 回移植分支 | 12 Mbps | 10.459 MB / 32.405 s | 2.58 Mbps | 未解决 |
| 原驱动，测试 socket 使用 AF41 DSCP | 12 Mbps | 12.210 MB / 32.143 s | 3.04 Mbps | 未解决，没有用于正式媒体 |
| Realtek 厂商派生 `8821cu` | 20 Mbps | 50 MB / 26.780 s | 14.94 Mbps | 全部传完，短测没有持续吞吐坍塌 |

这些是不同目标负载下的短测，不是最大带宽或一整天稳定性的保证。
2.4 GHz 临时连接能关联 AP，但没有恢复可用媒体，已自动回到原 5 GHz 配置并删除试验连接。

## 2. 驱动证据

- 内核：`6.1.99-rk3576`，ARM64；USB Wi-Fi：`0bda:c820`。
- 原内核模块：`rtw88_8821cu`；`ethtool` 驱动名：`rtw_8821cu`；固件：24.11。
- 原驱动的反汇编已经具有 8821C RFE 字段右移逻辑，不能把问题简单归因于缺少
  [2024 年 RFE 修复](https://github.com/lwfinger/rtw88/commit/9be45d8)。
- 新版 [rtw88 回移植](https://github.com/lwfinger/rtw88) 固定提交
  `a56bcd26e770257612a0803249cbd4095fc6feca` 能编译和加载，但媒体仍积压，已卸载。
- 有明显改善的 [厂商派生驱动源码](https://github.com/morrownr/8821cu-20210916)
  固定提交：`bda65aac150d2cde0df9603206eec23a6f3b77c4`。
  模块：`8821cu`；`ethtool` 名称：`rtl8821cu`；版本：
  `v5.12.0.4-1-g9241a6516.20210916`；固件：24.8。
- 本机编译使用该设备的内核 headers，GCC 11.4；内核原编译器为 GCC 10.3.1，
  构建有版本差异警告，但模块构建、符号检查和实际加载成功。
- 本次编译产物 SHA256：
  `9f36c75401f282d50b2ec4c07d0485438f30889b9221c0b1415dc89f5284315f`。
- 实测参数：`rtw_power_mgnt=0 rtw_ips_mode=0 rtw_drv_log_level=2`。
  没有修改发射功率、RFE 覆盖值、相机档位、码率、曝光或帧时间戳。

**可支持的结论**：原驱动/固件组合是本次持续上行异常的重要因素，换用另一组合后恢复明显。
因为驱动实现和固件一起发生变化，目前不能把问题精确归因到某一个寄存器或某一行代码，
也不能证明所有设备、所有历史断流都源于同一原因。

该厂商分支不是通用推荐：维护者优先推荐新版内核 rtw88，厂商分支未来内核兼容维护有限。
本项目只能按已验证硬件、内核、源码提交定向使用，不能给全部设备无条件替换驱动。

## 3. 已完成的软件修补

1. 增加 NetworkManager `up` / `reapply` 事件处理。
   网卡重新枚举或连接恢复后，异步执行每接口的队列调优，不阻塞联网流程。
2. 调优幂等：使用 `tc -j` 读取真实队列，已经是 `pfifo limit 128` 则不替换。
   避免重复事件清空现有队列；开机和重连调优使用锁协调。
3. 非目标驱动保持原样；接口已消失的过期事件安全返回。
4. 安装前验证部署文件齐全，避免半套文件覆盖现场配置。
5. 在 52d2 现场发现旧 systemd drop-in 多出一行无效的敏感内容，已清理；
   保留有效配置。原件仅保存在设备 root 可读的备份中，不进入仓库或公共归档。

自动验证：新增无线调优 7 项测试通过；现有部署脚本 11 项通过。
CTest 的 `deployment_scripts` 和 `sender_wifi_dispatcher` 两组通过。
实机验证：52d2 的队列上限由 256 自动恢复到 128；再次触发 `reapply`，
句柄保持 `8005:`，没有重建队列。e8 的异步调优服务退出状态为 0。

## 4. 第一轮跨切片实录：明确未全部通过

六路录制会话：`1788943598441389`，开始目录：`2026-09-09/164639`。
已录制 920 秒，覆盖一次 15 分钟切片。只有 52d2 使用厂商驱动，e8 保留原驱动。
12 个分片均交付 NAS，停止到交付状态完成约 25.95 秒，但严格验收 `ok=false`。

| 相机 | 首个 15 分钟 RGB/Depth 帧数 | 超过 500ms 的 RGB/Depth 间断 | 结论 |
| --- | --- | --- | --- |
| 52d2ef0c | 27018 / 27019 | 0 / 0 | 两个分片均 complete；RGB 编码前拒绝 1 个 JPEG 不完整帧 |
| e8cc0cb3 | 27020 / 27020 | 0 / 0 | 两个分片均 complete |
| ab748372 | 26277 / 26824 | 24 / 4 | 首片 partial，不能交付为完整数据 |
| b439137c | 27001 / 27059 | 0 / 0 | complete；曾有约 21 秒传输滞后，最终补齐 |
| fe0f7222 | 27007 / 27061 | 0 / 0 | complete |
| rk3588-ubuntu | 26993 / 27051 | 0 / 0 | partial：起始/切片等待关键帧导致边界滞后 |

全部 12 个分片的 CSV 未发现 global 时间戳倒退。六台相机跨切片的
RGB/Depth 源帧 ID 均增加 1，时间差约 27.2~41.5ms，即切片连接处本身没有缺帧。
帧数略高于 27000 的情况来自实际采集频率略高于名义 30 FPS，不用复制帧补齐。

ab 的采集继续维持约 30 FPS，16:57~16:59 连续出现 TCP 保留待发包与
CLOCK_SYNC 超时，接收写入队列和错误计数没有对应增长；RGB/Depth 源帧 ID
分别缺 732 / 236，与 sender 丢弃增量一致。证据定位为发送链路积压超过 900 帧缓冲，
不是 MP4 解码或 NAS 封装丢失。

52d2 的单个 JPEG 异常日志：16:59:10，`frame_id=25036`、139600 字节、
`missing jpeg soi/eoi marker`。这是编码前的输入检查，不是 TCP 接收坏帧。
没有保留该帧原始 payload，不能进一步断言是 USB 截断还是未支持的尾部形式。
没有通过补 EOI、复制上一帧、改时间戳或关闭校验来隐藏它。

## 5. 重启与部署验证

52d2 已将已验证的模块安装到
`/lib/modules/6.1.99-rk3576/updates/gwv3/8821cu.ko`，原内核模块没有覆盖。
启用 `06_configs/gwv3-rtl8821cu-modprobe.conf` 和
`06_configs/gwv3-rtl8821cu-modules-load.conf` 的定向配置。
第一次重启设置了 240 秒恢复保护；重启后已确认：

- Wi-Fi 自动使用 `rtl8821cu` / 固件 24.8；永久 MAC 不变。
- 相机仍为 USB 3.0 / 5000M，音频设备仍能枚举。
- sender 开机自启，RGB/Depth 约 30 FPS，CLOCK_SYNC 恢复有效。
- 首次开机恢复保护和临时试验回退定时器均已解除，不会随后突然切回旧驱动。

此覆盖仅适用于本次验证的内核。**升级内核前必须针对新内核重新编译/验证，
或先撤销覆盖配置，不能把当前 `.ko` 复制给其他内核使用。**
e8 没有换驱动；其他 Orange Pi 的 `wl` 驱动不在队列调优白名单内。

回退 52d2：停止该 sender，撤下 `/etc/modprobe.d/gwv3-rtl8821cu.conf`、
`/etc/modules-load.d/gwv3-rtl8821cu.conf` 和上述独立模块，执行
`sudo depmod -a` 后重启。必须保留原内核 `rtw88_8821cu` 模块和原 Wi-Fi 连接。
通过 Wi-Fi 远程执行时应准备本地恢复或延时回退，不能在唯一 SSH 会话中直接卸载网卡驱动。

## 6. 后续针对性修复与复验

ab 从 `666666` / 5220MHz 移到既有 `TP-LINK_5G_215E` / 5745MHz，
保留原网络作备选。新网络当前地址 `192.168.0.103`，receiver 仍为
`192.168.1.196`；相机身份和采集档位没有变化。
当前分组：TP-LINK 三台（52d2、e8、ab），666666 一台（b439），
88888888 两台（本机、fe）。单次换网会中断在途媒体，试验换网均在录制结束后执行。

本机关键帧请求改为由采集侧负责目标时刻，编码侧发立即执行的请求，
不重复使用帧的绝对系统时间作为 GStreamer running-time。
依据：[GStreamer ForceKeyUnit 说明](https://gstreamer.freedesktop.org/documentation/video/video-event.html)。
接口、帧 PTS、CSV 原始时间戳和 RGBD 配对保持原样。新增独立事件测试，
验证立即执行、重复请求、headers 标志和空目标处理。全部 sender CTest 10/10 通过；
本机 MPP 双分支 1080p 人工帧测试中请求第 43 帧，观察到第 43 帧 IDR。
旧实现的短人工帧测试也能通过，不能据此声称已复现所有长时间运行条件。

本机实录验证：17:20:17.967 收到开始控制，目标为 17:20:18.963，
17:20:18.983 发出一次关键帧请求，17:20:19.015 观察到 IDR。
目标到观察约 52ms；旧长测切片请求的目标到观察约 560ms。
还需用跨切片复验确认，不能只按这一个事件宣称长期稳定。

60 秒短录制 `2026-09-09/171832` 的六路文件均 complete、NAS 交付通过，
停止到交付状态完成约 18.16 秒。测试启动时本机正在恢复，初始在线清单只有五路，
本机随后加入并生成文件，因此这批不能替代预先六路全部在线的长测。

第二轮 920 秒六路复验已完成，开始目录 `2026-09-09/172018`，
下一片 `173518`。12 个分片均 complete，停止到 NAS 交付完成约 26.17 秒。
24 个 RGB/Depth 视频逐帧解码全部成功，解码帧数与 CSV 对应索引一致。
所有流没有 global 倒退、重复、无效 clock 行或超过 500ms 的内部间隔；
跨切片源帧 ID 均增加 1，采集时间差约 28.1~35.9ms。

52d2 首片 RGB/Depth 均为 27018 帧，没有源 ID 缺口。
e8 首片 27018/27020 帧，RGB 缺 2 个源 ID，最大间隔约 66.6ms。
其中 1 帧在编码前因 JPEG 不完整被拒绝；另 1 帧只有采集计数/源 ID 的缺口证据，
具体丢失位置尚未证明。不能将 complete 等同于每个采集帧均保留，也不能将这两帧都归为 USB 坏帧。

随后将六台主程序统一至 `c7423c61789f` 再做 120 秒验证，`2026-09-09/174353`
