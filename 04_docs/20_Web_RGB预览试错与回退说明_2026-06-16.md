# Web RGB 预览试错与回退说明

日期：2026-06-16

## 背景

多发送端同时工作时，接收端网页 RGB 预览出现卡顿。为降低网页预览压力，尝试过把网页 RGB 预览从旧版 JPEG 刷新切到 H264 视频流播放，并进一步尝试低码率独立预览流、自动重连和服务端 ffmpeg 清理。

现场验证后，当前视频流路线仍不够稳定，因此本次回退到旧版网页预览。

## 试错过程

1. H264 视频预览

   Web Monitor 增加 `/api/preview/rgb-video`，网页用 `<video>` 播放。后端通过 ffmpeg 把接收端的 H264 裸流临时封装成浏览器可播放的 fragmented MP4。

2. 低码率 RGB 独立预览流

   发送端增加低码率 `rgb_preview` 流，目标是保留录制 RGB 质量，同时让网页预览走低带宽版本。

3. 自动重连与卡顿检测

   前端增加视频帧进度检测，检测到长时间无新帧时重建视频连接。

4. ffmpeg 进程清理

   Web Monitor 增加服务端子进程清理逻辑，尝试避免浏览器刷新、断开或重连后残留多个 ffmpeg。

## 发现的问题

1. 浏览器端视频预览在多路情况下仍会卡顿或停在旧帧。
2. 同一路 RGB 预览可能残留多个接收端 ffmpeg 子进程，说明浏览器连接断开和服务端清理之间仍存在不稳定边界。
3. 低码率预览降低了单路预览带宽，但没有彻底解决网页端刷新不稳定。
4. 该路线增加了接收端 Web Monitor 的复杂度，现场可维护性下降。

这些问题属于接收端网页预览链路问题，不代表发送端重复采集，也不代表主 RGB/Depth 录制数据被修改。

## 本次回退

本次回退范围：

1. `09_web_monitor/server.py`

   回到旧版代理接口，仅保留 `/api/preview/rgb`、`/api/preview/rgb-main`、`/api/preview/depth` 等图片预览接口。网页预览不再由 Web Monitor 启动 ffmpeg。

2. `09_web_monitor/static/index.html`

   回到旧版 JPEG 刷新模式。主 RGB 按约 30Hz 请求 `/api/preview/rgb-main`，小窗口 RGB 按约 30Hz 请求 `/api/preview/rgb`，Depth 预览保持原逻辑。

3. `02_receiver_linux/src/main.cpp`

   重新打开 `kEnableJpegMainPreview`，保证旧版网页请求 `/api/preview/rgb-main` 时可以拿到主 RGB JPEG 预览。

   低码率 `rgb_preview` 流存在时，JPEG 图片预览优先从该低码率流解码，避免旧版网页回退后重新压高主 RGB 录制流压力；如果发送端没有 `rgb_preview` 流，则回退到主 RGB 流解码。

   为避免某一路预览帧稍大或 ffmpeg 解码管道短暂回压时小窗口变成空白，接收端保留上一张 JPEG 作为兜底；同时将 RGB 预览写管道预算提高到 25ms。

   2026-06-16 后续排查发现，主 RGB 预览专用解码器的请求保活窗口过短时，网页端偶发旧请求卡住会让主预览 ffmpeg 被接收端清理并反复重启；后端 `/api/preview/rgb-main` 仍可能通过普通 RGB 预览 fallback 返回变化图片，但网页主画面看起来会停在旧帧。接收端已将主 RGB 预览保活窗口单独放宽，并在状态接口中把 fallback 可用性也报告为 `main_rgb_preview_available`，降低主画面误判为不可用或反复重启的概率。

## 保留内容

接收端底层已经存在的 H264/低码率预览相关代码暂时不删除，避免影响后续排查和兼容性；但当前 Web Monitor 回退后不再调用视频预览路径。

## 后续建议

如果后续继续优化网页预览，建议不要再使用“每个浏览器连接启动一个 ffmpeg”的方式。更合适的方向是：

1. 接收端只保留一个预览转码/分发实例，同一路相机由多个浏览器共享。
2. 使用更标准的浏览器实时视频方案，例如 WebRTC 或稳定的 MSE 长连接。
3. 将录制链路和网页预览链路彻底隔离，网页预览丢帧不能影响接收端录制和主数据接收。
4. 每次预览路线改动都要同时验证：多浏览器刷新、断网重连、关闭页面、四路相机同时在线、接收端 CPU/内存/网络队列。

## 验证方法

回退后验证重点：

1. 接收端 Web Monitor 页面打开后，主 RGB 能刷新，不再产生新的 `ffmpeg ... /api/preview/rgb-h264` 预览进程。
2. `gwv3-gemini-receiver.service` 和 `gwv3-web-monitor.service` 均为 `active`。
3. 接收端 `/api/status` 中各路相机仍有 RGB/Depth FPS 和码率数据。
4. 录制开始、停止后 RGB MP4 和 Depth MKV 可正常落盘。
