## 范围

复核用户反馈的北京时间 13:11:20—13:22:04 录制，目录 `2026-09-10/131120`，会话 `1789017079849223`；录制窗口精确长度 643.418316 秒。

对照 AP 调整后的 `2026-09-10/133814` 首个 900 秒完整切片，会话 `1789018693072820`。两路均为 `lubancat-52d2ef0c_cam01`、`lubancat-e8cc0cb3_cam01`。

## 三项确认结果

### 1. 大量缺录主要发生在编码后发送/网络排队阶段

| 指标 | 52d2 | e8 |
| --- | ---: | ---: |
| RGB 记录帧数 | 11,266 | 15,551 |
| RGB 相邻源帧 ID 缺失数 | 8,050 | 3,766 |
| 最大正向 global 帧间隔 | 1.532753 s | 2.331816 s |
| RGB 视频索引缺口 | 0 | 0 |
| Depth 记录帧数 | 19,316 | 19,317 |
| Depth 相邻源帧 ID 缺失数 | 0 | 0 |
| 采集到绑定时间中位数 | 44 us | 25 us |
| 编码耗时中位数 | 33.586 ms | 34.554 ms |
| 编码耗时 p95 | 45.497 ms | 38.297 ms |
| 入发送队列到 receiver 中位数 | 27.248159 s | 23.406929 s |
| 入发送队列到 receiver p95 | 30.513097 s | 30.237519 s |

这些是实际收到帧的统计，无法直接还原每个已丢帧的全部生命周期。源 ID 缺失数与 `窗口秒数*30-已录帧数` 不完全相同，因为相机实际帧率并非数学上精确的 30.000 Hz。

同期状态显示采集约 30fps，RGB 发送显著下降、发送端丢弃计数增加，receiver 录制队列为 0、无写入错误。结合此前到 AP/receiver 延迟和 AP 调整对照，支持发送/无线瓶颈导致积压、发送端有界队列不能保住所有帧，而不是相机曝光造成秒级停采，也不是这批 NAS 写入慢导致 RGB 被丢。

`sender_packet_queued_to_receiver_us` 包含应用队列、TCP 发送、网络和接收处理，且两端时钟存在误差；不能把它全称为空口传播时间。但数十秒量级远大于本次毫秒级 offset，不影响主要积压阶段判断。

不能仅凭这些证据确定 AP 固件、客户端驱动、空口竞争各占多少，也不能逐帧归因所有缺失均发生在同一丢弃位置。源码中的 `record_queue_overwrite` 会累计 `rgb_dropped`，需要继续区分细分丢弃计数。

### 2. 固定帧率封装确实丢失了真实采集间隔

[ensure_rgb_pipe](../02_receiver_linux/src/detail/recording.inl) 当前命令包含：

```text
-fflags +genpts -r 30 -f h264 -i pipe:0 -c:v copy
```

`write_rgb_packet` 写入 pipe 的只有 H.264 payload，没有将对应 CSV 中的采集/global 时间传给封装器。裸 H.264 输入因此生成固定步长 PTS。

NAS 上两份实际文件分别经 `ffprobe` 验证：

- 52d2：375.533333 秒，`avg_frame_rate=30/1`，等于 11266/30。
- e8：518.366667 秒，`avg_frame_rate=30/1`，等于 15551/30。

meta 中的 `rgb_media_duration_us`、`rgb_target_duration_sec` 来自采集时间跨度，不是已经实现的 MP4 PTS；`rgb_retime_scale` 也只是计算出的元数据。当前 `fragmented_mp4` 直接交付不会将它应用到逐帧 PTS。

问题不在 fMP4 容器本身。换成普通 MP4 或对整个文件做一个线性倍率变速，也不能恢复每个局部缺口的真实位置。Depth 当前 `rawvideo -framerate` 输入同样不携带逐帧时间，只是这批 Depth 帧连续，使问题不明显。

### 3. 校时失效行均对应历史模型超过 10 秒期限

| 指标 | 52d2 RGB | e8 RGB |
| --- | ---: | ---: |
| clock_sync_valid 无效 | 1,208 | 5,717 |
| 无效行最小模型年龄 | 10.001552 s | 10.004352 s |
| 无效行最大模型年龄 | 31.432760 s | 42.570513 s |
| 有效行最大模型年龄 | 9.996852 s | 9.995423 s |
| global 时间戳倒退 | 0 | 0 |

模型年龄按 `frame_system_timestamp_us-clock_model_reference_timestamp_us` 计算。与 [ClockSyncTimeline::map](../02_receiver_linux/src/clock_sync_manager.cpp) 的历史模型有效期判定一致。Depth 也存在 2,799 / 7,236 行校时无效，说明不能把问题简单解释成“只有迟到的 RGB 被按当前时间误判”。

52d2 同期 sender 日志有多次 `clock_sync probe timeout or invalid response`，例如 13:11:03、13:11:18、13:11:28、13:11:43。receiver 模型更新仍间歇存在，但不足以保证每个历史采集时刻都有新鲜有效模型。

当前模型实现会保留历史估计并将过期状态标为无效，避免直接硬切时间轴；不能为了改善统计把 `clock_sync_valid` 强制置为 true。无效不等于本批发生时间戳倒退，但这些帧不能宣称具备可信的跨设备精度。

已知录制墙钟窗口仍可计算 `帧数/窗口秒数`，不需要因为存在无效行就否认窗口平均记录帧率。需要谨慎的是逐帧跨机对齐的精度和可信度。

## 后续修复与验收要求

1. RGB 录制采用可携带时间戳的封装输入或直接 muxer：在帧写入时绑定 PTS/DTS，以真实采集/全局时间相对录制窗口起点生成时间轴。先确认 H.264 是否含 B 帧，不能盲目将 PTS 等同 DTS。
2. 保留原 CSV 和 `rgb_video_frame_index` 的一帧一索引，不补造母版图像。缺口应表现为真实 PTS 间隔；首尾不足仍需显式标记，不能无条件拉到目标窗口长度。
3. 覆盖正常帧、1 秒丢帧、首帧迟到、尾帧缺失、15 分钟切片、时间戳倒退/过期、重连、崩溃恢复和音视频对应测试。用 `ffprobe -show_packets` 对照 CSV，不只验证可播放和总时长。
4. 时钟链路保留独立线程与通道，增加探测超时/样本拒绝原因、模型新鲜度和 holdover 状态统计；改善调度、无线排队并评估不确定度，不能靠放宽有效期掩盖误差。
5. 发送端补充每阶段丢弃原因及队列年龄观测。必要时在不改分辨率/帧率的前提下评估码率和预览竞争；长期带宽不足不能仅靠加大内存缓冲解决。
6. 历史已发布目录不原地覆写；需要按 CSV 修复播放时间轴时，应输出独立派生文件并标明缺帧及不可信同步区间。

上述 PTS 改造尚未实现和部署。本次仅完成复核与归档；生产录制保持运行。
