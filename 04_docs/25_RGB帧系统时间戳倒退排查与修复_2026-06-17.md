# RGB 帧系统时间戳倒退排查与修复说明

日期：2026-06-17

## 1. 问题现象

下游反馈 `orangepi5pro-2bfc47e0_cam02/2026-06-17/112218/test_Short_0015_frames.csv` 中，约第 526 个 RGB 帧后 `frame_system_timestamp_us` 反复倒退和前跳，导致同步脚本把后半段拆成大量小窗口，最终导出视频呈现低帧率逐帧播放。

同一段数据用 `local_time_us` 快速验证时窗口正常，说明接收端本地写文件时间线是单调的，但发送端随 RGB 包携带的帧系统时间戳已经异常。

## 2. 定位结论

排查接收端落盘文件后确认：

1. RGB 行的 `frame_system_timestamp_us`、`packet_system_timestamp_us`、`rgb_system_timestamp_us` 一致，接收端没有单独改坏某一列。
2. 坏点同时伴随 `frame_id` 回退，例如从新帧回到旧帧号，再跳回新帧号。
3. `rgb.mp4` 本身帧数和时长接近 30fps，异常主要来自 CSV 中同一路 RGB 帧号和系统时间戳被旧值重复绑定。
4. 2026-06-17 扫描到的坏段集中在 `orangepi5pro-2bfc47e0_cam02`；其他在线发送端同名任务未复现同类倒退。

根因在发送端 RGB H.264 编码输出与采集帧 timing 的绑定逻辑：旧逻辑优先用编码输出 PTS 回查采集 timing，遇到 `mpph264enc` 输出 PTS 缺失或偏移时会走 fallback，但 fallback 没有消费 timing 队列，导致旧 timing 仍留在队列里。后续编码输出再匹配到旧 timing 时，就可能把旧 `frame_id` 和旧 `system_timestamp_us` 重复发给接收端。

## 3. 修复内容

发送端修复：

1. `resolve_rgb_encode_timing()` 改为无论 PTS 匹配还是 fallback 都消费 timing 队列。
2. PTS 精确匹配成功时，删除匹配点之前的旧 timing，避免积压。
3. PTS 缺失或不可信时，按 FIFO 取最早采集 timing，保证编码输出顺序和采集顺序一致。
4. 增加 RGB 编码输出单调性保护：如果选中的 `frame_id` 或 `system_timestamp_us` 不大于上一帧，直接丢弃该编码包，并等待下一个 IDR。
5. 增加 `rgb_timing_mismatch_drops` 计数，便于运行日志中观察是否发生过真正的时间戳回退丢弃。
6. `mpph264enc max-pending=2` 改为运行时探测属性，插件支持才启用；旧板卡插件不支持该属性时自动退回原 pipeline，避免 `encoder_init_failed: no property "max-pending"`。

接收端修复：

1. `rgb_recorded_frames.csv` 合并到 `frames.csv` 时，重复 RGB key 不再覆盖第一次记录。
2. `frames.csv` 自身出现重复 RGB key 时，后续重复行标记为 `rgb_recorded=0`，避免同一个视频帧索引被多个 CSV 行复用。
3. 缺少 `frame_id`、`timestamp_us` 或 `frame_system_timestamp_us` 的行不生成合并 key。
4. 出现重复 key 时写入 receiver 日志，方便回溯坏段。

## 4. 下游使用建议

新数据仍推荐使用：

```text
frames.csv
stream_type == rgb
rgb_recorded == 1
rgb_video_frame_index 对应 rgb.mp4 的帧序号
frame_system_timestamp_us 用于跨发送端 RGB 时间对齐
```

`local_time_us` 只建议用于已经录坏的历史数据临时救急。新版本的目标是让 `frame_system_timestamp_us` 保持单路单调，继续作为下游对齐主列。

本地验证：

```text
cmake --build 12_build_sender_check --target gemini_sender -j$(nproc)
cmake --build 12_build_receiver_check --target gemini_receiver -j$(nproc)
clang-tidy sender/receiver touched files
git diff --check
```

在线验证结果：

1. 两台 OrangePi 发送端 RGB/Depth 均恢复接近 30fps。
2. `rgb_timing_mismatch_drops=0`。
3. 旧 `mpph264enc` 仍可能周期性打印 PTS mismatch fallback，这是编码器 PTS 偏移导致的保护路径；当前 fallback 会按 FIFO 消费采集 timing，不再重复使用旧 `frame_id` 和旧 `frame_system_timestamp_us`。
