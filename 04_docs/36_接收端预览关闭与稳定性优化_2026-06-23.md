# 接收端预览关闭与稳定性优化记录

日期：2026-06-23

## 背景

多设备三路发送时，网页预览已经关闭，但接收端仍可能保留预览相关负载：

- 接收端状态接口仍把有 RGB 包的相机标记为 `rgb_preview_available=true`，网页端或残留连接会继续拉取预览。
- 接收端 RGB 预览请求会触发 `ffmpeg` 解码进程。
- 接收端每个 depth 包会生成 BMP 伪彩预览。
- 本机双路发送端配置仍开启本机 OpenCV 预览和 `web_rgb_preview` 小码流，即使当前录制不需要预览。

这些负载与主链路采集、传输、落盘竞争 CPU 和网络，表现为接收端 CPU 高、残留 ffmpeg 进程、TCP 队列积压，以及本机双路 depth 到达帧率下降。

## 本次代码改动

接收端新增 `preview_enabled` 配置项：

- 默认值为 `true`，保持旧配置兼容。
- `06_configs/receiver_ubuntu-01.json` 显式设置为 `false`，当前接收端默认关闭预览。
- `/api/status` 和 `/api/config` 输出 `preview_enabled`。
- `preview_enabled=false` 时：
  - `rgb_preview` / `main_rgb_preview` / `depth_preview` 接口不再返回图像。
  - H264 预览流接口返回 `preview disabled`。
  - 不再更新 RGB 预览环形缓存。
  - 不再启动或喂入 RGB 预览 ffmpeg 解码器。
  - 不再对 depth 包生成 BMP 伪彩预览。

接收端远端部署时，当前运行分支已有 `preview_udp_enabled`，已在运行配置中一并关闭，避免 preview UDP 线程继续占资源。

2026-06-23 追加根因修复：

- 接收端预览改为按需处理。只有网页或 API 最近请求过 RGB/Depth 预览时，接收端才缓存 H.264 预览流、喂入 RGB 预览解码器、生成 Depth BMP 伪彩。
- 网页端读取 `/api/status` 的 `preview_enabled`。关闭时不再继续请求 RGB/Depth 预览接口，并清掉旧图片，避免“预览关了但浏览器还在拉流”。
- `--no-preview` 现在同时关闭发送端本机 OpenCV 预览和 `web_rgb_preview` 小码流，避免后台启动时仍编码、发送网页预览流。
- 预检脚本会打印 `config_web_preview`，启动项会明确显示 `launch_preview: local/web preview disabled by --no-preview`。
- `stop_receiver.sh` 会额外清理同仓库残留的 `uvicorn server:app` 进程，避免 PID 文件过期或 systemd 重启后出现多个网页服务抢占 8080。
- `prepare_rk3588_usb.sh` 将 `usbfs_memory_mb` 提高到 256、关闭 USB autosuspend，并将 `net.core.wmem_max/default` 提高到 `33554432/4194304`，让最高深度档和 Orange Pi 当前 32MiB 发送缓冲配置实际生效。

这部分是根因修复：录制或无浏览器访问时，预览链路不再消耗 CPU、内存带宽、ffmpeg 子进程和网络；需要临时查看画面时，再由网页请求触发短期预览处理。

## 现场额外发现

接收端 `192.168.66.196` 同时残留了 system 级 `gwv3-web-monitor.service` 和 user 级 `gwv3-web-monitor.service`。两套服务都会启动同一个 `uvicorn server:app --port 8080`，system 级服务抢不到端口后进入失败重启循环，表现为间歇出现第二个 `uvicorn`、网页卡顿、PID 文件与实际 MainPID 不一致。

现场已保留 user 级服务，禁用 system 级服务：

```bash
sudo systemctl disable --now gwv3-web-monitor.service
systemctl --user status gwv3-web-monitor.service
```

后续检查应确认 `ss -ltnp | grep :8080` 只有一个监听进程，且 `systemctl is-active gwv3-web-monitor.service` 为 `inactive`，`systemctl --user is-active gwv3-web-monitor.service` 为 `active`。

## 结论

当前系统瓶颈不是单一 Wi-Fi 问题。接收端预览解码、depth 伪彩生成，以及本机发送端残留预览编码共同占用了资源。关闭这些非录制必需路径后，三路主数据链路恢复到接近目标帧率。

建议后续录制稳定性优先时保持 `preview_enabled=false` 和发送端 no-preview。若要恢复网页预览，应走独立的低码率视频预览通道，并明确控制预览客户端数量、分辨率、码率和生命周期。
