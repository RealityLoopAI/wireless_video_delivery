# 接收端多发送端优化建议 2026-06-09

## 1. 背景

当前现场前提：

```text
网络设备与拓扑尽量不改
多发送端可能长期同时在线
不优先通过降低发送端规格解决问题
```

在此前提下，接收端仍有可做的优化空间，但重点不应理解为“简单增加线程数”，而应优先减少接收路径中的耦合、无效处理和争用。

## 2. 当前实现特点

接收端已经不是单线程：

```text
udp_loop      状态接收线程
tcp_loop      媒体监听线程
admin_loop    管理接口线程
每个 media TCP client accept 后再单独起线程处理
RGB 预览解码器内部也有独立 reader 线程
```

因此，多发送端互相影响的主要原因通常不是“没有多线程”，而是：

```text
多个发送端共享同一接收端 CPU / 内存 / 磁盘 / 预览解码 / 落盘处理
媒体接收线程在收包后仍承担了较多后续处理
非关键处理没有和主收包链路充分隔离
```

## 3. 建议优先级

### 3.1 第一优先级：收包与重处理解耦

建议将当前 `media_client_loop -> handle_media_packet()` 的同步处理链拆成三层：

```text
1. socket 收包线程：
   只负责 recv、协议解析、基础校验、轻量计数

2. per-camera 有界队列：
   每路 sender_id/camera_id 单独排队

3. 异步 worker：
   预览 worker
   录制 worker
   统计 / 导出辅助 worker
```

收益：

```text
某一路 preview / record 变慢时，不直接阻塞 TCP 收包
更容易做丢帧策略
更容易观察是哪一段先满
```

### 3.2 第二优先级：预览改成按需和分级

当前预览链路对多发送端影响很大，尤其是：

```text
RGB 预览解码
主预览高分辨率 RGB 解码
Depth 预览图生成
```

建议：

1. 非主预览路降低刷新频率，例如固定 3~5fps。
2. 无人查看的相机不持续生成预览。
3. Depth 预览默认低频更新；仅主查看路维持较高频率。
4. Web 页面只保一路主预览高规格，其余路使用低频缩略图。

后续升级方向：将 Web 预览从“连续 JPEG/MJPEG 拉图”改成低码率视频流。当前 JPEG 预览每一帧都是完整图片，浏览器高频拉图时容易把接收端到网页端的带宽推到几十 Mbps；后续可单独生成一条低码率 H.264 预览流，例如：

```text
960x540 @ 10fps, H.264 1.5~3Mbps
1280x720 @ 15fps, H.264 3~6Mbps
```

预期收益：

```text
Web 预览打开时，网络压力可从几十 Mbps 降到约 3~8Mbps
预览带宽降幅通常可达到 80%~95%
发送端原始 RGB H.264、Depth 数据和 NAS 落盘质量不受影响
```

实现选项：

1. 低延迟优先：WebRTC 或 fMP4/MSE。
2. 稳定性优先、可接受秒级延迟：HLS。
3. 低风险过渡版：仍保留当前 JPEG 预览，同时新增可选低码率视频预览入口。

收益：

```text
减少 CPU 占用
减少多路并发时的预览争用
降低“有人打开页面就把媒体处理拖慢”的概率
```

### 3.3 第三优先级：引入明确的背压降级策略

当前 sender 已经能看到接收端消费变慢后出现背压。接收端侧也应更主动地做“保主链路、牺牲次要处理”。

建议策略：

1. 收包优先于预览。
2. 录制主数据优先于非主预览。
3. 队列满时先丢旧预览帧，不先阻塞收包线程。
4. 主预览优先级高于普通 RGB 预览，普通 RGB 预览优先级高于 Depth 预览。

不要做的事：

```text
队列无限增长
为保证所有预览实时而拖慢录制或收包
让单路异常把所有 sender 一起拖慢
```

### 3.4 第四优先级：录制和后处理异步化

录制相关工作建议进一步与实时收包隔离：

1. 录制写入使用独立队列。
2. 分段关闭、retime、补写 meta、导出等动作不要阻塞实时媒体处理。
3. 如果磁盘或 NAS 抖动，优先影响录制队列，不直接影响在线收包。

说明：

```text
接收端如果既负责实时预览，又负责多路录制，还负责导出/retime，
必须把“实时路径”和“离线路径”拆开。
```

### 3.5 已落地：TCP 接收缓冲放大

2026-06-12 已在接收端代码中对媒体 TCP listen socket 和每个 media client socket 设置 `SO_RCVBUF=16MB`。Linux 内核会按内部记账显示约 2 倍，现场可用以下命令确认每路 `skmem` 中的 `rb33554432`：

```bash
ss -tinmp state established '( sport = :50010 or dport = :50010 )'
```

接收端系统参数也需要放大并持久化：

```text
net.core.rmem_default = 4194304
net.core.rmem_max = 33554432
net.ipv4.tcp_rmem = 4096 1048576 33554432
net.ipv4.tcp_moderate_rcvbuf = 1
```

该改动只能缓冲 Wi-Fi 或 CPU 的短时抖动，不能解决长期处理不过来的情况。如果 `Recv-Q` 持续增长，仍应优先关闭 Web 预览/ffmpeg 转码，或继续推进收包与预览/录制解耦。

## 4. 可以落地的最小改动版

如果希望先做低风险优化，建议顺序：

1. 非主预览降频。
2. Depth 预览按需生成。
3. 主预览切换时再启动对应 main RGB decoder，其余路不保主预览链路。
4. 对每路相机增加小的有界媒体队列，收包线程只负责入队。
5. 当预览队列满时丢最旧帧，不阻塞。

这个版本不要求整体重构，但通常已经能明显降低多发送端互相拖累。

## 5. 中等改动版

如果允许改动接收端媒体主链路，建议进一步做：

1. 每路相机独立 `media queue`。
2. `preview worker` 和 `record worker` 分离。
3. 统计每路队列长度、丢帧次数、处理耗时，并在 `/api/status` 输出。
4. 为不同任务定义优先级：

```text
收包 > 录制主数据 > 主预览 > 普通 RGB 预览 > Depth 预览
```

这个版本会比“多开几个线程”更有效，因为它真正减少了共享热点。

## 6. 不建议优先做的事

### 6.1 盲目增加线程数

原因：

```text
当前实现已经有多线程
CPU / cache / memory bandwidth 仍是共享资源
线程数增加后可能只会放大竞争和上下文切换
```

### 6.2 队列无限放大

原因：

```text
只会把瞬时卡顿变成长尾延迟
最终仍会在 sender TCP Send-Q 或接收端内存侧爆出来
```

### 6.3 为了保所有预览实时而让主链路退化

原则：

```text
预览是观察功能
收包和录制才是主链路
```

## 7. 观测项建议

如果后续要持续优化，建议接收端增加以下指标：

1. 每路媒体队列长度。
2. 每路预览丢帧次数。
3. 每路录制写入耗时。
4. 每路 preview / record worker 平均处理耗时。
5. 每路最近 10 秒实际处理 fps。
6. 全局活动 media clients 数与主预览 key。

这些指标应进入 `/api/status`，否则现场只能看 sender Send-Q，定位不够直接。

## 8. 建议结论

在“不改网络设备、不优先降档”的约束下，接收端最值得做的优化不是“再加线程”，而是：

1. 收包与预览/录制解耦。
2. 预览按需、分级、低频化。
3. 背压时优先牺牲预览，不拖主数据。
4. 将录制和后处理从实时链路剥离。

如果后续要正式实施，推荐先从“非主预览降频 + Depth 预览按需 + per-camera 有界队列”开始。
