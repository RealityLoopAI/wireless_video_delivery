## 代码确认的时间边界

- Sender 在编码完成、准备发布 MediaPacketJob 前记录 packet_queued 时间。它不代表 TCP 已发送或对端已确认。
- Receiver 在 read_media_packet_into 完整读取和解析后，进入 handle_media_packet 时记录 receiver_receive_timestamp_us。
- 此字段不是内核网卡到包时间。上一包处理阻塞会延后读取下一包，因此时间差不能全算作无线时延。
- 录制队列有界且容量满时会等待，这是数据保留策略；不能未经定位改成丢弃数据，只求预览数字好看。

## 本次代码修改

1. MediaPacketJob 保留单调时钟创建时间和首次发送尝试时间，重试时一起移动，不重置。
2. 原 send_ms 仅统计最后一次 send_media 调用；现改为从首次尝试到成功/失败的完整时间，包括背压重试及其间隔。
3. 延迟超过 250 ms 时，限频记录 camera、stream、frame、queue_ms、send_total_ms 和 sent。
4. 同时记录 TCP 发送队列字节、RTT、RTO、未确认包和累计重传计数。累计重传必须比较差值，不能当作本帧重传量。
5. Receiver 拆出 read_wait_ms、handle_ms，并记录处理结束时 socket_unread_bytes。任一耗时超过 250 ms 时限频输出，关联 frame/session。
6. sender.log 原来只保留 .1，改为最多 .1–.8，连同活动日志共最多 9 份。按配置的每文件容量轮转，不承诺固定保存天数。

250 ms 是诊断触发阈值，不是已经商定的业务验收阈值。诊断限频每连接/发送工作循环约一秒，不是每一异常帧必然都有日志；正常发送不持续记录 TCP 历史。这些限制应在解读结果时保留。

## 下次出现时如何定位

| 组合证据 | 优先排查，不是单指标定罪 |
| --- | --- |
| queue_ms 大 | Sender 出队不及时、前序包发送阻塞或调度延迟 |
| send_total_ms 大、TCP 队列高、重传差值增加 | 网络丢包/重传、拥塞及接收窗口；必要时补充抓包 |
| Receiver read_wait_ms 大，handle_ms 小 | 此连接长时间没完整读到包；仍可能是源端没有交付、网络或线程调度 |
| Receiver handle_ms 大，socket_unread_bytes 高 | 接收侧处理使后续包留在 socket，包括录制队列背压/锁/预览路径 |
| 两者都不大但跨帧异常 | 需要核查日志限频、系统调度和内核到包时刻，不能强行套上述结论 |

TCP send 成功只说明数据被本机内核接受，不保证 receiver 已到达；诊断不会改变这一事实。
