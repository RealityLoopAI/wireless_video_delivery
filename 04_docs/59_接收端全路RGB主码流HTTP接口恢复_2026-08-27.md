# 接收端全路 RGB 主码流 HTTP 接口恢复

日期：2026-08-27

## 结论

恢复 2026-08-11 已确定的全路 RGB 主码流方案，不新增 sender 直推，也不使用 receiver RTP 盲推：

```text
各 sender 的 RGBD 主链路
  -> receiver 192.168.66.196
  -> HTTP 8080 自动发现和按相机独立拉流
  -> 下游客户端按需并发连接所有在线 RGB 主码流
```

下游先调用：

```http
GET http://192.168.66.196:8080/api/status
```

然后为每个 `online == true && media_live == true` 的相机建立独立连接：

```http
GET http://192.168.66.196:8080/api/preview/rgb-h264-frames?sender_id=<sender_id>&camera_id=<camera_id>&quality=main&metadata=global
```

响应体是连续的 `GWHP v2 header + Annex-B H.264 access unit`。它保留 `timestamp_us`、`global_timestamp_us`、关键帧标志、宽高和流序号，适合下游解码、实时处理和近邻时间匹配。

## 本次恢复内容

新 receiver 迁移后，Web 层仍使用默认值：

```text
GWV3_WEB_MAX_MAIN_STREAM_CLIENTS=2
```

这会使第 3 路主码流收到 HTTP `503 main stream capacity reached`。生产配置现恢复为：

```text
GWV3_WEB_MAX_MAIN_STREAM_CLIENTS=16
```

16 个名额可容纳当前全路相机和额外联调客户端。每个客户端仍是独立有界实时读取；慢客户端不能阻塞 receiver 录制链路。

对应持久化位置：

- `06_configs/receiver_loop.json` 的 `web_max_main_stream_clients`
- `05_tools/install_receiver_autostart.sh` 生成的 Web systemd unit
- `05_tools/systemd/gwv3-web-monitor-multistream.conf` 现场 drop-in

## 与临时 RTP 直推的区别

2026-08-25 的 RTP 功能仅用于指定 sender 停止正常 RGBD 上传后，向固定主机直推一路 RGB。它不携带 GWV3/CLOCK_SYNC 元数据，也不适合作为当前全路数据接口。

2026-08-27 曾短暂启动 receiver 到 `.226` 的固定端口 RTP relay。核对旧接口文档后确认这不是原全路方案，已停止并移除，避免额外网络流量和协议重复。

## 带宽边界

receiver 不解码、不缩放、不重新编码，仅复制已收到的 H.264 payload。单个全路客户端的额外出口码率约等于所有在线 RGB 主码流码率之和；当前约为 `50~65 Mbps`。增加第二个全路客户端时，receiver 出口流量近似翻倍。
