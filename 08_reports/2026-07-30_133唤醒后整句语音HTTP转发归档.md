# 133 唤醒后整句语音 HTTP 转发归档

日期：2026-07-30

设备：`orangepi5pro-d12a4719`（`192.168.66.133`）

## 1. 目标

把原有持续 RTP/Opus 音频流改成按交互发送完整语句，同时保留本地唤醒、语音拍照和
文本 TTS：

1. “你好小环”唤醒后播放“我在”。
2. 回复播放完成后等待用户开始说话，等待上限 8 秒。
3. 用户开始说话后，以连续静音 600ms 判定结束，单句最长 60 秒。
4. 拍照指令播放“叮”，提示音结束后执行三连拍，不发送语音。
5. 其他内容或识别为空时播放“登”，提示音结束后异步发送完整 WAV。

## 2. 当前时序

整句录音保留约 200ms 前缓冲和 300ms 尾部。上传格式固定为 16kHz、单声道、
PCM signed 16-bit little-endian WAV。

发送接口：

```text
POST http://192.168.66.113:50020/api/audio
Content-Type: audio/wav
Body: 完整 WAV 字节
```

任意 `2xx` 响应均视为成功。首次失败后最多重试 3 次；发送队列容量为 8，队满时丢弃
最旧语音。WAV 仅保存在内存中，成功后发送端不保留临时文件。

交互期间外部 `POST /api/tts/speak` 仍可入队，但会等到分类、提示音和当前动作完成后
再播放，避免插入用户录音。原有 TTS 接口和三连拍拍照路径未改变。

## 3. 代码改动

- 新增 `utterance_forwarder.py`：后台 HTTP 队列、超时、重试、丢最旧和运行指标。
- 调整 `vosk_wake.py`：完整命令会话、600ms 端点检测、60 秒上限、提示音后执行动作。
- 调整 `speech_service.py`：本地提示音优先，交互期间延后外部 HTTP TTS。
- 新增“叮”“登”固定 WAV 及可重复生成脚本。
- 新增 133 专用 systemd drop-in，关闭持续 RTP，启用整句 HTTP 转发。
- 新增 macOS 参考接收脚本和接口文档。

持续 RTP 实现仍保留为兼容/诊断能力，但 133 的正式配置已设置
`XIAOHUAN_AUDIO_STREAM_ENABLED=0`。

## 4. 降级行为

- 下游未启动、超时或返回非 `2xx`：不阻塞唤醒、拍照和下一轮录音。
- 重试全部失败：本段语音丢弃并记录日志，不永久积压本地文件。
- 提示音文件不可用：记录错误并继续执行对应拍照或发送动作。
- 外部 TTS 网络不可用：沿用既有 TTS 失败处理，不影响整句音频发送线程。

## 5. 验证

本地自动化测试覆盖：

- PCM 到标准 WAV 编码及格式校验。
- 实际 HTTP 接收、原子落盘和 `202` 响应。
- HTTP 前两次失败、第三次成功的重试路径。
- 容量 8 队列的丢最旧策略。
- 本地提示音优先级和外部 TTS 延后。
- 三连拍 3 张、0.2 秒间隔及原有拍照兼容性。

跨设备验证从 133 向局域网测试接收端发送 1 秒 WAV，首次请求成功，HTTP 返回 `202`，
接收端完成落盘。正式 Mac 地址 `192.168.66.113:50020` 在部署时尚未启动接收脚本，
需要下游启动后再完成最终现场验收。

## 6. 部署结果

`NRestarts=0`。运行参数确认：

```text
audio_stream=False
utterance_forward=True
command_start_timeout_seconds=8.0
command_end_silence_seconds=0.6
command_max_speech_seconds=60.0
```

造成服务反复以状态 2 退出。处理方式是备份旧版本、停用旧 drop-in、一次性部署全部
依赖、执行远端 Python 语法检查并重新加载 systemd。旧版本备份目录：

```text

```
