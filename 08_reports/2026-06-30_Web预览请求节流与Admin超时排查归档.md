# 2026-06-30 Web 预览请求节流与 Admin 超时排查归档

## 背景

前端页面仍偶发显示：

```text
receiver admin unavailable: timed out
```

现场重新检查后确认：

- receiver 和 Web monitor 均已处于 `systemd --user` 托管。
- `gwv3-gemini-receiver.service`、`gwv3-web-monitor.service`、`gwv3-receiver-log-rotate.timer` 均为 `enabled active`。
- receiver 本机访问 `127.0.0.1:18080/api/status` 和 Web 代理 `127.0.0.1:8080/api/status` 均在毫秒级返回。
- 控制端到 `192.168.66.196` ping 稳定，0 丢包，平均约 3-4ms。

因此本次重点排查前端并发请求对 Web monitor / receiver admin 的压力。

## 根因

前端页面原先设置：

```text
MAIN_RGB_REFRESH_MS = 33
THUMB_RGB_REFRESH_MS = 33
MAIN_DEPTH_REFRESH_MS = 180
THUMB_DEPTH_REFRESH_MS = 650
```

同时 `previewAvailable()` 中只要 `rgb_packets > 0` 或 `depth_packets > 0`，就认为预览可请求。

这会导致：

1. 即使 `rgb_preview_available=false` 或 `depth_preview_available=false`，浏览器仍按高频率请求 `/api/preview/*`。
2. 三路相机时，小窗 RGB 会额外产生约 60 次/秒 HTTP 图片请求。
3. 这些请求多数可能返回 404，但仍会占用 Web monitor 线程和 receiver admin 请求通道。
4. 页面同时还有 `/api/status`、主 RGB、主 depth 请求；现场浏览器或多标签页情况下，容易把 admin 代理挤到 3 秒超时。

压力模拟结果：

```text
15 秒内小窗 RGB 请求约 910 次，其中 171 次 404
Depth 请求约 132 次
/api/status 本次模拟未超时，但请求风暴风险明确存在
```

## 修复

修改文件：

```text
09_web_monitor/static/index.html
```

调整：

1. 主 RGB 保持 30fps：

```text
MAIN_RGB_REFRESH_MS = 33
```

2. 小窗 RGB 从 30fps 降到 4fps：

```text
THUMB_RGB_REFRESH_MS = 250
```

3. 小窗 depth 从约 1.5fps 降到 1fps：

```text
THUMB_DEPTH_REFRESH_MS = 1000
```

4. 增加不可用预览的慢速探测：

```text
PREVIEW_PROBE_INTERVAL_MS = 1500
```

5. `previewAvailable()` 不再用 `rgb_packets/depth_packets` 直接判定小窗预览可用：

```text
小窗 RGB：只看 H264/JPEG 预览是否 fresh
Depth：只看 depth_preview_available 是否 fresh
```

6. 如果媒体包存在但预览缓存暂不可用，则只按 `PREVIEW_PROBE_INTERVAL_MS` 低频探测，不再 30fps 打 404。

7. 主 RGB 仍允许通过 `rgb_packets > 0` 触发高频请求，用于拉起主预览。

## 当前结论

本次问题不是 receiver 进程崩溃，也不是基础网络丢包，而是前端预览请求策略过激。  
主画面 30fps 可以保留，但小窗预览和不可用预览必须限频，否则容易把 admin 代理压到超时。

## 后续建议

1. 如果仍出现超时，优先确认是否有多个浏览器标签页同时打开 Web monitor。
2. 后续可在 `/api/status` 增加 Web 请求统计，例如最近 10 秒 `/api/preview/*` QPS、404 次数和超时次数。
3. receiver 侧 clock sync 日志当前仍比较密集，后续可单独做日志限频，降低磁盘和 stdout 压力。
