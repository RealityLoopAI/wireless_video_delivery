# 2026-06-10 RGB 时间戳与画面不同步排查整改归档

## 1. 背景

现场现象：

1. RK3588 发送端本机 OpenCV 预览中，`cam01 RGB` 和 `cam02 RGB` 看起来同步。
2. 下游工程师使用 `frames.csv` 时间戳对齐接收端保存的 `rgb.mp4` 后，画面仍然能看出不同步。
3. 下游反馈“画面信息和时间戳并不同步”。

本次排查涉及三台设备：

| 设备 | IP | 角色 | 账号 |
| --- | --- | --- | --- |
| RK3588 Ubuntu | `192.168.66.85` | 当前本机发送端，双路相机 | `linaro` |
| berry-desktop | `192.168.66.210` | 另一台发送端，`raspberrypi-01` | `berry` |
| fz-Standard-PC-i440FX-PIIX-1996 | `192.168.66.196` | 接收端、NTP 参考、NAS 落盘 | `fz` |

## 2. 已观察到的问题

### 2.1 `timestamp_us` 差很大

接收端保存的 `frames.csv` 中，跨相机直接比较 `timestamp_us` 会出现巨大差异。

原因：

```text
timestamp_us = Orbbec/SDK 设备时间戳
```

不同相机的设备时间戳不保证同一时间基准，不能用于跨相机或跨发送端同步。

解决：

```text
跨相机同步使用 frame_system_timestamp_us
旧数据缺失该字段时才退回 packet_system_timestamp_us
```

### 2.2 系统时间不是主要问题

检查三台设备的时间同步：

- RK3588 本机：以 `192.168.66.196` 为 NTP 参考，offset 为几十微秒级。
- berry-desktop：以 `192.168.66.196` 为 NTP 参考，offset 为几十微秒级。
- 接收端：NTP active，系统时间同步。

结论：

```text
跨设备系统时钟不同步不是本次肉眼错位的主因。
```

### 2.3 接收端字段落盘没有写反

在接收端短录 `tscheck` 和 `ptsmatch` 后检查：

```text
packet_system_timestamp_us == frame_system_timestamp_us
frame_system_timestamp_us 非 0
RGB 行单调递增
```

结论：

```text
接收端协议字段读取和 frames.csv 写入没有发现写反。
```

### 2.4 本机预览同步不等于下游保存视频同步

本机 OpenCV 预览链路：

```text
Orbbec RGB frame -> 本机 decode/resize -> OpenCV composite preview
```

下游保存视频链路：

```text
Orbbec RGB frame -> GStreamer H.264 encoder -> TCP media packet -> receiver -> ffmpeg -> rgb.mp4 -> OpenCV/cv2 read
```

预览没有经过 H.264 编码器、接收端封装和 MP4 解码，因此预览同步只能说明采集线程里帧时间接近，不能证明保存后 `rgb.mp4` 的视频帧和 `frames.csv` 行仍严格对应。

### 2.5 旧发送端存在 H.264 画面与协议头时间戳错配风险

旧发送端逻辑：

1. 给 GStreamer 输入 buffer 设置 `PTS = rgb_system_timestamp_us`。
2. 编码器输出 H.264 sample 时，没有读回输出 sample 的 PTS。
3. 直接把“当前采集帧”的 `frame_id/timestamp_us/system_timestamp_us` 写进“当前吐出的 H.264 payload”协议头。

如果编码器内部有排队或延迟，会出现：

```text
H.264 payload 实际画面 = 第 N-k 帧
协议头 frame_system_timestamp_us = 第 N 帧
```

这会导致下游按 `frame_system_timestamp_us` 对齐时，时间戳看似对齐，但画面内容错帧。

### 2.6 下游 new_sync 脚本仍有旧假设

桌面 `new_sync.rar` 中发现：

```text
sync_videos.py:
  TIME_CANDIDATES = ("packet_system_timestamp_us", "local_time_us", "timestamp_us")
  FrameRecord.video_index = len(rows)

sync_multi_segments.py:
  TIME_COLUMNS = ("packet_system_timestamp_us", "local_time_us", "timestamp_us")
  DEFAULT_TIME_COLUMN = "packet_system_timestamp_us"
  FrameRecord.video_index = len(rows)
```

问题：

1. 默认没有优先使用 `frame_system_timestamp_us`。
2. 默认假设第 N 个 RGB CSV 行就是 `rgb.mp4` 第 N 帧。

第二个假设在 H.264 开头不可解码、MP4 丢帧、旧发送端编码延迟时会失败。

## 4. 已完成的代码修复

提交：

```text
25f16d8 Align RGB packet metadata with encoder PTS
```

修改文件：

```text
01_sender_linux/include/gwv3_sender/gst_h264_encoder.hpp
01_sender_linux/src/gst_h264_encoder.cpp
01_sender_linux/src/main.cpp
04_docs/00_文档索引_v3.md
04_docs/16_RGB编码输出时间戳与下游视频索引同步整改说明_2026-06-10.md
```

核心修复：

1. `GstH264Encoder` 输出 `EncodedH264Frame`。
2. `EncodedH264Frame` 包含：

```text
data
pts_us
has_pts
```

3. 发送端缓存最近 RGB 输入帧的：

```text
frame_id
device_timestamp_us
system_timestamp_us
width
height
```

4. 编码器输出 H.264 sample 后，按输出 PTS 找回对应原始 RGB 帧，再写协议头。

修复后协议包里的：

```text
frame_id
timestamp_us
system_timestamp_us
```

描述的是当前 H.264 payload 实际画面对应的原始 RGB 帧。

### 6.2 其他发送端

所有会发送 RGB H.264 的设备都需要同步本修复。

判断标准：

```text
只要使用 GstH264Encoder 发送 RGB，就必须同步。
```

### 6.3 接收端

当前接收端可以先不改，因为已验证：

```text
packet_system_timestamp_us == frame_system_timestamp_us
```

后续建议增强：

```text
增加 rgb_video_frame_index
或输出 rgb_recorded_frames.csv
```

目的是让下游明确知道 `rgb.mp4` 第几帧对应哪一行 CSV，而不是靠 `video_index=len(rows)` 猜。

### 6.4 下游 new_sync

必须修改：

```python
TIME_COLUMNS = (
    "frame_system_timestamp_us",
    "packet_system_timestamp_us",
    "local_time_us",
    "timestamp_us",
)
DEFAULT_TIME_COLUMN = "frame_system_timestamp_us"
```

`FrameRecord` 增加：

```python
frame_system_timestamp_us: int | None
csv_row_number: int
```

输出 `sync_matches.csv` 时保留：

```text
<camera>_frame_system_timestamp_us
<camera>_packet_system_timestamp_us
<camera>_timestamp_us
<camera>_local_time_us
<camera>_frame_id
<camera>_video_index
<camera>_csv_row_number
```

真实渲染时建议使用：

```text
--time-column frame_system_timestamp_us
--verify-readable-frames
--align-decodeable-frames
```

不要使用：

```text
timestamp_us
local_time_us
```

做跨相机同步。

## 7. 仍然存在的边界

本次修复解决的是：

```text
H.264 payload 画面和协议头时间戳错配
```

不能解决的是：

```text
独立 USB 相机没有硬件同步导致的真实曝光时刻差
```

如果所有发送端都同步 `25f16d8`，下游也使用 `frame_system_timestamp_us` 和正确视频索引，运动画面仍有稳定残差，后续只能：

1. 做每路 `timestamp_offset_us` 软件固定补偿。
2. 或更换支持硬同步/外触发的相机方案。
