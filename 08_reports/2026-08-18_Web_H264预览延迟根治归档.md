# Web H.264 预览延迟根治归档

日期：2026-08-18

## 现象

接收、录制链路持续正常，但网页 RGB 预览运行一段时间后明显落后于实时画面，重新打开画面时也可能先快速播放一段旧画面。

## 根因

问题不在相机采集或接收端算力：排查时七路媒体均约 30 FPS，接收端录制队列为 0，Admin API 响应约 1-7 ms。

延迟来自预览专用链路的两级无界追赶：

1. 接收端为新 Web 客户端从缓存中的旧 IDR 开始发送，并持续补发客户端尚未消费的包。慢客户端会追赶旧画面，而不是回到实时端。
2. 浏览器把所有收到的帧持续提交给 WebCodecs，没有限制 `decodeQueueSize`。页面渲染稍慢时，解码队列会逐渐积累。
3. Web 连接断开或消费过慢时，接收端发送没有短超时，预览线程可能长期占用连接资源。

## 修复

### 接收端

- 新订阅记录订阅时的流序号，只等待订阅之后的新关键帧，不再回放旧 GOP。
- 客户端落后超过 12 个包时，直接跳到当前实时端并等待新关键帧，不追赶历史包。
- H.264 帧发送增加 150 ms 超时，慢连接会被及时断开，不长期占用 Admin 工作线程。
- 保留接收端 180 包共享缓存，录制链路和媒体 TCP 协议均未改动。

### 浏览器

- WebCodecs 解码队列上限设为 2。
- 超过上限时关闭并重建解码器，丢弃旧增量帧，等待下一关键帧恢复。
- 输入解析缓存限制为 4 MiB，避免异常连接造成前端内存持续增长。
- 修正 WebCodecs 重置后的状态恢复，防止触发低延迟保护后画面永久停止。

## 验证结果

- 本地 receiver 编译通过。
- `test_web_preview_low_latency.py` 通过。
- `test_receiver_hardening.py` 通过；当前测试机缺少 ffmpeg/ffprobe，因此该脚本中的封装收尾子项自动跳过。
- 部署后七路 sender 均在线，RGB/Depth 发送帧率约 29.9-30.9 FPS。
- 录制队列字节数为 0，分片收尾队列为 0。
- 单路主 H.264 预览实测：首帧 66 ms，首帧为 IDR，4 秒收到 119 帧，29.71 FPS，序号连续。
- Web 首页、状态和配置接口响应约 1-7 ms。

## 部署说明

已在接收端 `192.168.66.196` 本机重新编译 receiver，并重启：

- `gwv3-gemini-receiver.service`
- `gwv3-web-monitor.service`

浏览器需要刷新页面以加载新的 JavaScript。页面设置了 `Cache-Control: no-store`，刷新后不会继续使用旧页面代码。
