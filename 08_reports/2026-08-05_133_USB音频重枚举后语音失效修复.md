# 133 USB 音频重枚举后语音失效修复

日期：2026-08-05

## 现象和根因

`192.168.66.133` 的 `xiaohuan-wake.service` 仍显示 `active`，但无法正常唤醒。运行时日志显示录音子进程发生 `xrun`，随后 ALSA 短时无法解析 `Device_1`。

内核日志确认 16:55:05 同时发生：

- Gemini 305 所在 `usb 6-1` 断开。
- USB 音频 Hub 所在 `usb 1-1.1` 断开。
- Hub 多次枚举失败，内核报 `error -71` 和 `Maybe the USB cable is bad`。
- 麦克风约 15 秒后才重新枚举。

原语音进程最终能够重建录音管道，但 USB 重枚举会把麦克风硬件捕获增益恢复为默认 50%。启动脚本只在整个服务启动时下发 62% 和 `AGC=off`，原进程内重连没有重复下发，造成“进程活着但听不清”。

## 修复

- 新增 `audio_mixer.py`，从 `plughw:CARD=...,DEV=...` 稳定解析 ALSA 声卡名。
- `vosk_wake.py` 在每次录音管道打开前重新应用麦克风捕获增益和 AGC。
- `run_wake_service.sh` 把现有 `XIAOHUAN_MIC_CAPTURE_LEVEL` 和 `XIAOHUAN_MIC_AGC` 显式传给 Python 进程。
- 混音器下发失败不阻断原有音频重连和 systemd 降级逻辑。

## 验证

- Python 语法检查通过。
- 新增声卡解析/混音器命令单元测试通过。
- 现有 TTS 服务和整句音频转发测试通过。
- 133 HTTP TTS 返回 `202 accepted`，播放完成后录音在 0.27 秒内恢复。
- 故障注入时先把麦克风降到 50%，再终止 `arecord`子进程。主进程 PID 未变、`NRestarts=0`，录音 1.70 秒内重建，麦克风自动恢复为 62% 且 AGC 关闭。

## 硬件风险

本次修复解决了 USB 音频重枚举后的软件恢复缺口，但不能消除内核 `error -71` 对应的线缆、Hub 接触或供电风险。设备移动时仍应避免 USB 接头受力。
