# fMP4 直接交付与收尾加速归档

日期：2026-07-29

## 1. 背景

receiver 实时录制阶段本来就生成正常关闭的 fragmented MP4。旧交付流程为了兼容部分只支持传统 MP4 的播放器，还会在 NAS capture 完成后再次执行一次 `ffmpeg -c:v copy`：

```text
closed fMP4 -> 完整读取 RGB -> 写出传统 MP4 -> 校验 -> 最终发布
```

该步骤不改变 H.264 画面，却会对每路长文件增加一次完整读取和写入。现场切换前的 uploader 状态中，最近一次 NAS 源重封装耗时为 `58257 ms`。下游确认可直接接受 fMP4 后，这项播放器兼容成本不再必要。

## 2. 实现

新增接收端配置：

```json
{
  "recording_staging": {
    "rgb_output_mode": "fragmented_mp4"
  }
}
```

支持两种模式：

| 模式 | 行为 |
| --- | --- |
| `fragmented_mp4` | 校验 `moov+moof+mfra` 后直接发布 fMP4，不启动 RGB 整文件 remux |
| `conventional_mp4` | 保留旧的无损传统 MP4 重封装路径；缺少配置时仍使用该兼容默认值 |

可靠性语义未改变：

1. receiver 仍先写本地 staging。
2. 正常关闭的 RGB 必须有 `moov`、媒体 fragment 和尾部 `mfra`。
3. capture 仍先完整复制到 NAS 隐藏队列，并执行文件持久化和清单校验。
4. 最终目录仍通过发布日志恢复，并把 `recording_ready.json` 作为最后一步原子发布。
5. 缺少 `mfra`、NAS 中断或校验失败时不会发布虚假 ready，也不会删除唯一副本。
6. `recording_ready.json` 新增 `rgb_container_format` 和 `rgb_fragmented`，下游可明确识别实际容器。

状态接口新增：

```text
recording_staging.rgb_output_mode
recording_uploader.rgb_output_mode
recording_uploader.fragmented_passthroughs
```

生产模式显示：

```text
pipeline_mode=nas_first_fragmented_mp4
last_remux_source=fragmented_passthrough
```

## 3. 播放兼容性

fMP4 仍是标准 MP4 容器，扩展名继续使用 `.mp4`，编码仍为 H.264。VLC、mpv、ffplay 和基于 FFmpeg 的下游可直接播放、定位和解码。部分旧版系统播放器或剪辑软件只完整支持传统 MP4；这类环境可把配置切回 `conventional_mp4`。

下游只能消费带正式 `recording_ready.json` 的最终目录，不能读取本地 staging 或 NAS 隐藏 capture queue。

五路均满足：

4. `meta.closed=true`。
5. `meta.rgb_frames` 与 `frames.csv` 中 `rgb_recorded=1` 数量完全一致。
6. ready 声明 `rgb_container_format=fragmented_mp4`、`rgb_fragmented=true`。

```text
record_finalize_outstanding_segments=0
record_queue_total_bytes=0
```


如遇下游兼容性问题，优先只把：

```json
"rgb_output_mode": "conventional_mp4"
```

改回兼容模式并重启 receiver/uploader。无需回退录制队列、NAS capture、发布日志或数据格式的其他改动。

## 7. 结论

本次优化取消了生产路径中没有数据价值的 RGB 全文件重封装。停止接口、本地封口、NAS 可靠 capture 和原子 ready 语义保持不变；最终等待时间主要剩下“把新数据可靠写入 NAS”的必要耗时，不再叠加一次同尺寸 RGB 读写。
