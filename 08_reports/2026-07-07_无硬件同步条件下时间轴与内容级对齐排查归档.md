# 2026-07-07 无硬件同步条件下时间轴与内容级对齐排查归档

## 背景

当前硬件设施暂时无法增加同步线、触发器、PTP 相机或统一硬件时钟。因此本轮排查只考虑现有 Wi-Fi/TCP 传输、Orbbec RGBD 相机、多个 sender 与一个 receiver 的软件对齐方案。

当前工程已经实现：

- sender 采集 RGB + Depth 后写入 SDK 时间戳和 sender 系统时间戳。
- receiver 通过 clock_sync 维护每个 sender 相对 receiver 的 offset。
- receiver 写入 `global_timestamp_us = sender_system_timestamp_us + sender_offset_us`。
- 下游可以使用 `global_timestamp_us` 做多 sender 时间轴对齐。

## 当前实测结论

### 1. 软件 clock_sync 当前正常

2026-07-07 15:16 左右的在线三路 sender 状态：

- `orangepi5pro-b439137c_cam02`
- `orangepi5pro-d12a4719_cam01`
- `rk3588-ubuntu_cam01`

20 秒采样中三路 RGB/Depth 均约 30fps。三路最后一轮 offset 差：

- `b439137c` vs `d12a4719`: 约 `623us`
- `b439137c` vs `rk3588`: 约 `450us`
- `d12a4719` vs `rk3588`: 约 `173us`

结论：软件统一时间轴本身没有明显跑偏，已低于 5ms 目标。

### 2. 内容级不同步主要来自相机采样相位和 SDK 帧时间定义

sender 端 `time_sync` 日志显示：

| sender/camera | RGB - Depth system timestamp |
| --- | ---: |
| `rk3588-ubuntu_cam01` | 平均约 `43.9ms`，p95 约 `61.8ms` |
| `orangepi5pro-b439137c_cam02` | 平均约 `47.5ms`，p95 约 `64.1ms` |
| `orangepi5pro-d12a4719_cam01` / Gemini305 | 平均约 `-0.8ms`，p95 约 `-0.58ms` |

这说明不同 Orbbec 型号/SDK 输出的 RGB 和 Depth `systemTimeStampUs()` 含义不完全一致。Gemini305 的 RGB/Depth 时间更接近；旧 Gemini Pro 类设备的 RGB 与 Depth 存在几十毫秒级偏移。

### 3. 发送端处理性能不是当前主因

近期日志中：

- 本机 `rk3588-ubuntu_cam01`: RGB/Depth 输入和发送约 30fps，RGB 编码约 `0.14ms`，Depth 压缩约 `3.17ms`。
- `orangepi5pro-b439137c_cam02`: RGB/Depth 输入和发送约 30fps，RGB 编码约 `0.22ms`，Depth 压缩约 `5.22ms`。
- `orangepi5pro-d12a4719_cam01`: RGB/Depth 输入和发送约 30fps，RGB 编码约 `0.14ms`，Depth 压缩约 `6.74ms`。

结论：当前不是编码/发送线程整体追不上造成的持续漂移。

### 4. 最近录制 CSV 时间列没有倒退

检查 `/home/fz/Desktop/nas/.../2026-07-07/144151/test_Short_0035_frames.csv`：

- `frame_system_timestamp_us` 单调。
- `global_timestamp_us` 单调。
- 单帧间隔约 `33.3ms`。

这说明该批数据的时间轴列本身可用。

### 5. 最近邻重算比 frames.csv 当前 pair_delta 更能反映真实配对

同一相机 RGB/Depth 用 `global_timestamp_us` 做最近邻匹配：

- `b439_cam02`: 平均约 `9.10ms`
- `d12a_cam01`: 平均约 `0.83ms`
- `rk_cam01`: 平均约 `8.60ms`

三路 RGB 在共同时间窗口内做最近邻匹配：

- `b439` vs `d12a`: 平均约 `4.82ms`
- `d12a` vs `rk`: 平均约 `11.08ms`
- `b439` vs `rk`: 平均约 `14.70ms`

结论：无硬触发的 30fps 自由运行相机天然存在采样相位差，最大接近半帧约 `16.7ms` 是合理现象。下游不应只看 frames.csv 中逐包写出的 `pair_delta_ms`，应使用全量帧表按 `global_timestamp_us` 做最近邻/窗口匹配。

## 当前代码路径核对

发送端：

- `01_sender_linux/src/main.cpp`
- `frame_system_timestamp_us_or()` 优先使用 SDK `systemTimeStampUs()`，为 0 时回退到 host `now_us()`。
- RGB 在拿到 `colorFrame()` 后立即绑定 `RgbEncodeTiming`。
- Depth 在拿到 `depthFrame()` 后立即写入 `MediaFrameMeta`。
- 发送端已记录 `sender_capture_host_timestamp_us`、`sender_timing_bound_timestamp_us`、`sender_encode_start_timestamp_us`、`sender_encode_done_timestamp_us`、`sender_packet_queued_timestamp_us`。

接收端：

- `02_receiver_linux/src/main.cpp`
- `handle_media_packet()` 使用 `packet.system_timestamp_us + sender_offset_us` 生成 `global_timestamp_us`。
- 不覆盖原始 `timestamp_us` 或 `system_timestamp_us`。

配置：

- `frame_aggregate_mode` 默认值是 `disable`。
- 当前配置未启用严格 `full_frame_require` 或 `color_frame_require`。
- 现在使用 Orbbec `FrameSet` 取 RGB/Depth，但这不是跨相机硬同步，也不保证 RGB 和 Depth 是同一曝光时刻。

## 成熟案例与可借鉴方案

### 1. libsoftwaresync

Google Research 的软件同步方案使用网络消息估计设备时钟，再根据相机帧时间戳估计采样相位。它适合无硬同步设备，但不能替代硬触发。

参考：

- https://ar5iv.labs.arxiv.org/html/1812.09366

对本工程的启发：

- 继续保留 clock_sync。
- 增加每台相机的帧相位估计和内容 offset 补偿。

### 2. ROS message_filters ApproximateTime

机器人系统常用 ApproximateTime 策略在队列中找时间最接近的一组消息。它不解决相机真实曝光不同步，只负责对已有时间戳做近似配对。

参考：

- https://docs.ros.org/en/humble/p/message_filters/doc/index.html

对本工程的启发：

- 下游按 `global_timestamp_us` 做最近邻匹配。
- 设置可接受窗口，例如 `8ms`、`12ms` 或 `16ms`。
- 超出窗口的帧不要硬配，宁可丢弃。

### 3. Kalibr / OpenVINS temporal calibration

视觉惯性和机器人标定中，常把传感器时间偏移作为待估参数，与外参一起标定。这个思想适合本工程做每路相机的 `content_time_offset_us`。

参考：

- https://github.com/ethz-asl/kalibr/wiki/Multi-IMU-and-IMU-intrinsic-calibration
- https://docs.openvins.com/gs-calibration.html

对本工程的启发：

- 把每台相机的内容级偏移作为可配置标定参数。
- 下游使用 `aligned_timestamp_us = global_timestamp_us + content_time_offset_us`。

### 4. Flash / LED 离线同步

成熟离线工具会用闪光、LED 或屏幕亮度突变作为共同事件，对多路视频估计时间偏移。优点是不需要硬件接入相机，只需要让所有相机看到同一视觉事件。

参考：

- https://github.com/smidm/flashvideosynchronization

对本工程的启发：

- 录制一段 LED 闪烁、手机秒表、屏幕闪白或快速运动标定视频。
- 离线估计每路 RGB 的固定 `content_time_offset_us`。

### 5. 内容级多视角运动对齐

研究路线会用多视角运动轨迹、对极几何或学习方法估计时间偏移。适合后处理和研究，不建议作为当前工程第一优先级。

参考：

- https://stevenlsw.github.io/visualsync/

### 6. Orbbec 官方 metadata 与 align

Orbbec 官方支持帧级 metadata，包括 timestamp、sensor timestamp、exposure、gain、actual fps 等，并提供 RGBD align 示例。

参考：

- https://doc.orbbec.com/documentation/Orbbec%20Gemini%20330%20Series%20Documentation/Frame%20Metadata
- https://doc.orbbec.com/documentation/Orbbec%20Gemini%20330%20Series%20Documentation/C%2B%2B%20Sample%20Sync%20Align%20Viewer
- https://doc.orbbec.com/documentation/Camera%20Accessories/Set%20up%20Cameras%20for%20External%20Synchronization

对本工程的启发：

- 扩展 CSV，写入更多 SDK metadata。
- 区分设备 timestamp、sensor timestamp、system timestamp、曝光参数和 host receive time。
- 对不同型号相机分别建立时间偏移模型。

## 推荐的现阶段路线

在不改硬件前提下，推荐采用：

```text
clock_sync 统一 sender 系统时间
+ global_timestamp_us 落盘
+ 每台相机离线 content_time_offset_us 标定
+ 下游按 aligned_timestamp_us 做最近邻匹配
+ 超出窗口的帧丢弃
```

下游建议：

```text
aligned_timestamp_us = global_timestamp_us + content_time_offset_us
```

匹配策略：

- RGB 跨相机：按 `aligned_timestamp_us` 最近邻匹配。
- RGBD 同相机：按 `aligned_timestamp_us` 最近邻匹配，不只依赖 frameset 顺序。
- 窗口建议先试 `8ms`、`12ms`、`16ms` 三档。
- 超出窗口的帧不做训练样本。

## 当前判断

clock_sync 已经把 sender 系统时间轴对齐到亚毫秒级。当前下游看到的画面内容不同步，主要不是网络、receiver 或 clock_sync，而是无硬触发情况下相机采样相位和不同 Orbbec 型号的 SDK 帧时间定义差异。现有硬件条件下，应通过离线内容 offset 标定和最近邻匹配来处理。
