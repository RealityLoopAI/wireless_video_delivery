# 十五分钟多路切片 OOM 根因与异步收尾修复归档

日期：2026-07-16

## 现象

五路相机连续录制在首个 15 分钟边界前工作正常，轮转后管理 API 开始超时，录制队列持续增长，receiver 最终被 `systemd-oomd` 杀死。首段目录遗留 `.finalizing`、`.inprogress` 或临时 MP4，部分文件未发布 `recording_ready.json`。

现场关键数据：

- 五路在轮转前均接近 30 FPS，说明采集、时间戳和主传输不是首要故障点。
- 轮转后录制队列增长到约 1.55 GiB。
- user slice 内存峰值约 7.77 GiB。
- I/O PSI full 一度约 58%。
- receiver 被 OOM 杀死后由 systemd 自动重启。

## 根因

旧实现由每路录制 worker 在切片边界同步关闭并收尾自己的 `SegmentWriter`。五路同时到达 15 分钟边界时，会并发执行以下重操作：

1. 关闭 RGB/Depth ffmpeg 管道并等待子进程。
2. 校验长视频。
3. 将 fragmented RGB MP4 完整读取并 `-c:v copy` 重封装为普通 MP4。
4. 再次校验并原子发布 CSV、元数据和 ready 标志。

这使五个录制 worker 同时停收媒体包，并在 NAS 上并发做五组大文件读写。主媒体接收仍持续入队，完整 payload 被积压在 RAM 中，最终触发内存和 I/O 压力闭环。MP4 未正常收尾是进程被杀的结果，不是独立的编码器故障。

## 修复

接收端改为快速轮转加有界串行收尾：

1. 到达切片边界时先创建并启动新 `SegmentWriter`。
2. 在录制 worker 内原子交换 active writer，触发边界的数据包直接写入新切片。
3. 旧 writer 连同 ffmpeg 管道所有权移动到后台 `SegmentFinalizeTask`。
4. 全局只允许一个 finalizer 执行关闭、重封装、校验和原子发布，消除 NAS 并发全文件搬运。
5. 使用 `record_finalize_max_pending_segments` 限制待收尾任务，默认 8。
6. 队列满时延后自动轮转，继续写当前切片，不阻塞媒体线程，也不无限积压媒体 payload。
7. 显式停止同样走后台收尾；进程退出会等待 finalizer 清空。
8. API 增加全局及逐相机 finalizer 指标，便于判断是否可重启、升级或断电。
9. 停机和安装脚本将 `record_finalize_outstanding_segments=0` 纳入空闲条件，等待上限调整为 900 秒。
10. receiver systemd 停止超时调整为 900 秒，并降低被 systemd-oomd 优先回收的概率。

## 自动化验证

新增三路相机压力测试，使用真实 ffmpeg，并人为让每个 RGB 普通 MP4 重封装延迟 750 ms：

- 三路在旧段仍收尾时均能切换并持续写新段。
- `record_finalize_active_segments` 始终不超过 1。
- 可观察到多个 pending segment，证明轮转与收尾已解耦。
- finalizer 队列达到上限时轮转被延后，媒体录制继续。
- 录制队列峰值保持在 4 MiB 以下。
- 最终所有任务清空并生成 `recording_ready.json`。
- 普通构建连续三轮测试通过。
- AddressSanitizer 与 UndefinedBehaviorSanitizer 测试通过。

## 首轮 15 分钟现场验证

五路真实 sender 以 `segment_seconds=900` 录制并跨过首个边界：

- receiver 未重启，未再被 `systemd-oomd` 终止。
- 边界时观察到 5 个待收尾切片，但 `record_finalize_active_segments` 始终为 1。
- 五段长切片收尾分别耗时约 37.7-65.2 秒，期间新切片持续录制。
- 录制队列峰值约 43.95 MiB，较旧版约 1.55 GiB 显著下降。
- cgroup 总内存在 `MemoryHigh=3G` 附近平台化；anon 内存稳定，增长主要是可回收的 CIFS 文件页缓存。
- 5 路 15 分钟主切片均可解码，CSV RGB 行数与解码帧数逐路一致，约为 26990-27014 帧。

## 现场验证发现的第二个根因

首轮长测的主切片正常，但随后的 tail 切片在两路 sender 上出现 `frame_id`、`frame_system_timestamp_us`、`global_timestamp_us` 同时倒退：

- `orangepi5pro-b439137c_cam02` 出现 94 次倒退。
- `rk3588-ubuntu_cam01` 出现 76 次倒退。
- 单次时间倒退可达约 22.72 秒。

日志证明 sender 在 NAS 背压期间发生了 TCP 重连，而 receiver 短时同时处理新旧两条 media 连接。新连接的较新帧已入队后，落后数十秒的旧连接仍能补入旧帧，因此三个原始顺序字段一起倒退。这不是 clock sync 偏移计算错误，而是 receiver 缺少 media 会话所有权和旧会话隔离。

此外，旧路径在收到包后先做预览缓冲、Depth 解压和伪彩处理，最后才将完整 `MediaPacket` 拷贝到录制队列。预览工作量和重连竞态共同放大了入队顺序风险。

## TCP 会话隔离与录制优先修复

1. 每条 TCP media 连接获得单调递增的 `media_session_id`。
2. receiver 为每个 `sender_id/camera_id/stream_type` 维护唯一 owner。
3. 更新会话首包到达时原子取代 owner，并对旧 socket 执行 `shutdown()`。
4. 旧会话不能重新抢回 owner；后续包在入队前被拒绝。
5. 入口 owner 复核与录制队列插入在同一个临界区完成，关闭“校验后、入队前”的竞态窗口。
6. 包完整收到并完成身份检查后，立即进入录制队列，预览和 Depth 伪彩改为之后处理。
7. 录制队列和预览共享一个只读 `MediaPacket` 所有权，不再复制整块 RGB/Depth payload。
8. 新增会话接管、旧包拒绝、入队前延迟和队列等待延迟指标。

## 会话修复短测

五路真实 sender 使用 30 秒切片连续跨过三次自动轮转，再显式停止：

- 现场真实发生 1 次 RGB 预览路由重连并被新会话正确接管。
- `media_ingress_stale_packets=0`，没有旧包进入录制。
- `record_prequeue_peak_delay_ms=4`，证明录制入队已从预览重处理中解耦。
- 20 个切片全部完成收尾，零 finalizer 失败。
- `sync_input_guard --verify-video-frames` 检查全部通过。
- CSV 中 RGB 行数合计 14913，与解码帧数 14913 完全一致。
- 所有切片 `global_timestamp_us` 严格单调，MP4 均可完整解码。

## 会话修复后的第二轮 15 分钟验证

使用五路真实 sender 再次录制 15 分钟主段加约 90 秒 tail，并在主段中主动重启 `orangepi5pro-b439137c` sender：

- 主动重启后 RGB 和 Depth 两条主媒体会话均被新会话接管。
- b439 的 `frame_id` 出现 1 次预期的重启归零，但 `frame_system_timestamp_us` 和 `global_timestamp_us` 均为 0 次倒退。
- 轮转和停止收尾期间，RK RGB 自然发生新连接接管，旧会话随后尝试回灌 402 个积压包；全部被 `media_ingress_stale_packets` 拒绝。
- 所有 5 路的 `frame_system_timestamp_us` 和 `global_timestamp_us` 跨主段/tail 均为 0 次倒退。
- 自动轮转和显式停止共收尾 10 个切片，成功 10，失败 0，receiver 重启 0 次。
- 最大单路录制队列约 46.86 MiB，仅为旧版 1.55 GiB 的约 3%。
- 主段 RGB 帧数分别为 27002、26930、27017、27002、26982；b439 少约 2.7 秒对应主动重启停顿。
- 10 个目录均通过 `sync_input_guard` 快速完整性和时间单调检查。
- `sync_input_guard --verify-video-frames` 逐帧解码复核通过：CSV RGB 帧总数 148556，解码帧总数 148556，10 路匹配差异均为 0。

## 长测新发现：运行状态持久化占用全局锁

第二轮长测通过新增的入队前延迟指标捕获到一次 6.6 秒全路停顿：

- 五路的 receiver 读包时间同时中断约 6.62-6.66 秒。
- 同期 sender 的 `frame_system_timestamp_us` 仍以约 33 ms 递增，证明不是五台 sender 同时停采。
- 停顿开始于 14:55:08，结束后 14:55:14 打印 `camera_announce`，与锁内写入 166 KiB `receiver_runtime_state.json` 完全对应。
- TCP 缓冲使本次停顿后的数据能够追回，但长时占用全局锁会放大重连、延迟和丢包风险。

修复方式：

1. 在 receiver 全局锁内只更新内存状态、分配递增 revision 并拷贝快照。
2. 释放全局锁后再写临时文件并原子 rename。
3. 使用独立持久化互斥锁串行磁盘写入。
4. 若并发请求中更新的 revision 先完成，旧快照直接跳过，防止状态回退。
5. 相机名、文件前缀和默认前缀三个 Admin 保存路径也使用同一套锁外持久化。

新增 FIFO 慢写集成测试：故意让状态文件打开阻塞，同时发送 media 包并读取 Admin 状态。媒体包可在磁盘写入解锁前完成处理，证明持久化已与 media 全局锁解耦。真实 ffmpeg 集成测试连续三轮通过，ASan/UBSan 通过。

最终代码以 `build_source_hash=30b4b7d1dee11e6a` 部署后，在接收端同时对旧长段做逐帧解码的压力下再录制 90 秒：

- 5 路 RGB 分别落盘 2705、2704、2704、2702、2701 帧，均约 30 FPS。
- 5 路 `record_prequeue_peak_delay_ms` 均不超过 5 ms，未再出现 6.6 秒全路停顿。
- 最大单路队列约 1.53 MiB，停止后 16 秒内完成 5 路串行收尾。
- finalizer 成功 5，失败 0；`sync_input_guard --verify-video-frames` 复核 5 个目录全部有效，CSV RGB 帧总数和解码帧总数均为 13516。

## 运维验收

连续录制时允许同时出现 `recording=true` 与 `record_finalize_outstanding_segments>0`。判断一段可供下游使用仍以该目录满足以下条件为准：

```text
meta.json: closed=true
frames.csv 已原子发布
recording_ready.json: ready=true
```

重启、升级或关机前必须确认：

```text
record_finalize_outstanding_segments == 0
record_queue_total_bytes == 0
所有相机 segment_active == false
```

## 回退

若现场出现新回归，先停止录制并等待所有后台收尾归零，再恢复部署前备份的 receiver 二进制、配置和 systemd unit。不得在 `rgb_seekable.tmp.mp4` 正在生成时强杀 receiver。
