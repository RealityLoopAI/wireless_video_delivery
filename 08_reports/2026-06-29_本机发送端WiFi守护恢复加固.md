# 2026-06-29 本机发送端 Wi-Fi 守护恢复加固

## 现象

本机 RK3588 发送端只剩 watchdog，`gemini_sender` 子进程没有运行。接收端看不到本机画面。

## 定位

系统没有死机，Orbbec USB 设备仍能枚举。`sender_stdout.log` 中 watchdog 持续输出：

```text
wlan0 当前频率 2467MHz，低于要求 5000MHz
```

当时本机自动连到了 2.4GHz 的 `6666`。仓库默认 Wi-Fi guard 只要求频率不低于 5000MHz，但没有显式配置固定 SSID，因此旧逻辑只能检查失败并等待，不能主动切回 5GHz。

同时发现 `sender_stdout.log` 已到约 90MB。watchdog 监控子进程每次重启子进程时从日志开头扫描历史内容，导致一个 bash 进程短时间吃满一个 CPU 核。

## 修复

1. `05_tools/sender_wifi_guard.sh`
   - 在未显式设置 `GEMINI_SENDER_WIFI_CONNECTION` 时，自动扫描 NetworkManager 已保存的 Wi-Fi 连接。
   - 只选择当前可见、满足 `GEMINI_SENDER_WIFI_MIN_FREQ_MHZ` 的 Wi-Fi。
   - 多个候选时按 `connection.autoconnect-priority` 选择最高者；同优先级下选择频率更高者。
   - 这样设备掉到 2.4GHz 后，watchdog 会主动切回已保存的 5GHz，而不是一直空等。

2. `05_tools/sender_watchdog.sh`
   - 监控子进程从启动 `gemini_sender` 前的日志偏移开始读取。
   - 避免每次重启扫描整份历史日志，消除 watchdog bash 高 CPU。

3. 本机 NetworkManager 现场配置
   - `土著拯救器-5G` autoconnect priority 调到 80。
   - `6666` autoconnect priority 降到 10。

## 验证

修复后本机连接：

```text
SSID: 土著拯救器-5G
freq: 5240 MHz
tx bitrate: 433.3 MBit/s
```

本机发送端恢复：

```text
cam01 RGB 1920x1080@30
cam01 Depth 320x200@30
```

接收端 10 秒实测：

```text
RGB:   300 packets / 10s, 30.0 fps, 约 12.0 Mbps
Depth: 301 packets / 10s, 30.1 fps, 约 2.5 Mbps
```

watchdog 监控子进程 CPU 从约 100% 降到约 0.5%。
