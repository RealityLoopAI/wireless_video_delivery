# fMP4 增量镜像与收尾加速修复归档

日期：2026-07-30

## 1. 问题

fMP4 直接交付取消了停止后的 RGB 整文件重封装，但旧 uploader 仍要在 segment 关闭后，逐路把完整 RGB、Depth、CSV 和元数据从本地 staging 复制到 NAS。短录制的固定调度成本明显，十五分钟片段还会产生数 GB 的停止后复制，因此“已改为 fMP4”不等于“停止后立即 NAS ready”。

修复前五路约 15 秒短测：

- stop API：16.6ms；
- receiver 本地 writer/finalizer 空闲：0.249s；
- 全部 NAS ready：约 20.2s；
- RGB 没有再执行整文件 FFmpeg remux，主要耗时已经转移到 staging 到 NAS 的完整复制、fsync 和串行发布。

## 2. 本次实现

### 2.1 录制中增量镜像

`recording_uploader.py` 会在录制进行中扫描活动 segment，并把已经稳定的完整 4MB 块复制到 NAS 隐藏目录：

```text
<nas>/.gwv3_capture_queue/.gwv3-mirroring-<capture-key>/
```

默认每 2 秒扫描一次，并保留最后 4MB 不提前镜像。状态文件记录：

- sender/camera/segment 身份；
- 源文件 device/inode；
- 块大小、SHA-256 和已镜像字节数；
- uploader 实例 ID。

本地 staging 始终是权威副本。镜像只是可丢弃的预取缓存，不会取代本地录制。

### 2.2 停止后的接管

segment 关闭后：

1. 关闭该镜像目录的持久输出句柄；
2. 将隐藏镜像目录原子接管为 capture 临时目录；
3. 从本地文件重新读取并校验已镜像块；
4. 只重写变化的块并补齐尾部；
5. 并行 fsync 文件，校验完整 manifest；
6. 写 capture marker，并原子发布到 capture queue；
7. 保持原有 fMP4 结构校验、`recording_ready.json` 和最终目录原子发布。

原始 RGB fMP4 不做整文件 remux；生产状态仍为：

```text
pipeline_mode=nas_first_fragmented_mp4
rgb_output_mode=fragmented_mp4
last_remux_source=fragmented_passthrough
```

### 2.3 并发和调度

- `capture_workers=4`：不同相机的 staging 到 NAS capture 可并行；
- `finalize_workers=4`：不同相机的校验和发布可并行；
- 文件 fsync 可并行；
- 活动 segment 镜像优先于历史关闭 segment，避免积压时饿死当前录制；
- uploader 有进展时立即进入下一轮，不再强制等待完整扫描周期。

录制主写入仍优先。receiver 队列过大、队列年龄超限、正在 finalizer 或接近切片边界时，镜像和 capture 会暂停。

## 3. 故障与降级

- NAS 暂时不可用：只停止增量镜像，本地 staging 继续录制；
- uploader 重启：旧实例的未持久化镜像不会被盲目信任，必要时删除并从本地重新复制；
- 活动 segment 在镜像中关闭：立即中止活动镜像，由关闭后的 capture 流程接管；
- 块哈希或文件身份不匹配：放弃该文件的镜像复用并执行完整复制；
- capture/final publish 中断：保留原有锁、publish journal 和崩溃恢复；
- 没有增量镜像：自动退回旧的完整 capture，不影响可用性和数据完整性。

## 4. 验证结果

### 4.1 自动测试

在 receiver `192.168.66.196` 的原生 FFmpeg 环境执行：

```bash
python3 test_recording_uploader.py --uploader recording_uploader.py
python3 test_receiver_staging_pipeline.py \
  --receiver 12_build/bin/gemini_receiver \
  --uploader recording_uploader.py
```

两项均以退出码 0 通过。覆盖内容包括：

- 活动 RGB 和单 part Depth 的增量镜像；
- 关闭后只同步变化块和尾部，不重新完整复制媒体文件；
- capture 中断、NAS remux 失败、最终目录移动后中断；
- publish journal 恢复；
- fMP4 真实 receiver/uploader 隔离集成和可解码验证。

### 4.2 六路生产短测

测试前缀：

```text
fmp4_finalize4_20260730_160157_
```

六路录制约 30 秒：

| 指标 | 结果 |
| --- | ---: |
| start API | 40ms |
| stop API | 25ms |
| 停止到六路全部 NAS ready | 8.543s |
| 录制中已增量镜像 | 163,577,856 bytes |
| 最后一次 capture | 1,165ms |
| 最后一次 finalize | 264ms |
| 最后一次 publish | 39ms |
| uploader 失败 | 0 |
| pending segment | 0 |

对比同日逐步测试：

| 实现 | 停止到全部 NAS ready |
| --- | ---: |
| 旧串行完整 capture，五路约 15 秒 | 约 20.2s |
| 增量镜像 + capture 4 + finalize 2 | 15.461s |
| 增量镜像 + capture 4 + finalize 4 | 8.543s |

六路最终目录均包含 RGB MP4、Depth MKV、frames CSV、meta、calibration、FFmpeg 日志和 `recording_ready.json`。所有 RGB/Depth 均通过 FFprobe，并可在 5 秒位置解码。

`lubancat-e8cc0cb3_cam01` 在测试开始前就存在 sender RGB 0 FPS、时钟模型无效和大量发送失败；该路只录到约 12.37 秒 RGB。其最终文件可打开、可定位，但内容不完整属于 sender 源流异常，不是 uploader/fMP4 封装失败。

## 6. 结论与剩余风险

本次已经把停止后的主要动作从“复制整段视频”改成“校验已镜像块、同步尾部、fsync 并发布”，短测停止等待从约 20.2 秒降到 8.543 秒。start/stop API 本身仍在 100ms 内。

尚未用本版本完成十五分钟以上的连续多切片长测，因此不能把 8.543 秒直接承诺为十五分钟结果。长文件停止时仍需读取本地文件校验块哈希，并等待 NAS fsync；实际耗时取决于本地读速、NAS 延迟以及录制期间镜像是否持续跟上。后续验收应重点验证：

1. 五至六路十五分钟停止到 NAS ready；
2. 连续多个切片是否无 backlog；
3. 录制中断开并恢复 NAS 后是否能最终完整发布；
4. NAS capture 并发是否影响 receiver 实时落盘队列。
