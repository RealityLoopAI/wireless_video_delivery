# d12a4719 RGBD 180 度旋转部署归档

## 需求

`orangepi5pro-d12a4719/cam01` 因物理安装方向改变，从本次部署起需要同时将 RGB 和 Depth 旋转 180 度，其他发送端不受影响。

## 实现

- 新增每相机可选配置 `rotation_degrees`，仅允许 `0`、`90`、`180`、`270`。
- 仅 `orbbec_sdk` 采集后端可以使用该配置。
- Depth 在启动 pipeline 前通过 Orbbec SDK 设置 `OB_PROP_DEPTH_ROTATE_INT=180`。
- Gemini 305 当前固件对 `OB_PROP_COLOR_ROTATE_INT=180` 能成功写入并回读，但输出的 MJPG 数据没有实际旋转。因此 180 度配置下会明确将 RGB 设备旋转恢复为 0，并在 MJPG 解码为 BGR 后使用 OpenCV 完成一次 180 度旋转。
- 翻转后的同一份 BGR 帧同时供主 H.264 编码和 Web RGB 预览编码使用；本机 OpenCV 预览也应用同样旋转，保证预览、发送和录制方向一致。
- 90/270 度仍沿用 SDK 硬件旋转路径，未扩大本次改动范围。
- 设置 SDK 属性前检查读写权限，设置后读回验证；失败时回滚，避免 RGB/Depth 状态不明确。
- `camera_announce` 增加 `rotation_degrees`，接收端会随 `camera_announce_raw` 保留到录制元数据。

## 问题定位与方案取舍

- 原始日志显示 `color=true depth=true`，只能证明 SDK 属性写入成功，不能证明压缩后的 RGB 像素已经旋转。接收端抓帧确认 RGB 仍然倒置。
- 曾验证在 GStreamer JPEG 解码后增加 CPU `videoflip method=rotate-180`。该方案产生约 500 ms 编码积压，RGB 发送下降到约 12 FPS，并触发 encoder lag reset，因此未保留。
- RK3588 当前 GStreamer 环境没有可用的 RGA 旋转插件。最终采用 OpenCV 解码后旋转，并复用旋转后的 BGR，避免主码流和预览分别重复旋转。
- 本次没有改动 RGB/Depth 时间戳、`frame_id`、`pair_id`、媒体封包和接收端录制格式。

## 设备配置

`06_configs/sender_orangepi5pro-d12a4719_gemini305.json`：

```json
"rotation_degrees": 180
```
