# 接收端停止录制异步收尾优化归档

日期：2026-07-06

## 问题现象

网页端点击停止录制后，偶发报错：

```text
receiver admin unavailable: timed out
```

排查确认 receiver 主进程没有崩溃，录制文件也能最终关闭；问题主要发生在 Web Monitor 代理请求等待 receiver admin 返回时。

## 根因

旧流程中 `/api/record/stop-all` 和 `/api/record/stop` 是同步收尾：

1. receiver 收到停止请求。
2. 停止录制标志。
3. 等待各相机 record queue drain。
4. 关闭 RGB MP4 / Depth MKV 的 ffmpeg 管道。
5. 写 metadata、合并 CSV、写完文件尾。
6. 全部完成后 HTTP 请求才返回。

多路录制停止时，收尾可能需要 3 秒以上。Web Monitor 以前对 admin 请求统一使用 3 秒超时，所以前端会把“正常收尾耗时”误报成 receiver admin 不可用。

历史日志也能印证这一点：有 stop-all 请求从 `18:39:43` 到 `18:40:06` 才 finalized，用时约 23 秒。

## 本次改动

### 1. receiver stop 变为异步收尾

修改文件：

```text
02_receiver_linux/src/main.cpp
```

改动点：

- `/api/record/stop-all` 不再同步等待文件关闭。
- `/api/record/stop` 不再同步等待单路文件关闭。
- 停止请求立即返回：

```json
{
  "ok": true,
  "recording_all": false,
  "finalizing": true,
  "finalized": false
}
```

- 后台继续执行：
  - 等待 record queue 清空。
  - 关闭 segment。
  - 写完 MP4/MKV 文件尾。
  - 更新 `segment_finalizing=false`。

### 2. 保留线程生命周期

旧代码里已有未使用的 `close_segments_async()`，但使用 detach 线程。  
本次改为保存 `std::future<void>`：

- 异步收尾任务由 receiver 管理。
- receiver 停止时会等待后台收尾结束。
- 避免进程退出时后台线程继续访问 ReceiverApp。

### 3. 状态接口继续暴露收尾状态

状态接口已有字段：

```json
"segment_finalizing": true
```

本次 stop 请求返回后，前端可以通过 `/api/status` 观察每路是否仍在收尾。

### 4. Web Monitor 超时兜底

修改文件：

```text
09_web_monitor/server.py
```

改动点：

- 普通 status / preview admin 请求仍默认 3 秒超时。
- record stop 请求单独使用 60 秒超时兜底。
- 支持环境变量覆盖：

```text
GWV3_RECEIVER_ADMIN_TIMEOUT_S
GWV3_RECEIVER_RECORD_STOP_TIMEOUT_S
```

异步收尾后，正常情况下 stop 请求会在毫秒级返回；60 秒只是兜底。

### 5. 前端显示 FINAL 状态

修改文件：

```text
09_web_monitor/static/index.html
```

改动点：

- 当某路 `segment_finalizing=true` 时，卡片和主画面状态显示为 `FINAL`。
- 顶部摘要显示“X 路收尾”。
- 系统面板增加“录制收尾”字段。

## 注意事项

1. stop 请求返回 `finalizing=true` 时，表示停止录制命令已经生效，但文件还在后台收尾。
2. 下游或自动化脚本需要等待 `/api/status` 中所有相机 `segment_finalizing=false` 后，再认为本轮数据完全可用。
3. 如果未来出现长时间 `segment_finalizing=true`，应检查：
   - `record_queue_packets`
   - `record_active_writes`
   - ffmpeg 日志
   - NAS 写入速度

## 后续可选优化

1. 为 `/api/record/stop-all` 返回 `finalizing_cameras` 列表，便于自动化脚本直接知道哪些路在收尾。
2. 为 status 增加 `segment_finalizing_age_ms`，用于判断收尾是否卡住。
3. 如果 NAS 偶发慢写，可以增加收尾阶段 watchdog 日志频率。
