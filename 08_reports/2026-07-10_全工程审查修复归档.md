# 2026-07-10 全工程审查修复归档

## 范围

审查并整改 sender、receiver、CLOCK_SYNC、录制、Web、脚本、配置和构建测试。改动保持现有相机 SDK、GStreamer 编码、主媒体协议和 RGBD 下游格式，不做协议换代。

## 主要结论

1. 过去的掉线、Web admin timeout、MP4 收尾失败并非单点问题，而是队列无统一字节上限、线程/fd 生命周期、全局锁重处理和异常收尾共同造成。
2. 时间轴异常既有 SDK system timestamp 非单调问题，也有旧 offset 长期有效、模型漂移和错误地把设备 uptime 映射成系统 epoch 的风险。
3. 接收端对 UDP/压缩包缺少严格资源边界，局域网异常包可造成大内存分配和线程膨胀。
4. 现场设备源码和运行二进制长期存在 commit 不一致，必须把 build 版本上报作为验收项。

## 部署要求

1. 不覆盖各设备现场相机配置、Wi-Fi 守护参数和私有备份。
2. 各架构本机编译，不复制二进制。
3. receiver 无活动录制且 finalizing/queue 均为零后再重启。
4. 部署后检查 `build_commit`、`build_dirty`、`build_source_hash`、每路 FPS/码率、CLOCK_SYNC offset/delay、队列和错误计数。
5. 做一次短录制并用 `ffprobe`、CSV 行数和最终状态验收。

## 部署前实机验证

1. `192.168.66.196` 在独立 `/tmp` 构建 receiver，通过带真实 `ffmpeg/ffprobe` 的集成测试：RGB MP4 可读取并可 seek 到 1 秒位置，Depth FFV1 MKV 可读，CSV schema 完整，进程可优雅退出。
2. `192.168.66.206` 和 `192.168.66.133` 均在独立 `/tmp` 使用各自 ARM64 SDK 本机编译 sender，并通过全部配置模板验证。
3. 测试阶段未替换在线服务、未改现场相机配置；确认 receiver 当时没有活动录制后才进入正式部署阶段。

## 未解决的物理边界

软件时间轴不等于曝光硬同步。无同步线的自由运行相机仍可能存在一帧范围内的内容相位差，后续数据集应继续使用 `global_timestamp_us + 内容标定补偿`，并定期复核补偿漂移。
