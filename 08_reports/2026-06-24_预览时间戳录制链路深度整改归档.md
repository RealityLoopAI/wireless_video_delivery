# 2026-06-24 预览、时间戳、录制链路深度整改归档

## 背景

现场运行中同时出现过以下问题：

- Web 预览显示可用但画面不动或普通 RGB 小窗口 404。
- 发送端日志持续出现 `rgb encoder timing fallback reason=pts_mismatch`。
- 停止录制后如果很快断电或重启，RGB MP4 仍可能没有完成封装收尾。
- 高分辨率深度压缩时本机发送端 CPU 和内存带宽压力偏高。
- 配置中存在 `media_udp` / `web_rgb_preview.udp_enabled` 字段，容易误判当前媒体链路已经走 UDP。

## 本次修复

### 1. RGB 帧时间戳映射

发送端仍在采集到 Orbbec RGB 帧后立即读取：

- `frame->timeStampUs()` 作为设备时间戳。
- `frame->systemTimeStampUs()` 作为跨设备对齐用系统时间戳。

修复前，编码输出后会尝试用 GStreamer 输出 buffer 的 PTS 反查原始 `RgbEncodeTiming`。实测不同平台上输出 PTS 不一定保留输入系统时间域，本机曾出现数百秒级 `pts_mismatch`。

本次改为：对包含 VCL 的 H.264 输出按编码提交顺序 FIFO 绑定采集时记录的 `RgbEncodeTiming`，不再把 GStreamer 输出 PTS 当作系统时间戳匹配依据。这样协议头里的 `frame_system_timestamp_us` 与提交到编码器的原始 RGB 帧保持顺序一致。

### 2. 深度压缩内存搬运

修复前，压缩深度会先把 SDK 深度帧整帧复制进压缩队列，再压缩生成新 payload。

本次改为：压缩队列持有 SDK depth frame 的 shared owner 和原始 data 指针，压缩线程直接读取原帧内存。这样减少一次高分辨率深度整帧拷贝。

注意：压缩输出 payload 仍然必须生成新 buffer，这不是零拷贝。

### 3. Web 预览状态

修复前，接收端状态接口把“有 RGB 主码流包”也算作 `rgb_preview_available=true`，导致前端以为预览可用，但实际 JPEG 预览可能已过期。

本次状态拆分为：

- `rgb_h264_preview_available`
- `rgb_h264_preview_age_ms`
- `rgb_jpeg_preview_available`
- `main_rgb_jpeg_preview_available`

`rgb_preview_available` 不再因为 `rgb_packets > 0` 被置 true。

### 4. Web 前端 fallback

前端仍优先使用 WebCodecs 播放 H.264 预览流。若浏览器不支持 WebCodecs 或 H.264 解码中断，会标记该路 H.264 失败并回退到 JPEG endpoint，而不是一直卡在“RGB 视频中断”。

### 5. 录制收尾

修复前，`stop-all` / `stop camera` 返回后，实际 MP4/MKV `pclose`、`ffprobe`、`faststart`、H.264 repair 仍在 detached 线程里异步执行。如果用户马上断电，仍可能留下不可拖动或缺 moov atom 的 RGB MP4。

本次改为停止录制接口同步等待封装收尾完成后再返回。返回字段中：

- `finalizing=false`
- `finalized=true`

这表示接口返回时已经完成收尾。

### 6. CSV 帧索引

H.264 码流里可能存在 SPS/PPS 等非图像 NAL 包。它们需要写进 MP4 以保证解码，但不应该被下游当作 RGB 帧参与时间戳对齐。

本次将接收端 `frames.csv` 的 RGB 行限定为 VCL 图像包；非 VCL RGB 包仍写入视频文件，但不更新 `last_rgb`、不参与 RGB 帧统计、不写入帧索引。`rgb_recorded_frames.csv` 原本也是按 VCL 记录，二者语义现在对齐。

此外，启动阶段可能存在已经收到但最终未进入 RGB MP4 的 RGB 包。最终 merge `frames.csv` 时会直接丢弃这类未落盘 RGB 行，保留的 RGB 行均对应 `rgb_recorded=1` 和 `rgb_video_frame_index`。深度行仍完整保留。

### 7. UDP 配置澄清

当前仓库实际媒体链路仍是：

- 状态：UDP 50011
- 媒体：TCP 50010
- Web：HTTP 8080

发送端尚未实现 `media_udp` 或 `web_rgb_preview.udp_enabled` 对应的媒体 UDP 发送路径。本次将当前配置中的未实现 UDP 开关关掉，避免误导。

### 8. 深度复查补充

复查 H.264 NAL 起始码解析时，发现发送端 4 字节 start code 边界判断比接收端严格 1 字节。极短尾包场景下可能漏判 VCL/IDR。本次已按接收端解析口径修正。

复查录制文件时，发现 `frames.csv` 已经只保留真实落盘 RGB 帧，但 `meta.json` 里的 `rgb_frames`、`rgb_actual_fps`、`rgb_target_duration_sec` 仍可能按收到的 VCL 包统计。若录制开始阶段等待下一个关键帧，或者 ffmpeg 实际写入帧数少于接收帧数，就会出现 metadata 比 MP4/CSV 虚高。

本次改为：接收端 metadata 和 RGB retime 统一使用真实写入 `frames.csv` 的 RGB 帧统计。短录制验证中，三路 `meta_rgb_frames` 已与 `frames.csv` RGB 行数、MP4 帧数保持一致。

### 9. 接收端少拷贝整改

复查发现接收端 `handle_media_packet` 原先会先执行整包 `MediaPacket` 复制，即使 RGB H.264 不需要解码，也会复制一份 payload。现在改为只有压缩 depth 需要解码时才生成新的 decoded packet；RGB 和未压缩 depth 直接沿用 TCP 读入 buffer。

TCP 媒体客户端循环也改为每个连接复用 `MediaPacket`、header buffer 和 text buffer。这样 payload vector 会复用容量，不再每个媒体包反复分配/释放大块内存。

录制启动阶段的 RGB pending metadata 不再复制 payload。payload 仍只保留在启动解码所需的 pending H.264 字节流中。

### 10. 录制开始强制 RGB 关键帧

此前 RGB 录制必须从 H.264 IDR 帧开始。若用户刚好在两个自然 GOP 中间点开始录制，接收端需要先丢掉非 IDR 包，等下一次自然关键帧到来；短录制会表现为 RGB 起始少一截，但 MP4 本身并不是坏文件。

本次新增一条轻量控制链路：

- 接收端在收到 `/api/record/start-all` 或单路 `/api/record/start` 时，读取该相机最近一次 status UDP 的来源地址。
- 接收端向该 status endpoint 回发 JSON 控制包：`message_type=control`、`control=force_rgb_keyframe`。
- 发送端复用现有 status UDP socket 接收控制包，不新增端口和配置项。
- 发送端匹配 `sender_id/camera_id` 后，在对应 RGB 编码器下一帧输入前发送 GStreamer force-key-unit 事件。

2026-06-24 12:15 本机双路短录制验证：

- `rk3588-ubuntu_cam01`：RGB 179 帧，MP4 5.935s，首个 RGB 落盘帧距录制开始约 62.94ms，`frame_system_timestamp_us` 单调。
- `rk3588-ubuntu_cam02`：RGB 180 帧，MP4 5.909s，首个 RGB 落盘帧距录制开始约 62.71ms，`frame_system_timestamp_us` 单调。
- 两路 sender 日志均出现 `rgb keyframe requested ... reason=record_start_all` 与 `rgb keyframe force event queued`。
- 两路 MP4 均可被 `ffprobe` 读取帧数与时长，未复现 moov/索引不可读问题。

这条链路属于 best-effort 优化：如果 sender 刚离线、status endpoint 尚未建立，或者某个平台编码器不响应 force-key-unit 事件，接收端仍会保留原有“等待下一帧 IDR”的保护逻辑，保证不会从不可解码的非关键帧开始写 MP4。

### 11. 深度发送队列调度优化

现场双路 `1280x800@30` depth 使用 `pq8zlib` 时，发送端采集基本可以达到 30fps，但 `depth_sent_fps` 会在 25-29fps 波动。复查发现不是单纯网络 send 慢，典型 `depth_send_avg_ms` 只有约 0.3ms；主要问题来自发送端内部调度余量：

- 原先只有 1 个全局 depth compression worker，两路 depth 共用，单帧 `pq8zlib` 约 15-20ms，双路接近单线程上限。
- 压缩队列和媒体发送队列都偏 latest-slot，短时抖动会覆盖待处理 depth。
- 媒体队列每次都优先扫描 RGB；只要 RGB slot 持续有新包，depth 会被推迟，preview 也会参与竞争。

本次调整：

- depth compression worker 按相机数启动，本机双路为 2 个 worker。
- 同一路 depth compression slot 增加 4 帧 FIFO，并用 `in_flight` 保证同一路仍串行压缩，避免时间戳乱序。
- depth media slot 增加 4 帧 FIFO；RGB 和 preview 仍保持 latest-slot，避免延迟无限堆积。
- 媒体发送调度改为主数据 round-robin：RGB/depth 公平轮转，preview 只在没有主数据待发时发送。
- web RGB preview 编码前检查主数据积压；有积压时跳过本帧 preview 编码，让 CPU 和媒体队列优先服务 RGB/depth 主数据。

验证结果：

- 本机 sender 构建通过，双路配置校验通过。
- `codex_depthfair_` 10 秒短录制中，两路 RGB 仍为约 30fps，时间戳单调。
- 同次 depth 落盘：`cam01` 287 帧/约 9.93s，约 28.8fps；`cam02` 295 帧/约 9.99s，约 29.44fps。

结论：本次修复减少了内部队列覆盖和 RGB 对 depth 的调度抢占，但没有彻底保证双路高分辨率 depth 完整 30fps。剩余瓶颈更接近深度压缩耗时、单 TCP 实时链路和系统调度余量的综合上限。若要硬保证双路 depth 30fps，应继续做 depth 压缩算法降耗、主数据/预览通道拆分，或录制专用可靠队列。

### 12. LZ4 深度压缩实验入口

在 `pq8zlib` 队列调度优化后，继续增加两种可选 depth 压缩名：

- `q8lz4`：8bit 量化后整帧 LZ4 压缩。接收端此前已经具备解码能力。
- `pq8lz4`：8bit 量化后按 64K samples 分块 LZ4 压缩，payload 布局与 `pq8zlib` 类似，接收端本次补了解码分支。

发送端通过 `dlopen("liblz4.so.1")` 运行时加载 LZ4，不要求构建机安装 `liblz4-dev`。如果运行设备没有 `liblz4.so.1`，只有配置选择 LZ4 depth 压缩时才会报错；默认 `pq8zlib` 不受影响。

2026-06-24 本机双路 `1280x720 RGB + 1280x800 Depth` 临时测试：

| 模式 | cam01 depth fps | cam02 depth fps | depth compress avg | depth mbps |
| --- | ---: | ---: | ---: | ---: |
| `pq8zlib` 当前默认 | 29.77 平均，27.89 最低 | 29.07 平均，22.97 最低 | cam01 17.68ms / cam02 16.45ms | cam01 19.86 / cam02 20.70 |
| `q8lz4` 临时测试 | 28.58 平均，17.35 最低 | 29.02 平均，24.92 最低 | cam01 12.35ms / cam02 11.71ms | cam01 29.98 / cam02 31.58 |

结论：

- LZ4 确实降低发送端 depth 压缩 CPU 时间，大约下降 30%。
- 码率从约 20Mbps/路升到约 30-32Mbps/路；当前短测 TCP `Send-Q=0`，但多设备或 Wi-Fi 波动时风险更高。
- `q8lz4` 没有直接解决 depth 全帧 30fps 的所有抖动，说明剩余问题不只在 zlib CPU，还包括采集线程调度、RGB 预览编码、单 TCP 链路和接收端处理节奏。
- 当前默认配置继续保持 `pq8zlib`，LZ4 作为现场网络余量足够时的实验选项。

注意：接收端运行在 x86_64，本机发送端运行在 ARM64。不能把本机编译的 `gemini_receiver` 二进制直接拷贝到接收端使用；本次误测后已恢复接收端原 x86_64 备份二进制并确认 `50010/18080/8080` 恢复正常。若要正式启用 `pq8lz4`，必须在接收端设备本机编译或通过 CI 产出 x86_64 二进制，再部署。

### 13. Web RGB preview 独立媒体连接

前一版虽然已经让媒体发送队列优先 RGB/depth 主数据，但 web RGB preview 仍和主 RGB/depth 共用同一个 TCP 媒体连接。无线链路或接收端短时抖动时，预览包会和主数据在同一个 socket 里发生队头阻塞，表现为网页预览卡顿时主数据也更容易受影响。

本次调整：

- 发送端拆成 `main_media_queue` 和 `preview_media_queue`。
- 主 RGB 与 Depth 仍走主媒体发送线程和主 `Transport`。
- `rgb_preview` 走独立媒体发送线程和独立 `Transport`，因此会额外建立一条到接收端 `media_port=50010` 的 TCP 连接。
- 状态/控制 UDP 仍只走主 `Transport`；主状态和主媒体仍共用同一个互斥锁，避免同一个 `Transport` 被并发访问。
- 接收端协议没有改动；接收端本来支持多个媒体 TCP client，所以无需更新接收端源码。

现场验证：

- 接收端 `/api/status` 显示 `active_media_clients=2`，这是本机一个发送端开启 web RGB preview 后的预期现象。
- 本机 `ss -tinpe 'dst 192.168.66.196:50010'` 可看到 `gemini_sender` 建立两条媒体 TCP 连接。
- 重启新二进制后，本机双路最近 40 条性能日志：`cam01` RGB 30.05fps、preview 29.11fps、Depth 29.36fps；`cam02` RGB 30.05fps、preview 29.11fps、Depth 29.46fps；发送失败计数为 0。
- 当前仍保持默认 `pq8zlib`，没有切到 LZ4。

结论：该调整主要降低 web 预览对主 RGB/depth 链路的队头阻塞影响，属于实时性和稳定性优化，不等价于保证高分辨率 Depth 完整 30fps。Depth 是否满帧仍取决于采集、压缩、无线链路、接收端解压与落盘。

### 14. Web RGB preview 按需编码

继续复查发送端线程 CPU 后发现，双路运行且两路 web RGB preview 都开启时，发送端 CPU 主要消耗不在 TCP，而在 MJPEG 解码和预览编码路径。典型线程中 `mppjpegdec` 可占到约 75-87% CPU；此前即使浏览器没有查看某一路，发送端也会按配置持续生成该路 `rgb_preview`。

本次调整：

- `web_rgb_preview` 新增 `on_demand` 配置项，默认 `true`。
- 发送端每路 camera 增加 web preview lease；只有 lease 未过期时才创建/调用 web preview encoder。
- 接收端在网页主预览、缩略图或 H.264 预览流被请求时，通过 status UDP 发送 `control=set_web_rgb_preview_active` 给对应 sender/camera。
- 控制包为续租式，当前约每 0.5 秒续租一次，lease 约 2.5 秒。UDP 丢一个包不会立即断；无人查看后会自然过期。
- `on_demand=false` 时保留旧行为，用于兼容未升级接收端。

现场验证：

- 本机 sender、接收端源码构建通过；接收端已在 x86 设备本机编译并替换运行二进制。
- 无人查看 `cam02` 时，`cam02 rgb_preview_sent_packets_s=0`、`rgb_preview_mbps=0`，主 RGB 仍约 30fps，Depth 约 29fps。
- 主预览仍指向 `cam01` 时，`cam01` preview 保持活跃，这是预期行为。
- 主动请求 `cam02 /api/preview/rgb` 后，`cam02` preview 被拉起；停止请求约 7 秒后自动回到 0。
- 发送端总 CPU 从此前双路 preview 活跃时约 470% 降到当前只有一路主预览活跃时约 360%。实际数值随网页打开路数变化。

结论：这次优化降低了“无人查看预览也持续编码”的无效 CPU 消耗，尤其适合多相机多设备录制时减少发送端压力。它没有消除主 RGB 编码链路自身的 MJPEG 解码成本，也没有实现一解多编的 GStreamer tee 架构；后续若还要继续降 CPU，应把同一路 MJPEG 解码结果共享给主编码和 preview 编码，或把 preview 降级为直接从主 H.264 派生。

### 15. RGB MJPEG 一次解码双路编码实验

继续尝试降低发送端 RGB 预览 CPU：新增了一个实验性 `GstJpegDualH264Encoder`，目标是在发送端把同一路 MJPEG 只解码一次，然后通过 GStreamer `tee` 分成主 RGB H.264 和 Web RGB preview H.264 两个编码分支。

代码现状：

- 实验类保留在 `01_sender_linux/include/gwv3_sender/gst_h264_encoder.hpp` 和 `01_sender_linux/src/gst_h264_encoder.cpp`。
- 默认不启用。只有启动发送端前显式设置 `GEMINI_ENABLE_JPEG_TEE_ENCODER=1`，才会走该实验路径。
- 实验路径有保护：连续 `60` 帧没有主 RGB H.264 输出会销毁实验管线，清空 RGB encode timing 队列，并回退到稳定的独立主编码器和独立预览编码器。
- 同时修正 RGB 编码输出时间戳匹配：优先用 H.264 buffer PTS 匹配采集时绑定的 `system_timestamp_us`，避免编码器输出延迟时单纯 FIFO 造成 `frame_system_timestamp_us` 错配。

验证结论：

- `gst-launch-1.0` 离线实验中，`videotestsrc -> tee -> 双 mpph264enc` 可运行，`jpegenc -> mppjpegdec -> tee -> 双 mpph264enc` 也可运行。
- 但在实际 sender 的 `appsrc` 实时 MJPEG 帧输入下，实验管线在本机双相机上连续 60 帧没有产出主 H.264 包，触发 fallback。
- 销毁该实验管线时还观察到一次 GStreamer critical 日志，因此不能把它作为默认生产路径。
- 改回默认稳定路径后，本机双路发送正常：主 RGB 基本 30fps，Depth 约 27-31fps，`rgb_send_failures=0`、`rgb_timing_mismatch_drops=0`、TCP `Send-Q=0`。当前 cam01 Web 预览活跃时，发送端 CPU 约 350% 左右。

结论：当前 RK MPP + GStreamer `appsrc` 实时链路下，“MJPEG 一次解码后 tee 给两个 H.264 编码器”还不能作为可靠默认方案。后续若继续做这一项，建议单独做可控的 GStreamer 小程序长测，确认 appsrc 时间戳、pipeline preroll、mpp buffer 生命周期和 appsink drain 策略后再并入主发送端。短期生产路径继续使用独立主 RGB 编码和按需 Web preview 编码。

## 剩余边界

- 本次没有实现真正的 RTP/UDP 或 SRT 媒体传输；这是后续协议升级方向。
- RGB H.264 编码输入和输出仍存在内存拷贝，不是零拷贝链路。
- Linux TCP 接收、压缩/解压输出、ffmpeg pipe 写入仍有系统边界或算法输出拷贝，不能称为物理全链路零拷贝。本次整改目标是消除代码层面可避免的整包复制和重复分配。
- RGB 和 preview 仍采用 latest-slot；depth 已有小 FIFO，但网络或接收端处理不过来时仍可能丢实时媒体帧以控制延迟。要保证“完整 30fps 全帧落盘”，需要进一步引入录制专用可靠队列或端侧缓存策略。
- 多相机帧内容级同步仍受相机硬件曝光同步能力限制。软件时间戳可以保证时间轴更清楚，但不能替代硬件同步曝光。
- RGB MP4 录制必须从可解码关键帧开始。现在开始录制会主动请求 sender 立即出 RGB IDR，但仍需保留等待 IDR 的兜底逻辑，不能为了凑时长写入不可解码的非关键帧。
