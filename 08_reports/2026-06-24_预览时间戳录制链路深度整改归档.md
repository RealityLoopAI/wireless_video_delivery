# 2026-06-24 预览、时间戳、录制链路深度整改归档

## 背景

现场运行中同时出现过以下问题：

- Web 预览显示可用但画面不动或普通 RGB 小窗口 404。
- 发送端日志持续出现 `rgb encoder timing fallback reason=pts_mismatch`。
- 停止录制后如果很快断电或重启，RGB MP4 仍可能没有完成封装收尾。
- 高分辨率深度压缩时本机发送端 CPU 和内存带宽压力偏高。
- 配置中存在 `media_udp` / `web_rgb_preview.udp_enabled` 字段，容易误判当前媒体链路已经走 UDP。

## 本次修复

### 1. RGB 帧时间戳映射

发送端仍在采集到 Orbbec RGB 帧后立即读取：

- `frame->timeStampUs()` 作为设备时间戳。
- `frame->systemTimeStampUs()` 作为跨设备对齐用系统时间戳。

修复前，编码输出后会尝试用 GStreamer 输出 buffer 的 PTS 反查原始 `RgbEncodeTiming`。实测不同平台上输出 PTS 不一定保留输入系统时间域，本机曾出现数百秒级 `pts_mismatch`。

本次改为：对包含 VCL 的 H.264 输出按编码提交顺序 FIFO 绑定采集时记录的 `RgbEncodeTiming`，不再把 GStreamer 输出 PTS 当作系统时间戳匹配依据。这样协议头里的 `frame_system_timestamp_us` 与提交到编码器的原始 RGB 帧保持顺序一致。

### 2. 深度压缩内存搬运

修复前，压缩深度会先把 SDK 深度帧整帧复制进压缩队列，再压缩生成新 payload。

本次改为：压缩队列持有 SDK depth frame 的 shared owner 和原始 data 指针，压缩线程直接读取原帧内存。这样减少一次高分辨率深度整帧拷贝。

注意：压缩输出 payload 仍然必须生成新 buffer，这不是零拷贝。

### 3. Web 预览状态

修复前，接收端状态接口把“有 RGB 主码流包”也算作 `rgb_preview_available=true`，导致前端以为预览可用，但实际 JPEG 预览可能已过期。

本次状态拆分为：

- `rgb_h264_preview_available`
- `rgb_h264_preview_age_ms`
- `rgb_jpeg_preview_available`
- `main_rgb_jpeg_preview_available`

`rgb_preview_available` 不再因为 `rgb_packets > 0` 被置 true。

### 4. Web 前端 fallback

前端仍优先使用 WebCodecs 播放 H.264 预览流。若浏览器不支持 WebCodecs 或 H.264 解码中断，会标记该路 H.264 失败并回退到 JPEG endpoint，而不是一直卡在“RGB 视频中断”。

### 5. 录制收尾

修复前，`stop-all` / `stop camera` 返回后，实际 MP4/MKV `pclose`、`ffprobe`、`faststart`、H.264 repair 仍在 detached 线程里异步执行。如果用户马上断电，仍可能留下不可拖动或缺 moov atom 的 RGB MP4。

本次改为停止录制接口同步等待封装收尾完成后再返回。返回字段中：

- `finalizing=false`
- `finalized=true`

这表示接口返回时已经完成收尾。

### 6. CSV 帧索引

H.264 码流里可能存在 SPS/PPS 等非图像 NAL 包。它们需要写进 MP4 以保证解码，但不应该被下游当作 RGB 帧参与时间戳对齐。

本次将接收端 `frames.csv` 的 RGB 行限定为 VCL 图像包；非 VCL RGB 包仍写入视频文件，但不更新 `last_rgb`、不参与 RGB 帧统计、不写入帧索引。`rgb_recorded_frames.csv` 原本也是按 VCL 记录，二者语义现在对齐。

此外，启动阶段可能存在已经收到但最终未进入 RGB MP4 的 RGB 包。最终 merge `frames.csv` 时会直接丢弃这类未落盘 RGB 行，保留的 RGB 行均对应 `rgb_recorded=1` 和 `rgb_video_frame_index`。深度行仍完整保留。

### 7. UDP 配置澄清

当前仓库实际媒体链路仍是：

- 状态：UDP 50011
- 媒体：TCP 50010
- Web：HTTP 8080

发送端尚未实现 `media_udp` 或 `web_rgb_preview.udp_enabled` 对应的媒体 UDP 发送路径。本次将当前配置中的未实现 UDP 开关关掉，避免误导。

### 8. 深度复查补充

复查 H.264 NAL 起始码解析时，发现发送端 4 字节 start code 边界判断比接收端严格 1 字节。极短尾包场景下可能漏判 VCL/IDR。本次已按接收端解析口径修正。

复查录制文件时，发现 `frames.csv` 已经只保留真实落盘 RGB 帧，但 `meta.json` 里的 `rgb_frames`、`rgb_actual_fps`、`rgb_target_duration_sec` 仍可能按收到的 VCL 包统计。若录制开始阶段等待下一个关键帧，或者 ffmpeg 实际写入帧数少于接收帧数，就会出现 metadata 比 MP4/CSV 虚高。

本次改为：接收端 metadata 和 RGB retime 统一使用真实写入 `frames.csv` 的 RGB 帧统计。短录制验证中，三路 `meta_rgb_frames` 已与 `frames.csv` RGB 行数、MP4 帧数保持一致。

## 剩余边界

- 本次没有实现真正的 RTP/UDP 或 SRT 媒体传输；这是后续协议升级方向。
- RGB H.264 编码输入和输出仍存在内存拷贝，不是零拷贝链路。
- 发送端仍采用 latest-slot 队列，网络或接收端处理不过来时会丢实时媒体帧以控制延迟；要保证“完整 30fps 全帧落盘”，需要引入录制专用可靠队列或端侧缓存策略。
- 多相机帧内容级同步仍受相机硬件曝光同步能力限制。软件时间戳可以保证时间轴更清楚，但不能替代硬件同步曝光。
- RGB MP4 录制必须从可解码关键帧开始。短录制刚开始时如果还没等到下一帧 IDR，RGB 实际时长会短于录制请求时长；这不是 moov 损坏，但会让短片段前段少一小截。
