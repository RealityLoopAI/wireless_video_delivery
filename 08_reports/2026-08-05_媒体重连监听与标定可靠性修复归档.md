# 媒体重连、监听与标定可靠性修复归档

日期：2026-08-05

## 1. 问题与证据

1. 接收端媒体 TCP `listen()` backlog 固定为 16。历史内核计数为
   `TcpExtListenOverflows=1438`、`TcpExtListenDrops=1478`，多发送端同时重连时容易放大故障。
2. 发送端 TCP 建连超时为 250ms，短于 Linux 首次 SYN 重传周期。首个 SYN 丢失时会在内核重传前主动放弃。
3. RGB 传输失败后，旧逻辑在“生成 IDR”时就解除保护，而不是等 IDR 发送成功。IDR 自身发送失败会再次触发强制 IDR，现场曾出现约 12 秒上百次请求。
4. 标定接口只要没有抛异常就会标记为 profile-aware，即使返回的 RGB 内参或 D2C 外参为空；通用回退还可能拿到与当前分辨率不匹配的参数。
5. Wi-Fi 守护逻辑每次子进程启动都调用 `nmcli connection modify`，即使省电已经关闭，导致 NetworkManager 重复记录权限失败。

## 2. 修复内容

### 2.1 接收端

- 媒体 TCP backlog：16 -> 128。
- Admin TCP backlog：16 -> 64。
- 仍保留原有活跃连接上限，扩大 backlog 不会无限创建处理线程。

### 2.2 发送端重连

- 默认和全部标准配置的 `connect_timeout_ms`：250 -> 1500。
- 新增 `RgbTransportRecovery` 状态机：
  - 断线后丢弃非 IDR；
  - IDR 只有发送成功才解除恢复状态；
  - IDR 发送失败继续保持恢复状态；
  - 恢复关键帧请求按 1 秒节流；
  - 保留恢复期间丢帧计数和 `dropped_before` 标记。
- 新增发布构建中仍有效的显式单元测试，覆盖重复 arm、请求节流、非 IDR 丢弃和 IDR 成功/失败状态转换。

### 2.3 Orbbec 标定

- 保存启动 pipeline 时使用的准确 `ob::Config`。
- 优先调用官方 `Pipeline::getCalibrationParam(config)`。
- 依次回退到 profile API、设备标定列表和默认参数。
- 只有 RGB/Depth 内参完整、D2C 外参有效，并且内参尺寸与当前实际流档位完全一致时，才设置 `calibration.available=true`。
- 不再缩放或伪造 4:3 标定参数用于 16:9 RGB 档位；不匹配的原始标定列表仍保留供诊断。

### 2.4 Wi-Fi 守护

- 先读取运行时 `iw ... get power_save`；已经为 off 时立即返回。
- 只有确实需要时才尝试普通权限和 `sudo -n` 修改。
- NetworkManager profile 已为 `2/disable` 时不再重复修改。

### 3.1 受控重连测试

在 4 个新版 sender 运行时主动重启 receiver，receiver 约 4 秒恢复：

- 每路恢复关键帧请求被限制为每秒一次，共 2-4 次；未再出现逐帧 IDR 请求风暴。
- 每路均在 IDR 实际发送成功后输出 `rgb keyframe guard recovered`。
- 4 个 sender 的 systemd `NRestarts` 均保持 0。
- `TcpExtListenOverflows` 保持 1438，增量 0。
- `TcpExtListenDrops` 保持 1478，增量 0。
- 恢复后继续观察 30 秒，发送失败、重试丢帧和普通丢帧计数均无新增。
