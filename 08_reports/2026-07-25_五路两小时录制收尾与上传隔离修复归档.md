# 五路两小时录制收尾与上传隔离修复归档

日期：2026-07-25

## 1. 整改范围

本轮延续 2026-07-20 至 2026-07-24 的长时间录制整改，重点处理以下问题：

1. 15 分钟分片结束后，receiver 收尾耗时仍可能受大文件扫描影响。
2. uploader 的普通 MP4 重封装和 NAS 上传会与下一次 receiver 分片收尾竞争本地磁盘和 page cache。
3. RGB MP4 的封装粒度过细，导致长文件包含约 2.7 万个 fragment，放大结构扫描、索引和重封装开销。
4. 录制停止时间晚于最后一个媒体帧时，使用墙钟跨度校验 MP4 duration 会误判完整文件。
5. CIFS 偶发 `EFAULT` 等短暂错误时，单次失败会让完整暂存段长期滞留。
6. uploader 等待 receiver I/O 时，进度心跳会把等待阶段错误覆盖成 `uploading`，造成状态误报。

本轮不修改 sender 采集、RGB/Depth 配对、媒体传输协议、CLOCK_SYNC 或下游对齐逻辑。

## 2. 根因

### 2.1 duration 校验使用了错误的时间基准

旧 uploader 从 `segment_end_us - segment_start_us` 推导 RGB MP4 期望时长。该跨度包含以下非媒体时间：

- 等待首个可解码 IDR；
- sender 暂时断流或录制停止前的媒体空闲；
- receiver 管理状态仍处于录制中的尾部时间。

容器时长实际由写入帧数和 muxer FPS 决定。两者混用会把正常 MP4 判成 duration 不匹配，或放宽到无法发现真实截断。

### 2.2 receiver 的完整媒体探测仍处于实时收尾路径

启用本地 staging 后，receiver 的职责应是快速封口并原子发布 staged marker，完整 FFprobe 和播放器兼容重封装应由 uploader 处理。旧路径对 Depth MKV 和部分 MP4 仍执行完整探测，会让五路 finalizer 串行等待。

### 2.3 fragmented MP4 的结构扫描是 O(fragment 数)

发送端当前 H.264 基本每帧都是 IDR。使用 `frag_keyframe` 会让 15 分钟、30 FPS 文件产生约 2.7 万个 `moof`。旧结构检查从头遍历所有顶层 atom 才能找到末尾 `mfra`，多路同时关闭时会把本应很轻的完整性检查放大为大量随机小读。

### 2.4 uploader 与 receiver 共用 I/O 调度窗口

普通 MP4 重封装必须顺序读取完整 fMP4，再写出完整普通 MP4；NAS 发布还会再次读取本地文件。即使 uploader 位于独立进程和低优先级 cgroup，边界时已经提交到块层的 I/O 仍会增加 receiver 的 CSV 合并和媒体封口延迟。

### 2.5 暂停状态的可观测性错误

实际复制循环在 receiver 边界前已经调用暂停回调，但暂停期间用于刷新字节数的 `progress()` 又把 `active_phase` 改回 `uploading`。因此监控会看到“等待、上传、等待”抖动，无法可靠判断实际 I/O 是否停止。

## 3. 修复

### 3.1 正确计算容器期望时长

receiver 在 `meta.json` 新增：

```text
rgb_container_expected_duration_sec = rgb_frames / rgb_record_fps
depth_container_expected_duration_sec = depth_frames / depth_record_fps
```

录制 muxer 优先使用 sender announce 中的标称 FPS；announce 缺失或非法时才使用现有 FPS probe。uploader 优先使用容器期望时长，并保留旧元数据回退路径。

### 3.2 receiver 快速封口，uploader 完整验证

staging 模式下：

1. receiver 对 RGB fMP4 只检查头部 `moov/moof` 和文件末尾 `mfro -> mfra` 闭合关系。
2. receiver 对 Depth MKV 只检查非空文件和 EBML 头。
3. 完整 FFprobe、RGB 普通 MP4 重封装和最终 duration 校验移到 uploader。
4. 非 staging 模式仍保留原完整验证，避免改变历史部署语义。

### 3.3 固定约一秒一个 MP4 fragment

RGB muxer 从按关键帧切 fragment 改为：

```text
-movflags +empty_moov+default_base_moof
-frag_duration 1000000
```

这样 15 分钟文件约有 900 个 fragment，而不是约 2.7 万个；保留 fMP4 异常断电恢复边界，同时显著降低索引和扫描开销。uploader 输出仍为含 `moov`、不含 `moof` 的普通可拖动 MP4。

### 3.4 uploader 主动避开分片收尾

1. 每次 FFprobe、FFmpeg 重封装、文件复制、限速等待和 fsync 前都检查 receiver Admin 状态。
2. 默认在分片边界前 180 秒进入 `receiver_segment_boundary_wait`。
3. receiver 存在 outstanding finalizer 时进入 `receiver_finalize_wait`。
4. 外部 FFmpeg 在等待期间使用 `SIGSTOP`，恢复时使用 `SIGCONT`，暂停时间不计入任务超时。
5. Admin 短暂超时时保持已有暂停状态，不因一次超时错误恢复大文件 I/O。
6. 暂停阶段优先级高于进度心跳，字节计数可以刷新，但 `active_phase` 不再被覆盖。

### 3.5 NAS 异常恢复

1. 对 `EFAULT`、`EIO`、`ESTALE`、网络复位和超时等短暂错误最多重试 3 次并指数退避。
2. CIFS 不支持部分 `copystat` 操作时，只记录警告，不把已 fsync 的正确文件内容判为失败。
3. 保留隐藏临时目录、ready 最后发布和源目录 `flock` 语义。
4. 失败日志增加完整 traceback，便于区分复制、校验、原子改名和元数据错误。

### 3.6 资源配置

生产配置调整为：

```text
upload_bandwidth_limit_mbps=240
quiet_before_segment_finalize_ms=180000
pause_during_receiver_finalize=true
uploader Nice=5
CPUWeight=50
IOWeight=50
IOSchedulingPriority=4
```

提高上传器在安全窗口内的清队列能力，同时通过边界静默保证 receiver 收尾优先。

## 4. 自动化覆盖

新增或扩展测试覆盖：

1. announced FPS 与容器期望时长。
2. staging receiver 不因人工延迟的 MKV FFprobe 阻塞快速收尾。
3. 缺少末尾 `mfra` 的截断 fMP4 必须拒绝。
4. duration 使用媒体帧数/FPS，不使用管理墙钟跨度。
5. FFprobe、FFmpeg 和文件复制均能暂停、恢复和响应服务停止。
6. CIFS `EFAULT` 重试及不支持 `copystat` 的降级。
7. Admin 超时时已有暂停状态保持不变。
8. 暂停中的进度心跳不能覆盖 `receiver_segment_boundary_wait`。

接收端真实 FFmpeg 环境四项测试均通过：

```text

sync_input_guard_unit
recording_uploader_fault_injection
receiver_staging_pipeline_integration
```

### 5.2 在线运行和收尾

1. 8 次自动边界均恰好关闭 5 路，停止时再关闭 5 个尾段；receiver 累计新增 45 次成功收尾，失败为 0。
2. 40 个完整分片的单段收尾中位数为 `4.375 s`、P95 为 `7.078 s`、最大值为 `9.126 s`。
3. 完整分片媒体封口快检中位数为 `87.5 ms`、P95 为 `249 ms`；一次缓存/I/O 抖动峰值为 `1469 ms`，没有恢复为全文件扫描。
4. 5 个停止尾段单段收尾为 `43–62 ms`；`stop-all` 发出后约 `0.25 s` 内全部完成，不再阻塞下一次开始。
5. uploader 每次都在边界前约 180 秒进入 `receiver_segment_boundary_wait`，finalizer 活跃时进入 `receiver_finalize_wait`；静默窗内上传字节没有增长。
6. 采样监控中录制队列通常为 0，边界瞬时最大约 `43.9 KiB`，15 秒内清空；没有持续低于 27 FPS、写入错误增量或媒体掉线告警。

### 5.3 逐段离线完整性

最终数据共 `53.514 GiB`。45 个目录全部执行以下只读验收：

1. ready marker、`meta.json`、`frames.csv`、RGB MP4 和 Depth MKV 必须齐全且非空。
2. RGB MP4 必须含 `moov`、不含 `moof`，并能在 80% 位置随机跳转解码。
3. 45 个 RGB MP4 全量解码计帧，必须与 `rgb_recorded=1` 行数和 `meta.rgb_frames` 完全一致。
4. 45 个 Depth MKV 全量计包，必须与 Depth CSV 行数和 `meta.depth_frames` 完全一致。
5. RGB/Depth 帧号不得重复或倒退，`global_timestamp_us` 在段内和跨段均不得倒退。
6. 每段开头、中间、结尾各抽取一帧，共 135 帧检查亮度、对比度和哈希。

## 7. 保留边界

1. 普通可拖动 MP4 仍需要一次完整无损重封装，该成本只能异步隔离，不能凭空消除。
2. 本地系统盘是当前后台清队列上限。重封装时磁盘利用率约 `87–100%`、I/O wait 约 `28%`；本轮两小时录制数据完整，但停止时仍积压 23 段。若目标升级为 4 小时以上不间断录制，应优先增加/更换更快的 staging 盘，或实现直接向 NAS 临时目录重封装后原子发布。
3. 本地 staging 容量只能吸收有限时长的 NAS 故障；生产配置保留 10 GiB 低水位保护。
4. 突然断电时，尚未写出 `mfra` 的当前 fMP4 不会被伪装成 ready 文件。
5. `.133` 的长期温度明显高于其他 sender；当前没有热降频，但正式无人值守前仍应改善风道、散热器接触或主动风扇。
6. 无硬件触发/同步线时，CLOCK_SYNC 和 `global_timestamp_us` 不能替代曝光级硬同步。
