# 长时间录制系统风险与待修复项归档

- 首次现场检查：2026-07-17
- 状态复查：2026-07-20、2026-07-21
- 当前状态：历史整改前基线；2026-07-21 已完成软件修复和短时现场验收
- 目标：为后续长时间、多发送端录制整改保留现场证据、优先级和验收口径

> 后续状态：本文件保留整改前证据，不再作为当前实现说明。修复内容、部署和验证结果见 [2026-07-21_长时间录制全链路根治与验证归档.md](2026-07-21_长时间录制全链路根治与验证归档.md)。4 小时耐久复测、重复 USB reset 的硬件根因和颜色标定仍按新归档中的边界继续验收。

## 1. 结论

当前系统短时间发送和预览可以运行，但长时间录制已经碰到当前接收架构的有效上限，不是接收机 CPU、千兆网卡或局域网的绝对硬件上限。主要限制来自接收端 3/4 GiB cgroup 内存限额、直接写 CIFS NAS、RGB 实时双写 MP4 与恢复 H.264，以及分片结束后在同一 NAS 上完整读写大文件重封装。这些环节叠加后会形成 page cache 和录制队列膨胀、NAS I/O 停顿、TCP 反压，最终让多个 sender 同时发送超时和断流。

此外仍有三个独立风险：接收端子进程继承文件描述符、发送端离线时旧分片不能及时结束、Gemini 305 的 USB/SDK 重连及曝光稳定过程。它们会放大为 NAS 隐藏文件占用、分片时长不一致、MP4 收尾延迟、重连后状态残留和恢复初期暗帧。

`.133` 还存在独立的 Gemini 305 USB/SDK 停流风险。2026-07-20 复查时设备在线且未重启 sender，但该设备此前出现过 USB reset、XU 调用失败和取帧超时，不能仅以当前在线判定问题消失。

## 2. P0：必须优先处理

### 2.1 FFmpeg 子进程继承无关文件描述符

现场证据：

- receiver 使用 `std::system()` 启动部分 FFmpeg/外部命令。
- 相关文件描述符未统一设置 `FD_CLOEXEC`/`O_CLOEXEC`。
- NAS 上发现 24 个已删除文件仍被进程持有，共 228 个引用，约 9.28 GiB；CIFS 将其表现为 `.__smb*` 隐藏文件。
- 长时间运行的 FFmpeg 子进程会继承并继续持有旧 CSV、调试 H.264 等文件句柄。

影响：

- 文件删除后空间不能立即释放。
- SMB 句柄和 receiver 进程资源随运行时间增长。
- 增加分片收尾、NAS 写入和后续录制失败的概率。

后续修复方向：

1. 用可控的 `posix_spawn` 或 `fork`/`exec` 路径替代 `std::system()`。
2. 打开文件和 socket 时优先使用 `O_CLOEXEC`/`SOCK_CLOEXEC`，其余描述符显式设置 `FD_CLOEXEC`。
3. 子进程启动前只保留标准输入输出及明确需要传递的描述符。
4. 增加分片轮转后的 `lsof +L1` 回归检查。

### 2.2 NAS 上实时写入与 MP4 收尾争用

现场证据：

- 录制目录位于 CIFS 挂载 `//192.168.66.149/video_database`。
- 每路同时写 RGB MP4、RGB debug H.264、Depth 和 CSV。
- 分片结束时约 1.2 至 1.3 GiB 的 RGB 文件还会从 fragmented MP4 重封装为普通 MP4，单路约需 33 至 57 秒。
- 现场观察到约 2.54 GiB page cache、receiver cgroup 约 3.2 GiB 内存，以及明显 I/O pressure。
- 同一 15 分钟窗口内，部分 RGB 分片只有约 842 至 898 秒有效数据，Depth 相对完整，说明 RGB 链路更容易在轮转和反压时受影响。

影响：

- 多路同时收尾会与下一分片实时写入竞争 NAS 带宽。
- TCP 发送受到反压，进一步表现为预览卡顿、帧间隔增长或发送端积压。
- 分片时长、RGB/Depth 帧数和设备间窗口边界不一致。

后续修复方向：

1. 优先评估本地临时盘落盘，再异步搬运或延迟重封装到 NAS。
2. 将普通 MP4 收尾放入限并发后台队列，避免所有相机同时 remux。
3. 调试 H.264 改为按需启用，避免默认双写大码流。
4. 保证实时录制队列优先于预览和收尾任务，并对积压量设置可观测告警。

### 2.3 发送端离线时分片不能按时收尾

现场证据：

- `.133` 在分片边界前离线后仍停留在旧分片 `162149`，其他在线设备已经进入 `163649`。
- 对应旧 FFmpeg 进程没有及时退出，并继续持有旧文件描述符。
- 当前轮转行为至少部分依赖新媒体包到达，离线流缺少独立超时收尾路径。

影响：

- 离线设备产生超长、未正常结束或无法及时播放的 MP4。
- 重连后旧会话与新会话边界混淆。
- 多设备数据集的统一 15 分钟窗口被破坏。

后续修复方向：

1. 由 receiver 定时器驱动全局分片边界，不依赖某一路媒体包。
2. sender 超过离线阈值后主动结束该路 muxer、CSV 和调试文件。
3. 重连必须创建新会话/新分片，禁止复用旧 FFmpeg 管道。
4. CSV 记录离线区间和关闭原因，不能用静默缺帧掩盖故障。

### 2.4 四小时录制中的全链路阻塞证据

2026-07-20 的约四小时耐久录制中，按 receiver 到达时间统计到 45 个大于等于 5 秒的空洞，其中 23 组同时影响至少 3 台相机，公共停顿约 5 至 68.5 秒。多路在相近时刻一起停止，不符合单根 USB 线、单相机 SDK 或单 sender Wi-Fi 独立故障的特征。

15:22 附近取得的完整因果链如下：

1. receiver 对旧分片的收尾先后耗时约 39.8 秒、132 秒，后续任务等待约 171.8 秒。
2. 约 15:22:39 起，receiver 不再及时消费四路在线媒体流。
3. sender 相机采集仍接近 30 FPS，但 CLOCK_SYNC 开始超时，TCP 出现 partial-write timeout、RGB 发送失败和等待 IDR 的丢帧。
4. receiver 恢复消费后，sender 出现短时追赶发送；这说明采集本身没有在同一时刻全部停掉，阻塞位于 receiver/NAS 消费侧。
5. 同期 user slice 内存压力达到约 91.7%，`systemd-oomd` 杀掉 Web monitor，进一步证明存在接收端内存与 I/O 压力，而非媒体总带宽打满。

2026-07-16 的五相机测试还出现过更严重的同类现象：receiver cgroup 内存达到约 3.2 GiB、压力约 93.63%，随后整个 receiver cgroup 的 48 个进程被 `systemd-oomd` 杀死。所有录制同时未正常收尾，约 22 秒后服务重启。

当前服务限制和实现特征：

- `MemoryHigh=3 GiB`，`MemoryMax=4 GiB`。
- `write_debug_h264=false` 并不代表实时不写恢复 H.264；当前实现仍会打开并持续写 `rgb_debug.h264`，只在 MP4 成功收尾后删除。
- 普通 MP4 兼容收尾通过外部 FFmpeg 对完整文件重封装，在 CIFS 上产生额外的全文件读取和写入。
- 录制队列位于内存。单纯继续增大内存队列会延迟故障并放大 OOM 风险，不能吸收长时间 NAS 抖动。

结论：当前约 70 Mbit/s 的媒体入站流量未打满千兆网络，在线 sender 的 5 GHz 链路也未显示同步恶化。全路公共中断的首要根因是 receiver 录制、收尾和 NAS I/O 共用资源所形成的反压；网络抖动可能放大问题，但不是这批公共停顿的主因。

## 3. P1：设备与部署稳定性

### 3.1 `.133` Gemini 305 USB/SDK 停流

历史现场日志包含：

- `Wait for frame timeout`
- USB reset 和 `usb_submit_urb ... -19`
- `setXu failed`
- `did not claim interface`

当时 USB 链路枚举为 5000 Mbit/s，CPU 仍有较高空闲，因此不能简单归因于 USB 2.0 或 CPU 满载。设备温度曾达到约 77 至 79 摄氏度，但现有日志不足以证明过热直接触发停流。

2026-07-20 复查：

- sender 服务 active，`NRestarts=0`。
- `gemini_sender` 约占 194% CPU，整机仍约 71% idle，内存充足。
- SoC 约 68.4 摄氏度，最高 CPU thermal zone 约 70.2 摄氏度。
- 内核日志未发现 thermal throttling、overheat 或 critical temperature 记录。

2026-07-20 10:40 再次停流时取得了更直接的证据：

- 10:40:58 内核先报 `Set TR Deq Ptr cmd failed due to incorrect slot or ep state`，随后 reset `usb 6-1` 上的 SuperSpeed Gemini 305。
- SDK 随后连续 `Wait for frame timeout`、`setXu failed` 和 `did not claim interface`；RGB、Depth 同时停止，说明不是单独的网页 RGB 解码故障。
- sender 在 RGB/Depth 约 8 秒没有新帧后判定 `capture stream stalled`，10:41:08 开始重连，10:41:10 完成 pipeline 重建；网页 RGB 随媒体恢复。
- 09:58:59 至 10:40:58 之间共记录到 6 次 SuperSpeed reset，已属于重复性故障。
- 相机当前仍以 5000 Mbit/s 枚举；`usbcore.autosuspend=-1`、设备 runtime 状态为 active，因此 USB 2.0 降速和自动休眠不是此次直接原因。
- 恢复后连续 12 秒抽样，receiver 的 RGB 预览时间戳持续前进，预览帧龄约 34 至 50 ms。

后续处理应同时检查相机固件、xHCI 控制器兼容性、供电、USB 线材/端口、散热和 SDK 设备恢复流程；为 USB reset、超时和连续无帧增加计数与状态上报。恢复时需要完整重建 device/pipeline，而不是只重启发送线程。当前恢复机制有效，但单次仍会形成约 12 秒的画面冻结，不能替代对重复 USB reset 根因的处理。

### 3.2 设备版本和工作树不一致

现场发现各设备 commit 和本地改动不一致：本机、receiver、`.219`/`.112`、`.206` 并非运行同一版本，其中部分设备存在大量未提交改动。

影响是同一问题在不同设备上行为不同，也难以确认修复是否真正覆盖所有架构。后续需要：

1. 逐台盘点并保留确有价值的设备差异。
2. 将型号/架构差异收敛为受版本控制的配置 profile。
3. sender 状态中上报 commit、构建时间和配置摘要。
4. 统一发布清单，但继续在各设备原生编译适配对应架构。

### 3.3 暗帧必须按来源分类

本次逐帧和关键帧抽样后，暗帧并非单一原因：

1. `.133` Gemini 305 在 USB/SDK pipeline 重建后存在真实暗帧。多段录制中，相机恢复后同一静态场景亮度均值从约 89 至 91 降到约 36 至 37，持续约 1.5 至 2.4 秒后恢复。CSV 此时仍记录 `exposure=312`、`gain=16`、`auto_exposure=0`，说明 SDK 元数据或读回值不能证明 ISP 已经稳定应用手动参数。
2. 当前 sender 在 pipeline 启动后立即开始采集和发送，Gemini 305 的手动曝光延迟约 2 秒后才重试应用，因此恢复初期不稳定帧会进入录制。后续应增加 warmup 门控：完整重建 pipeline 后重新验证 UVC/SDK 曝光状态，并丢弃约 2 至 3 秒或直到亮度、时间戳和参数读回稳定的帧。
3. 最新 `test_Short_0048` 中 `.133` 开头约 5 秒的黑暗，经联系表检查是镜头被物体遮挡和移动，不是曝光控制故障。物理遮挡必须与重连暗帧分开统计。
4. 最新 15 分钟分片的关键帧亮度扫描未发现五路相机存在持续暗度下降；其余普通相机的相对变化约 1% 至 5%。因此没有证据支持“所有相机持续随机曝光失效”。

### 3.4 RGB 断流恢复时存在非 IDR 重试风险

录制样本显示，大 RGB frame ID 空洞后偶尔先落入一个非关键 P 帧，再出现下一帧 IDR。例如：

- `ab748372/135127`：缺失 1788 帧后，包 3171 为非关键帧，3172 才是关键帧。
- `b439137c/120627`：缺失 665 帧后，包 3279 为非关键帧，3280 才是关键帧；后续另一处也有相同模式。

代码路径中，发送失败后会启用“等待下一关键帧”保护，但失败的当前 job 同时被保存为 `retry_job`；重试分支直接重新发送该 job，没有再次经过关键帧保护判断。因此传输恢复后，可能把不具备可用参考帧的 P 帧发送给 receiver，表现为恢复瞬间的一帧灰、暗、花屏或解码异常。

这是一项已确认的协议恢复正确性风险，但静态场景样本中该 P 帧亮度也可能看起来正常，不能把所有暗帧都归因于它。后续修复应在任何发送失败、队列覆盖、连接重建后丢弃所有旧 retry job 和非 IDR 帧，只允许从新的 IDR 恢复 RGB 链路。

## 4. P2：数据完整性和可观测性

- CSV 合并仍见少量 RGB 元数据行缺失，应为每路增加“收到、编码、发送、接收、写盘”计数对账。
- receiver 中残留会话和累计重连计数容易混淆当前状态与历史故障，应为状态增加会话 ID 和当前分片 ID。
- 网络、CLOCK_SYNC 和 Web API 在 2026-07-17 检查窗口内总体正常：在线设备 offset 离散约 0.55 ms，API 响应约 13 至 23 ms，receiver CPU 约 22%。这些数据不支持将当时的主要故障直接归因于局域网或时钟同步。
- 故障排查必须区分采集缺帧、编码积压、TCP 反压、receiver 落盘阻塞和分片收尾，不能只用最终视频帧率倒推单一根因。

## 5. 建议实施顺序

1. 让实时录制先写 receiver 本地 SSD/NVMe；分片原子关闭后，再由独立进程或独立 cgroup 限速收尾并上传 NAS。按当前约 70 Mbit/s 估算，总流量约 31 GiB/小时，建议至少预留 100 至 200 GiB 本地暂存空间。
2. 真正关闭默认 RGB 恢复 H.264 双写；只有明确进入恢复模式或显式启用调试时才生成该文件。
3. 使用有容量上限、可恢复的磁盘待上传队列，记录 backlog、最老任务年龄、失败重试和磁盘水位。录制主链路优先，预览和上传允许降级。
4. 将 MP4 remux 与 NAS 上传移出 receiver 媒体接收资源域，并限制并发；NAS 短时不可用时保留本地完整分片，不反压实时 media socket。
5. 修复描述符继承并清除 `.__smb*` 根因。
6. 增加离线流超时收尾和定时器驱动的统一分片边界。
7. 修复 RGB 恢复路径：清空旧 retry job，并严格等待下一 IDR。
8. 为 `.133` 增加 Gemini 305 pipeline 重建后的曝光验证和 warmup 丢帧门控，同时保留 USB reset、XU 失败和连续无帧计数。
9. 统一部署版本、配置 profile 和运行版本上报。
10. 补齐全链路计数对账，再做四路以上长时间压力测试。

在根治前的临时缓解措施是将 receiver 的 `MemoryHigh/MemoryMax` 适度提高到例如 6/8 GiB，并在录制时关闭 Web 预览。它们只能提高缓冲余量，不能消除 CIFS 停顿和全文件 remux 引发的反压，因此不能作为最终方案。

## 6. 验收标准

- 连续运行至少 4 小时并跨越至少 16 次 15 分钟分片轮转。
- 轮转后 `lsof +L1` 不再出现旧录制文件被子进程持有，NAS 不持续增长 `.__smb*` 文件。
- 离线 sender 在配置超时内结束当前 MP4/CSV；重连后进入新会话和新分片。
- 在线流实际落盘帧率尽量保持 29.5 FPS 以上；超过 100 ms 的间隔必须能关联到明确的 sender 离线或链路故障记录。
- MP4 可被 `ffprobe` 正常解析并可拖动进度条，CSV 时间戳单调且字段数量一致。
- 发送端无持续 media backpressure，receiver 实时录制不被预览和 remux 长时间阻塞。
- 人为暂停 NAS 1 至 5 分钟时，实时录制仍能完整写入本地 staging；NAS 恢复后 backlog 自动上传，媒体接收线程不出现 TCP partial-write timeout。
- RGB 在断线重连、队列覆盖和 sender 重启后均从 IDR 开始恢复，解码日志和录制首帧不得出现孤立 P 帧。
- Gemini 305 pipeline 重建后的 warmup 帧不得进入正式录制；稳定后的首个发布帧应具有有效曝光状态和单调时间戳。
- 所有在线设备上报预期的 release/commit 和配置摘要。
- CLOCK_SYNC 在线时模型有效；无模型时正确降级且不影响录制。
