## 完成项

1. 安装 C++ 构建、FFmpeg、JSONCPP、chrony、CIFS、Python Web 等运行依赖。
2. 配置 SSH、QEMU guest agent 和 user linger，保证未登录时也能开机自启。
3. 将 NAS 以 CIFS 3.1.1 持久挂载，凭据文件权限为 `0600`，receiver 启动前强制检查挂载点可写。
4. 部署 receiver、Web monitor、照片上传、全天音频归档和日志轮转 user systemd 服务。
5. 新接收端作为 chrony 局域网时间基准，已将在线正式 sender 的媒体、CLOCK_SYNC 和 chrony 目标切换到 `.61`。
6. 将两台 LubaCat 的全天 RTP/Opus 音频归档目标切换到 `.61`，保留向 `.32` 的实时音频推流。
7. `.112 / orangepi5pro-f022c4` 继续按既定方案只向 `.226:5600` 推 RTP RGB，未切回正式 receiver。

## 启动问题与修复

虚拟机同时有 `ens3` 和 `ens4` 两块网卡。`ens3` 正常获得 `.61`，未使用的 `ens4` 也开启了 DHCP 自动连接，导致 NetworkManager 反复等待 45 秒并使 `NetworkManager-wait-online` 失败。

处理方式：

- 保留 `ens4` 连接配置，仅关闭 `connection.autoconnect`。
- 将 `/etc/netplan/01-network-manager-all.yaml` 权限修正为 `0600`。
- 修复后 NetworkManager 在启动约 3 秒时完成，无 failed systemd unit；接收端从重启到 receiver、Web 和 NAS 挂载全部可用约 13 秒。

### 时间状态

切换时发现两台 LubaCat 因旧 chrony 时间源 `.196` 离线，本机时间已落后约 81 天。本次已重新 step 到 `.61` 并统一时间源。第二次 receiver 重启后，CLOCK_SYNC 根据现有大跳变超时重建机制自动收敛，3 路在线相机最终 offset 约为：

- `lubancat-52d2ef0c`: `0.166 ms`
- `lubancat-e8cc0cb3`: `0.590 ms`
- `orangepi5pro-b439137c`: `0.081 ms`

这些数值只表示软件时钟轴偏差，不代表相机传感器曝光已硬件同步。
