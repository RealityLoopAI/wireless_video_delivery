# 发送端自启动与相机恢复机制补齐归档

日期：2026-07-14

## 背景

巡检发现 `rk3588-ubuntu` 本机与 `orangepi5pro-b439137c` (`192.168.66.206`) 的 sender 虽在运行，但分别属于 GNOME 终端临时 scope 和遗留 SSH session，重启设备后不会自动恢复。`.206` 同时使用旧版 `sender_watchdog.sh`，缺少当前版本的零帧、启动超时和 SDK 运行时保护。

## 部署变更

1. 新增本机 systemd 单位源文件：
   `05_tools/systemd/gwv3-gemini-sender-rk3588-ubuntu.service`。
2. 新增 `.206` systemd 单位源文件：
   `05_tools/systemd/gwv3-gemini-sender-orangepi5pro-b439137c.service`。
3. 两台设备均安装为 `/etc/systemd/system/gwv3-gemini-sender.service`，并执行 `systemctl enable --now`。
4. 两个单位均使用 `Restart=always`、`KillMode=control-group`、USB 预处理以及 `video/render` 补充用户组。
5. `.206` 已对齐当前 `sender_watchdog.sh` 和 `orbbec_runtime_guard.sh`，未更换 sender 二进制，未修改相机档位、曝光或传输参数。

## 恢复机制语义

- 所有正式配置仍保持 `hotplug.enabled=false`，不动态添加未知相机，避免 camera_id 及 RGB/Depth 路由变化。
- 已配置的相机按型号绑定；sender 进程存活时，拔插同型号相机由采集 worker 持续重连。
- 采集连续零帧或相机启动超时时，watchdog 终止并重建 sender 子进程。
- watchdog 主进程退出时，systemd 重启整个服务。
- 设备重启时，systemd 从 `multi-user.target` 自动启动 sender；无相机时 watchdog 保持恢复循环，后续插入已配置型号后可恢复。

## 验证结果

- 本机：`gwv3-gemini-sender.service` 为 `enabled + active`，`NRestarts=0`。
- `.206`：`gwv3-gemini-sender.service` 为 `enabled + active`，`NRestarts=0`。
- `.206` 受控终止 sender 子进程后，watchdog 在约 6 秒内将 PID `1939025` 替换为 `1940158`，采集与传输自动恢复。
- 接收端 12 秒计数窗口内，5 路 RGB 与 Depth 均为约 30 fps，`record_queue_total_bytes=0`，`record_write_errors=0`，clock sync 全部有效。
- `.133` Gemini 305 当日真实发生 SDK 控制通道异常与采集停滞，已由现有采集重连/watchdog 自动恢复，验证了实际相机故障恢复路径。

## 当前结论

当前 5 个在线 sender 均已具备开机自启动。对已配置的相机，恢复链路为“采集 worker 重连 -> watchdog 重建子进程 -> systemd 重启服务”。未开启任意新相机的动态扫描，这是为了保持数据集 camera_id 和存储路径稳定。
