# 133 语音播报与 USB 音频恢复修复归档

日期：2026-07-30

## 1. 现象

`192.168.66.133` 的“小环”语音链路出现两个相关问题：

1. 播完唤醒回复后，必须等待一段时间再说“拍照”才能识别；
2. 回复偶尔中途停止，随后收音或播报长时间不可用。

## 2. 定位结果

正常播放路径原先会主动终止整条麦克风/GStreamer/FFmpeg 管线，播完后重新打开设备并做 1.5 秒噪声标定。现场日志显示：

```text
audio capture recovered phase=post-playback attempt=1 elapsed=1.62s
```

因此“我在”播完后的正常收音空窗约为 1.62 秒。USB 状态不稳定时，恢复曾达到 13.95 秒。

内核日志还记录到 USB 音箱和麦克风所在的整个下级 Hub 多次掉线重枚举：

```text
USB disconnect
cannot submit urb ... -19
usb_set_interface failed ... -71
```

这属于 USB Hub、供电、线材或物理链路级异常，软件不能阻止设备真正消失，但必须在设备回来后自动恢复。

本次保留现场后进一步确认：

- `15:34:23` 至 `16:26:07`，外置 Hub `1-1.1` 整体掉线重枚举 9 次；
- Hub 为 `1a40:0101` USB 2.0 单 TT Hub；
- USB 音箱和麦克风均为 12Mbps full-speed USB Audio 等时设备，共用该 TT；
- 内核出现 `clear tt ... error -71`、`device descriptor ... error -71` 和
  `cannot submit urb ... error -19`；
- 没有发现内核上报的 USB over-current 或 undervoltage；
- 133 的 SoC 长期处于约 84-85 摄氏度，风扇 PWM 已为 255，CPU/GPU 正在热限频。

因此可以确定故障域在 Hub/USB 链路而不是 TTS 队列。温度、Hub 供电、连接线和单 TT
等时事务都属于风险项，但现有证据不足以把其中某一项单独认定为唯一物理根因。

同时发现 Hub 重枚举后 PulseAudio 会通过 `module-udev-detect` 自动管理两个 USB
声卡。设备节点已经回来时，语音采集仍连续约 10 秒收到 `Device ... is busy`，这正是
“设备只断了一两秒，语音却卡十几秒”的软件放大因素。

当前“我在”固定 WAV 总长约 0.420 秒，有效发音约 0.385 秒，末尾约 35ms 为纯静音。波形尾部单调衰减，没有截入原长句“有什么可以帮到您的”的下一字起音。

## 3. 修复

### 3.1 第一版常驻采集

- 播报期间不再销毁麦克风采集进程；
- 独立 drain 线程持续读取并丢弃识别 PCM，避免管道堵塞和扬声器回声进入 Vosk；
- 播完后仅保留 30ms 防回声尾窗；
- 正常路径不重新标定噪声，也不重新打开 ALSA/GStreamer；
- 只有采集进程确实退出或 USB 掉线时，才进入最长 20 秒的原进程恢复。

该版消除了正常路径的 1.5 秒重新标定，但实机长测证明当前单 TT Hub 不适合让麦克风
等时输入与音箱等时输出长期并发，因此没有作为 133 的最终运行策略。

### 3.2 RTP 音频门控

GStreamer 的 RTP/Opus 支路改为先发到进程内本地 UDP gate：

```text
GStreamer -> 127.0.0.1:<ephemeral-port> -> UDP gate -> 192.168.66.113:50020
```

音箱播报期间 gate 继续收包但不转发，避免把设备回复发送给监听端。播放结束后恢复转发，RTP 队列不会反向阻塞唤醒识别。

### 3.3 播放和设备恢复

- ALSA 从易变化的数字卡号改为 `plughw:CARD=Device...` 稳定声卡 ID；
- `aplay` 异常退出或设备忙时，在 15 秒窗口内重试同一段语音；
- 播放进程卡死时按音频时长设置超时并强制回收；
- 采集短读或读取超时后在主进程内重建，失败才交给 systemd 重启；
- 133 已安装 USB Hub 禁用 autosuspend 规则；该设置消除软件省电风险，但不能替代供电和线材排查。

### 3.4 排除 PulseAudio 热插拔竞争

- 新增 `systemd/90-xiaohuan-usb-audio-exclusive.rules`；
- 按当前麦克风 `08bb:2902` 和音箱 `8087:1024` 匹配 sound card；
- 对两者设置 `PULSE_IGNORE=1`，保留板载声卡和其他 USB 音频设备；
- `install_wake_service.sh` 自动安装规则并重载 udev；
- 133 当前 PulseAudio profile 已设为 off，规则也已部署到
  `/etc/udev/rules.d/`，重启和后续重枚举均生效。

### 3.5 最终半双工快速恢复

- 新增 `capture_playback_mode=keep|restart`，通用默认保持 `keep`；
- 133 的正式 systemd drop-in 固定为 `restart`；
- 播放前主动结束并完整回收 GStreamer/FFmpeg，释放麦克风 USB 等时端点；
- 播放结束后只验证一个 100ms 音频块，沿用上一轮噪声底，不再重新执行 1.5 秒标定；
- 显式关闭旧采集管道的 stdin/stdout/stderr，避免设备多次恢复后的文件描述符累积；
- RTP gate 在整个播报和重开期间暂停，重开成功后再恢复转发。

该策略牺牲约 0.23 秒的播放后重开时间，换取麦克风和音箱不再同时占用不稳定 Hub。

## 4. 实机验证

### 4.1 第一版常驻采集验证

通过 HTTP 队列播放“我在”前后：

```text
before_gst=50372
after_gst=50372
same_pid=yes
```

日志：

```text
audio capture kept alive across playback:
elapsed=1.677s drained_bytes=54000 echo_tail=0.030s
```

这里 1.677 秒包含在线 TTS 音频自身 1.32 秒和 HTTP 队列等待。该结果证明 Python
播放队列没有死锁，但后续满双工测试表明不能把这一路径作为当前硬件的长期配置。

### 4.2 音箱占用故障注入

先占用 ALSA 播放设备两秒，再提交播报：

```text
speaker playback retry attempt=1 ... 设备或资源忙
speaker playback retry attempt=6 ... 设备或资源忙
speech task finished ... success=true
same_pid=yes
```

设备释放后同一任务成功播放，麦克风采集 PID 未变化。

### 4.3 自动测试

以下测试通过：

```bash
python3 10_tests/test_voice_photo_burst.py
python3 10_tests/test_voice_tts_service.py
python3 -m py_compile \
  12_apps/xiaohuan_voice_photo/vosk_wake.py \
  12_apps/xiaohuan_voice_photo/speech_service.py
```

覆盖 UDP gate 暂停/恢复、播放期间 PCM drain、采集读取超时、顽固子进程回收、音箱重试、卡死播放器终止和固定提示音尾部检查。

### 4.4 Hub 重枚举恢复注入

通过 sysfs 主动让外置 Hub 取消授权后重新授权，模拟现场整 Hub 掉线。修改前同类现场
恢复耗时最高为：

```text
audio capture recovered phase=runtime attempt=20 elapsed=13.97s
```

排除 PulseAudio 竞争后实测：

```text
hub_reenumeration recovered=1 elapsed_ms=2739
```

恢复时间缩短到约 2.74 秒。重枚举后 PulseAudio 没有重新生成这两个 USB 声卡的
source/sink，ALSA PCM 仅由语音 GStreamer 占用。

另外，保持麦克风采集时连续无声打开/关闭音箱 60 次，没有触发新的 Hub reset。这说明
逐次启动 `aplay` 不是单一充分条件，因此没有贸然改为持续占用 USB 输出带宽的常驻
播放流。

### 4.5 持续满双工压力测试

保持现有麦克风采集，同时让 USB 音箱持续播放全零 PCM，用于提高问题复现概率：

- 第一轮有效运行约 65 秒，期间没有新增 Hub reset；
- 第二轮干净测试期间，`133` 在 `2026-07-30 16:51:35` 同时停止发送 status 和
  media，并从局域网消失；
- receiver、`192.168.66.206` 和 AP 同期正常；
- `133` 超过 6 分钟没有自动恢复，无法继续通过 SSH 读取现场。

这项测试没有通过。它说明风险不局限于 Python 播放线程，持续 USB Audio 负载下可能
出现整机供电、内核 EHCI/USB 或系统级卡死。

设备重启后确认：

- 新启动 boot ID 与原启动不同，故障后确实经过了硬重启；
- 上一启动没有正常关机尾迹；
- journal 为易失存储，`orangepi-ramlog` 在故障前最后一次落盘停在 00:00，16:51
  故障现场随断电丢失；
- `/sys/fs/pstore` 没有本次 panic，`/var/lib/systemd/pstore` 中仅有更早一次正常
  `reboot: Restarting system`，与本次事故无关；
- 因此可以排除“只有语音 Python 线程卡住”，但不能仅凭现有日志在供电跌落、EHCI
  硬卡死和整机其他硬件异常之间做唯一归因。

持续满双工压力测试不再重复执行。

### 4.6 最终半双工实机验证

重启后部署 `capture_playback_mode=restart`，现场连续完成 26 次真实播报：

```text
audio capture paused for half-duplex playback
audio capture recovered phase=post-playback-resume attempt=1 elapsed=0.22-0.25s calibrated=false
audio capture resumed after half-duplex playback
```

验证结果：

- 26/26 次均一次恢复；
- 采集短读 0 次，播放失败 0 次，语音服务自动重启 0 次；
- 当前启动内 USB disconnect、`-71`、`-19` 和 clear-TT 错误均为 0；
- 多轮“你好小环 -> 我在 -> 立即说拍照”识别成功并完成三连拍；
- 133 的 RGB/Depth 仍为约 29.9-30fps，发送失败为 0；
- CLOCK_SYNC 有效，媒体接收年龄约 4-22ms。

“我在”从开始播放到采集恢复约 0.82-0.86 秒，其中固定语音自身约 0.42 秒，播放结束
后的 USB 重开约 0.23 秒。相比旧版约 1.62 秒完整重新标定，命令识别盲区明显缩短。

## 5. 当前参数

```text
wake_response: 我在
wake_response_duration: 0.420s
echo_tail_seconds: 0.03
post_wake_command_seconds: 8
speaker_retry_seconds: 15
audio_read_timeout_seconds: 2
audio_recovery_seconds: 20
audio_recovery_interval_seconds: 0.5
capture_playback_mode: restart
```

如果仍出现回复中断，应先查 133 的 `dmesg` 是否又有整个 Hub 的
`USB disconnect/-19/-71`。软件现在会避免满双工并自动恢复，但物理链路在播音期间
消失时，已经送入音箱硬件的那一小段声音无法由软件无缝续播。

要从物理层消除该类中断，优先级依次是：确认风扇实际转动和散热器接触、检查 Hub
独立供电与上行线、将麦克风和音箱分到不同 USB root controller，或更换可靠的有源
multi-TT Hub。软件侧已经完成禁用 autosuspend、排除 PulseAudio 抢占、稳定 ALSA
名称、半双工快速重开和进程内自动恢复。物理层风险仍需靠更换供电/Hub/线材或拆分
USB root controller 才能彻底消除。
